Building and running ShareCraft

Status of this build, and what has been checked. This is a development build, not a release. The server is covered by automated tests, which run against a real PostgreSQL database (section 02). The scripts of the web pages have one automated test file, which covers only the check that a sign-in redirect stays on this site; the rest of the page scripts are not covered by automated tests. A hands-on check of the pages in a browser is recorded separately by the project owner's assistant, not in this document, so nothing here should be read as saying that check has been done; for the four file editors, what was and was not checked in a browser is listed in editors.html. The frame page's pure parts (the editor bridges, the save queue, the status wording) have their own automated test file, web/editor-host.test.mjs. The sections below describe what the code does.

01 / What you need

  • Rust, stable channel, installed with rustup. The project uses the 2024 edition.
  • The WebAssembly target, which lets Rust build the part that runs in the browser:
rustup target add wasm32-unknown-unknown
  • wasm-bindgen-cli version 0.2.130, exactly. It must match the wasm-bindgen version recorded in Cargo.lock. If it is missing or a different version, cargo xtask web stops and prints the command to run:
cargo install wasm-bindgen-cli --version 0.2.130 --locked

If a later change to Cargo.lock moves wasm-bindgen to another version, the command printed by cargo xtask web shows the version then needed.

  • PostgreSQL. The server keeps accounts, sign-in sessions, sharing, the revision index and events in a PostgreSQL database and will not start without one. Development has used PostgreSQL 18 on the local machine. Create an empty database and an account that may create tables in it. For the tests (section 02) create a second, separate database and give the same account permission to create schemas in it; the tests do not create databases.
  • A .env file in the repository root, made by copying .env.example and replacing its placeholder values. It names the databases by variable (DATABASE_URL for the server, TEST_DATABASE_URL for the tests). .env is not kept in Git. Keep real values only there: never put a database address or password in a command that is saved, in a commit or in a message.
  • Node.js, to run the automated test files for the page scripts, which cargo xtask check runs (section 02). Without it the check stops and says that Node.js is needed.
  • Only for the file editors: Trunk and the editors' source, described in section 13.

Git does not need to be installed to run ShareCraft, because the Git library is built in. You only need it to look at saved documents (section 09).

02 / Build and check

Run every command from the repository root, the folder that holds Cargo.toml.

This loads .env, then checks that no dependency has a copyleft licence, checks formatting, runs the lints with warnings treated as errors, runs all tests in the workspace, builds each browser-side crate for WebAssembly, and runs the page script tests with Node (below). It prints xtask: all checks passed and exits with code 0 when everything is in order:

cargo xtask check

This loads .env and then runs cargo test with whatever arguments you add, for example cargo xtask test -p server:

cargo xtask test

The tests need TEST_DATABASE_URL. Every test that uses the database creates its own schema in that database. A test does not drop its schema when it finishes; each run drops the test schemas it finds that are more than an hour old, so a schema stays until the first run after that hour (the scale tests, section 22, leave a schema of about 100,000 rows). A test that needs the variable and finds it unset fails with a message saying so; it is never skipped. That is why you run the tests through cargo xtask check or cargo xtask test, which load .env, and not through plain cargo test.

This loads .env and runs the scale tests, which plain test runs skip because they take minutes: a library of 100,000 files is loaded and the main operations on it are timed in a debug build (section 22). It prints each time and fails naming any time over its threshold:

cargo xtask scale

This builds the browser client and writes the page's script package to web/pkg. The folder is not kept in Git, so do this once after a fresh checkout and again after changing the browser client:

cargo xtask web

The scripts of the web pages (the .js files in web) have two automated test files. web/common.test.mjs tests the function that decides where to go after signing in, so that a crafted link cannot send someone to another site. web/editor-host.test.mjs tests the frame page's pure parts: telling a save from an export, the save queue, the status and banner wording and the two editor bridges, against stand-in editors. cargo xtask check runs them, and fails with a message saying so when Node.js is not installed; it never skips them. It also checks any installed editors against editors.toml (section 13). To run the page tests on their own:

node --test web/*.test.mjs

Database migrations keep LF line endings. The server identifies each database migration by a checksum of the file's exact bytes. With Git's core.autocrlf on (common on Windows), checking out a branch once rewrote a migration file with Windows line endings, and the server then refused to start on an existing database with migration 1 was previously applied but has been modified. .gitattributes now pins the migration files to LF on every checkout. If you see that message after an older checkout, check the migration files out again (for example git checkout -- crates/records/migrations).

The migrations are built into the server program, so a build could keep the old bytes after the files were checked out again. Since 10 November 2026 a small build script (crates/records/build.rs) makes Cargo rebuild that part whenever anything in the migrations folder changes, and a test (migration_files_have_no_carriage_returns) fails, saying what to check, if a migration file on disk has a Windows line ending.

For anyone else with a Windows clone: if your database was first migrated from a copy of 0001_initial.sql with Windows line endings, the server, now built from the LF file, refuses to start with the message above. For a development database, the remedy is to drop it and create it again; the server sets it up on its next start. Never edit a migration file to make the message go away.

03 / The first administrator

There is no public sign-up, and nobody can sign in until an account exists. The first account, an administrator, is made from the command line. DATABASE_URL must be set (in .env or the environment). The command brings the database schema up to date, then creates the account:

cargo run -p server -- add-user --email <email> --name <name> --admin

Leave out --admin to make an ordinary account. The password is not a command-line option, so that it never appears in a process list or a saved command history. The command asks for it with Password: and does not show what you type. If its input is piped instead of typed, it reads the first line of that input as the password. It prints created administrator <email> (<account id>), or created account ... for an ordinary account. The password and the database address are never printed.

After the first administrator exists, further accounts are made on the People page (section 06); the command line stays available for the same job.

04 / Run it and sign in

Start the server, still from the repository root. It needs DATABASE_URL, which it reads from .env in the current folder or a parent. It takes its address first, so an address already in use is reported at once. It then brings the database schema up to date and compares the revision index with Git (section 10). Only then does it say where it listens and start accepting connections:

cargo run -p server

It prints the content-tree line (section 19) and the revision-index line, then the address it listens on and WARNING: development mode, local connections only. If the database cannot be reached or brought up to date, it prints why and exits without printing the address. Once the address is shown, open the site in a browser at exactly one of these addresses:

http://127.0.0.1:8787/
http://localhost:8787/

A person who is not signed in is sent to the sign-in page, and after signing in comes back to the page they asked for. After signing in the first page lists the sites the person can see; a site opens to its libraries, and a library or folder lists its folders and files, with a New document form and an upload (section 17). A document opens at an address such as /doc.html#<document id>; the part after # is the document's identifier, and anyone with access can use the same address.

The server refuses a WebSocket connection, and every /api request, when its Host is not a loopback name (127.0.0.1, localhost or [::1]), or when the page's Origin differs from the address it was loaded from. In this build the site therefore cannot be reached through another hostname, another computer or a proxy.

Browsers keep cookies separately for 127.0.0.1 and localhost. To try two people at once on one computer, sign in as one at http://127.0.0.1:8787/ and as the other at http://localhost:8787/.

06 / Accounts and signing in

An account is one person: an email address, a display name, a password, and a flag saying whether they are an administrator. Accounts are created by an administrator, on the command line (section 03) or on the People page, where an administrator also chooses whether the new person is one. Nobody can register themselves, and nobody can change their own password yet.

What an account may contain
FieldRule
EmailAt most 254 characters, no spaces or control characters, one @ with something on each side. Case is ignored: two emails that differ only by case are the same account. Each email can have one account.
Name1 to 60 characters, at least one letter or digit, no control characters and no < or >. Names are shown to other people in a document and are credited in saved revisions.
Password10 to 256 characters. Nothing else is required. It is stored only as an Argon2id hash.

Signing in

The sign-in page sends the email and password to the server. When they match, the server starts a session that lasts 30 days and sets a cookie named sharecraft_session holding a random token. The cookie is marked HttpOnly (page scripts cannot read it) and SameSite=Lax. The server stores only a hash of the token. It is not marked Secure, because the build only serves plain HTTP on the local machine.

A wrong password, an unknown email and a disabled account all get the same answer, That email and password do not match., so the page does not reveal which emails have accounts. After 5 failed attempts for one email within 15 minutes, further attempts for it are refused with Too many attempts. Try again in a few minutes. The count is kept in the server's memory, so restarting the server resets it.

Signing out

The Sign out button is on the documents page. It ends that session and clears the cookie, and any open document pages of that session are removed (section 08). The same person's other sign-ins, in other browsers, stay signed in. A session also ends on its own after 30 days.

Managing people (administrators)

The People page lists every account with its email, whether it is an administrator and whether it is disabled. An administrator can add a person (email, name, password, administrator or not) and disable or enable an account.

  • Disabling an account ends all of its sessions at once and removes it from every open document. It cannot sign in again until an administrator enables it. Its documents and grants are kept.
  • At least one administrator must stay enabled: disabling the last one is refused with At least one administrator must stay enabled.
  • An administrator is treated as an owner of every document (section 07).

07 / Sharing and roles

A person who is an editor of a library or folder can create a document in it. The name is optional (it defaults to Untitled). Names follow the rules in section 17, and a document can be renamed and moved. A new document takes its access from the place it is in, as section 17 describes.

Access is granted to a person or to a group (section 23), on a site, library, folder or file, and passes down to what is inside it (section 17). A person with no role on a document cannot see it in a list and cannot open it. The server answers the same way for a document that does not exist and one you may not open, so you cannot find out that a document exists by guessing its address; the page says This document does not exist, or you do not have access to it.

The built-in roles (administrators can define more; section 23)
RoleReadChange the textShare and see events

OwnerYesYesYes

A viewer sees the live text and who else is there, but the text box is read-only and the page shows You can read this document but not change it. The server also refuses changes from a viewer, whatever the page does.

Administrators are owners of every document without needing a grant, so someone can always recover a document whose owners are gone. They appear in the Sharing list only if they were granted a role explicitly.

People who manage access can also share by link, and a person who reaches something they cannot open can ask for access. Both are described in section 24.

Sharing a document

Owners see a Sharing panel under the text. It lists everyone who has access to the document, whether it is its own or inherited, each with a role menu and a Remove button. To add someone, type their email, choose a role and press Share. Choosing another role in a person's menu changes their role at once. Sharing is by the email of an existing account, or by choosing a group from the list: No account has that email address. appears if there is none, and only owners can learn this. A document must keep at least one manager (section 23); removing or demoting the last one is refused with A document must keep at least one owner. Nobody can give more than they hold (section 23).

A change takes effect for people who have the document open straight away, without them reloading (next section).

08 / What a removed person sees

When a person's access to a document ends while they have it open, the server removes their connection at once instead of waiting for them to reconnect. The page then empties the text box and the list of people, hides the Sharing panel, stops trying to reconnect, and shows one of these in the status line:

Why a page was removed
CauseStatus shown
An owner removed their accessYour access to this document was removed.
They signed out (in this or another tab of the same session), or the session reached 30 daysYou were signed out.
An administrator disabled their accountYour account was disabled.

Reopening the document after losing access shows This document does not exist, or you do not have access to it. Opening any page when the session is over sends the person to the sign-in page.

Lowering a role from editor to viewer does not remove the person. Their text box becomes read-only, they are marked read only in the list of people, and if they had typed something the server had not yet accepted, it is refused and the status reads A change was refused because you can no longer edit this document. Raising a role makes the text box editable the same way. Every change of role is sent to the open page, including one that does not change whether the person may edit: a person made owner gets the Sharing panel, and an owner made editor or viewer loses it, without reloading.

These changes are made in PostgreSQL first and then sent to the open document inside the server process. This works because there is one server process. If the role cannot be read at that moment, the person's connections are removed rather than left open.

09 / Where data is kept

ShareCraft keeps two stores, and they hold different things.

Git and PostgreSQL
StoreHoldsIf it is lost
Git, the library repository under the data folderThe content of every document and its metadata, one Git commit per saved checkpoint. Only the server writes to it.Documents and their history are lost. Back up the data folder.
PostgreSQL, the database named by DATABASE_URLAccounts and password hashes, sign-in sessions, who has access to which document, the index of revisions, and events (sections 10 and 11).Nobody can sign in, and who may open which document is forgotten. The documents themselves are safe in Git. See below.

PostgreSQL needs its own backup. Backing up the data folder does not back up accounts, sharing or events, and backing up the database does not back up document content. Keep both, taken at about the same time. Only the revision index in PostgreSQL can be rebuilt from Git (section 10).

If PostgreSQL is lost and you start with an empty database, you must create the first administrator again (section 03). Starting the server then re-creates a record for each document found in Git, with no creator and no grants, so only administrators can open them until they share them again. Accounts, passwords, sharing and events are not recovered by this. The content tree is rebuilt from Git as well (section 18).

The Git repository

Documents are stored in one bare Git repository under the data folder:

<data folder>/libraries/00000000-0000-0000-0000-000000000001.git

With the defaults that is data/libraries/00000000-0000-0000-0000-000000000001.git. The data folder is not kept in Git. Every document lives in that one library for now.

Inside the repository, the main branch holds, for each document identifier:

  • docs/<doc_id>/content: the document text, or for a file document the file's bytes exactly as saved.
  • docs/<doc_id>/meta.json: the metadata for that revision, as JSON: the document's name, free-form fields, and the people credited so far.

Each saved checkpoint is one Git commit. The commit's author is the account that made the change; if several accounts contributed since the last checkpoint, the others are named on Co-authored-by lines. Their addresses are of the form <account id>@sharecraft.invalid, not real email addresses. The document identifier is the one after the # in the page's address. To look at a saved document with plain git, run these from the repository root:

git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git log main
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/content
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/meta.json

Replace <doc_id> with the identifier. Only read from the repository this way. Content must reach it through the server, which is the only thing that writes to it.

When a checkpoint is written

Live changes are not committed one by one. The server writes a checkpoint when no change has arrived for 2 seconds, or at the latest 30 seconds after the first change that has not been saved yet, whichever comes first. When the last person leaves a document, it is saved straight away. If that final save fails, the server tries again after 2 seconds, doubling the wait each time up to 30 seconds, for up to 10 attempts in all (about three minutes); then it gives up and prints a message to the server's console. The document stays open on the server while it is still trying, even after the grace period. A save that fails while people are connected is retried after the idle time.

The page shows the state next to the document title: Saving…, Saved, or Saving failed, retrying.

The server keeps the most recent 1000 log entries behind the last checkpoint, and keeps a document open for a grace period of 60 seconds after the last person leaves it. A browser that drops for a short time therefore catches up, resends its changes and keeps the typing it did while disconnected, including when it was the only one there, as long as it is back within the grace period. After that, the document is closed and saved; a tab that comes back later is given the saved text, and any typing it did while disconnected cannot be kept (section 12). The same happens after a server restart.

10 / The revision index, start-up reconcile and rebuild

PostgreSQL holds a list of each document's revisions: the Git commit id, its position in the document's history, its parent, when it was committed and who is credited. The documents page uses it to show each document's last save time. The list is an index: Git is the authority, and the index can always be replaced from it.

  • After each checkpoint the server adds the new revision to the index in the background. If this fails, the content is still safe in Git, the failure is printed to the server's console and recorded as an event, and the next start repairs the index.
  • At every start the server reconciles: for each document in Git it compares the newest revision in the index with Git's, and replaces the document's list from Git when they differ. It prints one line before it prints its address and begins accepting connections, for example Reconciled revisions with Git: 3 documents in Git, 1 updated, 0 failed. A document that cannot be read is listed on the console and the server still starts.
  • rebuild replaces the list of every document in Git, whether or not it looks out of date. Use it if you suspect the index is wrong. It needs DATABASE_URL and the data folder, brings the schema up to date, prints Rebuilt revisions from Git: ... with the same counts, names any document it could not rebuild, and exits with a failure code if there was one:
cargo run -p server -- rebuild

Neither reconcile nor rebuild writes to Git. If Git was changed by something other than the server, the next checkpoint of that document stops with a conflict (section 12) instead of merging.

How an owner reads them. There is no events page yet. An owner of a document (or an administrator) who is signed in reads that document's events by opening this address in the same browser:

http://127.0.0.1:8787/api/docs/<doc_id>/events

The answer is JSON: the latest 200 events of that document, oldest first, each with an id, a time, the kind, the account ids of the actor and the subject (null when there is none), and the details. People appear as account ids, not names. To match an id to a person, open /api/docs/<doc_id>/access (owners only; it lists everyone granted access, with names and emails) or, as an administrator, /api/admin/users. Someone with no role on the document gets 404, and a viewer or editor gets 403.

The events that belong to no document (accounts, sign-ins, failed sign-ins) cannot be read through the site. They are in the events table in PostgreSQL, readable by whoever runs the database.

12 / Stopping the server, and notices on the document page

Stopping the server (for example with Ctrl+C) ends it at once. The server loses any changes made since the last checkpoint, which can be up to 30 seconds of typing. Everything up to the last saved revision is kept in the Git repository and is loaded again the next time the document is opened. Accounts, sessions and sharing are in PostgreSQL and are unaffected; people stay signed in across a restart.

Notices about the connection and saving

A tab that is still open shows Connection lost. N changes waiting and keeps that status for the whole outage while the page retries in the background (first after 0.5 seconds, with the wait doubling up to 8 seconds between tries). When the server is back, the status returns to Saved.

If the server was restarted, or the document was closed after its grace period and opened again, the tab is reset to the last saved text, and the status says what that cost:

  • If the saved text is older than the text the server had accepted, it reads This document was reopened from its last save. Changes made after that save were lost. This happens when the server stopped before saving. If changes typed while the connection was lost were also thrown away, it adds N changes you typed while disconnected could not be kept.
  • If the saved text is everything the server had accepted, but the tab held changes typed while disconnected, it reads N changes could not be kept. This is the usual case after the grace period.
  • If nothing differs, nothing was lost and the status simply returns to Saved.

If the server kept running but could no longer take the tab back where it left off, the tab is brought up to date with the server's text and, if it had to throw away changes, reads N changes could not be kept. These messages stay until you next type. If saving is failing at the same time, the status reads Saving failed, retrying. followed by the message.

Wait for the status to read Saved before you stop the server.

13 / The editors: building and installing them

Spreadsheets, word documents, PDFs and 3D designs open in four editors: GridCraft, WordCraft, PdfCraft and SolidCraft. Each is a fork of another project's open-source editor. ShareCraft does not contain them: each is built on this machine from its fork into editors/<id>/ in the repository root, and the server serves it from there. That folder is not kept in Git. Where each fork comes from, what was changed in it, and what was checked, is in editors.html. Text documents need none of this.

What you need

  • Trunk, the tool the editors use to build their web version. Install it for your own user (no administrator rights are needed). Development used trunk 0.22.1:
cargo install trunk --locked
  • The WebAssembly target (section 01) and Git.
  • Time, memory and disk space. A build takes from about 10 minutes (GridCraft) to about 50 minutes (SolidCraft); most of the time goes into the optimiser, which used up to 5.6 GB of memory for SolidCraft. The installed editors take 26 MB to 160 MB each, the compressed copies described below add roughly another 55 to 65 per cent of that, and the build's intermediate files take several gigabytes more.

A Windows Firewall prompt for trunk.exe. During one build Windows asked whether to let trunk.exe accept network connections. The process was trunk build --release, which serves nothing, and it held no network connections when it was looked at; why the prompt appeared was not established. The build needs no incoming connections, so choosing Cancel is safe. No firewall setting was changed.

Cloning the forks

The build tool expects each fork in a folder beside the ShareCraft repository, on its sharecraft branch. From the folder that holds ShareCraft:

git clone --branch sharecraft https://github.com/ThineCraft/GridCraft GridCraft
git clone --branch sharecraft https://github.com/ThineCraft/WordCraft WordCraft
git clone --branch sharecraft https://github.com/ThineCraft/PdfCraft PdfCraft
git clone --branch sharecraft https://github.com/ThineCraft/SolidCraft SolidCraft

To update a fork from its original project later, also add that project as a remote named upstream (for example git -C GridCraft remote add upstream https://github.com/storytold/gridcraft); editors.html gives the steps.

The build tool

editors.toml in the repository root records, for each editor, its original project and base commit, its fork, branch and folder, and the fork commit last built and checked. From the ShareCraft repository root:

cargo xtask editors list               # each editor: commit recorded, state of its folder, installed build
cargo xtask editors build gridcraft    # build one editor (gridcraft, wordcraft, pdfcraft, solidcraft) and install it
cargo xtask editors compress [id]      # add or refresh the compressed copies of installed editors (all, or one)
cargo xtask editors verify             # every installed editor matches editors.toml, and no compressed copy is out of date

What build does. It first refuses, with a message saying why, if the fork's folder is missing, is not on the recorded branch, has uncommitted changes, was not cut from the recorded base commit, or if Trunk is not installed (it says how to install it and never installs it itself). It then:

  1. makes a clean temporary copy of the fork's committed head (a Git worktree) in the system's temporary folder, outside the repositories folder;
  2. runs trunk build --release --public-url ./ in the editor's web app folder of that copy;
  3. refuses a build whose index.html points at addresses outside its own folder;
  4. computes a fingerprint (a SHA-256 hash) of each script and style written inside index.html, for the security policy (section 17);
  5. writes editor.json, the manifest: the editor's id and version, its fork and upstream commits, the build date (in UTC) and those fingerprints;
  6. copies the fork's licence, notice and attribution files into licenses/, and refuses if there is no licence or notice file;
  7. writes a Brotli copy (.br) and a gzip copy (.gz) beside each file of at least 1,024 bytes whose name ends in .wasm, .js, .mjs, .css, .html, .json, .svg, .txt or .webmanifest, in the new build, before anything is replaced (see below);
  8. only then replaces editors/<id>, leaving out files and folders whose names start with a dot (such as Trunk's empty .trunk-lock). A failed build, including a failure to write the compressed copies, leaves the installed editor as it was. The temporary copy is removed in every case.
  9. prints xtask: restart the ShareCraft server to serve this build.

Why a clean temporary copy. Cargo applies a configuration file (.cargo/config.toml) found in any folder above the one it builds in. A developer's own settings there would silently change what is built; one such file on the owner's machine points one of SolidCraft's libraries at a local copy. Building from a copy outside the repositories folder means only the fork's own settings apply, and the fork's folder is never changed by the build. If build finds a Cargo configuration above the temporary folder (other than Cargo's own home folder), it refuses and says to set TMP and TEMP to a folder outside it.

Where the compiled pieces go. Cargo's intermediate files go to one folder per editor under SHARECRAFT_EDITOR_TARGET_DIR, or under sharecraft-editor-target in the system's temporary folder when it is not set. Keeping them makes a rebuild faster.

verify checks each installed editor against editors.toml: the fork commit it was built from must be the recorded commit, its upstream commit the recorded base, and the fingerprints in its manifest must match its index.html. It also reports any compressed copy that is older than the file beside it (the file changed after the copy was made), naming the editor and saying to run cargo xtask editors compress <id>. cargo xtask check runs it too, for installed editors only, so a machine with no editors built still passes.

The compressed copies. The editors' WebAssembly files are tens of megabytes, so the server sends a compressed copy where it can. The build tool writes the copies at install time, so the server does no compression work while it runs. A browser that accepts Brotli gets the .br copy, one that accepts only gzip gets the .gz copy, and any other request gets the plain file; the answer keeps the plain file's content type. The sign-in check, the same-origin check, the editor policy, no-cache and nosniff are the same for all three (section 20). A file that is not worth compressing (under 1,024 bytes, or a kind not listed above, such as images) has no copies.

cargo xtask editors compress (give an editor's id to do just one) adds or refreshes the copies in editors that are already installed, so an editor built before this change does not have to be rebuilt. It prints, for each editor, the sizes of the compressible files plain, with gzip and with Brotli, and the time taken; Brotli is slow on large files, so it takes from about 20 seconds (GridCraft) to nearly 2 minutes (SolidCraft). An editor that is not installed is reported as such. The copies are made from the plain files and replace any copies already there.

Never edit a copy by hand, and compress after any change made outside the build tool. The server serves a copy without comparing it to its file, so a copy that is out of date is what browsers get. If you change an editor's files in any way other than cargo xtask editors build, run cargo xtask editors compress <id> afterwards. A lone .gz or .br that has no partner is taken to be a file the editor itself ships and is left alone.

Measured on 11 November 2026, the Brotli copies of an editor's compressible files are about 22 to 27 per cent of their plain size. The figures for each editor, and what was and was not checked in the browser, are in editors.html, section 02.

Restart the server after cargo xtask editors build. The server reads the installed editors once, when it starts, so until it is restarted it keeps serving the build it found then; the build tool's last line says so. A folder whose manifest is missing or wrong is skipped with one warning line, and the server still starts.

Known problem: restarting after a killed build

If a build is killed (for example by a reboot), the temporary copy it made can be left behind. The next build may then refuse to start, with the "Cargo config above" message, when the leftover copy holds the fork's own Cargo settings file (WordCraft commits one; the check trips before the leftover is cleared). Clear it by hand with git worktree remove (give it the leftover folder, with --force if Git asks), run from the fork's folder, then build again.

Built editors contain the builder's local folder paths, and must be rebuilt with path remapping before they are published; see editors.html.

A document is either a text document, edited in doc.html as before, or a file document: a spreadsheet (.xlsx, GridCraft), a word document (.docx, WordCraft), a PDF (.pdf, PdfCraft) or a 3D design (.solidcraft.json, SolidCraft). 15 / The file session, the editing seat and saving

A file session is the server's record of who has a file document open. It uses the same WebSocket address (/ws/docs/<id>), the same sign-in and role checks and the same removal as a text document (section 08). Unlike a text document's session it holds no content: only who is there, the current revision, and who holds the editing seat. The file's bytes travel over HTTP (section 16).

Joining, in two steps

When a page asks to join, the server accepts the request but does not yet let the page in. It checks the person's access once more, and only then admits the page: it is sent the list of people, the current revision and the seat, and may take the seat. Someone whose access ended between the two steps is sent the removal message instead, and nobody else ever sees them come and go.

The editing seat

  • At most one page holds the seat. A page whose person may edit (editor or owner) takes it when it joins while the seat is free. Viewers never take it.
  • The holder's page is given a seat token: 32 random bytes, sent only to that page, new each time the seat is given. A save must carry it.
  • The seat is freed when its holder leaves, is removed, or loses the right to edit. It is not handed on: the others are told it is free, and a page takes it only by joining again, because its copy of the file may be old.
  • One exception, chosen on purpose: a page whose connection dropped and that joins again while the seat is free takes it without reloading. If its copy is older than the stored file, its first save is refused as a conflict, and the page stops saving (below).

The save path

  1. The editor hands the page the whole file. The page uploads it with PUT /api/docs/<id>/content?base=<revision>, carrying the seat token and the revision its copy was made from.
  2. The server checks the person's role before it reads the upload (no role is 404; a viewer is 403), then hands the bytes to the file session. Nothing else can write a file document's content.
  3. The session refuses the save unless it comes from the seat holder with the current token (403), and unless it was made from the current revision (409, naming the current one).
  4. It writes the bytes as one Git commit, credited to the seat holder alone, and tells everyone in the session it is saving and then that it is saved. A write that has started finishes even if the person goes away or is removed meanwhile.
  5. One save is written at a time, and one more may wait behind it. A further save arriving then is answered 503 with {"error":"busy"} and nothing is done. The page itself never sends more than one save plus one waiting.

Saving the same bytes again answers the current revision with "changed": false and writes nothing.

After a 409 the page stops saving for that page load. With one seat, a conflict means the stored file moved past the page's copy, so trying again could never succeed, and guessing a newer base would overwrite someone's save. The banner reads This file was changed somewhere else, so your last save was not stored. Download your copy, then reload. with Download my copy and Reload. Later saves from the editor are kept in the page for Download my copy but not uploaded.

If the Git repository was changed by something other than the server, the next save finds a revision it did not expect. The session then refuses every later save and ends once everyone has left, as a text document does (section 12).

A file session stays open for the grace period (60 seconds) after the last person leaves. There is nothing to save when it ends: every save was already written.

Inherited access

Access is given on a site, library, folder or file, to a person or a group, as a role (the built-in roles are in section 07; roles and groups are in section 23). An item inherits its access from the nearest item above it that has access of its own; that item is its scope. A site is always a scope. Giving someone access on an item that inherits, or removing someone from it, first breaks inheritance: the item becomes a scope of its own, starting with a copy of the assignments it inherited, and then the change is made. Inherit again deletes the item's own assignments, so it follows the scope above once more. Nothing below the item is read or written when either happens, so the cost does not grow with the number of files.

A person who has a role only somewhere below an item sees that item on the way down, with limited access (no role of their own on it), and sees only the path to what they were given. Administrators are owners of everything, as in section 07. When a change alters who may open a file that is open, the server works out each connected person's role again straight away: connections that lost access are removed (Your access to this document was removed.), and the others get their new rights. A file that is deleted removes everyone connected to it. Section 08 describes what the person sees.

18 / The content tree in Git and in PostgreSQL

The tree is recorded in the same repository as the documents (section 09), one JSON file per item, beside docs/ on the main branch:

  • docs/<doc_id>/content and docs/<doc_id>/meta.json: as before.
  • tree/<xx>/<node_id>.json: one item of the tree (a site, library, folder or file). The file is named after the item's identifier, which for a file is its document identifier, and kept in the sub-folder named by the identifier's first two hexadecimal digits (tree/3f/3f2a…json), so tree/ holds at most 256 sub-folders. A change to one item then rewrites only its own sub-folder of a few hundred entries, not a folder of every item: in a library of 100,000 files that is the difference between a rename taking well under a second and taking many. Servers before 12 November 2026 kept every record directly in tree/; the first start of a newer server moves them (section 19).
  • refs/sharecraft/docs/<doc_id>: the last commit that changed that document, as before.
  • refs/sharecraft/tree: the last commit that changed tree/.

A record looks like this (two-space indent, one line per field):

{
  "schema": 1,
  "id": "<node id>",
  "kind": "document",
  "parent": "<id of the library or folder it is in; null for a site>",
  "site": "<id of its site; a site's own id for the site>",
  "name": "Budget 2028.xlsx",
  "created": { "at": "<RFC 3339 time>", "by": { "id": "<account id>", "name": "<name>" } },
  "deleted": null
}

kind is site, library, folder or document. A deleted item is not removed from Git: its record stays with deleted set to the time and person, so its history is kept and its name is free again.

One change, one commit. Each create, rename, move or delete is one Git commit on main, credited to the person who made it. A change that touches several items writes them in the same commit: moving a folder to another site rewrites the site of everything below it. A tree commit does not move any document's ref, so a checkpoint of a file open at that moment is never refused because of it. To look at the tree with plain git, from the repository root (read only, as in section 09):

git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git ls-tree main tree/
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:tree/<xx>/<node_id>.json
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git log refs/sharecraft/tree

PostgreSQL mirrors it. After the commit, the server writes the same facts to PostgreSQL in one transaction with the event, and the pages read the tree from there. Git is the authority for the tree, as it is for documents. If the database refuses the change after the commit (the person's role changed meanwhile, or the name was taken), or fails before the change could be judged allowed, a second commit takes the change back in Git. If the database write fails after the change was judged allowed, the server tries to repair that item from Git, and if it cannot, it refuses further tree changes with 503 unavailable until a repair of the whole tree succeeds. A take-back that cannot be written to Git also stops tree changes; it is written again before that repair, so a refused change never reaches PostgreSQL. A take-back still unwritten when the server stops is lost, and the next start copies the refused change from Git (see section 21). At every start the server compares every record in Git with its row and rewrites the rows that differ (section 19).

Permissions are not in Git. Who has access to what, and which items take it from above, is kept only in PostgreSQL, and every change of it is written to the event log: access.granted, access.changed and access.revoked (section 11), now for any item, not only documents. Roles, groups and memberships are in PostgreSQL only too, with their own events (section 11). Tree changes are events too: node.created, node.renamed, node.moved and node.deleted, with document.created as before for a file, and tree.adopted once for an upgrade (section 19). Git alone can therefore give back the tree and the content, but not who may open them. This is why PostgreSQL needs its own backup (section 09). If PostgreSQL is lost and the database is empty, the next start rebuilds the tree from Git and gives each site its three groups, with no members (section 23); an administrator, who holds every permission, puts people back into them and shares the items again.

19 / Upgrading an installation that already has documents

Before the content tree, every document stood alone, with its own list of people. On the first start after upgrading, the server puts each existing document into the tree and moves its list of people onto it. Back up both stores first (section 09): the data folder and the PostgreSQL database.

Run cargo xtask web after every upgrade, before starting the server. The text editor's WebAssembly client in web/pkg is built from the source but not kept in Git, and cargo xtask check does not look at it, so an upgrade leaves the old one in place without any warning. An old client can misread what a newer server sends: one built before deleting files existed showed This document does not exist, or you do not have access to it. instead of This document was deleted. to people who had the file open.

Upgrading to a server from 12 November 2026 or later moves the tree records, one way. On its first start the server moves every record from tree/<node_id>.json into its sub-folder tree/<xx>/<node_id>.json (section 18), in one Git commit by ShareCraft with the message tree: move records into sub-folders. Only refs/sharecraft/tree moves with main; no document's ref does, and no document's content changes. An older server started on the repository afterwards would find no tree at all. Back up the data folder before upgrading (section 09), so that you can go back.

Upgrading to a server with groups and roles (12 November 2026) changes the database as well, one way. Four migrations run on the first start. A server from before groups and roles, started on the upgraded database, refuses to start: it finds migrations it does not know. Started with the old database but the upgraded repository, it would find no tree, because the records have moved into sub-folders. Back up the PostgreSQL database as well as the data folder before upgrading (section 09): the backup is the only way back. What they do is in section 23: every grant becomes an assignment; every grant on a site becomes a membership of the site's Owners, Members or Visitors group; nobody gains or loses access.

What the start does, in order

  1. Moves tree records into sub-folders. Only records still at their old place move; a later start finds none and writes nothing. A record found at both places, which should not happen, is kept from whichever place has the later record (its time of creation or, if it was deleted, of deletion; the sub-folder's on equal times), and the start-up line says how many there were.
  2. Reconciles the tree. Every tree/ record in Git is compared with its row in PostgreSQL, and the rows that differ are written. On a first upgrade there are no records yet.
  3. Adopts existing documents. This runs only if some document has no place in the tree, some grant is still recorded the old way (per document), or some site, deleted or not, lacks its three groups. Otherwise nothing is done.
  4. Reconciles the revision index (section 10), as before.

What adoption does

  • Home > Documents. A site named Home with a library named Documents is made, by the account name ShareCraft, in the same Git commit that records the documents. Every document without a place goes into that library. Each keeps its creation time, and is credited to its creator where there is one. Home gets its three groups (Home Owners, Home Members and Home Visitors) with no members, as does any other site that lacks them; administrators hold every permission without being members, and add people to the groups.
  • Renames. Names now follow the rules in section 17, so a name can change. Each refused character (control characters and " * : < > ? / \ |) becomes _, as does a trailing dot; a name that ends up empty becomes Untitled; a name over 120 characters is shortened, keeping its extension. A name already used in the library, ignoring case, gets (2), (3) and so on before the extension: two documents called Notes.txt become Notes.txt and Notes (2).txt. The new name is stored on the document as well as in the tree. The number renamed is on the start-up line.
  • Grants move to per-document permissions. Each document that had people granted keeps exactly those people and roles, as assignments of its own: it becomes a scope that does not inherit from Home. A document shared with only some people therefore stays visible to only them (and to administrators). The number of grants moved is on the start-up line.
  • One event. tree.adopted records the counts (documents, renamed, grants moved). Nothing is lost if the start is interrupted: if the Git commit was written and the database change was not, the next start's reconcile writes the items and adoption moves the grants.

An enabled administrator is needed

Someone has to be able to fill the new site's groups and own its documents, so adoption needs at least one enabled administrator. If there is none, nothing is written, the server still starts, and it prints this on the console, naming the command to run:

sharecraft-server: existing documents not adopted: existing documents need an administrator to own them, and there is no enabled administrator; add one with `sharecraft-server add-user --admin --email <email> --name <name>` and start the server again

Until the server is started again with an administrator, the existing documents have no place in the tree and nobody can open them.

The start-up line

The server prints one line for the tree before the line for the revision index (section 10), and before it prints its address. After an upgrade it reads like this (the numbers are examples):

Reconciled the tree with Git: no records to move into sub-folders; 0 nodes in Git, 0 updated, 0 failed; 12 documents adopted into Home, 3 renamed, 11 grants moved

The first clause says what the move did: no records to move into sub-folders, or for example 1250 records moved into sub-folders, followed, if any record was at both places, by , 2 found at both places, the later of each kept. If the move cannot be written the server prints why and exits. On later starts the line ends ; nothing to adopt. When there is no enabled administrator it ends ; nothing adopted, followed by the message above on standard error. Each node that could not be reconciled is listed on standard error with the reason, and the server still starts. If the tree cannot be read from Git at all, or the adoption fails for another reason, the server prints why and exits without printing its address.

Anything that used GET /api/docs to list documents must change: it now answers 405 (section 17).

20 / The editor pages' security policy, and why it is built from hashes

A Content Security Policy is a header that tells the browser what a page may load and run. The site's own pages allow only scripts from this site and WebAssembly, may hold a frame from this site (frame-src 'self', for the frame page), and may not be put inside anyone's frame (frame-ancestors 'none').

The editors' files, under /editors/<id>/, get their own policy instead:

default-src 'self'; script-src 'self' 'wasm-unsafe-eval' <script hashes>; style-src 'self' <style hashes>;
img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self';
worker-src 'self' blob:; frame-src 'self' blob:; frame-ancestors 'self';
base-uri 'none'; form-action 'none'
  • frame-ancestors 'self' lets the editor be shown inside ShareCraft's frame page, and nowhere else.
  • base-uri 'none' (a page cannot change the address its links are read against) and form-action 'none' (no form can be sent anywhere) take away two things the editors, which draw everything themselves, never use.
  • There is no object-src 'none', which would forbid browser plug-ins: WordCraft and PdfCraft print through a PDF shown in a hidden frame under this same policy, and the browser's PDF viewer may count as a plug-in. Plug-ins stay limited to this site by default-src 'self', as before. Printing has not been checked in any browser.
  • 'wasm-unsafe-eval' lets the browser compile the editor's WebAssembly. Despite the name, it does not allow scripts to run text as code.
  • The hashes. Each editor's index.html, as its build tool writes it, has a few small scripts and styles written inside the page. A policy that blocks scripts written into a page is what stops an injected script from running, and allowing all of them ('unsafe-inline') would undo that. Instead the policy names each allowed piece by its fingerprint, a SHA-256 hash of its exact text. The browser runs a piece only if its text has exactly that hash. The hashes are computed when the editor is built and kept in its manifest; the server checks each is a well-formed hash before using it, and drops a manifest that has a bad one.
  • Line endings. Browsers turn Windows line endings (CR LF) into plain LF before they compute a hash. A Windows checkout of a fork has CR LF in its files, so the build tool does the same before hashing. Without this, GridCraft's first build had a hash the browser did not accept; the tool was fixed, and that editor rebuilt.

The editors' files are served only to signed-in people, from a page of this site, with Cache-Control: no-cache (the browser asks whether a file changed before using its copy) and X-Content-Type-Options: nosniff. Where a compressed copy exists and the browser accepts it, the answer also carries Content-Encoding: br (or gzip) and Vary: Accept-Encoding, and keeps the plain file's Content-Type (application/wasm for a WebAssembly file). Anything else, including a path that tries to leave the editor's folder in any spelling, is 404. Every file in an installed editor's folder is served this way, including editor.json. The build tool no longer installs dot files; an editor installed before 10 November 2026 may still hold an empty .trunk-lock file, which is harmless and goes with the next build.

Because the editors come from ShareCraft's own address, they run with the rights of the person using them; that is why they are built only from ThineCraft's own forks (decision D20 in scope.html).

21 / Known limits of this build

  • Local connections only. The server will not listen on a non-loopback address and refuses connections that do not come from a page it served (section 04). Two people on two computers cannot use it together. Passwords must not cross a network without encryption, and encryption (TLS) is a separate piece of work.
  • Accounts are made by an administrator. There is no sign-up, and nobody can change their own password yet, nor reset a forgotten one.
  • No single sign-on, multi-factor sign-in or guests. Access is a password account, given to a person or to a group on a site, library, folder or file. Groups cannot contain groups.
  • Only the first part of sites and libraries. The tree and inherited access are built (sections 17 to 19). Groups, roles and the inheritance explorer are built (section 23). Sharing links, anyone links and access requests are built (section 24). Not built yet: guests, domain allow and block lists, notifications, service identities, audience targeting, branding, and metadata edited after creation. A library of 100,000 files is measured (section 22).
  • Links work on this machine only. A link's address is built from the address the person making it is using, and the server listens on the local machine only (section 04). A link opened on another computer will not reach it. Anyone links do not yet count how often they are used.
  • No page for events (section 11), and no way to see the document's saved revisions from the site: use Git (section 09).
  • One server process. Removal from live sessions is sent inside the process; running several server processes would need a different mechanism.
  • Large pastes go in pieces. One change can be at most 512 KiB as sent (section 05); a larger paste is refused with a message asking for smaller parts.
  • One person edits a file at a time. GridCraft, WordCraft, PdfCraft and SolidCraft files open from ShareCraft and save back as Git revisions, but only the holder of the editing seat can save; others read under a banner. Editing a file together is Stage 2 work. Saving is on demand, never automatic.
  • The editors save only while their tab is shown. A Save sent while the browser tab is hidden waits until the tab is shown again. While hosted, the editors refuse New, Open and Close and keep the document they were given; PdfCraft may still open some views as extra tabs. See editors.html.
  • Editors are built on this machine (section 13), take tens of minutes each, and are not published. A build to be published must first be rebuilt with path remapping.
  • The first open of an editor is still a large download. The editors are sent compressed (section 13), but SolidCraft's WebAssembly file still arrives as about 34.5 MB the first time it opens, and the others as 7 MB to 13 MB. A browser keeps them afterwards. Sizes are in editors.html. Opening and editing in each editor after compression was added has not been checked.
  • Uploads only make new documents. A file cannot be replaced by uploading.
  • PostgreSQL needs its own backup (section 09), and the event log is never trimmed.
  • A take-back is kept only in memory. If a refused tree change could not be taken back in Git (section 18) and the server stops before it is written, the next start's reconcile puts the refused change into PostgreSQL. Both need Git to fail first; check the console for could not take back a tree change.

23 / Groups, roles and the inheritance explorer

Added on 12 November 2026 (plan 2A, on the branch platform-groups-roles). Access is given to a person or to a group. What it allows is a role, and a role is a set of permissions. All of it, like every permission, is kept in PostgreSQL only, and every change is an event (sections 11 and 18).

Permissions

There are six, a fixed list. Every permission except view includes view.

The permissions

The three built-in roles have fixed ids. They cannot be changed or deleted.

Custom roles. An administrator can define more on the Roles page (/roles.html). A custom role has a generated id, a name of 1 to 60 characters that no other role has (ignoring case), and at least view: view is added to any set that lacks it. Changing a custom role's permissions changes the access of everyone who holds it, everywhere, and reaches open sessions before the request answers: an editor whose role loses edit becomes read-only at once. A role that is assigned anywhere cannot be deleted (role_in_use).

Groups and site groups

A group is a set of people that can be given a role like one person. There are two kinds.

  • Site groups. Every site, deleted or not, has three: Owners, Members and Visitors, given the Owner, Editor and Viewer roles on the site. A site group stores its site, not a name. Its name is the site's current name followed by Owners, Members or Visitors (for example Projects Owners). It is built when it is read, so it follows a rename, and it is shown with its site. It can have the same display name as an organisation group, so the pages and answers always name the site beside it. The groups are made with the site, in the same transaction, and the person who creates the site becomes a member of its Owners. A site group cannot be deleted (site_group).
  • Organisation groups. These belong to no site. They have a stored name of 1 to 60 characters, unique ignoring case. Only administrators create them. One that is assigned anywhere cannot be deleted (group_in_use).

Groups cannot contain groups. Who may change a group's members: an administrator (every group), and anyone with manage_site on a site (that site's groups).

What a person sees of groups. Administrators, and people who manage access somewhere, see the organisation groups and the groups of the sites they can reach, never a site name they could not otherwise see. Whoever manages a site's groups also sees them and their members, and the site's list of groups, even without manage_access. Everyone else sees no groups. A group's members are shown only to those who manage the group and to administrators. Where an access page lists a group the person may not see, it shows no name (hidden).

No more than you hold

Nobody can give anyone more than they hold. A person may give a role on an item, or add someone to a group, only if every permission of that role (for a group, of every role it is given, wherever it is given) is one they hold there themselves. Otherwise the request is refused with beyond_your_access. Administrators are exempt. This is stricter than SharePoint, where anyone who can manage permissions can give Full Control.

Every place keeps a manager

Every scope keeps at least one assignment whose role includes manage_access. A change that would leave one without is refused with last_manager. This covers removing an assignment, giving a manager a lesser role, and changing a custom role: a role change that would leave any place without a manager is refused, so an administrator grants another manager first. An empty Owners group still counts as a manager. If the group that managed a place has been emptied, an administrator can always repair it.

24 / Sharing links and access requests

Added on 13 November 2026 (plan 2B, on the branch platform-links-requests). Two things are new. A person who manages access can share a file or folder by link. And a person who reaches something they cannot open can ask for access. Like all permissions, both are kept in PostgreSQL only, and every change is an event (sections 11 and 18).

Links only work on the local machine while the server is in development mode. The address of a link is built from the address the person making it is using, and the server listens on the local machine only (section 04).

Who can share by link

Only a person with manage_access on the item can make, list or revoke its links. SharePoint lets ordinary members share; ShareCraft does not. The link's role must be one the person holds there themselves (beyond_your_access; administrators are exempt, section 23). It may never include manage_access or manage_site (link_role_too_high), so a link never makes anyone a manager and never counts towards the last-manager rule (section 23). The access page has a Share by link panel, and the item's live links are listed there with their kind, role, expiry and how many people used them.

Signed-in links

A signed-in link is for anyone with an account. It is a hidden link group with the link's role assigned on the item. If the item inherits its access, making the link breaks inheritance first and gives the item its own permissions, as in SharePoint. Everything in section 23 then applies unchanged: the one access decision, locking, and live sessions.

  • An expiry is optional for a signed-in link.
  • Opening the link while signed in shows Open with Editor access (or the link's role). Pressing it sends a POST from the page, and that adds the person to the group. A person who already holds that much is not added. A plain visit never joins anyone.
  • A link group is never listed among groups and never offered in a group list or filter. The access, membership and group routes refuse it with link_group. In the explorer it shows as "Signed-in link (Editor, expires 1 December)", never as a group with a name. Filtering the explorer by a person also finds the breaks where a signed-in link they joined is assigned, shown as the link. On a break below a link's item that holds a copy of its assignment, the access page points to the link's own item, where it is listed and revoked; it names that item only to someone who may see it (a break moved out from under the item keeps its copy, and its new managers are told only "the item it was made on"). A break with anyone links shows "Anyone links: 2 live".
  • Restoring inheritance on an item that removes a link group's last assignment revokes that link, with the reason "inheritance restored".

Anyone links

An anyone link lets a person without an account view and download. It is not a group, because such a person has no session. The link's token is checked on every request.

  • Off by default. An administrator switches them on in Sharing settings (/sharing.html, linked from People), with a plain warning. Switching them off stops every anyone link at once, on the next request. They are not revoked, and they work again if the setting is switched back on before they expire.
  • View and download only. The role is always Viewer. An anyone link never opens an editor, a session, the access page, the explorer or any other route.
  • Always expiring. An expiry is required, and it may be at most anyone_link_max_days away (30 unless an administrator changes it). The request itself checks the time, so it stops at the expiry instant. The limit is checked when a link is made: lowering it later does not shorten links that already exist, which last until their own expiry unless revoked (the settings page says so next to the field).
  • What it reaches. The landing page; the listing of a shared folder and what is below it; downloads of files at or below the item; and the text of a plain-text document as last saved (unsaved live edits are not shown). A file never saved has nothing to download: the page shows "Not saved yet" in place of Download.
  • It stops at breaks. A folder or file below the item that has its own permissions is not reached, and neither is anything once it is moved out of the item or deleted, itself or through a folder above it. This is exactly what a signed-in Viewer link would reach.
  • No anonymous answer sets a cookie.

Tokens and addresses

  • A token is 32 random bytes from the operating system, written as 64 lowercase hex characters in the address /l/<token>. Only that spelling works: the same token in capitals is not found.
  • Only a SHA-256 hash is stored. The address is shown once, when the link is made, in a read-only box with a Copy button: "This address is shown only now. If you lose it, make a new link." A manager who needs it again makes a new link. The list of links never carries an address.
  • Every /l/ page and /api/l/ answer carries Cache-Control: no-store and Referrer-Policy: no-referrer. The sign-in page also sends no referrer.
  • If the visitor is not signed in, the landing page keeps the token in the tab's session storage, sends them to sign in, and returns them to /link.html. The token is in no address except the link's own.
  • An address that does not work shows one page, "This link does not work. It may have expired or been turned off.", whatever the reason. The server answers 404 link_not_found.

Expiry, revoking and the sweeper

Revoking is immediate (S5). For a signed-in link, the group's assignments (including copies below an item that broke inheritance later) and all its members are removed in one transaction, and open documents below the item are rechecked before the answer, so a person who came in only through the link is removed or limited at once. A person who also has access another way keeps it. A revoked anyone link fails on its next request.

The sweeper runs every minute inside the server and revokes each expired link as a manager would: one transaction per link, an event, and a recheck of open documents. An expired signed-in link stops within a minute. An anyone link stops at the expiry instant, because the request checks the time itself. The sweeper writes one line to the log when it revokes something, and also deletes request attempts older than a day. A database error does not stop the server: the sweeper tries again the next minute. Deleting an item revokes its links with the reason "item deleted".

Access requests

Wherever the page says "This document does not exist, or you do not have access to it", it also offers a short Request access form (a message of up to 500 characters).

  • The answer is identical for an item that exists, one that does not, and one the person can already open: "If this item exists, the people who manage it will see your request." Nothing is recorded for the last two.
  • The limit is 20 a day per person and counts every submission, recorded or not. It is checked before anything else (too_many_requests), so it says nothing about the item.
  • One open request per person per item. A second one updates the message.
  • The request goes to everyone with manage_access on the item. They see it on the Requests page (/requests.html), with a badge on the home page. Each shows the item's path, the person, their message and its age.
  • Approve chooses a role within the approver's own access and gives it to the requester directly on the item. It never downgrades: if the requester already holds that much, the answer is already_has and the request stays open. Decline may carry a reply the requester sees.
  • The requester sees their own requests only once decided, under My requests on the home page, with the decision and reply. The item is named only if they can now see it. Open requests are never listed, so the list cannot show which items exist.

Events

link.created, link.used (first use by each person), link.revoked (with the reason: manager, expired, item deleted, inheritance restored), request.created, request.approved, request.declined and setting.changed.
