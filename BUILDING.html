01 / What you need

  • Rust, stable channel, installed with rustup. The project uses the 2024 edition.
  • The WebAssembly target, which lets Rust build the part that runs in the browser:
rustup target add wasm32-unknown-unknown
  • wasm-bindgen-cli version 0.2.130, exactly. It must match the wasm-bindgen version recorded in Cargo.lock. If it is missing or a different version, cargo xtask web stops and prints the command to run:
cargo install wasm-bindgen-cli --version 0.2.130 --locked

If a later change to Cargo.lock moves wasm-bindgen to another version, the command printed by cargo xtask web shows the version then needed.

  • PostgreSQL. The server keeps accounts, sign-in sessions, sharing, the revision index and events in a PostgreSQL database and will not start without one. Development has used PostgreSQL 18 on the local machine. Create an empty database and an account that may create tables in it. For the tests (section 02) create a second, separate database and give the same account permission to create schemas in it; the tests do not create databases.
  • A .env file in the repository root, made by copying .env.example and replacing its placeholder values. It names the databases by variable (DATABASE_URL for the server, TEST_DATABASE_URL for the tests). .env is not kept in Git. Keep real values only there: never put a database address or password in a command that is saved, in a commit or in a message.
  • Node.js, to run the automated test files for the page scripts, which cargo xtask check runs (section 02). Without it the check stops and says that Node.js is needed.
  • Only for the file editors: Trunk and the editors' source, described in section 13.

Git does not need to be installed to run ShareCraft, because the Git library is built in. You only need it to look at saved documents (section 09).

02 / Build and check

Run every command from the repository root, the folder that holds Cargo.toml.

This loads .env, then checks that no dependency has a copyleft licence, checks formatting, runs the lints with warnings treated as errors, runs all tests in the workspace, builds each browser-side crate for WebAssembly, and runs the page script tests with Node (below). It prints xtask: all checks passed and exits with code 0 when everything is in order:

cargo xtask check

This loads .env and then runs cargo test with whatever arguments you add, for example cargo xtask test -p server:

cargo xtask test

The tests need TEST_DATABASE_URL. Every test that uses the database creates its own schema in that database. A test does not drop its schema when it finishes; each run drops the test schemas it finds that are more than an hour old, so a schema stays until the first run after that hour (the scale tests, section 22, leave a schema of about 100,000 rows). A test that needs the variable and finds it unset fails with a message saying so; it is never skipped. That is why you run the tests through cargo xtask check or cargo xtask test, which load .env, and not through plain cargo test.

This loads .env and runs the scale tests, which plain test runs skip because they take minutes: a library of 100,000 files is loaded and the main operations on it are timed in a debug build (section 22). It prints each time and fails naming any time over its threshold:

cargo xtask scale

This builds the browser client and writes the page's script package to web/pkg. The folder is not kept in Git, so do this once after a fresh checkout and again after changing the browser client:

cargo xtask web

The scripts of the web pages (the .js files in web) have two automated test files. web/common.test.mjs tests the function that decides where to go after signing in, so that a crafted link cannot send someone to another site. web/editor-host.test.mjs tests the frame page's pure parts: telling a save from an export, the save queue, the status and banner wording and the two editor bridges, against stand-in editors. cargo xtask check runs them, and fails with a message saying so when Node.js is not installed; it never skips them. It also checks any installed editors against editors.toml (section 13). To run the page tests on their own:

node --test web/*.test.mjs

Database migrations keep LF line endings. The server identifies each database migration by a checksum of the file's exact bytes. With Git's core.autocrlf on (common on Windows), checking out a branch once rewrote a migration file with Windows line endings, and the server then refused to start on an existing database with migration 1 was previously applied but has been modified. .gitattributes now pins the migration files to LF on every checkout. If you see that message after an older checkout, check the migration files out again (for example git checkout -- crates/records/migrations).

The migrations are built into the server program, so a build could keep the old bytes after the files were checked out again. Since 10 November 2026 a small build script (crates/records/build.rs) makes Cargo rebuild that part whenever anything in the migrations folder changes, and a test (migration_files_have_no_carriage_returns) fails, saying what to check, if a migration file on disk has a Windows line ending.

For anyone else with a Windows clone: if your database was first migrated from a copy of 0001_initial.sql with Windows line endings, the server, now built from the LF file, refuses to start with the message above. For a development database, the remedy is to drop it and create it again; the server sets it up on its next start. Never edit a migration file to make the message go away.

03 / The first administrator

There is no public sign-up, and nobody can sign in until an account exists. The first account, an administrator, is made from the command line. DATABASE_URL must be set (in .env or the environment). The command brings the database schema up to date, then creates the account:

cargo run -p server -- add-user --email <email> --name <name> --admin

Leave out --admin to make an ordinary account. The password is not a command-line option, so that it never appears in a process list or a saved command history. The command asks for it with Password: and does not show what you type. If its input is piped instead of typed, it reads the first line of that input as the password. It prints created administrator <email> (<account id>), or created account ... for an ordinary account. The password and the database address are never printed.

After the first administrator exists, further accounts are made on the People page (section 06); the command line stays available for the same job.

04 / Run it and sign in

Start the server, still from the repository root. It needs DATABASE_URL, which it reads from .env in the current folder or a parent. It takes its address first, so an address already in use is reported at once. It then brings the database schema up to date and compares the revision index with Git (section 10). Only then does it say where it listens and start accepting connections:

cargo run -p server

It prints the content-tree line (section 19) and the revision-index line, then the address it listens on and WARNING: development mode, local connections only. If the database cannot be reached or brought up to date, it prints why and exits without printing the address. Once the address is shown, open the site in a browser at exactly one of these addresses:

http://127.0.0.1:8787/
http://localhost:8787/

A person who is not signed in is sent to the sign-in page, and after signing in comes back to the page they asked for. After signing in the first page lists the sites the person can see; a site opens to its libraries, and a library or folder lists its folders and files, with a New document form and an upload (section 17). A document opens at an address such as /doc.html#<document id>; the part after # is the document's identifier, and anyone with access can use the same address.

Browsers keep cookies separately for 127.0.0.1 and localhost. To try two people at once on one computer, sign in as one at http://127.0.0.1:8787/ and as the other at http://localhost:8787/.

06 / Accounts and signing in

An account is one person: an email address, a display name, a password, and a flag saying whether they are an administrator. Accounts are created by an administrator, on the command line (section 03) or on the People page, where an administrator also chooses whether the new person is one. Nobody can register themselves, and nobody can change their own password yet.

What an account may contain
FieldRule
EmailAt most 254 characters, no spaces or control characters, one @ with something on each side. Case is ignored: two emails that differ only by case are the same account. Each email can have one account.
Name1 to 60 characters, at least one letter or digit, no control characters and no < or >. Names are shown to other people in a document and are credited in saved revisions.
Password10 to 256 characters. Nothing else is required. It is stored only as an Argon2id hash.

Signing in

The sign-in page sends the email and password to the server. When they match, the server starts a session that lasts 30 days and sets a cookie named sharecraft_session holding a random token. The cookie is marked HttpOnly (page scripts cannot read it) and SameSite=Lax. The server stores only a hash of the token. It is not marked Secure, because the build only serves plain HTTP on the local machine.

A wrong password, an unknown email and a disabled account all get the same answer, That email and password do not match., so the page does not reveal which emails have accounts. After 5 failed attempts for one email within 15 minutes, further attempts for it are refused with Too many attempts. Try again in a few minutes. The count is kept in the server's memory, so restarting the server resets it.

Signing out

The Sign out button is on the documents page. It ends that session and clears the cookie, and any open document pages of that session are removed (section 08). The same person's other sign-ins, in other browsers, stay signed in. A session also ends on its own after 30 days.

Managing people (administrators)

The People page lists every account with its email, whether it is an administrator and whether it is disabled. An administrator can add a person (email, name, password, administrator or not) and disable or enable an account.

  • Disabling an account ends all of its sessions at once and removes it from every open document. It cannot sign in again until an administrator enables it. Its documents and grants are kept.
  • At least one administrator must stay enabled: disabling the last one is refused with At least one administrator must stay enabled.
  • An administrator is treated as an owner of every document (section 07).

07 / Sharing and roles

A person who is an editor of a library or folder can create a document in it. The name is optional (it defaults to Untitled). Names follow the rules in section 17, and a document can be renamed and moved. A new document takes its access from the place it is in, as section 17 describes.

Access is granted to a person or to a group (section 23), on a site, library, folder or file, and passes down to what is inside it (section 17). A person with no role on a document cannot see it in a list and cannot open it. The server answers the same way for a document that does not exist and one you may not open, so you cannot find out that a document exists by guessing its address; the page says This document does not exist, or you do not have access to it.

The built-in roles (administrators can define more; section 23)

A viewer sees the live text and who else is there, but the text box is read-only and the page shows You can read this document but not change it. The server also refuses changes from a viewer, whatever the page does.

Administrators are owners of every document without needing a grant, so someone can always recover a document whose owners are gone. They appear in the Sharing list only if they were granted a role explicitly.

People who manage access can also share by link, and a person who reaches something they cannot open can ask for access. Both are described in section 24.

Sharing a document

Owners see a Sharing panel under the text. It lists everyone who has access to the document, whether it is its own or inherited, each with a role menu and a Remove button. To add someone, type their email, choose a role and press Share. Choosing another role in a person's menu changes their role at once. Sharing is by the email of an existing account, or by choosing a group from the list: No account has that email address. appears if there is none, and only owners can learn this. A document must keep at least one manager (section 23); removing or demoting the last one is refused with A document must keep at least one owner. Nobody can give more than they hold (section 23).

A change takes effect for people who have the document open straight away, without them reloading (next section).

08 / What a removed person sees

When a person's access to a document ends while they have it open, the server removes their connection at once instead of waiting for them to reconnect. The page then empties the text box and the list of people, hides the Sharing panel, stops trying to reconnect, and shows one of these in the status line:

Why a page was removed
CauseStatus shown
An owner removed their accessYour access to this document was removed.
They signed out (in this or another tab of the same session), or the session reached 30 daysYou were signed out.
An administrator disabled their accountYour account was disabled.

Reopening the document after losing access shows This document does not exist, or you do not have access to it. Opening any page when the session is over sends the person to the sign-in page.

Lowering a role from editor to viewer does not remove the person. Their text box becomes read-only, they are marked read only in the list of people, and if they had typed something the server had not yet accepted, it is refused and the status reads A change was refused because you can no longer edit this document. Raising a role makes the text box editable the same way. Every change of role is sent to the open page, including one that does not change whether the person may edit: a person made owner gets the Sharing panel, and an owner made editor or viewer loses it, without reloading.

These changes are made in PostgreSQL first and then sent to the open document inside the server process. This works because there is one server process. If the role cannot be read at that moment, the person's connections are removed rather than left open.

09 / Where data is kept

ShareCraft keeps two stores, and they hold different things.

Git and PostgreSQL
StoreHoldsIf it is lost
Git, the library repository under the data folder, with the content store (blobs) beside itThe content of every document (in Git for older versions, in the content store for newer ones) and its metadata, one Git commit per saved checkpoint. Only the server writes to it.Documents and their history are lost. Back up the data folder.
PostgreSQL, the database named by DATABASE_URLAccounts and password hashes, sign-in sessions, who has access to which document, the index of revisions, and events (sections 10 and 11).Nobody can sign in, and who may open which document is forgotten. PostgreSQL needs its own backup. Backing up the data folder does not back up accounts, sharing or events, and backing up the database does not back up document content. Keep both, taken at about the same time. Only the revision index in PostgreSQL can be rebuilt from Git (section 10).

If PostgreSQL is lost and you start with an empty database, you must create the first administrator again (section 03). Starting the server then re-creates a record for each document found in Git, with no creator and no grants, so only administrators can open them until they share them again. Accounts, passwords, sharing and events are not recovered by this. The content tree is rebuilt from Git as well (section 18).

The Git repository

Documents are stored in one bare Git repository under the data folder:

<data folder>/libraries/00000000-0000-0000-0000-000000000001.git

With the defaults that is data/libraries/00000000-0000-0000-0000-000000000001.git. The data folder is not kept in Git. Every document lives in that one library for now.

Inside the repository, the main branch holds, for each document identifier:

  • docs/<doc_id>/content: for a version saved since 14 November 2026, a pointer to the bytes in the content store (section 25). For an older version, the document text, or for a file document the file's bytes exactly as saved.
  • docs/<doc_id>/meta.json: the metadata for that revision, as JSON: the document's name, free-form fields, and the people credited so far.

Each saved checkpoint is one Git commit. The commit's author is the account that made the change; if several accounts contributed since the last checkpoint, the others are named on Co-authored-by lines. Their addresses are of the form <account id>@sharecraft.invalid, not real email addresses. The document identifier is the one after the # in the page's address. To look at a saved document with plain git, run these from the repository root:

git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git log main
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/content
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/meta.json

Replace <doc_id> with the identifier. Only read from the repository this way. Content must reach it through the server, which is the only thing that writes to it.

When a checkpoint is written

Live changes are not committed one by one. The server writes a checkpoint when no change has arrived for 2 seconds, or at the latest 30 seconds after the first change that has not been saved yet, whichever comes first. When the last person leaves a document, it is saved straight away. If that final save fails, the server tries again after 2 seconds, doubling the wait each time up to 30 seconds, for up to 10 attempts in all (about three minutes); then it gives up and prints a message to the server's console. The document stays open on the server while it is still trying, even after the grace period. A save that fails while people are connected is retried after the idle time.

The page shows the state next to the document title: Saving…, Saved, or Saving failed, retrying.

The server keeps the most recent 1000 log entries behind the last checkpoint, and keeps a document open for a grace period of 60 seconds after the last person leaves it. A browser that drops for a short time therefore catches up, resends its changes and keeps the typing it did while disconnected, including when it was the only one there, as long as it is back within the grace period. After that, the document is closed and saved; a tab that comes back later is given the saved text, and any typing it did while disconnected cannot be kept (section 12). The same happens after a server restart.

10 / The revision index, start-up reconcile and rebuild

PostgreSQL holds a list of each document's revisions: the Git commit id, its position in the document's history, its parent, when it was committed and who is credited. The documents page uses it to show each document's last save time. The list is an index: Git is the authority, and the index can always be replaced from it.

  • After each checkpoint the server adds the new revision to the index in the background. If this fails, the content is still safe in Git, the failure is printed to the server's console and recorded as an event, and the next start repairs the index.
  • At every start the server reconciles: for each document in Git it compares the newest revision in the index with Git's, and replaces the document's list from Git when they differ. It prints one line before it prints its address and begins accepting connections, for example Reconciled revisions with Git: 3 documents in Git, 1 updated, 0 failed. A document that cannot be read is listed on the console and the server still starts.
  • rebuild replaces the list of every document in Git, whether or not it looks out of date. Use it if you suspect the index is wrong. It needs DATABASE_URL and the data folder, brings the schema up to date, prints Rebuilt revisions from Git: ... with the same counts, names any document it could not rebuild, and exits with a failure code if there was one:
cargo run -p server -- rebuild

Neither reconcile nor rebuild writes to Git. If Git was changed by something other than the server, the next checkpoint of that document stops with a conflict (section 12) instead of merging.

How an owner reads them. There is no events page yet. An owner of a document (or an administrator) who is signed in reads that document's events by opening this address in the same browser:

http://127.0.0.1:8787/api/docs/<doc_id>/events

The answer is JSON: the latest 200 events of that document, oldest first, each with an id, a time, the kind, the account ids of the actor and the subject (null when there is none), and the details. People appear as account ids, not names. To match an id to a person, open /api/docs/<doc_id>/access (owners only; it lists everyone granted access, with names and emails) or, as an administrator, /api/admin/users. Someone with no role on the document gets 404, and a viewer or editor gets 403.

The events that belong to no document (accounts, sign-ins, failed sign-ins) cannot be read through the site. They are in the events table in PostgreSQL, readable by whoever runs the database.

12 / Stopping the server, and notices on the document page

Stopping the server (for example with Ctrl+C) ends it at once. The server loses any changes made since the last checkpoint, which can be up to 30 seconds of typing. Everything up to the last saved revision is kept in the Git repository and is loaded again the next time the document is opened. Accounts, sessions and sharing are in PostgreSQL and are unaffected; people stay signed in across a restart.

Notices about the connection and saving

A tab that is still open shows Connection lost. N changes waiting and keeps that status for the whole outage while the page retries in the background (first after 0.5 seconds, with the wait doubling up to 8 seconds between tries). When the server is back, the status returns to Saved.

If the server was restarted, or the document was closed after its grace period and opened again, the tab is reset to the last saved text, and the status says what that cost:

  • If the saved text is older than the text the server had accepted, it reads This document was reopened from its last save. Changes made after that save were lost. This happens when the server stopped before saving. If changes typed while the connection was lost were also thrown away, it adds N changes you typed while disconnected could not be kept.
  • If the saved text is everything the server had accepted, but the tab held changes typed while disconnected, it reads N changes could not be kept. This is the usual case after the grace period.
  • If nothing differs, nothing was lost and the status simply returns to Saved.

If the server kept running but could no longer take the tab back where it left off, the tab is brought up to date with the server's text and, if it had to throw away changes, reads N changes could not be kept. These messages stay until you next type. If saving is failing at the same time, the status reads Saving failed, retrying. followed by the message.

Wait for the status to read Saved before you stop the server.

13 / The editors: building and installing them

Spreadsheets, word documents, PDFs and 3D designs open in four editors: GridCraft, WordCraft, PdfCraft and SolidCraft. Each is a fork of another project's open-source editor. ShareCraft does not contain them: each is built on this machine from its fork into editors/<id>/ in the repository root, and the server serves it from there. That folder is not kept in Git. Where each fork comes from, what was changed in it, and what was checked, is in editors.html. Text documents need none of this.

What you need

  • Trunk, the tool the editors use to build their web version. Install it for your own user (no administrator rights are needed). Development used trunk 0.22.1:
cargo install trunk --locked
  • The WebAssembly target (section 01) and Git.
  • Time, memory and disk space. A build takes from about 10 minutes (GridCraft) to about 50 minutes (SolidCraft); most of the time goes into the optimiser, which used up to 5.6 GB of memory for SolidCraft. The installed editors take 26 MB to 160 MB each, the compressed copies described below add roughly another 55 to 65 per cent of that, and the build's intermediate files take several gigabytes more.

A Windows Firewall prompt for trunk.exe. During one build Windows asked whether to let trunk.exe accept network connections. The process was trunk build --release, which serves nothing, and it held no network connections when it was looked at; why the prompt appeared was not established. The build needs no incoming connections, so choosing Cancel is safe. No firewall setting was changed.

Cloning the forks

The build tool expects each fork in a folder beside the ShareCraft repository, on its sharecraft branch. From the folder that holds ShareCraft:

git clone --branch sharecraft https://github.com/ThineCraft/GridCraft GridCraft
git clone --branch sharecraft https://github.com/ThineCraft/WordCraft WordCraft
git clone --branch sharecraft https://github.com/ThineCraft/PdfCraft PdfCraft
git clone --branch sharecraft https://github.com/ThineCraft/SolidCraft SolidCraft

To update a fork from its original project later, also add that project as a remote named upstream (for example git -C GridCraft remote add upstream https://github.com/storytold/gridcraft); editors.html gives the steps.

The build tool

editors.toml in the repository root records, for each editor, its original project and base commit, its fork, branch and folder, and the fork commit last built and checked. From the ShareCraft repository root:

cargo xtask editors list               # each editor: commit recorded, state of its folder, installed build
cargo xtask editors build gridcraft    # build one editor (gridcraft, wordcraft, pdfcraft, solidcraft) and install it
cargo xtask editors compress [id]      # add or refresh the compressed copies of installed editors (all, or one)
cargo xtask editors verify             # every installed editor matches editors.toml, and no compressed copy is out of date

What build does. It first refuses, with a message saying why, if the fork's folder is missing, is not on the recorded branch, has uncommitted changes, was not cut from the recorded base commit, or if Trunk is not installed (it says how to install it and never installs it itself). It then:

  1. makes a clean temporary copy of the fork's committed head (a Git worktree) in the system's temporary folder, outside the repositories folder;
  2. runs trunk build --release --public-url ./ in the editor's web app folder of that copy;
  3. refuses a build whose index.html points at addresses outside its own folder;
  4. computes a fingerprint (a SHA-256 hash) of each script and style written inside index.html, for the security policy (section 17);
  5. writes editor.json, the manifest: the editor's id and version, its fork and upstream commits, the build date (in UTC) and those fingerprints;
  6. copies the fork's licence, notice and attribution files into licenses/, and refuses if there is no licence or notice file;
  7. writes a Brotli copy (.br) and a gzip copy (.gz) beside each file of at least 1,024 bytes whose name ends in .wasm, .js, .mjs, .css, .html, .json, .svg, .txt or .webmanifest, in the new build, before anything is replaced (see below);
  8. only then replaces editors/<id>, leaving out files and folders whose names start with a dot (such as Trunk's empty .trunk-lock). A failed build, including a failure to write the compressed copies, leaves the installed editor as it was. The temporary copy is removed in every case.
  9. prints xtask: restart the ShareCraft server to serve this build.

Why a clean temporary copy. Cargo applies a configuration file (.cargo/config.toml) found in any folder above the one it builds in. A developer's own settings there would silently change what is built; one such file on the owner's machine points one of SolidCraft's libraries at a local copy. Building from a copy outside the repositories folder means only the fork's own settings apply, and the fork's folder is never changed by the build. If build finds a Cargo configuration above the temporary folder (other than Cargo's own home folder), it refuses and says to set TMP and TEMP to a folder outside it.

Where the compiled pieces go. Cargo's intermediate files go to one folder per editor under SHARECRAFT_EDITOR_TARGET_DIR, or under sharecraft-editor-target in the system's temporary folder when it is not set. Keeping them makes a rebuild faster.

verify checks each installed editor against editors.toml: the fork commit it was built from must be the recorded commit, its upstream commit the recorded base, and the fingerprints in its manifest must match its index.html. It also reports any compressed copy that is older than the file beside it (the file changed after the copy was made), naming the editor and saying to run cargo xtask editors compress <id>. cargo xtask check runs it too, for installed editors only, so a machine with no editors built still passes.

The compressed copies. The editors' WebAssembly files are tens of megabytes, so the server sends a compressed copy where it can. The build tool writes the copies at install time, so the server does no compression work while it runs. A browser that accepts Brotli gets the .br copy, one that accepts only gzip gets the .gz copy, and any other request gets the plain file; the answer keeps the plain file's content type. The sign-in check, the same-origin check, the editor policy, no-cache and nosniff are the same for all three (section 20). A file that is not worth compressing (under 1,024 bytes, or a kind not listed above, such as images) has no copies.

cargo xtask editors compress (give an editor's id to do just one) adds or refreshes the copies in editors that are already installed, so an editor built before this change does not have to be rebuilt. It prints, for each editor, the sizes of the compressible files plain, with gzip and with Brotli, and the time taken; Brotli is slow on large files, so it takes from about 20 seconds (GridCraft) to nearly 2 minutes (SolidCraft). An editor that is not installed is reported as such. The copies are made from the plain files and replace any copies already there.

Never edit a copy by hand, and compress after any change made outside the build tool. The server serves a copy without comparing it to its file, so a copy that is out of date is what browsers get. If you change an editor's files in any way other than cargo xtask editors build, run cargo xtask editors compress <id> afterwards. A lone .gz or .br that has no partner is taken to be a file the editor itself ships and is left alone.

Measured on 11 November 2026, the Brotli copies of an editor's compressible files are about 22 to 27 per cent of their plain size. The figures for each editor, and what was and was not checked in the browser, are in editors.html, section 02.

Restart the server after cargo xtask editors build. The server reads the installed editors once, when it starts, so until it is restarted it keeps serving the build it found then; the build tool's last line says so. A folder whose manifest is missing or wrong is skipped with one warning line, and the server still starts.

Known problem: restarting after a killed build

If a build is killed (for example by a reboot), the temporary copy it made can be left behind. The next build may then refuse to start, with the "Cargo config above" message, when the leftover copy holds the fork's own Cargo settings file (WordCraft commits one; the check trips before the leftover is cleared). Clear it by hand with git worktree remove (give it the leftover folder, with --force if Git asks), run from the fork's folder, then build again.

Built editors contain the builder's local folder paths, and must be rebuilt with path remapping before they are published; see editors.html.

15 / The file session, the editing seat and saving

A file session is the server's record of who has a file document open. It uses the same WebSocket address (/ws/docs/<id>), the same sign-in and role checks and the same removal as a text document (section 08). Unlike a text document's session it holds no content: only who is there, the current revision, and who holds the editing seat. The file's bytes travel over HTTP (section 16).

Joining, in two steps

When a page asks to join, the server accepts the request but does not yet let the page in. It checks the person's access once more, and only then admits the page: it is sent the list of people, the current revision and the seat, and may take the seat. Someone whose access ended between the two steps is sent the removal message instead, and nobody else ever sees them come and go.

The editing seat

  • At most one page holds the seat. A page whose person may edit (editor or owner) takes it when it joins while the seat is free. Viewers never take it.
  • The holder's page is given a seat token: 32 random bytes, sent only to that page, new each time the seat is given. A save must carry it.
  • The seat is freed when its holder leaves, is removed, or loses the right to edit. It is not handed on: the others are told it is free, and a page takes it only by joining again, because its copy of the file may be old.
  • One exception, chosen on purpose: a page whose connection dropped and that joins again while the seat is free takes it without reloading. If its copy is older than the stored file, its first save is refused as a conflict, and the page stops saving (below).

The save path

  1. The editor hands the page the whole file. The page uploads it with PUT /api/docs/<id>/content?base=<revision>, carrying the seat token and the revision its copy was made from.
  2. The server checks the person's role before it reads the upload (no role is 404; a viewer is 403), then hands the bytes to the file session. Nothing else can write a file document's content.
  3. The session refuses the save unless it comes from the seat holder with the current token (403), and unless it was made from the current revision (409, naming the current one).
  4. It writes the bytes as one Git commit, credited to the seat holder alone, and tells everyone in the session it is saving and then that it is saved. A write that has started finishes even if the person goes away or is removed meanwhile.
  5. One save is written at a time, and one more may wait behind it. A further save arriving then is answered 503 with {"error":"busy"} and nothing is done. The page itself never sends more than one save plus one waiting.

Saving the same bytes again answers the current revision with "changed": false and writes nothing.

After a 409 the page stops saving for that page load. With one seat, a conflict means the stored file moved past the page's copy, so trying again could never succeed, and guessing a newer base would overwrite someone's save. The banner reads This file was changed somewhere else, so your last save was not stored. Download your copy, then reload. with Download my copy and Reload. Later saves from the editor are kept in the page for Download my copy but not uploaded.

If the Git repository was changed by something other than the server, the next save finds a revision it did not expect. The session then refuses every later save and ends once everyone has left, as a text document does (section 12).

A file session stays open for the grace period (60 seconds) after the last person leaves. There is nothing to save when it ends: every save was already written.

17 / The content tree and its routes

Content is kept as a tree: a site holds libraries, a library holds folders and files, and a folder holds more folders and files. Every item has an identifier that does not change when it is renamed or moved; a file's identifier is its document identifier. Only an administrator can create a site, and every new site gets a library named Documents. A site cannot be moved or deleted, and a library cannot be moved or deleted either.

The pages are / (the sites a person can see), /site.html?id=<id>, /library.html?id=<id> (a library or a folder) and /access.html?id=<id> (who has access to an item, and where that access comes from).

Known and intended. These answers can tell a person a little about items they cannot see; they are kept because hiding it would cost more than it protects:

  • Creating, renaming or moving an item to a name that a hidden item in the same place already has answers name_taken, so they learn that an item with that name is there.
  • Moving a file from a restricted folder to a widely shared one needs only editor at both ends, so an editor can widen who sees it (as in SharePoint). A file that inherits takes its new place's permissions when moved; a file with its own permissions keeps them.

Inherited access

Access is given on a site, library, folder or file, to a person or a group, as a role (the built-in roles are in section 07; roles and groups are in section 23). An item inherits its access from the nearest item above it that has access of its own; that item is its scope. A site is always a scope. Giving someone access on an item that inherits, or removing someone from it, first breaks inheritance: the item becomes a scope of its own, starting with a copy of the assignments it inherited, and then the change is made. Inherit again deletes the item's own assignments, so it follows the scope above once more. Nothing below the item is read or written when either happens, so the cost does not grow with the number of files.

A person who has a role only somewhere below an item sees that item on the way down, with limited access (no role of their own on it), and sees only the path to what they were given. Administrators are owners of everything, as in section 07. When a change alters who may open a file that is open, the server works out each connected person's role again straight away: connections that lost access are removed (Your access to this document was removed.), and the others get their new rights. A file that is deleted removes everyone connected to it. Section 08 describes what the person sees.

18 / The content tree in Git and in PostgreSQL

The tree is recorded in the same repository as the documents (section 09), one JSON file per item, beside docs/ on the main branch:

  • docs/<doc_id>/content and docs/<doc_id>/meta.json: as before.
  • tree/<xx>/<node_id>.json: one item of the tree (a site, library, folder or file). The file is named after the item's identifier, which for a file is its document identifier, and kept in the sub-folder named by the identifier's first two hexadecimal digits (tree/3f/3f2a…json), so tree/ holds at most 256 sub-folders. A change to one item then rewrites only its own sub-folder of a few hundred entries, not a folder of every item: in a library of 100,000 files that is the difference between a rename taking well under a second and taking many. Servers before 12 November 2026 kept every record directly in tree/; the first start of a newer server moves them (section 19).
  • refs/sharecraft/docs/<doc_id>: the last commit that changed that document, as before.
  • refs/sharecraft/tree: the last commit that changed tree/.

A record looks like this (two-space indent, one line per field):

{
  "schema": 1,
  "id": "<node id>",
  "kind": "document",
  "parent": "<id of the library or folder it is in; null for a site>",
  "site": "<id of its site; a site's own id for the site>",
  "name": "Budget 2028.xlsx",
  "created": { "at": "<RFC 3339 time>", "by": { "id": "<account id>", "name": "<name>" } },
  "deleted": null
}

kind is site, library, folder or document. A deleted item is not removed from Git: its record stays with deleted set to the time and person, so its history is kept and its name is free again.

One change, one commit. Each create, rename, move or delete is one Git commit on main, credited to the person who made it. A change that touches several items writes them in the same commit: moving a folder to another site rewrites the site of everything below it. A tree commit does not move any document's ref, so a checkpoint of a file open at that moment is never refused because of it. To look at the tree with plain git, from the repository root (read only, as in section 09):

git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git ls-tree main tree/
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:tree/<xx>/<node_id>.json
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git log refs/sharecraft/tree

PostgreSQL mirrors it. After the commit, the server writes the same facts to PostgreSQL in one transaction with the event, and the pages read the tree from there. Git is the authority for the tree, as it is for documents. If the database refuses the change after the commit (the person's role changed meanwhile, or the name was taken), or fails before the change could be judged allowed, a second commit takes the change back in Git. If the database write fails after the change was judged allowed, the server tries to repair that item from Git, and if it cannot, it refuses further tree changes with 503 unavailable until a repair of the whole tree succeeds. A take-back that cannot be written to Git also stops tree changes; it is written again before that repair, so a refused change never reaches PostgreSQL. A take-back still unwritten when the server stops is lost, and the next start copies the refused change from Git (see section 21). At every start the server compares every record in Git with its row and rewrites the rows that differ (section 19).

Permissions are not in Git. Who has access to what, and which items take it from above, is kept only in PostgreSQL, and every change of it is written to the event log: access.granted, access.changed and access.revoked (section 11), now for any item, not only documents. Roles, groups and memberships are in PostgreSQL only too, with their own events (section 11). Tree changes are events too: node.created, node.renamed, node.moved and node.deleted, with document.created as before for a file, and tree.adopted once for an upgrade (section 19). Git alone can therefore give back the tree and the content, but not who may open them. This is why PostgreSQL needs its own backup (section 09). If PostgreSQL is lost and the database is empty, the next start rebuilds the tree from Git and gives each site its three groups, with no members (section 23); an administrator, who holds every permission, puts people back into them and shares the items again.

19 / Upgrading an installation that already has documents

Before the content tree, every document stood alone, with its own list of people. On the first start after upgrading, the server puts each existing document into the tree and moves its list of people onto it. Back up both stores first (section 09): the data folder and the PostgreSQL database.

Run cargo xtask web after every upgrade, before starting the server. The text editor's WebAssembly client in web/pkg is built from the source but not kept in Git, and cargo xtask check does not look at it, so an upgrade leaves the old one in place without any warning. An old client can misread what a newer server sends: one built before deleting files existed showed This document does not exist, or you do not have access to it. instead of This document was deleted. to people who had the file open.

Upgrading to a server from 12 November 2026 or later moves the tree records, one way. On its first start the server moves every record from tree/<node_id>.json into its sub-folder tree/<xx>/<node_id>.json (section 18), in one Git commit by ShareCraft with the message tree: move records into sub-folders. Only refs/sharecraft/tree moves with main; no document's ref does, and no document's content changes. An older server started on the repository afterwards would find no tree at all. Back up the data folder before upgrading (section 09), so that you can go back.

Upgrading to a server with groups and roles (12 November 2026) changes the database as well, one way. Four migrations run on the first start. A server from before groups and roles, started on the upgraded database, refuses to start: it finds migrations it does not know. Started with the old database but the upgraded repository, it would find no tree, because the records have moved into sub-folders. Back up the PostgreSQL database as well as the data folder before upgrading (section 09): the backup is the only way back. What they do is in section 23: every grant becomes an assignment; every grant on a site becomes a membership of the site's Owners, Members or Visitors group; nobody gains or loses access.

What the start does, in order

  1. Moves tree records into sub-folders. Only records still at their old place move; a later start finds none and writes nothing. A record found at both places, which should not happen, is kept from whichever place has the later record (its time of creation or, if it was deleted, of deletion; the sub-folder's on equal times), and the start-up line says how many there were.
  2. Reconciles the tree. Every tree/ record in Git is compared with its row in PostgreSQL, and the rows that differ are written. On a first upgrade there are no records yet.
  3. Adopts existing documents. This runs only if some document has no place in the tree, some grant is still recorded the old way (per document), or some site, deleted or not, lacks its three groups. Otherwise nothing is done.
  4. Reconciles the revision index (section 10), as before.

What adoption does

  • Home > Documents. A site named Home with a library named Documents is made, by the account name ShareCraft, in the same Git commit that records the documents. Every document without a place goes into that library. Each keeps its creation time, and is credited to its creator where there is one. Home gets its three groups (Home Owners, Home Members and Home Visitors) with no members, as does any other site that lacks them; administrators hold every permission without being members, and add people to the groups.
  • Renames. Names now follow the rules in section 17, so a name can change. Each refused character (control characters and " * : < > ? / \ |) becomes _, as does a trailing dot; a name that ends up empty becomes Untitled; a name over 120 characters is shortened, keeping its extension. A name already used in the library, ignoring case, gets (2), (3) and so on before the extension: two documents called Notes.txt become Notes.txt and Notes (2).txt. The new name is stored on the document as well as in the tree. The number renamed is on the start-up line.
  • Grants move to per-document permissions. Each document that had people granted keeps exactly those people and roles, as assignments of its own: it becomes a scope that does not inherit from Home. A document shared with only some people therefore stays visible to only them (and to administrators). The number of grants moved is on the start-up line.
  • One event. tree.adopted records the counts (documents, renamed, grants moved). Nothing is lost if the start is interrupted: if the Git commit was written and the database change was not, the next start's reconcile writes the items and adoption moves the grants.

An enabled administrator is needed

Someone has to be able to fill the new site's groups and own its documents, so adoption needs at least one enabled administrator. If there is none, nothing is written, the server still starts, and it prints this on the console, naming the command to run:

sharecraft-server: existing documents not adopted: existing documents need an administrator to own them, and there is no enabled administrator; add one with `sharecraft-server add-user --admin --email <email> --name <name>` and start the server again

Until the server is started again with an administrator, the existing documents have no place in the tree and nobody can open them.

The start-up line

The server prints one line for the tree before the line for the revision index (section 10), and before it prints its address. After an upgrade it reads like this (the numbers are examples):

Reconciled the tree with Git: no records to move into sub-folders; 0 nodes in Git, 0 updated, 0 failed; 12 documents adopted into Home, 3 renamed, 11 grants moved

The first clause says what the move did: no records to move into sub-folders, or for example 1250 records moved into sub-folders, followed, if any record was at both places, by , 2 found at both places, the later of each kept. If the move cannot be written the server prints why and exits. On later starts the line ends ; nothing to adopt. When there is no enabled administrator it ends ; nothing adopted, followed by the message above on standard error. Each node that could not be reconciled is listed on standard error with the reason, and the server still starts. If the tree cannot be read from Git at all, or the adoption fails for another reason, the server prints why and exits without printing its address.

Anything that used GET /api/docs to list documents must change: it now answers 405 (section 17).

20 / The editor pages' security policy, and why it is built from hashes

A Content Security Policy is a header that tells the browser what a page may load and run. The site's own pages allow only scripts from this site and WebAssembly, may hold a frame from this site (frame-src 'self', for the frame page), and may not be put inside anyone's frame (frame-ancestors 'none').

The editors' files, under /editors/<id>/, get their own policy instead:

default-src 'self'; script-src 'self' 'wasm-unsafe-eval' <script hashes>; style-src 'self' <style hashes>;
img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self';
worker-src 'self' blob:; frame-src 'self' blob:; frame-ancestors 'self';
base-uri 'none'; form-action 'none'
  • frame-ancestors 'self' lets the editor be shown inside ShareCraft's frame page, and nowhere else.
  • base-uri 'none' (a page cannot change the address its links are read against) and form-action 'none' (no form can be sent anywhere) take away two things the editors, which draw everything themselves, never use.
  • There is no object-src 'none', which would forbid browser plug-ins: WordCraft and PdfCraft print through a PDF shown in a hidden frame under this same policy, and the browser's PDF viewer may count as a plug-in. Plug-ins stay limited to this site by default-src 'self', as before. Printing has not been checked in any browser.
  • 'wasm-unsafe-eval' lets the browser compile the editor's WebAssembly. Despite the name, it does not allow scripts to run text as code.
  • The hashes. Each editor's index.html, as its build tool writes it, has a few small scripts and styles written inside the page. A policy that blocks scripts written into a page is what stops an injected script from running, and allowing all of them ('unsafe-inline') would undo that. Instead the policy names each allowed piece by its fingerprint, a SHA-256 hash of its exact text. The browser runs a piece only if its text has exactly that hash. The hashes are computed when the editor is built and kept in its manifest; the server checks each is a well-formed hash before using it, and drops a manifest that has a bad one.
  • Line endings. Browsers turn Windows line endings (CR LF) into plain LF before they compute a hash. A Windows checkout of a fork has CR LF in its files, so the build tool does the same before hashing. Without this, GridCraft's first build had a hash the browser did not accept; the tool was fixed, and that editor rebuilt.

The editors' files are served only to signed-in people, from a page of this site, with Cache-Control: no-cache (the browser asks whether a file changed before using its copy) and X-Content-Type-Options: nosniff. Where a compressed copy exists and the browser accepts it, the answer also carries Content-Encoding: br (or gzip) and Vary: Accept-Encoding, and keeps the plain file's Content-Type (application/wasm for a WebAssembly file). Anything else, including a path that tries to leave the editor's folder in any spelling, is 404. Every file in an installed editor's folder is served this way, including editor.json. The build tool no longer installs dot files; an editor installed before 10 November 2026 may still hold an empty .trunk-lock file, which is harmless and goes with the next build.

Because the editors come from ShareCraft's own address, they run with the rights of the person using them; that is why they are built only from ThineCraft's own forks (decision D20 in scope.html).

21 / Known limits of this build

  • HTTPS comes from a proxy. In development mode the server answers on this computer only (section 04). Production mode (section 29) serves people on other computers, but only behind a reverse proxy or tunnel that provides HTTPS; ShareCraft does no TLS itself. Production mode has been checked on the build computer through a local HTTPS proxy, not yet on a real public address.
  • Accounts are made by an administrator. There is no sign-up, and nobody can change their own password yet, nor reset a forgotten one.
  • No single sign-on, multi-factor sign-in or guests. Access is a password account, given to a person or to a group on a site, library, folder or file. Groups cannot contain groups.
  • Only the first part of sites and libraries. The tree and inherited access are built (sections 17 to 19). Groups, roles and the inheritance explorer are built (section 23). Sharing links, anyone links and access requests are built (section 24). Uploads, the recycle bin, copy and quotas are built (section 25). Not built yet: guests, domain allow and block lists, notifications, service identities, audience targeting, branding, and metadata edited after creation. A library of 100,000 files is measured (section 22).
  • Links reach other computers only in production mode. In development mode a link's address is built from the address the person making it is using, on this computer (section 04); in production mode it names the public address (section 29). Anyone links do not yet count how often they are used.
  • No page for events (section 11), and no way to see the document's saved revisions from the site: use Git (section 09).
  • One server process. The locks of the content store and upload sessions are inside the process too (section 25). Removal from live sessions is sent inside the process; running several server processes would need a different mechanism.
  • Large pastes go in pieces. One change can be at most 512 KiB as sent (section 05); a larger paste is refused with a message asking for smaller parts.
  • One person edits a file at a time. GridCraft, WordCraft, PdfCraft and SolidCraft files open from ShareCraft and save back as Git revisions, but only the holder of the editing seat can save; others read under a banner. Editing a file together is Stage 2 work. Saving is on demand, never automatic.
  • The editors save only while their tab is shown. A Save sent while the browser tab is hidden waits until the tab is shown again. While hosted, the editors refuse New, Open and Close and keep the document they were given; PdfCraft may still open some views as extra tabs. See editors.html.
  • Editors are built on this machine (section 13), take tens of minutes each, and are not published. A build to be published must first be rebuilt with path remapping.
  • The first open of an editor is still a large download. The editors are sent compressed (section 13), but SolidCraft's WebAssembly file still arrives as about 34.5 MB the first time it opens, and the others as 7 MB to 13 MB. A browser keeps them afterwards. Sizes are in editors.html. Opening and editing in each editor after compression was added has not been checked.
  • Replacing a file by uploading has no page yet. The upload routes can add a new version to a file (sections 16 and 25), but no page offers it.
  • PostgreSQL needs its own backup (section 09), taken together with the data folder (section 25), and the event log is never trimmed.
  • A take-back is kept only in memory. If a refused tree change could not be taken back in Git (section 18) and the server stops before it is written, the next start's reconcile puts the refused change into PostgreSQL. Both need Git to fail first; check the console for could not take back a tree change.

23 / Groups, roles and the inheritance explorer

Added on 12 November 2026 (plan 2A, on the branch platform-groups-roles). Access is given to a person or to a group. What it allows is a role, and a role is a set of permissions. All of it, like every permission, is kept in PostgreSQL only, and every change is an event (sections 11 and 18).

Permissions

There are six, a fixed list. Every permission except view includes view.

The three built-in roles have fixed ids. They cannot be changed or deleted.

Custom roles. An administrator can define more on the Roles page (/roles.html). A custom role has a generated id, a name of 1 to 60 characters that no other role has (ignoring case), and at least view: view is added to any set that lacks it. Changing a custom role's permissions changes the access of everyone who holds it, everywhere, and reaches open sessions before the request answers: an editor whose role loses edit becomes read-only at once. A role that is assigned anywhere cannot be deleted (role_in_use).

Groups and site groups

A group is a set of people that can be given a role like one person. There are two kinds.

  • Site groups. Every site, deleted or not, has three: Owners, Members and Visitors, given the Owner, Editor and Viewer roles on the site. A site group stores its site, not a name. Its name is the site's current name followed by Owners, Members or Visitors (for example Projects Owners). It is built when it is read, so it follows a rename, and it is shown with its site. It can have the same display name as an organisation group, so the pages and answers always name the site beside it. The groups are made with the site, in the same transaction, and the person who creates the site becomes a member of its Owners. A site group cannot be deleted (site_group).
  • Organisation groups. These belong to no site. They have a stored name of 1 to 60 characters, unique ignoring case. Only administrators create them. One that is assigned anywhere cannot be deleted (group_in_use).

Groups cannot contain groups. Who may change a group's members: an administrator (every group), and anyone with manage_site on a site (that site's groups).

What a person sees of groups. Administrators, and people who manage access somewhere, see the organisation groups and the groups of the sites they can reach, never a site name they could not otherwise see. Whoever manages a site's groups also sees them and their members, and the site's list of groups, even without manage_access. Everyone else sees no groups. A group's members are shown only to those who manage the group and to administrators. Where an access page lists a group the person may not see, it shows no name (hidden).

No more than you hold

Nobody can give anyone more than they hold. A person may give a role on an item, or add someone to a group, only if every permission of that role (for a group, of every role it is given, wherever it is given) is one they hold there themselves. Otherwise the request is refused with beyond_your_access. Administrators are exempt. This is stricter than SharePoint, where anyone who can manage permissions can give Full Control.

Every place keeps a manager

Every scope keeps at least one assignment whose role includes manage_access. A change that would leave one without is refused with last_manager. This covers removing an assignment, giving a manager a lesser role, and changing a custom role: a role change that would leave any place without a manager is refused, so an administrator grants another manager first. An empty Owners group still counts as a manager. If the group that managed a place has been emptied, an administrator can always repair it.

24 / Sharing links and access requests

Added on 13 November 2026 (plan 2B, on the branch platform-links-requests). Two things are new. A person who manages access can share a file or folder by link. And a person who reaches something they cannot open can ask for access. Like all permissions, both are kept in PostgreSQL only, and every change is an event (sections 11 and 18).

In development mode, links only work on this computer. The address of a link is built from the address the person making it is using, and the server listens on this computer only (section 04). In production mode a link names the public address, for example https://share.example.com/l/…, whatever address its maker used (section 29).

Who can share by link

Only a person with manage_access on the item can make, list or revoke its links. SharePoint lets ordinary members share; ShareCraft does not. The link's role must be one the person holds there themselves (beyond_your_access; administrators are exempt, section 23). It may never include manage_access or manage_site (link_role_too_high), so a link never makes anyone a manager and never counts towards the last-manager rule (section 23). The access page has a Share by link panel, and the item's live links are listed there with their kind, role, expiry and how many people used them.

Signed-in links

A signed-in link is for anyone with an account. It is a hidden link group with the link's role assigned on the item. If the item inherits its access, making the link breaks inheritance first and gives the item its own permissions, as in SharePoint. Everything in section 23 then applies unchanged: the one access decision, locking, and live sessions.

  • An expiry is optional for a signed-in link.
  • Opening the link while signed in shows Open with Editor access (or the link's role). Pressing it sends a POST from the page, and that adds the person to the group. A person who already holds that much is not added. A plain visit never joins anyone.
  • A link group is never listed among groups and never offered in a group list or filter. The access, membership and group routes refuse it with link_group. In the explorer it shows as "Signed-in link (Editor, expires 1 December)", never as a group with a name. Filtering the explorer by a person also finds the breaks where a signed-in link they joined is assigned, shown as the link. On a break below a link's item that holds a copy of its assignment, the access page points to the link's own item, where it is listed and revoked; it names that item only to someone who may see it (a break moved out from under the item keeps its copy, and its new managers are told only "the item it was made on"). A break with anyone links shows "Anyone links: 2 live".
  • Restoring inheritance on an item that removes a link group's last assignment revokes that link, with the reason "inheritance restored".

Anyone links

An anyone link lets a person without an account view and download. It is not a group, because such a person has no session. The link's token is checked on every request.

  • Off by default. An administrator switches them on in Sharing settings (/sharing.html, linked from People), with a plain warning. Switching them off stops every anyone link at once, on the next request. They are not revoked, and they work again if the setting is switched back on before they expire.
  • View and download only. The role is always Viewer. An anyone link never opens an editor, a session, the access page, the explorer or any other route.
  • Always expiring. An expiry is required, and it may be at most anyone_link_max_days away (30 unless an administrator changes it). The request itself checks the time, so it stops at the expiry instant. The limit is checked when a link is made: lowering it later does not shorten links that already exist, which last until their own expiry unless revoked (the settings page says so next to the field).
  • What it reaches. The landing page; the listing of a shared folder and what is below it; downloads of files at or below the item; and the text of a plain-text document as last saved (unsaved live edits are not shown). A file never saved has nothing to download: the page shows "Not saved yet" in place of Download.
  • It stops at breaks. A folder or file below the item that has its own permissions is not reached, and neither is anything once it is moved out of the item or deleted, itself or through a folder above it. This is exactly what a signed-in Viewer link would reach.
  • No anonymous answer sets a cookie.

Tokens and addresses

  • A token is 32 random bytes from the operating system, written as 64 lowercase hex characters in the address /l/<token>. Only that spelling works: the same token in capitals is not found.
  • Only a SHA-256 hash is stored. The address is shown once, when the link is made, in a read-only box with a Copy button: "This address is shown only now. If you lose it, make a new link." A manager who needs it again makes a new link. The list of links never carries an address.
  • Every /l/ page and /api/l/ answer carries Cache-Control: no-store and Referrer-Policy: no-referrer. The sign-in page also sends no referrer.
  • If the visitor is not signed in, the landing page keeps the token in the tab's session storage, sends them to sign in, and returns them to /link.html. The token is in no address except the link's own.
  • An address that does not work shows one page, "This link does not work. It may have expired or been turned off.", whatever the reason. The server answers 404 link_not_found.

Expiry, revoking and the sweeper

Revoking is immediate (S5). For a signed-in link, the group's assignments (including copies below an item that broke inheritance later) and all its members are removed in one transaction, and open documents below the item are rechecked before the answer, so a person who came in only through the link is removed or limited at once. A person who also has access another way keeps it. A revoked anyone link fails on its next request.

The sweeper runs every minute inside the server and revokes each expired link as a manager would: one transaction per link, an event, and a recheck of open documents. An expired signed-in link stops within a minute. An anyone link stops at the expiry instant, because the request checks the time itself. The sweeper writes one line to the log when it revokes something, and also deletes request attempts older than a day. A database error does not stop the server: the sweeper tries again the next minute. Deleting an item revokes its links with the reason "item deleted".

Access requests

Wherever the page says "This document does not exist, or you do not have access to it", it also offers a short Request access form (a message of up to 500 characters).

  • The answer is identical for an item that exists, one that does not, and one the person can already open: "If this item exists, the people who manage it will see your request." Nothing is recorded for the last two.
  • The limit is 20 a day per person and counts every submission, recorded or not. It is checked before anything else (too_many_requests), so it says nothing about the item.
  • One open request per person per item. A second one updates the message.
  • The request goes to everyone with manage_access on the item. They see it on the Requests page (/requests.html), with a badge on the home page. Each shows the item's path, the person, their message and its age.
  • Approve chooses a role within the approver's own access and gives it to the requester directly on the item. It never downgrades: if the requester already holds that much, the answer is already_has and the request stays open. Decline may carry a reply the requester sees.
  • The requester sees their own requests only once decided, under My requests on the home page, with the decision and reply. The item is named only if they can now see it. Open requests are never listed, so the list cannot show which items exist.

Events

25 / Files: the content store, uploads, the recycle bin, copy and quotas

Added on 14 November 2026 (plan 3A, on the branch platform-files, not yet merged). File bytes no longer live in Git. They live in a content store on disk, and Git holds a short pointer. On top of that sit resumable uploads, a two-stage recycle bin, copy and bulk operations, and storage quotas for sites. Plan 3A took no decisions of its own about who may see or do what: the permission rules of sections 17 and 23 apply unchanged, with the exceptions named below.

The content store

Every file's bytes are kept once, under the name of their SHA-256 hash. Two files with the same bytes share one stored copy.

<data folder>/blobs/<first two hex digits>/<64 hex digits of the SHA-256>
<data folder>/blobs/tmp/<id>.tmp          bytes still arriving
<data folder>/uploads/<id>.part           a resumable upload in progress (section 16)

New content is written into tmp, hashed on the way in, flushed to disk, and then renamed into its place. A file that is already stored is not written again. A byte is never read into memory all at once: saves, uploads and downloads stream in pieces of 64 KiB.

The pointer in Git

In the Git repository, docs/<doc_id>/content for a file now holds this, exactly, and nothing else:

sharecraft-blob 1
sha256 <64 lowercase hex digits>
size <the size in bytes, written without leading zeros>

A file whose content is exactly that form is a pointer. Anything else is read as the file's own bytes. That second case is how every version saved before this plan still reads (see "Upgrading from inline content"). Text documents work the same way: each checkpoint writes its text to the store and commits a pointer. Git history therefore stays small, and each revision still names its bytes exactly.

Blob safety: claims, holds and erasure

The danger is a stored file being erased while a version in Git still names it, or while a save is just about to name it. Four things prevent that.

  • Claims. Before a version is committed to Git, the server claims its content in PostgreSQL (a pending row in blob_refs). When the commit is in, the claim is settled: the pending row becomes a completed row naming the document and revision. If the commit fails or finds nothing to change, the claim is withdrawn. A claim also checks that the file is still on disk; if it is not, the save fails with 503 and nothing names missing bytes.
  • Holds. From the moment content is stored until its claim is settled, the server holds it in memory, so no erasure can take it. A request that hangs keeps its hold for as long as it hangs. Holds are not kept in PostgreSQL.
  • Erasure only when nothing names the content. The server counts every row, pending ones included, under a lock, and erases only at zero and with no hold. Bytes shared by several files or versions stay until the last one goes.
  • No erasure while the rows may be incomplete. Two flags in the maintenance_flags table say so: blob_refs_upgrade (set by migration 0009) and blob_refs_dirty (set whenever a row could not be written). While either is set, nothing is erased and the files simply stay.

One server per data folder

Run only one server process on a data folder. The locks that keep claims, holds, erasures and upload sessions in order are inside the process, as the removal of live sessions already is (section 21). Two servers on one folder could erase a file the other is about to name.

Upgrading from inline content

Migrations 0009 to 0012 run on the first start of the new server, and the blob rows and site usage are rebuilt then (two more lines on the console: Reconciled stored content with Git and Reconciled the sites' usage). Like the earlier migrations they are one way: a server from before this plan refuses to start on the upgraded database.

  • Old versions are not rewritten. Versions saved before this plan keep their bytes inline in Git and read exactly as before. Only new saves write pointers. Nothing in Git history is changed.
  • Saving the same bytes as an old inline version still counts as "unchanged" and writes nothing, because the old content is hashed to compare. Copying a file whose latest version is inline writes that content into the store first.
  • Sizes of old versions are read from Git when usage is rebuilt, so they count toward quotas.
  • An item deleted before the upgrade becomes a first-stage bin entry with its original deletion time (migration 0011). If that was more than 93 days ago, the first sweep purges it.

Backups

Back up the data folder and the PostgreSQL database together, taken at about the same time, and restore them as a pair. The data folder now holds the content store as well as the Git repository (a file's pointer without its stored bytes cannot be downloaded; the answer is 503). The database holds the claims and rows that the sweeps trust when they decide that content is unused, so do not restore one without the other. Take the backup before this upgrade as well (section 19). Backing up while the server is stopped is the safe way; a copy taken while it runs can miss a file saved during the copy. On start, the content rows are recorded again from Git for every document whose recorded head differs, and a failure there sets the flag that stops all erasure until a rebuild from Git succeeds.

  • Restoring brings back the entry and everything deleted with it, with their own permissions. This stops someone from removing items that others made stricter on purpose. It does tell the person that such a place exists.

Copy and bulk operations

Copy. POST /api/nodes/<id>/copy {parent, name?} needs view on the source and add on the destination, and a folder cannot be copied into itself. The copy has new ids, is made by the person copying, inherits its access from the new place (no permissions or links are copied) and has only the latest version of each file; history is not copied. A folder copy leaves out anything the person cannot view. Copied files share the stored bytes of the originals, so no space is used on disk, but the copies count against the destination site's quota. Name clashes are settled by adding (2) and so on, and the answer reports it.

A copy is one tree commit plus one checkpoint commit for all the copied files' first versions. If the second commit fails, the copy is taken back: the new items are removed, claims are withdrawn, and the answer is 503. No empty copies are left and no node.copied event is written for it. If view is lost on an item part-way through, the whole copy is refused.

Bulk. POST /api/bulk {op, items, parent?} takes move, copy, delete or restore for up to 500 items (422 invalid_request above that, or for a move or copy with no parent). The request body may be up to 64 KiB. Each item goes through the same code as the single-item route and gets its own result, in order: {id, ok, error?, new_id?, renamed?}, where error is the code the single route would have answered. One item failing does not stop the others. The pages use it for selecting several files.

Quotas

Each site has a quota in bytes, or none. A site's usage counts every stored version of every item in it, in both stages of its recycle bin; a purge gives the space back. A version stored in Git before this plan counts by its size in Git.

  • Reservations. Before it is committed, a save, a one-request upload, a copy and a resumable upload session set aside the bytes they will add (an upload session sets aside its declared size when it starts, and holds it until it finishes, is abandoned or is swept). The check used + reserved + new bytes ≤ quota and the reservation are made together under a lock, so two uploads cannot both take the last space. A reservation not turned into usage is given back, and a stop of the server drops any that were interrupted.
  • The refusal is 507 quota_exceeded. Saves and one-request uploads are refused before the body is read when Content-Length already shows it does not fit. An upload that went over only when it finished leaves its session open and reserved.
  • Moves between sites. Moving an item to another site takes its bytes with it. A move is refused with 507 quota_exceeded if they do not fit in the destination. A save or upload finish whose file has meanwhile moved to another site checks for room there.
  • Never refused. Deleting, restoring, moving to the second stage and purging never need room. Live text-document checkpoints are counted but never refused, since refusing one would lose a person's typing.
  • The second stage still counts. Only a purge frees space.
  • Only administrators set quotas. PUT /api/sites/<id>/quota {bytes}, with null for none (403 for anyone else, 404 for something that is not a site). A quota below current usage is allowed: the site then takes nothing more until space is freed. It records quota.changed. People with manage_site see the site's usage, its quota and a warning from 90% on its page; administrators without manage_site see the quota field only.
  • Usage is a counter kept at each commit. It is rebuilt from the recorded version sizes at a start when a flag in the usage_flags table asks for it (migration 0012 sets one), and a purge of a version whose size was not recorded asks for a rebuild.

Name cleaning

A name given to an upload or a copy is cleaned instead of refused, and the answer reports it in renamed {from, to}; the page shows the new name.

  • Spaces at the ends are trimmed. Control characters and each of " * : < > ? / \ | become _. A trailing dot becomes _.
  • Windows reserved names. If the first part of the name (up to the first dot, ignoring trailing spaces) is CON, PRN, AUX, NUL, COM1 to COM9 or LPT1 to LPT9, in any case, an _ is added after it: con.pdf becomes con_.pdf, and LPT1.backup.pdf becomes LPT1_.backup.pdf. This applies to folders too.
  • A name that ends up empty becomes Untitled. A name longer than 120 characters is shortened and keeps its extension. A name that is only an extension (.xlsx) is refused with 400.
  • A name that is already used in the place is settled by on_conflict for uploads, or gets (2), (3) for a copy or a restore.

26 / Sites: templates, lifecycle, hubs and navigation

Added on 14 November 2026 (plan 3B, built on the branch platform-sites and merged into main on 14 November 2026 as 40a1dbc). A site now has a kind, a description, a language and a time zone. It can be made from a template, archived, deleted and restored, made a hub or joined to one, and given a navigation bar. The permission rules of sections 17 and 23 apply unchanged, with the exceptions named below. The owner's decisions behind this are D32 to D36 in scope.html.

Who does what. Only administrators create, archive, reactivate, delete, restore and permanently delete sites, make a hub, unregister a hub, edit the global navigation and manage templates. A person with manage_site (a site's Owners) changes the site's settings and its own navigation, joins it to a hub or leaves, and deletes a library to the bin.

The Git layout

Site settings are kept in Git beside the content tree, one JSON file each, in the library repository (section 18). A change that also changes the tree (creating or renaming a site) writes both in one commit.

sites/<first two hex digits of the id>/<site id>.json    one site's settings
templates/<xx>/<template id>.json                      one saved template
org/navigation.json                                  the global navigation
refs/sharecraft/sites                                the last commit that changed any of them

A site file holds these fields, in this order, written with two-space indents and a final newline: schema (1), id, kind (team or communication), description, language, time_zone, template (a saved template's id, a built-in name, or null), archived (when and by whom, or null), hub (the hub's navigation, or null), joined_hub (a hub's site id, or null) and navigation (the site's own list, or null for automatic). A site made before this plan has no file. It reads as the organisation's defaults (kind team, no description), and the first start of the new server gives its database row those values. When an administrator changes the defaults, the rows of the sites with no file follow at once, under the tree lock, with no event for each (the settings change is the record), so they show the new defaults straight away, a change's from values are what the owner saw, and the next start finds nothing to repair. The file is written at the site's first change.

The database row in sites mirrors the file. At every start the server compares each site's row with its file and repairs a row that differs, recording site.changed with repaired set; the same is done for templates and the global navigation. The start-up line reads Reconciled the site records with Git: …. When a change fails after Git has it, the server repairs the database from Git, or marks the tree out of step as in section 18, and the next change that finds it back in step repairs the rows.

Templates

There are two built-in templates, Team site (team) and Communication site (communication). Each makes one library called Documents, with automatic navigation and the organisation's language and time zone. An administrator can also save a site as a template. A saved template carries the site's kind, language, time zone, live libraries and folders, and navigation. It carries no files, nothing from the recycle bin, no people, no permissions and no identifiers.

  • Navigation in a template names libraries by name. A link to a folder becomes a link to its library. A link to another site, to the site itself or to something deleted is dropped, and so is a heading's child that has nowhere to go. An audience is kept only as owners, members or visitors, meaning the new site's own groups; targeting on organisation groups is lost.
  • Names are cleaned by the rules of "Name cleaning" in section 25 when a template is saved or imported, and each change is reported in cleaned {from, to}. Links follow their library through the cleaning.
  • Creating a site: POST /api/sites {name, template?, description?, language?, time_zone?}. It writes the site, its libraries, folders and settings in one commit and one database transaction, and makes the three groups with ids chosen beforehand so the navigation can name them. The person creating becomes an Owner. Without a template the site is a Team site.

The package format

A template is carried between installations as a JSON file, from GET /api/templates/<id>/package (built-in ones too) to POST /api/templates/import. The file holds sharecraft_template (the format version, 1), name, description and body (kind, language, time_zone, libraries with their folders, and navigation). Unknown fields are refused. A package never holds an identifier: an item id, a {"node": …} target or a group id in an audience is refused with the reason identifiers. Import sends the raw file as the request body.

Organisation defaults, language and time zone

GET /api/settings/regional (anyone signed in) and PUT /api/settings/regional {default_language?, default_time_zone?} (administrators) hold the organisation's defaults, en and UTC at first. They are given to sites made afterwards, and at once to the sites made before this plan that have no file yet (see the Git layout above); a site with a file keeps its own values. A site's own language (a BCP 47 tag, at most 35 characters) and time_zone (an IANA name such as Europe/London, at most 100) are changed with PATCH /api/sites/<id> and decide how its pages show dates, times and numbers. Bad values answer 422 invalid_language or invalid_time_zone. Translating ShareCraft's own words comes later (D35). The time zone database comes from the jiff crate, built in.

Archiving

An administrator archives a site with POST /api/sites/<id>/archive and reactivates it with POST /api/sites/<id>/reactivate. Both are repeatable: asking for the state a site is already in changes nothing and records nothing.

  • Read-only for everyone, administrators included. Whatever a person's permissions would let them change, they hold only view while the site is archived. Every write answers 403 archived: saving, uploading, renaming, moving, deleting, restoring, sharing, links, requests, memberships, quotas, and a signed-in person redeeming a link. A request for access by someone who can see the item answers 403 archived; to anyone else the usual 202 and nothing recorded.
  • Sessions end. Open editing sessions in the site end for everyone with the reason archived, and every upload session into it is abandoned (its reservation is given back). A session that slipped through is refused at its next chunk.
  • Anyone links answer as expired (404 link_not_found). They are not revoked and work again on reactivation.
  • Hidden from discovery. The site directory and the hub lists show an archived site only to people who manage it (and administrators).
  • Managers still see. People with manage_site and administrators still read the site's bin, explorer, access page, links and group member lists. Restoring or purging from the bin is refused while archived.
  • Saving the site as a template is allowed from an archived site, since it reads and writes nothing in the site.
  • Archiving is serialised with tree changes. A change to permissions, links or memberships that was judged a moment before the archive commits can still land.

Deleting a library

A library can now be deleted (DELETE /api/nodes/<id>) by a person with manage_site on its site, who also needs delete on the library and on every place below it with its own permissions (403 forbidden_below otherwise). It goes to the first stage of the recycle bin as one entry, with everything live in it, and the bin lists it with kind library. Restoring it works like restoring a folder, and a name that is now taken gets (2). Purging a library also purges every entry below it that was deleted earlier on its own, since none could be restored into a library that is gone.

Deleting, restoring and purging a site

Only administrators, and only through these routes; anyone else gets 403 before anything is looked up. DELETE /api/nodes/<site> by an administrator deletes the site too; for anyone else it is still 400 is_site.

  • Deleting (DELETE /api/sites/<id>) keeps the site for 93 days in the deleted-sites list (GET /api/admin/sites). It is in no bin and nobody but an administrator can find it: every other route, for every person including administrators, answers 404 (a second delete, archive or reactivate answers 409 site_deleted). Open sessions end with the reason deleted and uploads are abandoned. Links, requests, permissions and memberships are left as they were, so a restore brings everything back. That includes access the site's groups were given on other sites' items: those groups vanish from lists while the site is deleted, but their assignments elsewhere keep giving access until the site is purged. The entries in the site's own bin keep their own dates.
  • Restoring (POST /api/admin/sites/<id>/restore) brings the site back as it was. If another site has taken its name, it comes back as Name (2) and the answer says so in renamed_from. 409 not_deleted for a live site.
  • Purging (DELETE /api/admin/sites/<id>) is by an administrator, or by the server at 93 days (the minute sweep). It cannot be undone. It runs in this order: (1) open sessions end and uploads are abandoned; (2) the site is marked purging; (3) one Git commit marks every tree record of the site purged, removes the site's own file (Git history keeps the old one), and clears the joined hub of every site that had joined this one if it was a hub; (4) one database transaction removes the site's links, access requests, assignments, memberships, groups, upload sessions and usage row, and clears its hub settings; (5) stored content that nothing else names is erased, and the site.purged event gets versions and bytes_freed; (6) the purging mark is cleared. Content that another site's files also name stays.
  • Resuming after a stop. The sweeper's first pass after a start finishes any site still marked purging, so a stop between the steps loses nothing. A site whose purge has begun can no longer be restored (404). A purge that is refused or fails before its Git commit is made, or whose commit is taken back (for example the administrator lost the role meanwhile), clears the purging mark again: the site stays deleted and can still be restored, and the sweeper leaves it until its 93 days are up. Once Git holds the purge, a failure leaves the mark and the sweeper finishes it. If the server stopped after the Git commit but before the database transaction, the start-up reconcile mirrors the purged records first, and the stored content that this releases is not erased at once: it falls to the sweep of unnamed content, which erases content with no row once it is a day old (section 25). The event site.purged can then be recorded twice.
  • Deleting a role or an organisation group while a site is deleted removes its assignments there for good, as for a live site; a later restore does not bring them back.

Hubs

As in SharePoint, a hub is a site that gives a navigation bar to the sites that join it. An administrator makes a site a hub (PUT /api/sites/<id>/hub {navigation}) and can unregister it (DELETE …/hub), which releases every member. A site joins at most one hub, there is one level (a hub cannot join a hub, and a site that has joined one cannot become a hub: 409 is_hub; joining something that is not a hub is 409 not_a_hub), and joining never changes who can see or do anything. Owners of a site (manage_site) join and leave it with PUT /api/sites/<id>/joined-hub {hub} (hub: null leaves); they need to be able to view the hub. Making a hub, joining and leaving all record events. Joining an archived hub is not refused; an archived hub is listed only to people who manage it.

Navigation

A site's pages show up to three bars: the organisation's global bar, the hub bar of the hub the site joined (a hub shows its own), and the site's local bar. The local bar is automatic (every library the person can see, by name) until an Owner saves a custom list. An item is a link to a library or folder (or a site, in global and hub bars), a web address, or a heading with one level of children below.

  • Audience targeting only hides. An item can be limited to up to 10 groups. A person outside them does not see it, but it never grants or refuses access to what it points at.
  • The server filters names. What a person gets is already filtered: an item whose place they cannot view, or that is deleted, is left out together with its children, as is a heading left with none. A hub whose site the person cannot see still shows its (filtered) bar, with the hub's id and name null. Nothing in an answer names a place the person cannot see.
  • Managers see what is targeted. People who manage a list see items aimed at groups they are not in, marked targeted: true. Who manages: manage_site for a local list, administrators for hub and global lists.
  • Saving needs view. A person saving a list must be able to view every place it links to, and every audience group must exist and not be a link group; otherwise 422 invalid_navigation, which does not say which, so a missing place cannot be told from one that cannot be seen.
  • Saving the value a list already has writes no commit. A refused save is taken back in Git. The editing form's pre-checks are looser than the server's (space-only labels, control characters and spaces in addresses reach the server, which refuses them).
  • Pages show an address only if it passes the same rules; anything else is drawn as plain text, never as a link. The editor has buttons, not dragging.

The navigation routes accept bodies up to 512 KiB, since 100 items with 2,000-character addresses do not fit the usual 16 KiB.

27 / Libraries: kinds, any file type, scanning, previews and policies

Added on 14 November 2026 (plan 3C, on the branch platform-libraries, not yet merged). A library now has a kind and settings, can hold a file of any type, checks each new file with a malware scanner the organisation runs, shows previews and thumbnails, and can be told which file types and sizes it takes. The permission rules of sections 17 and 23 apply unchanged. The owner's decisions behind this are D37 to D39 in scope.html.

Who does what. A person with manage_site (a site's Owners) changes a library's kind and settings and makes libraries. Only administrators make a library of the asset kind, change a library away from it, set the organisation's blocked file types, set up the scanner, release or delete quarantined files, and ask for the old files to be scanned.

Library records in Git

Each library has a second Git record beside its tree record, in the same repository (section 18). It holds the library's kind and settings.

libraries/<first two hex digits of the id>/<library id>.json    one library's kind and settings
refs/sharecraft/sites                                          the last commit that changed any site, template or library record

A library file holds these fields, in this order, written with two-space indents and a final newline: schema (1), id, kind, description (0 to 500 characters), folders (true or false), allowed_types (a list of extensions, or null for every type), blocked_types (a list) and max_file_bytes (a number, or null for no limit of the library's own). Lists are written over several lines, as in site files. An extension is lower case with its leading dot (.png, .tar.gz), 2 to 20 characters of letters, digits and dots, and a list holds at most 100.

  • Old libraries have no file. A library made before this plan is read as a document library with no description, folders on, every type allowed, nothing blocked and no limit. Its file is written the first time it is changed. Changing the defaults later does not matter for these: they are the defaults.
  • One commit. A library made through the new route writes its file in the same commit as its tree record. A change to the settings is one commit, mirrored into the libraries table in PostgreSQL after it, judged again there, and taken back by a second commit if refused. This is how site records work (section 26).
  • Compared at every start. The server compares each library's row with its file and repairs a row that differs, as for sites. The start-up line now names site, library and template records.
  • Templates carry library settings. A site saved as a template keeps each library's kind and settings in a settings object inside that library's entry, left out when they are the defaults, so templates and packages from before this plan are unchanged. A package with none is read as document libraries with the defaults. A site made from a template recreates its libraries with those settings.
  • A purged library keeps its row and file, as a purged site does.

Folders off

A library with folders set to false refuses new folders, and the copy of a folder into it, and the move of a folder into it from another library, with 409 folders_off. Folders already there stay. They can be emptied, deleted, restored, and moved around inside the same library. A site made from a template recreates the template's folders even in a folders-off library.

Any file type

A file that no editor opens is a document with the new editor value other. It has versions, a recycle bin entry, sharing and quota like any file. It opens as a preview where its type has one, and otherwise offers a download. Which name gets which editor:

  • A name ending in an editor's own extension (.txt, .xlsx, .docx, .pdf, .solidcraft.json) opens in that editor, as before. Every other name is other.
  • Rename rules. An editor's file keeps its extension. An other file may take any extension except an editor's, which answers 422 wrong_extension. Every new name is checked against the file policies below.
  • POST /api/docs with editor: "other" answers 400 upload_required: such a file can only come in by upload. New versions come through upload sessions, as for editors' files. The editors' seat save refuses an other file, and a WebSocket to one answers 400, since it has no editor.
  • A name that is blocked is refused wherever it is typed, including a new text document in an image library.
  • Invisible characters. A new name may not hold invisible or direction-changing Unicode (Unicode's format characters: the right-to-left override and the other direction controls U+202A to U+202E and U+2066 to U+2069, zero-width characters U+200B to U+200F, U+FEFF, the soft hyphen and the like), since Invoice, a right-to-left override and fdp.exe shows as Invoiceexe.pdf. A new document, folder, library or site, a rename and a template's names refuse them with 422 invalid_name; an upload, a copy and the library and folder names of an imported template package replace each with _ and say so (renamed), as for the other characters names cannot hold. Names that already hold them are left as they are. The cost: emoji joined with a zero-width joiner, and the zero-width non-joiner some scripts use, are cleaned too.

File policies

A name is refused with 422 blocked_file_type {"extension"} when its extension is in the organisation's block list, or when its library does not take it. A size over the library's max_file_bytes is refused with 413 file_too_large {"limit"}. No type is blocked by default.

  • The order of the checks: the organisation's block list, then the library's blocked_types, then its effective allowed list (its allowed_types, or the image list for an image library, or every type); the name before the size.
  • The extension is the longest suffix of the name that is in the list being checked, matched without regard to case, so .tar.gz is tried before .gz. When a list does not hold the name's type, the answer names the name's own suffix from its last dot, or an empty string if it has none that can be an extension.
  • The organisation's list: GET /api/settings/files and PUT /api/settings/files {blocked_file_types}, administrators only. Entries are trimmed and lower-cased; a list that is not at most 100 valid, distinct extensions is 422 invalid_request. The change is recorded as setting.changed and holds the tree lock while it is made.

Malware scanning over ICAP

The organisation runs its own scanner. ShareCraft talks to it over ICAP (RFC 3507) and never scans itself. The client is written in the server and has no extra dependency. Scanning is off until an administrator gives an address on the Sharing settings page (Malware scanner) or with PUT /api/settings/scanner.

The settings are kept even when that test fails, so a scanner can be named before it is running (files wait meanwhile). The page's Test button sends the saved address again to run the same test, and records a setting.changed with no change.

How a scan goes

  • A worker sends each new content to the scanner as an ICAP RESPMOD request, the file as a chunked HTTP response body read from the content store in 64 KiB pieces. It is never held whole in memory. It asks OPTIONS first and honours the scanner's Preview and 100 Continue. It runs at most 2 scans at once, wakes on every new upload and on settings changes, and looks for due work every 5 seconds.
  • 204 is clean. 200 or 403 with X-Infection-Found, X-Violations-Found or X-Virus-ID is infected, and the threat name is kept (200 characters at most). The request says Allow: 204, so a scanner that leaves the file alone answers 204, and a 200 means it replaced the file. A 200 with no infection header is therefore judged by the HTTP response it carries: a 2xx status (or no response at all) is clean; any other status, such as the 403 block page some scanners send instead of a header, is infected, with the threat name from that response's headers if it has one and "blocked by the scanner" otherwise. Anything else, a bad answer, a refused connection or running out of time is a failure.
  • The result belongs to the content, not to the file. It is kept in the blobs row, so the same bytes uploaded twice are scanned once. Scan results live in the database, not in Git.
  • Retries. A failed scan is tried again after 1 minute, then 5, then 15, then every 60 minutes, for ever. Meanwhile an upload's content stays held (unless scanner_unavailable is allow) and in the store; content no upload named stays available.
  • Uploads first. Content an upload is waiting for is always sent to the scanner before any other, so the backlog that "Scan existing files" queues never keeps new uploads waiting.

What is held, and for whom

  • With no scanner configured, new content is unscanned and available at once. Content already found infected stays held. Clearing the scanner's address does not release content that is waiting or has failed: such uploads are listed on the Quarantine page (a waiting one as "Waiting for the scanner"), where an administrator can release or delete them.
  • Uploads are held until clean: a new file, a new version, and a copy made by New from template. Held means held for everybody, the uploader and administrators included. Administrators have one way through, Release.
  • Editor saves are scanned afterwards, not held. Holding them would stop people reopening a spreadsheet they had just saved. They stay available while the scanner is down too: a failed or too-large scan holds only content an upload named, so a scanner outage never locks what the editors saved. A save that is found infected is quarantined as soon as the scanner says so. The content's hold is decided once, for the content: if the same bytes were also uploaded, they are held. A text document's checkpoint is new content each time, so a text document being typed into causes a scan for each checkpoint. A text room that is open when its content is found infected keeps the text for the people already in it; new joins and downloads are refused.
  • A template whose content is still pending (an editor save not yet scanned) is not offered, and New from template with it answers 423 held with scan: "pending".
  • Routes that answer 423 held {"scan"}: download, ranged download, a download of an older version, preview, thumbnail, an anyone link's download, text and preview, opening in an editor (the WebSocket upgrade, and the text room), copy (single and bulk), and New from template. Listing, renaming, moving, deleting and sharing still work. GET /api/docs/<id> still answers 200, with scan and threat, so the page can say why.
  • The marks. The document's own answer and every children listing, the anyone-link listing included, carry "scan": "held" or "scan": "quarantined" and, for the second, threat. Everybody who can see the file sees them. After an upload finishes, the upload panel asks once whether the file is held and says "Being checked for malware"; a file's page says the same, hides Download, and asks again every 10 seconds for up to 5 minutes.

Large files and the 120-second deadline. scanner_timeout_seconds covers the whole exchange, not each step, so a scanner that dribbles its answer cannot tie up a worker. The cost is that a very large file over a slow link to the scanner can run out of time. At the 2 GiB default limit, 120 seconds needs about 17 MiB a second. The scan is then recorded failed and retried, and would fail again. Raise the setting (up to 3600) for large files, or lower scanner_max_bytes so they wait for an administrator instead.

Files from before the upgrade, and "Scan existing files"

Content stored before the upgrade is unscanned. It was all editors' files, so it stays available and is not scanned automatically. An administrator can press Scan existing files on the Sharing settings page, or POST /api/admin/scan-existing, which queues all of it and answers how many files were queued ({queued}).

  • Queued content stays available while it waits (state pending, no hold), and is quarantined if it turns out infected. So an infected old file can still be downloaded until its scan finishes.
  • If the scan of queued content fails, or it is too large, it stays available and is retried. Only infected content is taken away.
  • Uploads go to the scanner before the queued backlog, however long it is.
  • Content rows rebuilt from Git (section 10: a lost database, or one restored from a backup older than the data folder) have lost their scan results, which live only in the database. A content row the rebuild has to create is pending and held until it is scanned when a scanner is configured, so a restore never lets an infected upload back out; it is unscanned (available) when none is. A row that still exists keeps its state. After rebuilding with no scanner configured, set the scanner up and press Scan existing files.

Quarantine: release and delete

A file whose current version is infected is quarantined. Everyone who can see it sees the mark and the threat's name. Only administrators see the organisation's list, on the Quarantine page (GET /api/admin/quarantine), which also lists uploads held because their scan failed, they were too large, or they are still waiting for the scanner (pending, shown as "Waiting for the scanner"; an upload made just now appears there until its scan ends, and one left waiting after the scanner's address was cleared stays until an administrator acts). Site owners and the uploader cannot release it.

  • Release (POST /api/admin/quarantine/<sha256>/release {reason}): the reason is 3 to 500 characters. The content is marked released for every file that names it, and content.released records who, why and the state it was in. It works for infected, failed, too-large and pending content; anything else is 404. A release made while a scan is running wins over its result.
  • Delete (POST /api/admin/quarantine/<sha256>/delete): purges every file whose current version names that content, skipping the recycle bin, and erases the content and its thumbnail once nothing names it. Content an older version still names stays. The page asks for confirmation and says how many files were deleted. content.deleted records who and how many. It cannot be undone.

A real scanner

This section does not walk through installing one. The usual choice is ClamAV with c-icap and its ClamAV service module, run on a machine the organisation controls. The address then looks like icap://scanner.example:1344/srv_clamav; the service name is whatever the scanner calls its service. ShareCraft understands the headers X-Infection-Found, X-Violations-Found and X-Virus-ID, and a 200 that replaces the file with a block page. It was tested against the stand-in only (see "What was checked"), which the tests also make answer with a block page and no header. Run it once against ClamAV with c-icap, and against any scanner that blocks with a replacement page, before relying on it.

Your computer's own antivirus can delete stored files

Warning. Antivirus on the computer that runs ShareCraft scans the data folder like any other folder, and it may delete the bytes of a stored file. This happened on 14 November 2026: Windows Defender removed the EICAR test file from data\blobs (and, a minute before, from data\uploads), so the scan found the content missing.

  • What ShareCraft then shows. A content whose bytes have vanished cannot be scanned, so the scan is recorded failed, with the detail "the content is not in the store". An uploaded file is then held as failed, listed for administrators on the Quarantine page without a threat name (as "The scanner could not check it"), and retried on the schedule above. It is never let through by accident. An administrator can delete it there. A file no upload named (an editor save), or one that was already clean and then vanished, is not held, but it cannot be downloaded either: there is nothing left to send.
  • What to decide. Uploads are already scanned by the ICAP scanner, so an organisation should decide whether to exclude the data folder (SHARECRAFT_DATA, section 9) from the host's scanning. Excluding it avoids files disappearing from under the server. Not excluding it adds a second scanner, at the cost of the problem above. Either is a choice for the organisation; ShareCraft does not make it.
  • Backups should be taken as in section 19, from a copy of the data folder made before the antivirus has had its way, or with the folder excluded.

  • Where from. The brand centre takes images from asset libraries (section 27). A site's look also takes images from that site's own libraries. Anywhere else is 400 wrong_place.
  • Types, judged by the content and never by the name: PNG, JPEG, WebP, GIF and SVG. Anything else is 422 not_an_image. Raster images may be at most 8,000 by 8,000 pixels, read from the header only.
  • Sizes. A logo, thumbnail, footer logo or icon at most 1 MiB; a header image or background at most 5 MiB (413 image_too_large).

  • SVG. It must be UTF-8, well-formed XML with an svg root, no DOCTYPE and no processing instruction other than a leading XML declaration. The hub rule

A site that joined a hub uses the hub's theme and the hub's fonts (D42; fonts since plan 4B, section 30). Its own logo, header, navigation style, tab icon and footer stay its own. Its own theme and fonts are kept, unused, and comes back when it leaves the hub. The owner can still edit it while the site is in a hub, and Change the look says the hub's theme is in use. The rule is worked out each time a look is read and never written, so joining, leaving, the hub changing its theme, unregistering the hub, and archiving or deleting it never overwrite a site's own theme. An archived hub still lends its theme; a deleted one does not. The hub is named only to people who can see it.

Sign-in protection

These apply in both modes; in development every attempt comes from 127.0.0.1.

  • Per account: 5 failures within 15 minutes lock that email address until the oldest failure is 15 minutes old. While locked, even the right password is refused.
  • Per address: 30 failures within 15 minutes from one client address lock that address out of signing in to any account. An IPv6 address counts as its /64. A successful sign-in does not reset the address's count.
  • A refusal is 429 too_many_attempts with Retry-After and retry_after in the body, in seconds, whether or not the account exists. The sign-in page says how many minutes to wait.
  • Password checks at once: at most as many as the computer has processor cores (at least 2). Others wait up to 10 seconds, then get 503 busy with Retry-After: 10.
  • A known account's sign_in.failed event is written after the answer is decided, so an unknown email and a wrong password take the same work: one Argon2 check each.
  • When an account or address reaches its limit, one sign_in.locked event is recorded: {by: "account" | "address", until, address}, naming the account when known.
  • Anyone-link guessing: an address that gets 60 404 answers under /api/l/ within 15 minutes gets 429 too_many_attempts there until the oldest is 15 minutes old.
  • The counts are kept in memory and start again when the server restarts.

What the proxy must do

  • Terminate HTTPS for the public address and send requests to ShareCraft's listening address.
  • Pass Host unchanged, or set X-Forwarded-Host to the public host.
  • Set X-Forwarded-For and X-Forwarded-Proto: https.
  • Pass WebSocket upgrades through (the text editor and file sessions use them).
  • Allow request bodies of at least 9 MB: uploads arrive in 8 MiB parts.

Caddy does all of this by default (share.example.com { reverse_proxy 127.0.0.1:8787 }). nginx needs proxy_set_header for the three headers, the WebSocket Upgrade and Connection headers, and client_max_body_size.

Trying it on one computer

cargo xtask tls-proxy [--listen 127.0.0.1:8443] [--to 127.0.0.1:8787] [--name sharecraft.localhost] is a small HTTPS proxy for development only. It makes a self-signed certificate in memory for the name, localhost and 127.0.0.1, prints its SHA-256 fingerprint, adds the forwarded headers and passes WebSockets. Start the server with SHARECRAFT_PUBLIC_URL=https://sharecraft.localhost:8443 and SHARECRAFT_HSTS_SECONDS=0 (so the browser keeps no HSTS for that name), run the proxy, and open https://sharecraft.localhost:8443/. The browser warns about the certificate; continue only for this local check.

32 / The shared collaboration library and live room

The live room is the server room for editors that understand ShareCraft’s live protocol. An editor sends an opaque change: the server does not read or alter its content. The room gives changes one order, writes each one to PostgreSQL before sending it on, and sends that order to every participant. The shared collab-live library in each editor keeps the agreed document and the person’s shown document, resends unconfirmed changes after a reconnect, sends the heartbeat, and goes back and re-runs waiting changes when the agreed order changes.

GridCraft engine integration now exists in the fork. On the GridCraft branch coauthor-g3, the in-process GridLiveEditor/GridCoauthor adapter sends and applies the first identity-targeted gridcraft/1 commands through this library. It is built and reviewed but not yet merged into the fork’s sharecraft branch. It has no socket or browser host connection; that connection is G5.

The live room is off for every document in this build. Config.live_editors stays empty until G5 wires the real browser and desktop hosts. The in-process GridCraft adapter does not change that. Text documents still use the text room and file documents still use the existing one-person file session. Setting an editor in Config.live_editors is a code-level opt-in for tests and later integration; there is no user setting for it yet.

Log retention and purge

The server runs a live-log retention sweep when it starts and then once an hour. An entry is kept until a verified revision covers its log position. It is then kept for a further 30 days before the sweep removes its detail. Unverified entries stay. The document’s log head stays even when all covered entry detail has gone, so positions never repeat or move backwards.

Purging a document deletes its live logs inside the same PostgreSQL purge transaction. If the outcome of COMMIT is unknown, ShareCraft keeps the Git purge and leaves the normal Git-first reconcile to make PostgreSQL agree; it does not take the purge back on the assumption that the commit failed.

How a sync reads and applies a branch

  1. Read the branch head with a conditional request. An unchanged entity tag can answer 304 without spending the normal GitHub rate-limit allowance. Then read the recursive tree.
  2. Apply the library’s name, file-type and maximum-file-size policies before fetching content. Use one tarball when more than 20 distinct blobs are needed and the tree fits the caps; otherwise request blobs, four at a time.
  3. Verify every downloaded file against its Git blob ID. The whole tree, every needed byte and every blob identity are read and checked before the first tree or revision write. A truncated tree, corrupt blob or repository over a cap changes nothing.
  4. Plan additions, changes, removals and file moves. Every tracked node is verified by its actual parent and name, not only by whether it still exists; an interrupted move is therefore repaired on the next sync. A file move keeps the same node and its permissions. Folder/file name replacements are ordered so the old folder is binned before the file takes its name; temporary ~sync names avoid move-and-rename collisions.
  5. Git file names in one folder that are equal ignoring case are ordered by original repository-path byte order and every member receives a visible suffix before its extension, starting at (1): Readme.md and readme.md are shown as Readme (1).md and readme (2).md. A generated name that meets a literal repository name keeps advancing through the ordinary case-insensitive uniqueness rule. The original repository path remains the source identity, so group growth, shrinkage and renumbering rename existing nodes in place. This was the owner’s decision on 17 November 2026 because DriveCraft runs on case-insensitive Windows file systems and would otherwise overwrite one member; neither file is made to look like the “real” unsuffixed one. Symlinks, submodules, names ShareCraft cannot represent, blocked file types and over-size files are hidden and counted. Empty folders are not mirrored. Non-ASCII control and bidirectional characters in tar names remain a deferred limit.
  6. Repository removals go to the ShareCraft recycle bin. Every version below a connected library is excluded from the site’s stored and displayed usage as well as quota admission, including after a usage rebuild and while in the recycle bin. Purging it cannot subtract usage that was never counted. Disconnecting makes the surviving files ordinary and immediately recomputes the site’s usage, so all their versions count before a later upload is judged. The file bytes are nevertheless copied into ShareCraft’s content store; fetching them lazily or treating that copy as a cache is future work. A path purged through malware quarantine stays absent until the branch gets another commit.

The administrator settings source_max_files and source_max_bytes cap a connection. Their defaults are 50,000 files and 2 GiB (2,147,483,648 bytes), and each must be at least 1. This release has no settings API or page for them; change them directly in the database.

The worker

  • Polling: poll_seconds may be from 60 to 86,400 seconds. Wakes for one library are coalesced. At most two source syncs run at once.
  • Failures: ordinary failures back off by min(60 seconds × 2n, 1 hour). A successful or stopped result resets the in-memory failure count.
  • GitHub rate limits: the reset time is kept in retry_at; automatic wakes do not run before it. A stale-generation sync cannot shorten or erase that wait.
  • Stopped connections: a deleted branch, renamed or deleted repository, or rejected token moves the source to not_connected. Automatic attempts stop until an owner changes it or selects Sync now; the last mirrored files remain readable.
  • Concurrency and recovery: the PostgreSQL advisory lock prevents two syncs of one library at once. A syncing record older than 15 minutes is recovered only while its source lock is free, so a live long sync is not reset.

While the library page is open, a change to the source's last synchronized commit reloads the current folder so that its listing follows the mirrored tree.

The GitHub webhook

GitHub calls POST /hooks/github/<library>. Set the delivery content type to application/json; form-encoded deliveries are not understood and answer 204. The X-Hub-Signature-256 value is sha256= followed by the lowercase HMAC-SHA256 over the exact raw request body, using the webhook secret’s displayed hex text as the HMAC key. A valid ping answers 200. A valid push for the connected branch answers 202 and wakes a sync. Other events, another branch and an unparseable JSON body answer 204. A missing or wrong signature answers 401; an unknown library, missing connection or missing/unreadable secret answers 404.

The body limit is 5 MiB. A global in-flight semaphore admits eight webhook bodies at once; another is refused with 429 before its body is read. Webhook failures have their own throttle, separate from sharing-link lookups; known libraries are counted per client address and library, while unknown-library attempts use an address-wide bucket. In production mode the server needs a public HTTPS address, through the production proxy rules, before GitHub can reach this route.

Read-only connected libraries

Every content-changing HTTP route refuses a connected library with HTTP 409 and source_read_only, including when the caller is an administrator. The editor WebSocket seat is read-only and is narrowed again after access changes. The complete route classification is in crates/server/tests/source_readonly.rs; its guard fails when a route is added without a decision. The guards live in handlers and the editor seat, not in the shared tree functions, because the sync engine must use those functions to apply the repository.

Reading, previewing, downloading, access changes, sharing, links and copying out remain allowed. Moving out is refused. Deliberate exceptions are purging an entry already in the recycle bin, site lifecycle including site purge and restore, and malware-quarantine purge. Restoring an entry into the connected library is refused. Purge paths remove the matching source item records, connection and sealed secrets where applicable.

Secrets and the data folder

Repository tokens and webhook secrets are sealed with AES-256-GCM. The 32-byte key is secret.key in the ShareCraft data folder, normally installed atomically by the hard-link path on first use; a documented fallback is not atomic. The fallback no longer removes a key path it did not create, so it cannot delete a key installed by another process. There is no administrator or installer step. Only ciphertext, nonce and key identifier are stored in PostgreSQL. Plain secrets are never placed in Git, events, logs, ordinary API responses or error text; the webhook-creation response is the deliberate one-time exception that gives the new secret to its owner.

Windows access rule. On Windows, secret.key inherits the data folder’s access rules. ShareCraft does not set an owner-only ACL, because that would require unsafe code or another crate. The data folder must therefore be private to the account that runs the server. Another local user who can read that folder can read the key.

Known limits and deferred minor findings

These are the deferred minor findings recorded in the plan ledger. They are listed plainly; they were not silently treated as fixed.

  • Secrets: Secret derives PartialEq and Clone, and key bytes are not zeroized on drop. The early secrets tests did not cover every wrong-key-id, empty-ciphertext and tampered-tag case.
  • Key creation: the race test has no barrier; the # Errors documentation omits Failed; and the hard-link fallback is untested and not atomic. The fallback's removal of another process's installed key was fixed in the final review wave.
  • Source records: the records-only secrets test cannot by itself prove that the real sealing path stores no plaintext, although the later end-to-end API leak test exercises the real seal. The partial library_sources_due index may be unused.
  • GitHub client: the decompression cap uses Rc<Cell> and is not Send (it is used only within the sync); non-ASCII control and bidirectional characters remain allowed in tar names; enterprise-managed GitHub owner names containing _ are rejected; and two tests write 256 MiB streams.
  • Sync engine: temporary_name duplicates tree::split_extension, and below duplicates path logic in shown_names. A failed move can leave a temporary ~sync name. An unchanged-branch 304 skips tracked-node liveness checking. A gone folder can take untracked children to the bin; a new case-only sibling can rename an existing document; adoption keeps the old case; and apply steps are not wrapped in to_completion. The earlier missing dirty marker was addressed before Task 7.
  • Lifecycle: the bin-purge half of the lifecycle test asserts only that the node is deleted. A site purge during a sync can make that sync fail cleanly with a database error because the purge does not take the source lock. after_purge does not remove library_sources when the purged node is the connected library itself, which the current guard prevents. Secret deletion assumes secrets are not shared between connections. A quarantined path stays absent until a new repository commit.
  • API and generation: changing only the poll interval or webhook secret advances the generation and causes a redundant sync, although it now preserves an active rate-limit wait; handler requeues are not conditional on generation. A failed connection purges its new library only if it remains empty, and otherwise bins it. Stale-generation sync events were a deferred issue and were later suppressed in Task 7.
  • Worker and UI: the real worker runs in every test server and could race a source-sync test that lasts longer than a minute. Only JSON webhook deliveries are understood. sync_once returning Ok(None) means no new report: unchanged, busy or superseded; this ambiguity is documented and the worker decides by reading the database. The source API does not expose retry_at, so the page shows a reset clock only when it can extract one from the server-owned rate-limit sentence.

Parked behaviour

  • Shutdown during a sync: stopping the worker can cancel a tree mutation midway. This is treated like a process stop; the dirty marker, path adoption and tracked-node checks repair it on the next sync.
  • Webhook form encoding: a delivery sent as application/x-www-form-urlencoded is ignored with 204. The setup page tells administrators to choose application/json.
  • Quarantine purge: a mirrored path purged through malware quarantine stays absent until the branch receives a new commit.

Rulings that affect operation

  • The GitHub TLS client uses the operating system through reqwest native TLS. There is no process-global crypto-provider installation.
  • A stale syncing record is reset to connecting only with the source lock, both at start and during worker recovery.
  • The read-only guard is in HTTP handlers and the editor seat, not in shared tree functions. Bin purge, site lifecycle and quarantine purge remain allowed; copying out is allowed, moving out and restoring in are refused.
  • A worker wake respects not_connected and a future retry time. Owner changes and Sync now can clear a stopped or failed state, but do not evade a rate limit.
  • Poll-only and webhook-secret changes preserve an active rate-limit wait. Token, branch and folder changes reset it because they change the request identity or scope.
  • sync_once keeps its ambiguous Ok(None) result to avoid broad interface churn; only the worker consumes it and checks the stored state.
  • The page never invents a GitHub rate-limit reset time: it shows one only when the server-owned error sentence contains it.

How a checkpoint is made

  • When. After 15 seconds with no new change, or at the latest 120 seconds after the first unsaved change, the room gives one capable editor a one-use write ticket for the current position.
  • Writing. The editor uploads its identity data and then the workbook to PUT /api/docs/{id}/live-checkpoint?ticket=&at=&base=. The length of the identity data is in the X-ShareCraft-Session-Data-Length header and is checked before the body is read. The bytes go to the content store and become a new revision in Git, on top of the base the ticket named. The Git write runs off the room’s own task, so the room keeps ordering changes while it runs.
  • Checking. Another person’s capable editor, on the same kind of build as the writer (browser or desktop), gets a verify ticket. It writes the same position itself and sends two SHA-256 hashes to POST /api/docs/{id}/live-checkpoint/hash as {ticket, at, sha256, session_sha256}: one of the file bytes, and one of the identity data it would upload with them. Both must match what the writer uploaded; a mismatch on either is a dispute. A match marks the checkpoint verified. Joiners then load it plus the changes after it, and the log before it can be swept after 30 days. The writer is never asked to check its own checkpoint, from any of their tabs, including after a restart. The bytes carry computed values, so an editor on the other kind of build is not asked: with no same-build checker present, the checkpoint stays unverified and the sole-editor rule below applies. Editors on different builds still compare entered content every 64 changes.
  • Cancelled tickets. A ticket ends when its holder leaves, when it lapses, when the position it names is dropped, or when the room moves to another base. An unused ticket lapses 120 seconds after it is given. Once its upload starts, the deadline is the upload’s instead: 120 seconds plus the upload’s declared length (or the largest allowed, when none is declared) at 64 KiB a second, so a large workbook on a slow link can still be saved. The lengths are checked before the ticket is used, so a request refused for them does not use it up. A lapsed upload is refused (403); an upload made from an older base than Git’s current revision is refused as stale (409 with the current revision).
  • Unknown outcomes. If the Git write’s outcome is unknown, the room asks Git again with growing waits (5 seconds up to 5 minutes). After 8 failed tries it takes the revision Git holds as the base and asks for a fresh checkpoint.
  • Connected libraries. Both checkpoint routes refuse a file in a GitHub-connected library with 409 source_read_only before the ticket is checked.

  • Not checked: real browsers, a desktop host, presence, or a live room turned on for any document. These are G5.
  • Not checked: a server stopped part way through a two-part major write, other than with the injected failures in the tests.

A client that gave up its held change and sends a later one after the hold is sent the log again, and its change is stored. Every join is told, before its catch-up, whether changes wait (ChangesPaused) or not (ChangesResumed), so a client never sends into a hold and one that missed a resume is released. A returning client whose batch was dropped with its edit right is released by that batch’s ReturnReady.

A copy lost with the connection is therefore never the last, and a client that holds no such batch ignores the repeat.

  • Restart tie-break. When two verified checkpoints stand at the same position (a major version and a base adopted there later), a restart loads the one verified last.
  • Known limits: an honest difference between two editors that repeats within the hour excludes both people from checking for a day; the exclusion is recorded and the owner can see it. 36 / File-share libraries

Built on 17 to 19 November 2026 as plan 6, phase A2 of SC-27, Phase 1 (read-only), on the branch fileshare-surfacing, and merged into the release integration branch on 19 November 2026. A library can be connected to a folder on a file share (a UNC path such as \\server\share\folder) or on the server. Its folders and files appear in the library as ordinary items. File bytes are read from the share when first opened, into a bounded cache in the content store, and the library is read-only in ShareCraft. Phase 2 (writing through to the share) is not built.

Off until an administrator approves a folder. Nothing can be connected until an administrator lists approved folders in the share_roots setting, through PUT /api/settings/shares. The default is an empty list, so every connect is refused with share_not_approved. There is no page for any of this yet: the routes are reachable only through the API, and the settings routes answer administrators only.
