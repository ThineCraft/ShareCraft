Building and running ShareCraft

How to build and run the development build of ShareCraft: people sign in with their own accounts, share plain-text documents with each other, and edit them together in browser tabs. This page also says what the build does not do yet.

Status of this build, and what has been checked. This is a development build, not a release. The server is covered by automated tests, which run against a real PostgreSQL database (section 02). The scripts of the web pages have one automated test file, which covers only the check that a sign-in redirect stays on this site; the rest of the page scripts are not covered by automated tests. A hands-on check of the pages in a browser is recorded separately by the project owner's assistant, not in this document, so nothing here should be read as saying that check has been done. The sections below describe what the code does.

01 / What you need

  • Rust, stable channel, installed with rustup. The project uses the 2024 edition.
  • The WebAssembly target, which lets Rust build the part that runs in the browser:
rustup target add wasm32-unknown-unknown
  • wasm-bindgen-cli version 0.2.130, exactly. It must match the wasm-bindgen version recorded in Cargo.lock. If it is missing or a different version, cargo xtask web stops and prints the command to run:
cargo install wasm-bindgen-cli --version 0.2.130 --locked

If a later change to Cargo.lock moves wasm-bindgen to another version, the command printed by cargo xtask web shows the version then needed.

  • PostgreSQL. The server keeps accounts, sign-in sessions, sharing, the revision index and events in a PostgreSQL database and will not start without one. Development has used PostgreSQL 18 on the local machine. Create an empty database and an account that may create tables in it. For the tests (section 02) create a second, separate database and give the same account permission to create schemas in it; the tests do not create databases.
  • A .env file in the repository root, made by copying .env.example and replacing its placeholder values. It names the databases by variable (DATABASE_URL for the server, TEST_DATABASE_URL for the tests). .env is not kept in Git. Keep real values only there: never put a database address or password in a command that is saved, in a commit or in a message.
  • Node.js, to run the automated test file for the page scripts, which cargo xtask check runs (section 02). Without it the check stops and says that Node.js is needed.

Git does not need to be installed to run ShareCraft, because the Git library is built in. You only need it to look at saved documents (section 09).

02 / Build and check

Run every command from the repository root, the folder that holds Cargo.toml.

This loads .env, then checks that no dependency has a copyleft licence, checks formatting, runs the lints with warnings treated as errors, runs all tests in the workspace, builds each browser-side crate for WebAssembly, and runs the page script tests with Node (below). It prints xtask: all checks passed and exits with code 0 when everything is in order:

cargo xtask check

This loads .env and then runs cargo test with whatever arguments you add, for example cargo xtask test -p server:

cargo xtask test

The tests need TEST_DATABASE_URL. Every test that uses the database creates its own schema in that database, drops it afterwards, and also drops leftover test schemas more than an hour old. A test that needs the variable and finds it unset fails with a message saying so; it is never skipped. That is why you run the tests through cargo xtask check or cargo xtask test, which load .env, and not through plain cargo test.

This builds the browser client and writes the page's script package to web/pkg. The folder is not kept in Git, so do this once after a fresh checkout and again after changing the browser client:

cargo xtask web

The scripts of the web pages (the .js files in web) have one automated test file, web/common.test.mjs. It tests the function that decides where to go after signing in, so that a crafted link cannot send someone to another site. cargo xtask check runs it, and fails with a message saying so when Node.js is not installed; it never skips it. To run it on its own:

node --test web/*.test.mjs

03 / The first administrator

There is no public sign-up, and nobody can sign in until an account exists. The first account, an administrator, is made from the command line. DATABASE_URL must be set (in .env or the environment). The command brings the database schema up to date, then creates the account:

cargo run -p server -- add-user --email <email> --name <name> --admin

Leave out --admin to make an ordinary account. The password is not a command-line option, so that it never appears in a process list or a saved command history. The command asks for it with Password: and does not show what you type. If its input is piped instead of typed, it reads the first line of that input as the password. It prints created administrator <email> (<account id>), or created account ... for an ordinary account. The password and the database address are never printed.

After the first administrator exists, further accounts are made on the People page (section 06); the command line stays available for the same job.

04 / Run it and sign in

Start the server, still from the repository root. It needs DATABASE_URL, which it reads from .env in the current folder or a parent. It takes its address first, so an address already in use is reported at once. It then brings the database schema up to date and compares the revision index with Git (section 10). Only then does it say where it listens and start accepting connections:

cargo run -p server

It prints the revision-index line, then the address it listens on and WARNING: development mode, local connections only. If the database cannot be reached or brought up to date, it prints why and exits without printing the address. Once the address is shown, open the site in a browser at exactly one of these addresses:

http://127.0.0.1:8787/
http://localhost:8787/

A person who is not signed in is sent to the sign-in page, and after signing in comes back to the page they asked for. After signing in the documents page lists the documents the person can open and has a New document form. A document opens at an address such as /doc.html#<document id>; the part after # is the document's identifier, and anyone with access can use the same address.

The pages the server provides:

Pages
PageWhoWhat it does
/signin.htmlEveryoneEmail and password form.
/ (documents)Signed-in peopleLists your documents with your role and last save time, creates a new one, and has the Sign out button. Administrators also see a link to People.
/doc.html#<id>People with a role on the documentThe text box, who is in the document, the save status, and, for owners, the Sharing panel (section 07).
/people.htmlAdministratorsLists every account, adds an account, disables or enables one (section 06). Other people see Only administrators can manage people.

Use those addresses only. The server refuses a WebSocket connection, and every /api request, when its Host is not a loopback name (127.0.0.1, localhost or [::1]), or when the page's Origin differs from the address it was loaded from. In this build the site therefore cannot be reached through another hostname, another computer or a proxy.

Browsers keep cookies separately for 127.0.0.1 and localhost. To try two people at once on one computer, sign in as one at http://127.0.0.1:8787/ and as the other at http://localhost:8787/.

05 / Settings

The server reads these environment variables. DATABASE_URL is required; the others are optional. Before reading them, the server and its commands load .env from the current folder or a parent, if there is one; a variable already set in the environment wins over .env.

SHARECRAFT_ADDR127.0.0.1:8787IP address and port to listen on, for example 127.0.0.1:9000. Must be a loopback address; the server refuses to start otherwise. A hostname such as localhost is not accepted for this setting (the page itself can still be opened at http://localhost:8787/).

The default folders are relative to the folder you start the server from, which is why the commands above are run from the repository root. Example with a different port and data folder:

$env:SHARECRAFT_DATA = "C:\sharecraft-data"

If you change the port, open the site at that port instead of 8787, still using 127.0.0.1 or localhost.

06 / Accounts and signing in

An account is one person: an email address, a display name, a password, and a flag saying whether they are an administrator. Accounts are created by an administrator, on the command line (section 03) or on the People page, where an administrator also chooses whether the new person is one. Nobody can register themselves, and nobody can change their own password yet.

What an account may contain
FieldRule
EmailAt most 254 characters, no spaces or control characters, one @ with something on each side. Case is ignored: two emails that differ only by case are the same account. Each email can have one account.
Name1 to 60 characters, at least one letter or digit, no control characters and no < or >. Names are shown to other people in a document and are credited in saved revisions.
Password10 to 256 characters. Nothing else is required. It is stored only as an Argon2id hash.

Signing in

The sign-in page sends the email and password to the server. When they match, the server starts a session that lasts 30 days and sets a cookie named sharecraft_session holding a random token. The cookie is marked HttpOnly (page scripts cannot read it) and SameSite=Lax. The server stores only a hash of the token. It is not marked Secure, because the build only serves plain HTTP on the local machine.

A wrong password, an unknown email and a disabled account all get the same answer, That email and password do not match., so the page does not reveal which emails have accounts. After 5 failed attempts for one email within 15 minutes, further attempts for it are refused with Too many attempts. Try again in a few minutes. The count is kept in the server's memory, so restarting the server resets it.

Signing out

The Sign out button is on the documents page. It ends that session and clears the cookie, and any open document pages of that session are removed (section 08). The same person's other sign-ins, in other browsers, stay signed in. A session also ends on its own after 30 days.

Managing people (administrators)

The People page lists every account with its email, whether it is an administrator and whether it is disabled. An administrator can add a person (email, name, password, administrator or not) and disable or enable an account.

  • Disabling an account ends all of its sessions at once and removes it from every open document. It cannot sign in again until an administrator enables it. Its documents and grants are kept.
  • At least one administrator must stay enabled: disabling the last one is refused with At least one administrator must stay enabled.
  • An administrator is treated as an owner of every document (section 07).

07 / Sharing and roles

A person with an account can create a document on the documents page. The name is optional (it defaults to Untitled); it can be 1 to 120 characters and cannot contain control characters, / or \. The creator becomes its owner. A name cannot be changed afterwards yet.

Access is granted per document, to one person at a time. A person with no grant on a document cannot see it in their list and cannot open it. The server answers the same way for a document that does not exist and one you may not open, so you cannot find out that a document exists by guessing its address; the page says This document does not exist, or you do not have access to it.

Roles
RoleReadChange the textShare and see events
ViewerYesNoNo
EditorYesYesNo
OwnerYesYesYes

A viewer sees the live text and who else is there, but the text box is read-only and the page shows You can read this document but not change it. The server also refuses changes from a viewer, whatever the page does.

Administrators are owners of every document without needing a grant, so someone can always recover a document whose owners are gone. They appear in the Sharing list only if they were granted a role explicitly.

Sharing a document

Owners see a Sharing panel under the text. It lists everyone who has been granted access, each with a role menu and a Remove button. To add someone, type their email, choose a role and press Share. Choosing another role in a person's menu changes their role at once. Sharing is by the email of an existing account: No account has that email address. appears if there is none, and only owners can learn this. A document must keep at least one owner; removing or demoting the last one is refused with A document must keep at least one owner.

A change takes effect for people who have the document open straight away, without them reloading (next section).

08 / What a removed person sees

When a person's access to a document ends while they have it open, the server removes their connection at once instead of waiting for them to reconnect. The page then empties the text box and the list of people, hides the Sharing panel, stops trying to reconnect, and shows one of these in the status line:

Why a page was removed
CauseStatus shown
An owner removed their accessYour access to this document was removed.
They signed out (in this or another tab of the same session), or the session reached 30 daysYou were signed out.
An administrator disabled their accountYour account was disabled.

Reopening the document after losing access shows This document does not exist, or you do not have access to it. Opening any page when the session is over sends the person to the sign-in page.

Lowering a role from editor to viewer does not remove the person. Their text box becomes read-only, they are marked read only in the list of people, and if they had typed something the server had not yet accepted, it is refused and the status reads A change was refused because you can no longer edit this document. Raising a role makes the text box editable the same way. Every change of role is sent to the open page, including one that does not change whether the person may edit: a person made owner gets the Sharing panel, and an owner made editor or viewer loses it, without reloading.

These changes are made in PostgreSQL first and then sent to the open document inside the server process. This works because there is one server process. If the role cannot be read at that moment, the person's connections are removed rather than left open.

09 / Where data is kept

ShareCraft keeps two stores, and they hold different things.

Git and PostgreSQL
StoreHoldsIf it is lost
Git, the library repository under the data folderThe content of every document and its metadata, one Git commit per saved checkpoint. Only the server writes to it.Documents and their history are lost. Back up the data folder.
PostgreSQL, the database named by DATABASE_URLAccounts and password hashes, sign-in sessions, who has access to which document, the index of revisions, and events (sections 10 and 11).Nobody can sign in, and who may open which document is forgotten. The documents themselves are safe in Git. See below.

PostgreSQL needs its own backup. Backing up the data folder does not back up accounts, sharing or events, and backing up the database does not back up document content. Keep both, taken at about the same time. Only the revision index in PostgreSQL can be rebuilt from Git (section 10).

If PostgreSQL is lost and you start with an empty database, you must create the first administrator again (section 03). Starting the server then re-creates a record for each document found in Git, with no creator and no grants, so only administrators can open them until they share them again. Accounts, passwords, sharing and events are not recovered by this.

The Git repository

Documents are stored in one bare Git repository under the data folder:

<data folder>/libraries/00000000-0000-0000-0000-000000000001.git

With the defaults that is data/libraries/00000000-0000-0000-0000-000000000001.git. The data folder is not kept in Git. Every document lives in that one library for now.

Inside the repository, the main branch holds, for each document identifier:

  • docs/<doc_id>/content: the document text.
  • docs/<doc_id>/meta.json: the metadata for that revision, as JSON: the document's name, free-form fields, and the people credited so far.

Each saved checkpoint is one Git commit. The commit's author is the account that made the change; if several accounts contributed since the last checkpoint, the others are named on Co-authored-by lines. Their addresses are of the form <account id>@sharecraft.invalid, not real email addresses. The document identifier is the one after the # in the page's address. To look at a saved document with plain git, run these from the repository root:

git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git log main
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/content
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/meta.json

Replace <doc_id> with the identifier. Only read from the repository this way. Content must reach it through the server, which is the only thing that writes to it.

When a checkpoint is written

Live changes are not committed one by one. The server writes a checkpoint when no change has arrived for 2 seconds, or at the latest 30 seconds after the first change that has not been saved yet, whichever comes first. When the last person leaves a document, it is saved straight away. If that final save fails, the server tries again after 2 seconds, doubling the wait each time up to 30 seconds, for up to 10 attempts in all (about three minutes); then it gives up and prints a message to the server's console. The document stays open on the server while it is still trying, even after the grace period. A save that fails while people are connected is retried after the idle time.

The page shows the state next to the document title: Saving…, Saved, or Saving failed, retrying.

The server keeps the most recent 1000 log entries behind the last checkpoint, and keeps a document open for a grace period of 60 seconds after the last person leaves it. A browser that drops for a short time therefore catches up, resends its changes and keeps the typing it did while disconnected, including when it was the only one there, as long as it is back within the grace period. After that, the document is closed and saved; a tab that comes back later is given the saved text, and any typing it did while disconnected cannot be kept (section 12). The same happens after a server restart.

10 / The revision index, start-up reconcile and rebuild

PostgreSQL holds a list of each document's revisions: the Git commit id, its position in the document's history, its parent, when it was committed and who is credited. The documents page uses it to show each document's last save time. The list is an index: Git is the authority, and the index can always be replaced from it.

  • After each checkpoint the server adds the new revision to the index in the background. If this fails, the content is still safe in Git, the failure is printed to the server's console and recorded as an event, and the next start repairs the index.
  • At every start the server reconciles: for each document in Git it compares the newest revision in the index with Git's, and replaces the document's list from Git when they differ. It prints one line before it prints its address and begins accepting connections, for example Reconciled revisions with Git: 3 documents in Git, 1 updated, 0 failed. A document that cannot be read is listed on the console and the server still starts.
  • rebuild replaces the list of every document in Git, whether or not it looks out of date. Use it if you suspect the index is wrong. It needs DATABASE_URL and the data folder, brings the schema up to date, prints Rebuilt revisions from Git: ... with the same counts, names any document it could not rebuild, and exits with a failure code if there was one:
cargo run -p server -- rebuild

Neither reconcile nor rebuild writes to Git. If Git was changed by something other than the server, the next checkpoint of that document stops with a conflict (section 12) instead of merging.

11 / Events and how an owner reads them

The server writes an event to PostgreSQL for each notable thing that happens: who did it, who or what it was done to, which document, when, and a few details. Events never contain document text, passwords or tokens. There is no automatic deletion: the log only grows.

Event kinds
KindWhenBelongs to a document
document.createdA document was created (its name is in the details).Yes
access.granted, access.changed, access.revokedAn owner gave someone a role, changed it (old and new role in the details), or removed it.Yes
editing.joined, editing.leftSomeone opened the document in a tab, or their connection ended.Yes
editing.removedThe server removed someone's connection; the reason (access_revoked, signed_out, account_disabled) is in the details.Yes
revision.savedA checkpoint was written to Git (the commit id and the people credited are in the details).Yes
revision.save_failed, revision.conflictA save failed, or Git held a newer revision than the server expected.Yes
revision.index_failedA revision could not be added to the index (section 10).Yes
user.created, user.disabled, user.enabledAn account was created, disabled or enabled. The actor is empty when the command line did it.No
session.started, session.endedSomeone signed in, or signed out.No
sign_in.failedA sign-in for an existing account failed; the reason is wrong_password or disabled. Attempts with an unknown email are not recorded.No

How an owner reads them. There is no events page yet. An owner of a document (or an administrator) who is signed in reads that document's events by opening this address in the same browser:

http://127.0.0.1:8787/api/docs/<doc_id>/events

The answer is JSON: the latest 200 events of that document, oldest first, each with an id, a time, the kind, the account ids of the actor and the subject (null when there is none), and the details. People appear as account ids, not names. To match an id to a person, open /api/docs/<doc_id>/access (owners only; it lists everyone granted access, with names and emails) or, as an administrator, /api/admin/users. Someone with no role on the document gets 404, and a viewer or editor gets 403.

The events that belong to no document (accounts, sign-ins, failed sign-ins) cannot be read through the site. They are in the events table in PostgreSQL, readable by whoever runs the database.

12 / Stopping the server, and notices on the document page

Stopping the server (for example with Ctrl+C) ends it at once. The server loses any changes made since the last checkpoint, which can be up to 30 seconds of typing. Everything up to the last saved revision is kept in the Git repository and is loaded again the next time the document is opened. Accounts, sessions and sharing are in PostgreSQL and are unaffected; people stay signed in across a restart.

Notices about the connection and saving

A tab that is still open shows Connection lost. N changes waiting and keeps that status for the whole outage while the page retries in the background (first after 0.5 seconds, with the wait doubling up to 8 seconds between tries). When the server is back, the status returns to Saved.

If the server was restarted, or the document was closed after its grace period and opened again, the tab is reset to the last saved text, and the status says what that cost:

  • If the saved text is older than the text the server had accepted, it reads This document was reopened from its last save. Changes made after that save were lost. This happens when the server stopped before saving. If changes typed while the connection was lost were also thrown away, it adds N changes you typed while disconnected could not be kept.
  • If the saved text is everything the server had accepted, but the tab held changes typed while disconnected, it reads N changes could not be kept. This is the usual case after the grace period.
  • If nothing differs, nothing was lost and the status simply returns to Saved.

If the server kept running but could no longer take the tab back where it left off, the tab is brought up to date with the server's text and, if it had to throw away changes, reads N changes could not be kept. These messages stay until you next type. If saving is failing at the same time, the status reads Saving failed, retrying. followed by the message.

Wait for the status to read Saved before you stop the server.

13 / Known limits of this build

  • Local connections only. The server will not listen on a non-loopback address and refuses connections that do not come from a page it served (section 04). Two people on two computers cannot use it together. Passwords must not cross a network without encryption, and encryption (TLS) is a separate piece of work.
  • Accounts are made by an administrator. There is no sign-up, and nobody can change their own password yet, nor reset a forgotten one.
  • No single sign-on, multi-factor sign-in, guests or groups. Access is a password account, granted to one person at a time for one document.
  • No sites, libraries, folders or inheritance. Every document is a separate item with its own list of people. Documents cannot be renamed or have their metadata edited after creation.
  • No page for events (section 11), and no way to see the document's saved revisions from the site: use Git (section 09).
  • One server process. Removal from live sessions is sent inside the process; running several server processes would need a different mechanism.
  • Large pastes go in pieces. One change can be at most 512 KiB as sent (section 05); a larger paste is refused with a message asking for smaller parts.
  • Plain text only. There is no formatting, and no spreadsheet, document, PDF or 3D editing yet.
  • The four editors are not connected yet. WordCraft, GridCraft, PdfCraft and SolidCraft do not open files from ShareCraft in this build.
  • PostgreSQL needs its own backup (section 09), and the event log is never trimmed.
