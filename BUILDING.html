Building and running ShareCraft

How to build the first working piece of ShareCraft, a plain-text document that two browser tabs edit together, and what it does and does not do yet.

01 / What you need

  • Rust, stable channel, installed with rustup. The project uses the 2024 edition.
  • The WebAssembly target, which lets Rust build the part that runs in the browser:
rustup target add wasm32-unknown-unknown
  • wasm-bindgen-cli version 0.2.130, exactly. It must match the wasm-bindgen version recorded in Cargo.lock. If it is missing or a different version, cargo xtask web stops and prints the command to run:
cargo install wasm-bindgen-cli --version 0.2.130 --locked

If a later change to Cargo.lock moves wasm-bindgen to another version, the command printed by cargo xtask web shows the version then needed.

Git does not need to be installed to run ShareCraft, because the Git library is built in. You only need it to look at saved documents (section 05).

02 / Build and check

Run every command from the repository root, the folder that holds Cargo.toml.

This runs formatting, lints, all tests, and a WebAssembly build of each browser-side crate. It prints xtask: all checks passed and exits with code 0 when everything is in order:

cargo xtask check

This builds the browser client and writes the page's script package to web/pkg. The folder is not kept in Git, so do this once after a fresh checkout and again after changing the browser client:

cargo xtask web

03 / Run it

Start the server, still from the repository root:

cargo run -p server

It prints the address it listens on and a reminder that this is a development build with no sign-in. Then open the page in a browser at exactly one of these addresses:

http://127.0.0.1:8787/
http://localhost:8787/

The page adds a document identifier after a # in the address. To edit the same document in a second tab or window, copy the whole address, including the part after #, and open it there. Type a name in the name box so you can tell the sessions apart.

Use those addresses only. The server refuses a WebSocket connection when its Host is not a loopback name (127.0.0.1, localhost or [::1]), or when the page's Origin differs from the address it was loaded from. In this build the page therefore cannot be reached through another hostname, another computer or a proxy.

04 / Settings

The server reads three environment variables. All are optional.

Environment variables
VariableDefaultMeaning
SHARECRAFT_ADDR127.0.0.1:8787IP address and port to listen on, for example 127.0.0.1:9000. Must be a loopback address; the server refuses to start otherwise. A hostname such as localhost is not accepted for this setting (the page itself can still be opened at http://localhost:8787/).
SHARECRAFT_DATA./dataFolder where documents are stored.
SHARECRAFT_WEB./webFolder of page files served at /.

The default folders are relative to the folder you start the server from, which is why the commands above are run from the repository root. Example with a different port and data folder:

# PowerShell
$env:SHARECRAFT_ADDR = "127.0.0.1:9000"
$env:SHARECRAFT_DATA = "C:\sharecraft-data"
cargo run -p server

If you change the port, open the page at that port instead of 8787, still using 127.0.0.1 or localhost.

These values are fixed in this build and cannot be changed through the environment:

Fixed settings
SettingValueMeaning
Checkpoint idle time2 secondsA checkpoint is written once no change has arrived for this long (section 05).
Longest time unsaved30 secondsA checkpoint is written at the latest this long after the first unsaved change.
Grace period60 secondsHow long a document stays open on the server after the last person leaves it, so a browser that reconnects within this time carries on without losing its typing.
Largest single change512 KiBThe largest change a page sends in one piece, measured as sent. A larger paste is refused and the page shows That change is too large to send in one piece. Paste it in smaller parts.

05 / Where data is kept

Documents are stored in one bare Git repository under the data folder:

<data folder>/libraries/00000000-0000-0000-0000-000000000001.git

With the defaults that is data/libraries/00000000-0000-0000-0000-000000000001.git. The data folder is not kept in Git. Every document lives in that one library for now.

Inside the repository, the main branch holds, for each document identifier:

  • docs/<doc_id>/content: the document text.
  • docs/<doc_id>/meta.json: the metadata for that revision, as JSON.

Each saved checkpoint is one Git commit. The document identifier is the one after the # in the page's address. To look at a saved document with plain git, run these from the repository root:

git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git log main
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/content
git --git-dir=data/libraries/00000000-0000-0000-0000-000000000001.git show main:docs/<doc_id>/meta.json

Replace <doc_id> with the identifier. Only read from the repository this way. Content must reach it through the server, which is the only thing that writes to it.

When a checkpoint is written

Live changes are not committed one by one. The server writes a checkpoint when no change has arrived for 2 seconds, or at the latest 30 seconds after the first change that has not been saved yet, whichever comes first. When the last person leaves a document, it is saved straight away. If that final save fails, the server tries again after 2 seconds, doubling the wait each time up to 30 seconds, for up to 10 attempts in all (about three minutes); then it gives up and prints a message to the server's console. The document stays open on the server while it is still trying, even after the grace period. A save that fails while people are connected is retried after the idle time.

The page shows the state next to the document title: Saving…, Saved, or Saving failed, retrying.

The server keeps the most recent 1000 log entries behind the last checkpoint, and keeps a document open for a grace period of 60 seconds after the last person leaves it. A browser that drops for a short time therefore catches up, resends its changes and keeps the typing it did while disconnected, including when it was the only one there, as long as it is back within the grace period. After that, the document is closed and saved; a tab that comes back later is given the saved text, and any typing it did while disconnected cannot be kept (section 06). The same happens after a server restart.

06 / Stopping the server

Stopping the server (for example with Ctrl+C) ends it at once. The server loses any changes made since the last checkpoint, which can be up to 30 seconds of typing. Everything up to the last saved revision is kept in the Git repository and is loaded again the next time the document is opened.

A tab that is still open shows Connection lost. N changes waiting and keeps that status for the whole outage while the page retries in the background (first after 0.5 seconds, with the wait doubling up to 8 seconds between tries). When the server is back, the status returns to Saved.

If the server was restarted, or the document was closed after its grace period and opened again, the tab is reset to the last saved text, and the status says what that cost:

  • If the saved text is older than the text the server had accepted, it reads This document was reopened from its last save. Changes made after that save were lost. This happens when the server stopped before saving. If changes typed while the connection was lost were also thrown away, it adds N changes you typed while disconnected could not be kept.
  • If the saved text is everything the server had accepted, but the tab held changes typed while disconnected, it reads N changes could not be kept. This is the usual case after the grace period.
  • If nothing differs, nothing was lost and the status simply returns to Saved.

If the server kept running but could no longer take the tab back where it left off, the tab is brought up to date with the server's text and, if it had to throw away changes, reads N changes could not be kept. These messages stay until you next type. If saving is failing at the same time, the status reads Saving failed, retrying. followed by the message.

Wait for the status to read Saved before you stop the server.

07 / Known limits of this build

  • No sign-in. Anyone who can open the page on this computer can read and change every document. The page and the server console both say so.
  • Identity is a typed name. The name box is a label for other people in the session. It proves nothing, and two people can type the same name.
  • Local connections only. The server will not listen on a non-loopback address and refuses connections that do not come from the page it served (section 03).
  • Large pastes go in pieces. One change can be at most 512 KiB as sent (section 04); a larger paste is refused with a message asking for smaller parts.
  • Plain text only. There is no formatting, and no spreadsheet, document, PDF or 3D editing yet.
  • PostgreSQL is not used yet. Nothing in the server reads or writes a database. A local development database is configured through .env for the next plan: copy .env.example to .env and fill in the values. .env is not kept in Git.
  • The four editors are not connected yet. WordCraft, GridCraft, PdfCraft and SolidCraft do not open files from ShareCraft in this build.
  • Access removal is not built. There are no permissions, so there is nothing to revoke.

08 / Licences

The revisions crate stores documents in Git using gix (gitoxide), a Git implementation written in Rust and licensed MIT or Apache 2.0. No C library is involved and no copyleft code is linked. Repositories it writes are ordinary Git repositories: the git command line reads them as usual.
