ThineCraft / ShareCraft / Design proposal

S3 Surfacing libraries

A document library whose files live in an existing S3 bucket, with no versioning needed. The same design later covers normal file servers and other online Git repositories. ShareCraft shows the objects as files and folders, applies its own permissions and features over them, and lets DriveCraft sync them to computers like any other library. Azure Blob Storage plugs into it too.

01 / Intent and shape

Status. This is a design proposal. The owner's words of 16 November 2026 are the only direction: "A new type of Document library that is S3 Surfacing. The ability to connect to an S3 source and surface them as files in SharePoint with the ability to Sync using DriveCraft. I think we'd have to do the same for Azure as well, but S3 is more popular." The owner then confirmed on 16 November 2026: the idea is S3 (or another store) instead of Git for holding file bytes; the store can be external to ShareCraft; no versioning is needed; and the same should be done for normal file servers, with the library's existing limits on file types, and for other online Git repositories whose documents are stored in Git. He then set the build order: GitHub first, file share second, then S3 tested first against Cloudflare R2, and decided that a save to a Git repository is a direct commit. Everything else here is proposed and nothing is built. Section 02 lists the decisions that need the owner.

What it is. A fifth library kind, alongside document, image, template and asset (D39). An administrator connects it to a bucket, and optionally a prefix inside it. From then on the bucket's objects appear in ShareCraft as files in folders. People open, preview, search and share them in the browser, and sync them to their computers with DriveCraft. The bytes stay in the bucket. ShareCraft is the front door, not a copy.

Why. Organisations already hold large file estates in object storage: archives, media, exports from other systems, backups people need to reach. SharePoint cannot show them as a library without migrating them. A ShareCraft library that surfaces them gives those files permissions, links, search, previews and desktop sync without a migration and without a second copy to pay for.

Goals.

  • Connect AWS S3 and S3-compatible stores (MinIO, Ceph RGW, Cloudflare R2, Backblaze B2 and the like) through one source type.
  • Show keys as folders and files, with stable identities, so links, permissions and DriveCraft's catalog survive.
  • Keep the bucket the authority for bytes. Never silently overwrite or delete something that changed in S3.
  • Sync with DriveCraft through the same API contract as any ShareCraft library (SC-23), with no special client mode beyond what the contract already says.
  • Build around a storage-source abstraction so Azure Blob Storage is a second implementation, not a redesign.

Non-goals.

  • Not a migration tool. Moving the bytes into ShareCraft is SC-17 and stays separate.
  • Not a general object browser for developers: no bucket policy editing, no lifecycle-rule management, no bucket creation.
  • Not a mount of the bucket as a drive on the server. ShareCraft speaks the S3 API.
  • Not an S3 server. ShareCraft does not expose an S3-compatible endpoint for its own libraries.

Anti-goals (a failure even if it technically works).

  • A surfaced library that lets a person see an object ShareCraft's permissions say they may not.
  • Any path that writes to the bucket without going through the collaboration spine's checkpoint and conflict rule (S3 and S4 in sequencing.html). D15 forbids a second save path.
  • A surprise bill: a sync, a search index or a scan that reads a whole bucket without anyone having been told the cost.
  • A secret that appears in Git, a log, an event, an error message or a backup in readable form.

03 / The storage source

The library never talks to S3 directly. It talks to a storage source, a small Rust trait that describes what ShareCraft needs from any object store. S3 is the first implementation. Azure Blob Storage is the second (section 13). The trait is sketched here so the S3 specifics stay on one side of it.

trait StorageSource: Send + Sync {
    /// What this store can do. Probed when the source is connected and re-probed on request.
    fn capabilities(&self) -> Capabilities;
    /// Check the connection: credentials, bucket, prefix, versioning, notifications.
    async fn probe(&self) -> ProbeReport;

    /// One page of keys under a prefix. With a delimiter, folders come back as prefixes.
    async fn list(&self, prefix: &str, delimiter: Option<char>, page: Option<PageToken>) -> Result<ListPage>;
    async fn list_versions(&self, key: &str, page: Option<PageToken>) -> Result<VersionPage>;
    async fn head(&self, key: &str, version: Option<&VersionId>) -> Result<ObjectInfo>;
    async fn get(&self, key: &str, version: Option<&VersionId>, range: Option<Range>) -> Result<ByteStream>;

    /// Writes. `precondition` carries the revision the caller based its change on.
    async fn put(&self, key: &str, body: ByteStream, precondition: Precondition, checksum: Sha256) -> Result<ObjectInfo>;
    async fn copy(&self, from: &ObjectRef, to_key: &str, precondition: Precondition) -> Result<ObjectInfo>;
    async fn delete(&self, key: &str, version: Option<&VersionId>, precondition: Precondition) -> Result<DeleteOutcome>;

    /// Push-style change detection, where the store offers it.
    async fn change_feed(&self) -> Result<Option<Box<dyn ChangeFeed>>>;
}

struct Capabilities {
    versioning: Versioning,          // None | Enabled | Suspended | Native (Git) | Unknown; None is normal
    conditional_write: bool,         // If-Match / If-None-Match on put
    additional_checksums: bool,      // x-amz-checksum-sha256 or equivalent
    notifications: Vec<FeedKind>,    // SqsQueue | Webhook | EventGrid ...
    inventory: bool,
    object_lock: bool,
    archive_tiers: bool,             // objects that must be restored before reading
    real_directories: bool,          // file servers, Git, Azure hierarchical namespace; false for S3
    native_change_events: bool,      // file servers: OS notifications; Git: push webhooks
}

Capabilities are probed, not assumed. S3-compatible stores differ: some lack versioning, conditional writes, notifications or additional checksums. The library settings page shows the probe result in plain words ("This bucket has no versioning, so write-back is not offered"), and features switch themselves on and off from it. The probe never changes the bucket.

Sources without versions. A source with no versioning, or a file server, is a complete, supported case, not a degraded one. Items then have one version (the current one); history says so; and Revision is whatever the source offers to detect change: ETag for S3; size plus modified time (and a content hash once read) for a file server; the commit and blob IDs for a Git repository. The write rule in section 05 is built for the no-version case first.

04 / How the library models S3 objects

Keys become folders

S3 has no folders. A key such as reports/2026/q3/summary.pdf is one flat name. ShareCraft splits keys on / after removing the configured prefix. reports, reports/2026 and reports/2026/q3 each become a folder in the tree, and summary.pdf becomes a file in the last one. A folder exists in ShareCraft while any key lies beneath it. The surfaced tree is a projection of the listing.

  • Folder marker objects. A zero-byte object whose key ends in / (what the AWS console makes for "Create folder") is read as an explicit, possibly empty folder and is hidden as a file. When ShareCraft creates an empty folder in read-write mode it writes the same kind of marker.
  • Keys that cannot be shown. Empty segments (a//b), . or .. segments, control characters and invalid UTF-8 cannot be a ShareCraft name. They are not dropped. They are listed in an administrator report ("Not shown, and why"), with a count on the library page.
  • Names that collide in ShareCraft but not in S3. ShareCraft's names are unique among siblings regardless of case (nodes_sibling_name), and Windows cannot hold Report.pdf and report.pdf together. S3 can. The first key in key order keeps the name; the others are shown with a visible suffix (report (S3 copy 2).pdf) and flagged. The same rule serves names Windows refuses (a colon, a trailing dot, CON). DriveCraft already has a path-check and a Problems view for refused names (paths.rs, problems.rs); the server flags first so the person sees it in the browser too.
  • Depth and size. Keys can be 1,024 bytes; Windows paths cannot. Over-long paths are flagged the same way and held out of sync.

Identity

Spine rule S1 says every item has an identifier independent of its name and location. A surfaced item gets a UUID, kept in a mapping table keyed by (library, key). The mapping stays when an object is deleted, for the tombstone retention period, so a key deleted and re-created keeps its identity, its links and its ShareCraft metadata. A rename made in ShareCraft (read-write mode) is a server-side copy plus delete in S3 and moves the mapping, so the identity survives the rename. A rename made directly in S3 looks like a delete and a create. The scan treats a vanished key and a new key with the same size, ETag and modified time in the same pass as a probable move, keeps the identity, and records it for the administrator. Anything less certain is a delete and a create.

Versions

Bucket stateWhat a "version" isWhat version history shows
Versioning enabledThe S3 versionId. The current version is the latest non-delete-marker.Every S3 version, with time, size, ETag and, for those written through ShareCraft, the person who saved. A delete marker shows as a deletion. Restoring an old version copies it forward as a new version; nothing is erased.
No versioning (the expected case)The ETag together with the size and modified time. Only the current version exists.One entry, "current", with a note: this storage keeps no history. ShareCraft does not invent a history it cannot restore, and does not keep copies in its own store to fake one.

The ETag is the revision identifier that spine rule S4 needs ("this checkpoint is based on revision X"). It is not a content hash for multipart or KMS-encrypted objects, so ShareCraft uses it only to detect change, never to prove content. Content identity is a SHA-256 that ShareCraft computes when it first streams the bytes, or reads from the object when it was written with an additional SHA-256 checksum. An object ShareCraft has never read has a size, an ETag and a modified time but no SHA-256, and the interface says "not yet read" rather than showing an empty hash.

Metadata

  • From S3, read-only: content type, content disposition, storage class, last modified, size, ETag, version ID, user metadata (x-amz-meta-*) and object tags. They appear as read-only S3 properties; user metadata and tags can be shown as columns on request.
  • ShareCraft's own metadata (columns, content types, managed metadata, SC-04 to SC-06 and SC-26) is stored in ShareCraft's JSON records and PostgreSQL, keyed by the item's identity, as for any library. It is not written into the object. Writing it back as user metadata would need a copy-in-place of every object, creating a new version, costing a request each, and failing for objects over 5 GB without multipart copy. An option to write chosen fields back as object tags can be added later.
  • File type and preview come from the extension and the sniffed content, not from S3's content type alone, which is often wrong (binary/octet-stream).

Storage classes

Objects in an archive tier (Glacier Flexible Retrieval, Deep Archive) are listed but cannot be read until restored. They show as Archived: restore needed, with a "Request restore" action for people who may, after a cost note (section 12). Sync leaves them out and reports them as a notice (section 11). Instant-retrieval classes behave as normal objects.

Records kept for each source

source_changes.seq is what the DriveCraft cursor is made from (section 11). Surfaced items live in their own table, not in nodes, so a bucket of ten million objects does not bloat the content tree; tree and explorer views read both. This table split is a proposal; plan 3A to 3C code should be read again before the build plan fixes it.

05 / Read-only and read-write surfacing

A source is connected in one of two modes. A library can be moved from read-only to read-write by an administrator, after the probe says it is safe. It can be moved back at any time.

ActionRead-onlyRead-write
Browse, open, preview, download, search, share linksYesYes
Sync down with DriveCraftYes (DriveCraft marks the folder read-only; its changes are never sent up)Yes, in both directions
Upload a new fileNoConditional write, refused if the key now exists (If-None-Match: *)
Edit in a ShareCraft editorOpens read-onlyLive session; checkpoint writes a new S3 version (section 10)
Rename, moveNoServer-side copy then delete; identity kept. Not atomic, not free for large objects
DeleteNoPermanent by default; a delete marker if the bucket happens to be versioned; or the optional holding area (section 10)
Metadata and permissions held in ShareCraftYes (these live in ShareCraft)Yes

Read-only is a ShareCraft promise, backed by the credential. The administrator is advised to give a read-only library a read-only credential (s3:GetObject, s3:ListBucket, s3:GetObjectVersion). The probe tries no write; it reads the policy where it can and says "this credential appears able to write" if so. A read-only library can be made safe by IAM alone, which is the stronger statement.

Read-write requirements. A credential allowed PutObject, DeleteObject and CopyObject on the prefix and, preferably, conditional-write support. Versioning is not required. Without it an overwrite or delete cannot be undone from the storage side, so the settings page states in plain words that saves replace the file and deletes are permanent, and offers the holding area (section 10) for deletes. Without conditional writes the server does a HEAD-then-PUT, which leaves a small race window; the settings page says so, and this is the main reason to prefer the real AWS service or a conditional-write-capable store for read-write.

Every write goes through the spine. An edit, an upload from the browser, a DriveCraft upload and an editor checkpoint all arrive as "a change based on revision R". The server compares R to the current ETag or version and either writes with the matching precondition or refuses with a conflict (S4). There is no other way to write.

06 / Conflicting writes made directly in S3

Other systems write to the bucket: applications, pipelines, people with the AWS console. ShareCraft cannot stop them, and does not try. Four cases need a rule.

CaseWhat ShareCraft does
A file changes in S3 while nobody in ShareCraft has it openChange detection updates the item (new ETag, size, version). Browsers show the new version; DriveCraft receives an edit in its next delta. No conflict exists.
A file changes in S3 while a ShareCraft session is openThe session keeps going on its base revision. A banner says "This file changed in the bucket at 14:02. Your changes will be saved as a copy." At checkpoint, the conditional write is refused by S3 (precondition failed) or caught by the ETag check, and ShareCraft saves a sibling copy, name (edited by Ana 2026-11-16 14:20).ext, as a new object. Nothing already in S3 is overwritten.
A DriveCraft upload is based on an ETag S3 has since replacedThe upload is refused with a conflict (RemoteError::Conflict, as DriveCraft already handles). DriveCraft keeps the local file as a conflict copy and downloads the new remote version, as it does with SharePoint.
A file is deleted in S3 while it is open, or being syncedThe item becomes a tombstone. An open session is told the file is gone and offered "Save my copy to this folder". DriveCraft receives a delete; if the person has local unsynced changes, DriveCraft keeps the file, as it already does (left on, left_on.rs).
Two ShareCraft users edit the same fileCo-authoring, not a conflict: one session, as D22. Only the checkpoint meets S3.

The residual risk. With no conditional writes (some S3-compatible stores), a write by another system between ShareCraft's HEAD and PUT can be overwritten. With versioning on it remains recoverable as an earlier S3 version; without it the earlier bytes are lost. Either way ShareCraft records it as an event ("overwrote version X written outside ShareCraft") so an administrator can find it. The settings page names this exposure when it applies.

Echo suppression. ShareCraft's own writes come back as S3 events or appear in the next listing. Each write records the resulting ETag and version ID, so detection can recognise and ignore its own change instead of announcing it as someone else's edit.

07 / Change detection

ShareCraft must learn that the bucket changed, so browsers and DriveCraft stay current. The three mechanisms are cumulative, not alternatives. The first always runs. The others lower latency and cost for those who set them up.

MechanismHow it worksLatencyStrengthsWeaknesses

The list is paged (up to 1,000 keys per request) and resumable.Minutes (set per library; default 5 min, doubling when nothing has changed, down to 1 min on demand)Needs nothing from the customer beyond read access. Inventory (optional, large buckets)S3 Inventory writes a daily or weekly manifest (CSV, ORC or Parquet) of all objects into another bucket. Reconciliation is the safety net. Whatever delivers hints, a full or inventory-based reconciliation runs on a slower schedule and brings the table to the bucket's truth. Every item carries last_seen_seq: after a complete pass, an item not seen is a tombstone. A pass that failed part-way records nothing as deleted.

The change log. Each applied change gets a seq in source_changes and publishes an event on the spine's stream (S7) so audit, search indexing, notifications and the DriveCraft delta all read one source. If a table is rebuilt from a fresh listing, a new epoch starts and DriveCraft is told to resynchronise (RemoteError::ResyncRequired already exists for this case).

Initial scan. Connecting a large bucket starts a background import with progress shown on the library page ("1.2 million of about 4 million objects"). The library is usable while the import runs, with a "listing still in progress" notice. Folders appear as they are discovered. The listing count estimate comes from the probe or the Inventory manifest where there is one.

08 / Credentials

A source's credential is the most sensitive thing this feature holds. The rule is absolute: no secret is stored in plain text, and none is ever written to Git, an event, a log line, an error message or a backup export in readable form.

MethodUseWhat ShareCraft stores
Ambient identity (preferred)ShareCraft runs where the cloud gives it an identity: an EC2 instance profile, ECS or EKS role, or web-identity token. The AWS default credential chain is used. Cross-account access uses AssumeRole with an external ID to avoid the confused-deputy problem.Only the role ARN and external ID. No secret at all.
Access key and secretThe universal method, and the only one for most S3-compatible stores and for ShareCraft on a Windows PC or an on-premises server.The access key ID is stored as a label. The secret is stored only as ciphertext (below).
AnonymousA public bucket, read-only.Nothing.
Federated per-person access (not in the first release)Short-lived credentials per signed-in person through web-identity federation, so S3's own policy applies to them.Needs an identity provider ShareCraft does not have yet (the open item in the scope's tenancy and identity decision).

Protecting a stored secret.

  • Envelope encryption. Each secret is encrypted with AES-256-GCM under a secret key held by the server, never in PostgreSQL or Git. The database row holds the algorithm, key ID, nonce and ciphertext. Key IDs allow rotation: a new key is added, secrets are re-encrypted in the background and the old key is retired.
  • Where the secret key lives. On Windows, in a file in the installation's data folder readable only by the account the server runs as, created at first start, so no administrator step is needed (the owner's rule on per-machine admin work). Where an operating-system store is available, the key can be sealed under it (DPAPI at user scope, or a cloud key-management service); these are options, not the requirement. Decision 5 asks the owner to confirm this. The consequence to state: a backup of the database alone cannot read the secrets; a backup that also contains the key file can. The backup guidance says to keep them apart.
  • Write-only in the interface. After saving, the secret is never shown again; the form shows "set" and offers "replace". Nothing in an API response or event carries it. Redaction is tested by a standing test that scans logs and responses for planted secrets.
  • Least privilege, checked. The setup page gives a ready-made minimal IAM policy for the bucket and prefix, read-only or read-write, to copy. The probe reports a credential that can do far more than needed ("can write and delete everywhere in this account") as a warning, not a block.
  • Rotation and failure. A failed authentication marks the source Not connected, keeps the last known tree readable (stale, with a banner) and sends an alert to the library's owners. It does not retry in a loop that could lock the account.
  • Who can manage. Creating and changing a source is a site-owner action with an administrator role; the credential itself can be replaced but never read. Every change is in the event log with the person, never the value.
  • Egress and endpoints. Only HTTPS endpoints are accepted, with certificate checks on. A custom endpoint (S3-compatible store) must be explicitly entered by an administrator, and ShareCraft refuses addresses in private or link-local ranges unless an administrator allows that range, so the feature cannot be used to make the server probe its own network.

09 / Permissions mapping

ShareCraft's permissions (SC-11: sites, libraries, folders and files, inheritance with breaks, groups and roles, sharing links) apply to the surfaced tree exactly as they do to any library. The surfaced items are nodes with ids, so access can be given, inherited and broken at any folder or file, and the inheritance explorer shows where each person's access comes from.

LayerWho decidesWhat it means
What ShareCraft can reachThe S3 credential's IAM policy and the library's prefixThe outer limit. Nobody can see through ShareCraft what the credential cannot read.
Who can see and do what in the libraryShareCraft roles and inheritanceThe only layer ShareCraft users meet. Viewer, Editor, Owner and custom roles keep their meaning. An Editor in a read-only library can edit metadata held in ShareCraft but cannot change the files.
What S3 itself allowsBucket policy, ACLs, Object LockNot read by ShareCraft for authorisation. ShareCraft does not translate S3 ACLs into ShareCraft permissions.

The honest consequence. All ShareCraft users reach S3 through one service identity. ShareCraft is the only place its permissions are enforced. Someone with direct S3 access, an application with the same credential or a person using the AWS console is outside ShareCraft's permission model, and ShareCraft's audit trail does not see their reads. The library page says so. S3 server access logs or CloudTrail data events remain the record for those accesses.

Starting access. A new surfaced library starts with only its creator as owner, and everything below inherits. No access is derived from the bucket. A bulk helper maps prefixes to groups ("finance/ visible to the Finance group") by breaking inheritance at those folders; it is a convenience over ordinary SC-11 operations, and its result is visible in the inheritance explorer.

Items that appear later. A new object inherits from the folder it lands in. A new top-level prefix inherits from the library. Where a folder has its own permissions, new objects in it follow them, so an object written by another system into a restricted folder is restricted from the first moment ShareCraft sees it. The lag between the write and the next detection is a visibility gap in the other direction: the object is not yet shown.

Links. Sharing links (including anyone links) work on surfaced files. An anyone link serves bytes through ShareCraft with the link's expiry. It never exposes a pre-signed URL or the bucket name. If the object is deleted in S3, the link stops working.

Later: per-person S3 identities. With an identity provider (scope decision on tenancy and identity), ShareCraft could pass the signed-in person's identity to S3 so that S3's own policy decides too. That makes ShareCraft enforcement and S3 enforcement agree by construction. It is a different, larger design and is deliberately not in the first release.

11 / The contract DriveCraft sync needs

How DriveCraft syncs today

The sync engine (engine.rs) is written against a Remote trait (remote.rs), "so that ShareCraft can be added later as a second implementation". Microsoft Graph (graph.rs) is the only implementation. The trait asks for exactly these things:

  • delta(drive, link) returns pages of RemoteItem plus either a next_link (more pages) or a delta_link (the bookmark for next time), and can answer ResyncRequired.
  • download(drive, item, dest) returning size and hash; upload(drive, target, src, mtime) where the target is New{parent,name} or Replace{item, etag}, failing with Conflict if the etag is stale.
  • create_folder, delete(item, etag), move_item, child, children, item.
  • permissions(drive, items) and identity(), so the client can tell what the person may do (own-permission items, groups).

A RemoteItem has: id, parent_id, name, kind (file, folder, other), size, etag, ctag, hash (optional), mtime_ns, is_root, deleted, own_permissions. The client catalog (SQLite) keeps the server part apart from the per-machine part; a conflict leaves a conflict copy; a deletion held back by local changes is "left on"; refused names go to the Problems view; a per-library seed is stored in the library itself.

The SC-23 API that ShareCraft owes DriveCraft is not built: it is in Stage 4, and DriveCraft's own scope says "the ShareCraft connector waits on that API's design". Signing in to ShareCraft from DriveCraft is refused today (main.rs). So the surfaced library does not need its own sync protocol. It needs to be a library that SC-23 serves like any other.

What does not fit well, and how it is handled

  • Size. DriveCraft keeps every file whole on disk; "files on demand are not part of this", and I found no folder-selection feature in its catalog or engine. Syncing a 2 TB bucket downloads 2 TB. The contract cannot fix that. It needs folder-level selection in DriveCraft (sync this prefix only) before surfaced libraries of any size are sensible, and an advisory on the library ("about 2.1 TB; DriveCraft will copy everything you select"). A request to the DriveCraft side, not built here.
  • Cost multiplication. Many computers each pulling the same bytes would each trigger S3 egress. The cache in ShareCraft answers the second and later requests for the same object (section 12).
  • Modification times and attributes. No local permissions, ACLs or extended attributes are stored in S3. Those are not synced for any ShareCraft library either.
  • Move and rename are copy and delete in S3, so a rename of a folder of 100,000 objects is 100,000 copies and deletes. It is refused above a configured count unless the owner confirms the cost. DriveCraft's rename detection must not turn a local folder rename into that without warning; the server's refusal returns a clear message the client shows.
  • Delta from outside. A bulk change in S3 (a million objects written by a pipeline) becomes a large delta. The server paginates, and DriveCraft's existing pacing (pace.rs) applies.

Not needed from DriveCraft. It will not read the bucket, hold an S3 credential or know the library is surfaced, except for the capabilities block and unavailable reason. It must never be given a pre-signed URL unless the owner enables direct download (decision 8). If so, the URL is short-lived, one object, and the hash and scan result are still checked from ShareCraft's answer.

Worked examples (illustrative, from the rates above):

  • Polling. 5 million objects is 5,000 LIST requests per pass, about $0.025. Every 5 minutes for a month is about 8,600 passes, about $215. Every hour, about $18. Events with an hourly reconcile cost almost nothing. Polling a large bucket every five minutes is a poor default. The scheduler therefore sets the interval from the object count and a monthly request budget that the administrator sees and can change.
  • Sync. A 500 GB library synced by 30 people over the internet is 15 TB of egress, about $1,350, if every pull comes from S3. With ShareCraft's cache the first pull fetches 500 GB (about $45), and the other 29 are served from the cache. The cache must therefore be sized for the working set, and the settings page shows hit rate.
  • Full-text indexing. 200 GB of Office and PDF files, read once: about $18 of egress, plus a GET per file. The estimate is shown before it starts.

Controls. (1) A monthly request and transfer budget per source, with a warning at 80% and a pause (reads continue from cache, detection slows) at 100%, with the administrator's override. (2) Cost estimates before expensive actions: full indexing, scan the library, thumbnail the library, initial import, bulk rename. (3) A usage panel per library: requests by kind, bytes out, cache hit rate, an estimated bill for the month. (4) A suggestion, when ShareCraft's location and the bucket's region differ, to move the server or use a gateway endpoint. ShareCraft sees only its own requests; the AWS bill is the authority, and the panel says so.

15 / Open questions

  1. Is the tree really kept out of Git? Decision 1 breaks D24 for this kind. The alternative, Git records for folders and for the items that carry ShareCraft-specific data (metadata, own permissions), is possible; it keeps D24's spirit and bounds Git by what ShareCraft adds, not by bucket size. Which does the owner prefer?
  2. How big a bucket must be supported? 100,000 objects, 10 million, a billion? The scope's 100,000-file DriveCraft target belongs to the client and not to ShareCraft. The answer sets polling versus event-only, whether Inventory is required rather than optional, and table sizing.
  3. Whose AWS account pays and operates the setup? A customer who owns a bucket must create IAM policies and optionally queues. How much of that can ShareCraft script (a downloadable CloudFormation or Terraform snippet) rather than describe?
  4. Where does a typical ShareCraft run? In the same AWS region as the bucket (cheap, fast), on-premises, or on the owner's Windows PC? It changes egress cost, latency and what "ambient identity" can mean.
  5. Is a ShareCraft-side lock acceptable? Check-out over a surfaced file binds only ShareCraft and DriveCraft users. Is that enough, or should read-write surfaced libraries not offer check-out?
  6. Should DriveCraft be able to sync a surfaced library as read-only only, at first? It would remove the largest write-back risk from phase B.
  7. Which S3-compatible stores must work at launch? Cloudflare R2 is the first target (decided) and AWS S3 is the reference; MinIO is the easiest to test locally. R2 has its own gaps (for example in versioning, object tagging and event notifications, which go through Cloudflare Queues), to be confirmed against its current documentation. Each other store has quirks in listing, checksums and conditional writes, and "S3-compatible" is not a guarantee.
  8. Object Lock and compliance. Is a records declaration on a surfaced file allowed without Object Lock behind it, with the warning, or refused?
  9. The path through a firewall. A ShareCraft behind a corporate firewall cannot receive S3 event webhooks. SQS polling works from inside; webhooks need production mode's public address. Which is supported first? (This design puts SQS first.)
  10. Multi-source libraries. One library over several buckets or prefixes ("mount" prefixes as top-level folders)? The record model allows it; the interface and permissions explanation are heavier. Out of the first release unless the owner wants it.
  11. File servers: which shape first? The file share is second in order. This document assumes a Windows UNC path or a path on the ShareCraft server first; an SMB share reached from Linux needs different credential and change-detection handling.
  12. The holding area. With no versioning, should it be on by default for read-write libraries (safer, but costs storage and writes a reserved folder into a store other systems share), or off (clean, deletes permanent)?
  13. Git: protected branches. Direct commits are decided, and GitHub is first. A repository whose branch refuses direct pushes cannot be written to; should ShareCraft then fall back to a pull request, or stay read-only with a clear message? (Proposed: stay read-only with the message, and revisit.)
  14. Git: whose name is on the commit? The ShareCraft person as author, with ShareCraft as committer, is proposed. Some repositories require signed commits, which a service cannot do for a person.
  15. Verification debt. Nothing here has been run against a real bucket. The AWS price figures, S3's conditional-write coverage in compatible stores, SDK licence and feature coverage in Rust, and DriveCraft's handling of a missing hash all need checking before the build plan is fixed.

16 / Approaches considered

Three ways to build "S3 in a ShareCraft library" were weighed. The owner's request, taken with the existing code, points to the second.

ApproachWhat it isForAgainst
1. ImportCopy bucket contents into an ordinary ShareCraft library (a migration, SC-17), perhaps repeated.Simplest. Reuses everything. No special permissions model.Not what was asked: a second copy to pay for, always stale, and nothing flows back. It is the right answer for customers who want to leave S3, and stays available.
2. Surface (recommended)The bucket stays the authority. ShareCraft keeps a projection of the tree, a bounded cache, and its own metadata and permissions, and writes back through the spine.Matches "surface them as files... with the ability to Sync". One copy of the data. Azure fits behind the same trait.New change detection, conflict handling and cost controls. Retention is weaker than for ordinary libraries (section 10).
3. GatewayExpose ShareCraft as an S3 or WebDAV front end over the bucket, or let DriveCraft talk to S3 directly with its own credentials.Least work in ShareCraft. DriveCraft could sync any bucket on its own.Bypasses ShareCraft permissions, scans, links and audit; puts S3 credentials on every computer; breaks the rule that DriveCraft uses only the SC-23 API and gets no unrestricted credentials.

The decisions that turn approach 2 into a build plan are listed in section 02. No product code is written until the owner accepts the design.
