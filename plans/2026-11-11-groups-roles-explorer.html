Groups, roles and the inheritance explorer: implementation plan

ShareCraft · Stage 2, platform plan 2A · Written 11 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: access can be given to groups as well as people; roles are named sets of permissions that administrators can define; every site has Owners, Members and Visitors groups; an inheritance explorer shows every place where inheritance is broken, with its path, who has access and why, and what restoring it would change; and a library of more than 100,000 files is shown to behave: breaking and restoring inheritance at library, folder and file level stays fast and correct.

Architecture: an assignment gives a principal (a person or a group) a role on a scope. A role is a set of permissions from a fixed list. A person's access on a node is the union of the permissions of every assignment on its source scope that names them or a group they belong to. Groups, roles and assignments are kept in PostgreSQL only, like all permissions (D24). The explorer reads only scopes (nodes with their own permissions), never the files between them, so its cost follows the number of breaks, not the size of the library. The Git tree records move into 256 sub-folders so that a change to one node no longer rewrites a folder of 100,000 entries.

Tech stack: the existing workspace: axum, sqlx and PostgreSQL (records), gix (revisions), plain HTML and JavaScript in web/. No new dependencies.

Spec: scope.html SC-11 (groups, configurable permission roles, delegated administration, inheritance at every level, the inheritance explorer, no size threshold), D10, D18, D23, D24; acceptance tests A04, A14, A15. Plan 1 (content tree and inherited permissions) is the base. Owner decisions of 11 November 2026: plan 2 is split into 2A (this plan) and 2B (sharing links and access requests); roles are permission sets that administrators define, with Viewer, Editor and Owner built in; anyone-links are built in 2B, off by default.

Not in this plan

  • Sharing links, anyone-links, expiry, domain restrictions and access requests (plan 2B).
  • Service identities and application credentials (SC-14, with the API work). Guests and single sign-on (after the identity provider decision).
  • Groups inside groups. Audience targeting. Search.

Global constraints

  • Permissions live in PostgreSQL only (D24). Roles, groups, memberships and assignments are database rows; every change records an event. Nothing in this plan writes permissions to Git.
  • The permission list is fixed: view (list, open, download, join a session read-only), add (create folders and files, upload, move into), edit (change content, rename, move out, take the editing seat), delete, manage_access (see and change access, break and restore inheritance, use the explorer), manage_site (create and rename libraries, rename the site, manage the site's groups). Every permission except view includes view.
  • Built-in roles have fixed ids and cannot be changed or deleted: viewer {view}; editor {view, add, edit, delete}; owner {all six}. Custom roles have generated ids, a unique name (ignoring case, 1–60 characters) and at least view. Only administrators create, change or delete roles. A role in use cannot be deleted (role_in_use).
  • Access is a union. A person's permissions on a node are the union over every assignment on its source scope naming them or a group they are a member of. An enabled administrator has every permission everywhere; a disabled account has none (plan 1's rules stand).
  • Nobody raises their own access. A person may assign a role, or add someone to a group, only if that role's (or that group's role's) permissions on the scope are a subset of their own there. Administrators are exempt. Refused with beyond_your_access.
  • One locking order: the node chain top-down (plan 1), then the groups involved in one pass ordered by id, then the roles involved ordered by id; each row once, in the strongest mode the transaction needs (FOR UPDATE for what it writes, FOR SHARE for what it judges by). An access decision made under locks is worked out again after all of them are held. A role change takes the role row FOR UPDATE; a membership change takes the group row FOR UPDATE.
  • Every scope keeps a manager: at least one assignment whose role includes manage_access. An administrator can always repair a scope whose managing group has been emptied; this is stated, not prevented.
  • Site groups: every site, deleted or not, has three groups, shown as "Site Owners", "Site Members" and "Site Visitors", assigned Owner, Editor and Viewer on the site. A site group stores its site and purpose, not a name: its name is built from the site's current name when read, so it follows renames and never collides. Organisation groups (no site) have stored names, unique ignoring case. People with manage_site on a site manage its groups' members; administrators manage every group and create organisation groups (groups with no site).
  • Revocation is immediate (S5). A change of membership, of an assignment, or of a role's permissions reaches every open session it affects before the request answers, as in plan 1.
  • Cost follows breaks, not files (D10, A14). Breaking and restoring inheritance, the explorer, its counts and its export read and write only scopes and their assignments.
  • Names and visibility: a person who manages access somewhere sees organisation groups and the groups of sites they can reach (never a site name they could not otherwise see); a group's member list only to people who manage that group and administrators. The explorer's person filter matches direct assignments and memberships of groups whose members the viewer may see. The explorer shows only nodes the viewer has manage_access on, and counts only what it shows.
  • Never print .env, database addresses or passwords. Documents are HTML with colour banding on tables and long lists.

Review focus

  1. A person in two groups with different roles on the same scope has the union of both; removed from one group, they keep the other's permissions, in an open session too. (Task 2, union_over_groups; Task 4, leaving_one_group_keeps_the_other.)
  2. Changing a custom role's permissions changes the access of everyone holding it, everywhere, including open sessions (an editor whose role loses edit becomes read-only at once). (Task 4, role_change_reaches_open_sessions.)
  3. The explorer never shows a node, name or count outside the viewer's manage_access scope: an owner of one folder sees only that folder's subtree. (Task 3, explorer_stays_inside_the_viewers_scope.)
  4. Upgrading from plan 1: site-level grants become memberships of the site's groups; every other grant stays a direct assignment with the same role; nobody gains or loses access. (Task 2, upgrade_keeps_everyones_access.)
  5. In a library of 100,000 files, breaking inheritance on the library while someone has a file open in it: their access is correct before, during and after, and nothing is processed per file. (Task 5, large_library_break_while_open.)

Task 3: the inheritance explorer

Files: create crates/records/src/explorer.rs, crates/records/tests/explorer.rs, crates/records/migrations/0006_indexes.sql (an index nodes (id) where unique_scope and deleted_at is null for finding breaks, and the children index of Task 5, so the explorer never scans files).

Interfaces produced:

  • records::Break { node: Crumb, path: Vec<Crumb>, kind: NodeKind, assignments: Vec<AssignmentView>, inherited_from: Option<Crumb> /* the scope it would inherit from */, broken_by: Option<(UserRef, OffsetDateTime)>, changed_by: Option<(UserRef, OffsetDateTime)>, breaks_below: i64 }; AssignmentView { principal: PrincipalView /* user or group with name */, role: RoleRef, perms: Perms }. broken_by is the latest inheritance.broken event on the node; changed_by the latest access event on it.
  • records::ExplorerFilter { principal: Option<Principal>, kinds: Vec<NodeKind> } (the place is the root).
  • Db::breaks(&self, viewer: UserId, root: NodeId, filter: &ExplorerFilter, after: Option<&str>, limit: u32) -> Result<Option<(Vec<Break>, Option<String>)>, DbError>: every scope strictly below root (and root itself when it is a scope) that the viewer has manage_access on, in path order, paged. None when the viewer lacks manage_access on root. A principal filter keeps breaks with an assignment to that principal (for a person: to them directly or to a group whose members the viewer may see).
  • Db::break_counts(&self, viewer, parent: NodeId) -> Result<Vec<(NodeId, i64)>, DbError>: for each child of parent the number of breaks at or below it, for the explorer's tree; built from the list of scopes and their ancestors, not by walking files.
  • records::RestorePreview { node: Crumb, inherit_from: Crumb, people: Vec<(UserRef, Perms /* before */, Perms /* after */)>, unchanged_breaks_below: i64 }; Db::restore_preview(&self, viewer, node) -> Result<RestorePreview, AccessError>: for every person named on either scope, directly or through a group, their permissions now and after restoring, listing only those that change; descendants that inherit follow; breaks below are listed as unaffected.
  • records::breaks_csv(breaks: &[Break]) -> String: one row per assignment (path, kind, principal kind, principal, role, permissions, broken by, broken at), RFC 4180 quoting, cells starting with = + - @ prefixed with an apostrophe.
