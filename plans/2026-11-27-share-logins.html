Stored share logins, and secrets from an outside provider

Implementation plan, 27 November 2026. Branch share-logins in H:\Source\repos\ThineCraft\ShareCraft-logins, cut from main 2472d85. Build target J:\cargo-target\sharecraft-logins. It follows File Share Phase 1 (2026-11-17-file-share-surfacing.html; BUILDING section 36; scope D72 to D74). Nothing below is built yet.

What this adds. An administrator can store a login (user name and password) for a file server. ShareCraft then signs in to that server with it before reading any approved folder there. Today the server can read a share only as the account it runs under (D73).

Why it starts with secrets. The owner plans to run several ShareCraft front ends later. They must all read the same stored logins, tokens and keys from a cloud key vault. Today every secret is sealed with secret.key in one server's data folder, which a second front end cannot open. The owner asked that the vault not be built into the ShareCraft executable (27 November 2026). So secrets move behind a small documented HTTPS contract. Any vault can sit behind it as a separate adapter service. Today's sealed store stays built in as the default for a single server.

Rulings already made

  • One login per server, not per folder. Windows lets one account hold only one set of credentials per server at a time; a second set fails with error 1219. So a login belongs to a server (\\host), and it covers every approved folder on that server. (Claude's recommendation, adopted 27 November 2026, when the owner answered with the provider instruction instead.)
  • Signing in uses the Windows API, not net use. ShareCraft calls WNetAddConnection2W, the call net use makes itself. There is no child process, the password is never on a command line, and no drive letter is mapped. The connection is temporary (CONNECT_TEMPORARY) and is not restored at the next sign-in. This needs windows-sys as a direct dependency of crates/server, for Windows targets only. The crate is already in Cargo.lock through other crates.
  • Linux keeps the administrator's mounts. On Linux the mount's own credentials decide, as before. A login can be stored only for a UNC root, which is usable only on Windows. A Linux server refuses a login with 422 logins_windows_only.
  • Secrets come from an outside provider over HTTPS (owner's choice, 27 November 2026). ShareCraft knows only the contract below. A vault adapter, such as one for Azure Key Vault, is a separate service and is not part of this plan. Without a configured provider, the built-in sealed store is used.
  • Existing secrets stay where they are. Each secrets row records which store holds it. Old rows stay local and keep working. New secrets go to the configured provider. Moving old secrets to the provider is not in this plan; a later command can do it.
  • A login is tried before it is stored. The PUT signs in with the new login first. If Windows refuses, nothing is stored and the answer says why.
  • Removing the last approved folder on a server removes its login, in the same transaction as the settings write. Its secret is forgotten.

Global constraints

  • No password, token or key ever appears in a log line, an error message, an API answer, an audit event or a test's printed output. Secret's Debug and Display stay [hidden].
  • The provider contract (verbatim): 
    PUT    {base}/v1/secrets/{name}   body {"value":"<base64>"}   → 204
GET    {base}/v1/secrets/{name}                                → 200 {"value":"<base64>"} | 404
DELETE {base}/v1/secrets/{name}                                → 204 | 404 (both mean gone)
Authorization: Bearer <token>      Content-Type: application/json
name = "sharecraft-" + the secret's uuid as 32 lower-case hex digits (matches ^sharecraft-[0-9a-f]{32}$)
  • Configuration: SHARECRAFT_SECRET_PROVIDER is the base URL. It must be https://, or http:// to a loopback address only. SHARECRAFT_SECRET_PROVIDER_TOKEN_FILE is the path of a file holding the bearer token. The token is not an environment variable, so it stays out of environment dumps. A URL without a token file, or a token file without a URL, stops the server at start with a plain sentence.
  • Provider requests time out after 10 seconds. A failure is SecretError::Unavailable. The API answers 503 secret_store_unavailable, and a library shows "The secret store could not be reached."
  • Opened values are cached in memory for 60 seconds, keyed by secret id. A put or forget made by this process drops that entry. Other front ends see a change within 60 seconds.
  • Share login user names are 1 to 256 characters, with no control characters and no /. Passwords are 1 to 256 bytes with no NUL.
  • Migration number 0029, after main's 0028_live_checkpoint_stamp.sql.
  • Decision numbers: scope D75 onwards (D74 is the last used).
  • Pages: they pass at 375 px and in dark mode, use the existing settings-page styles, and band long lists.
  • Commits end with Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>. Merging and pushing wait for the owner.

Review focus

  • The provider is down during a sync or a webhook. The library shows a plain error and retries. The webhook answers 503, not 404, so GitHub redelivers. Nothing is deleted. Test in Task 2.
  • Two front ends. One front end stores a login and another reads it through the provider. Test in Task 2: two SecretStores share one fake provider; a put on one is read on the other after its cache expires.
  • The server already holds a connection to the host with other credentials (error 1219), for example a drive the service account mapped. The answer is 409 login_conflict, with a sentence naming the server. Test in Task 4 with the fake connector.
  • The password is changed on the file server, so the stored login now fails. The library shows "The stored login for \\host was refused", and a new login from the settings page fixes it without a restart. Test in Task 4.
  • A site is purged while its secrets live in the provider. The secrets are deleted from the provider by the sweep, not left behind. Test in Task 2.

What the code looks like today (verified 27 November 2026)

  • AppState::secrets() returns the SecretBox (lib.rs:230). It is opened from data_dir at start (lib.rs:177).
  • Secrets are written by store_secret and forget_secret in api/sources.rs:202-230, which call seal, then db.put_secret(&SealedRow) and db.delete_secret.
  • Secrets are read in three places:
    • source_sync::token_of (source_sync.rs:2042), for the GitHub token. S3 also uses it for its keys (s3.rs:803).
    • webhooks.rs:107-122, for the webhook secret.
    • api/sources.rs:1894.
    Each one calls db.get_secret, builds a Sealed and calls unseal with a context such as token_context(library).
  • sites.rs:852-900 deletes a purged site's secrets rows in its own SQL transaction.
  • Approved roots are the SHARE_ROOTS setting, a JSON list of strings. They are changed by change_shares (api/settings.rs) under lock_share_connections. shares_out answers roots, the limits and runs_as. The page is web/sharing.js (around line 428).
  • reqwest 0.13 with native TLS is already a dependency of the server. xtask already has fake_icap.rs as a model for the fake provider.

  add column forgotten_at timestamptz,

Produces:

pub struct SecretProvider { /* base Url, token: Secret, reqwest::Client (10 s timeout) */ }
impl SecretProvider {
    pub fn from_env() -> Result<Option<SecretProvider>, String>;   // Err: a sentence for start-up
    pub async fn put(&self, name: &str, value: &[u8]) -> Result<(), SecretError>;
    pub async fn get(&self, name: &str) -> Result<Option<Vec<u8>>, SecretError>;
    pub async fn delete(&self, name: &str) -> Result<(), SecretError>;      // 404 is Ok
}
pub fn provider_name(id: SecretId) -> String;   // "sharecraft-" + 32 lower-case hex
impl SecretStore { pub async fn sweep_forgotten(&self, db: &Db) -> usize; }

Behaviour:

  • put with a provider configured works in this order:
    1. Insert a row with provider='external' and no ciphertext, to get its id.
    2. Put the value to the provider under that id's name.
    3. If the provider put fails, delete the row and return Unavailable.
    The context is not used for outside values; the vault protects them.
  • get follows the row's own provider. An external row with no provider configured is Unavailable("this server has no secret provider configured").
  • forget deletes a local row at once, as today, and sets forgotten_at on an external row. sweep_forgotten, run every minute by the existing worker loop, deletes each forgotten value at the provider and then its row. A failed delete is retried at the next sweep.
  • sites.rs purge: in its transaction it deletes local rows and marks external rows forgotten_at = now().
  • Cache: 60 seconds per id, dropped by this process's put and forget.
  • cargo xtask fake-secret-provider --port <n> --token-file <path> serves the contract from memory on 127.0.0.1 only. It writes a random token to the file when the file does not exist. Requests with the wrong token answer 401.

pub enum LoginFailure { Refused, Conflict, Unreachable, Other(u32) }
pub trait ShareConnector: Send + Sync {
    fn connect(&self, remote: &str, username: &str, password: &Secret) -> Result<(), LoginFailure>; // remote = \\host\share
    fn disconnect(&self, remote: &str);
}
pub struct WNetConnector;   // cfg(windows)
pub struct NoConnector;     // elsewhere: connect is Other(0)
pub struct ShareLogins { /* connector, connected: Mutex<HashMap<String /*remote*/, SecretId>> */ }
impl ShareLogins {
    pub async fn ensure(&self, state: &AppState, root: &SharePath) -> Result<(), LoginFailure>; // no login: Ok
    pub fn invalidate(&self, remote: &str);
    pub fn forget_server(&self, server: &str);   // disconnect every remote of the server
    pub fn set_connector_for_tests(&self, c: Arc<dyn ShareConnector>);
}
impl AppState { pub fn share_logins(&self) -> &ShareLogins; }

Behaviour:

  • WNetConnector::connect calls WNetAddConnection2W with NETRESOURCEW { dwType: RESOURCETYPE_DISK, lpLocalName: null, lpRemoteName: remote } and the flag CONNECT_TEMPORARY. The UTF-16 password buffer is overwritten with zeros after the call. Error codes map as follows:
    • 1326, 5 and 86 → Refused
    • 1219 → Conflict
    • 53, 67 and 1203 → Unreachable
    • anything else → Other
    disconnect calls WNetCancelConnection2W(remote, 0, TRUE).
  • ensure works in this order:
    1. The remote is \\host\share, the first two segments of the root.
    2. If the server has no login, return Ok.
    3. If the remote is already connected with the current secret id, return Ok.
    4. Otherwise get the password through SecretStore, which is how front ends share logins, connect in spawn_blocking, and remember the remote.
  • share.rs: listing, stat and open of a root call ensure first. When one of them fails with access denied and the server has a login, it calls invalidate and ensure again, then retries once. A Refused sets the library's error to "The stored login for \\host was refused. An administrator can set it again under Settings › File shares." Conflict and Unreachable get their own plain sentences.
  • The settings PUT runs in this order:
    1. forget_server.
    2. Connect to one approved root's remote on that server with the new login.
    3. If that fails, answer 422 login_refused, 409 login_conflict or 503 server_unreachable, and store nothing.
    4. If it succeeds, store the login, then wake that server's libraries.
    The DELETE calls forget_server.
