Rulings already made

  • Structure changes are synchronous. Rename, move, delete, restore and copy inside a bucket run in the request, under the library's source lock, bucket first and tree second, the way slice 1's create_folder does. They do not go through source_writes. Cost if wrong: a 1,000-object folder holds the request for a minute or two; a queue can replace it later.
  • At most 1,000 objects in one step (MOVE_MAX_OBJECTS). A folder holding more is refused before anything is changed, with the count. Folder marker objects count.
  • Copies before deletes. Every move and hold copies every object first. A failed copy deletes the copies it already made and changes nothing else. A failed delete after all copies succeeded still finishes the tree change: the originals left behind are reported as "left behind" and come back as new files at the next listing. Nothing is ever lost; at worst something is duplicated.
  • Never move or hold content that changed outside. Before each file is copied, a HEAD checks it against the tag ShareCraft recorded, and the copy carries x-amz-copy-source-if-match on that ETag. A mismatch refuses the whole step (WriteError::Changed) and wakes a listing.
  • Files over 5 GiB. CopyObject stops at 5 GiB, and slice 2 does not build part-by-part copy. Such objects cannot be renamed, moved, copied or deleted from ShareCraft (source_too_large_to_move). Uploads to S3 are capped at 5 GiB for the same reason, so everything ShareCraft writes can be moved.
  • Busy files. A file with a pending write (saving or failed), or a folder with such a file anywhere inside it, cannot be renamed, moved, deleted or copied from (source_item_saving). The person waits, or discards the failed save. Repathing queued writes is not built.
  • Names. A name taken ignoring case is refused (name_taken), not numbered, for rename, move and copy. Slice 1 does the same for new folders. Restore is the exception: it takes a numbered name, as the ordinary bin does.
  • The holding folder.
    • Deleted content goes to <prefix>.sharecraft-bin/<YYYY-MM-DD>/<bin entry id>/<library-relative path>, using the UTC date of the delete.
    • The bin entry keeps its ordinary rows, and a new source_held row names the held root.
    • Purge and the 93-day purge delete the held objects first. If the library is read-only by then, nothing is written: the entry is purged, the objects stay, and an event says so.
    • Disconnecting a library drops its source_held rows and leaves the objects.
  • The holding sweep. It runs once a day for each read-and-write S3 library. It deletes only objects under <prefix>.sharecraft-bin/ whose date folder is more than 94 days old and whose entry id no source_held row names. It never deletes anything else.
  • Copy between libraries goes through ShareCraft:
    • Out of S3, it reads the bytes (external::materialise) and makes ordinary files, which count against the destination site's quota.
    • Into a writable S3 library, it creates the nodes and stages one write per file, so the scan gate and the 30-second worker apply.
    • From one S3 library to another, it does both.
    Moving between libraries stays refused.
  • Multipart.
    • Above S3::single_put_max() (512 MiB), the worker writes in 64 MiB parts (settable for tests), each read from the staged file at an offset.
    • Each part is signed with its own SHA-256, and the condition goes on the completion.
    • A source_multipart row is written before the upload starts and removed when the upload completes or is aborted. Any failure after the start aborts.
    • The sweep aborts rows older than a day, which only a crash leaves behind. There is no bucket listing of uploads.
  • The upload limit for an S3 library becomes min(5 GiB, config.max_file_bytes, cache_max_bytes / 2).
  • Still refused in S3 libraries (409 source_action_unavailable, with a reworded message): new blank file, new from template, and moving between libraries.
  • Restore and Purge in a read-only or blocked library. Restore is refused (source_read_only or source_write_blocked). Purge goes ahead and leaves the held objects, as in the holding-folder rule above.
  • Requests are counted by the existing meter (class Write; copies count zero bytes, parts count their bytes). Nothing caps them, as in slice 1.
  • Editor saves flush when the room empties, not 60 seconds later when the file session ends.

Rules

  • move_source_items is one transaction. It rewrites repository_path and path for the row equal to from, and for every row whose value starts with from when from ends with / (a folder), replacing that leading part with to. It answers the number of rows changed. Both unique constraints must hold at commit; a target already taken answers DbError and changes nothing. A row whose path differs from its repository_path (a case-collision suffix) keeps its suffix part.
  • writes_below counts source_writes rows of the library whose path equals repository_path, or starts with it when it ends with /.
  • defer_held sets retry_at. held answers the row whatever retry_at holds; callers decide.
  • stale_multiparts answers rows started before before, oldest first.
  • Switching a library to read-only (set_source_mode) and disconnecting it answer WritesPending while source_multipart rows exist, just as for source_writes. source_held rows do not block either.
  • Purging a node (tree.rs) or a site (sites.rs) deletes source_held rows naming those nodes, and source_multipart rows naming them, in the same transaction.

Rules

  • send_once takes a query (&[(&str, &str)]), signed as reads sign theirs. Writes are still sent once and never retried.
  • copy:
    • It sends PUT to_key with x-amz-copy-source: /<bucket>/<URI-encoded from_key> and x-amz-copy-source-if-match: from_etag, plus If-None-Match: * or If-Match from cond.
    • A 200 whose body is <Error> is a failure, mapped by its code.
    • Above COPY_MAX, it answers Unsupported before sending.
    • After it succeeds, it HEADs to_key and answers that.
  • start_multipart sends POST ?uploads with x-amz-meta-sharecraft-sha256 set to the whole file's hash, so a lost completion answer is recognised as in slice 1.
  • put_part streams len bytes from offset of path in 64 KiB pieces. It signs body.sha256 and refuses a short file (Other). A new Payload constructor takes the offset and length. Numbers run from 1 to 10,000.
  • complete_multipart sends POST ?uploadId= with the XML body (signed with its real hash) and the condition. A 200 with <Error> is a failure. After it succeeds, it HEADs the key and answers that.
  • abort_multipart sends DELETE ?uploadId=. A 404 (NoSuchUpload) counts as done.
  • mapped: NoSuchUpload maps to NotFound; EntityTooSmall, InvalidPart and InvalidPartOrder map to Other.
  • Counting: every call counts as class Write. Parts count their bytes up; copies count none.
  • The quiet 404. failure() logs nothing for a 404 answer to HEAD or DELETE. Every other failure still logs S3 answered <status> <code>.
  • The fake gains:
    • CopyObject, honouring x-amz-copy-source-if-match, If-None-Match and If-Match, and keeping the source's x-amz-meta-sharecraft-sha256;
    • Create, UploadPart (checking each part's hash), Complete (honouring the conditions; every part except the last must be at least 5 MiB, unless the test lowers that) and Abort;
    • open_multiparts() -> Vec<(String /*key*/, String /*upload id*/)>;
    • faults error_in_200_next() (the next copy or completion answers 200 with an <Error> body), fail_part(n) and min_part_bytes(u64);
    • new kinds in writes(): ("COPY", to, cond), ("PART", key, n), ("COMPLETE", key, cond) and ("ABORT", key, "").
    A PUT carrying x-amz-copy-source is never stored as an ordinary PUT.

Rules

  • Paths and keys. Paths are library-relative; a folder path ends with /. Keys are built with object_key, except holding keys, which are built by hand from the prefix and the root. A holding key over 1,024 bytes answers Failed before anything is done.
  • Which objects a folder step covers. The step lists every key under the folder first (list_page with that prefix, all pages), including its marker. More than MOVE_MAX_OBJECTS answers TooMany(count) before any write. Any object larger than COPY_MAX answers TooLargeToMove before any write.
  • Checking against the recorded tags. Each file that known lists is checked: a HEAD whose tag_of differs from the recorded tag answers Changed before any write. For a folder, keys the listing finds that known does not list are also Changed, because they appeared outside.

    1. All copies, with x-amz-copy-source-if-match.
    2. If any copy fails: delete the copies already made and answer the mapped error; a 412 on the source answers Changed.
    3. Then all deletes of the sources, carrying on past failures. left_behind counts the failed ones.
    seen holds each destination's HEAD from the copy.

    • its second segment parses as a date before older_than;
