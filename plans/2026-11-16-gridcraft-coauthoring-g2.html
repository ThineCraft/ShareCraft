GridCraft live co-authoring, plan G2: the shared library and the opaque-entry room: implementation plan

ShareCraft · Stage 2, editor track · Written 16 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: build the two halves of live co-authoring that know nothing about spreadsheets:

  • the shared collaboration library, a Rust crate that each editor fork builds in. It joins a session, sends a person's changes, resends them after a dropped connection, sends the heartbeat every minute, keeps the agreed and shown states, goes back and re-runs waiting changes, and makes lasting identities;
  • the opaque-entry room on the server. It puts every change in one order, stamps it, keeps it in PostgreSQL before passing it on, never looks inside it, ends a person's place after three missed heartbeats, ends the session when the last person has gone, and applies the cancelling rule.
Everything is tested with a small stand-in document, so no GridCraft code is needed.

Why now: G2 does not depend on G1's results (see the G1 plan's road table), so it can be built while the owner decides on G1's "go with conditions". G3 (GridCraft) and G5 (the bridge) both build on it.

Architecture:

  • A new crate, crates/collab-live, holds the library. It does no input or output of its own: the host hands it each frame received and the current time in milliseconds, and it returns the frames to send and what happened. So the same code serves the browser build and the desktop build, and every rule can be tested without a network.
  • The wire messages go in a new module of the existing protocol crate, protocol::live, beside the text and file messages.
  • The server gets a third kind of room, the live room (crates/server/src/live_room.rs), reached through the existing /ws/docs/{doc_id} address for documents whose editor is listed in a new setting that is empty by default. The server depends on protocol only. It uses collab-live only in its tests.
  • The log is kept in four new PostgreSQL tables, added by migration 0018_live_log.sql, through a new module crates/records/src/live.rs.
  • The text room (room.rs) and the file session (file_room.rs) do not change (C15, C17).

Tech stack: the ShareCraft Rust workspace (edition 2024); serde, serde_json, thiserror and uuid as already used; proptest 1.12.0 for property tests (already a test dependency of collab-text); sqlx and PostgreSQL through records; tokio with paused time for timing tests. No new runtime dependency.

Proposals in this plan for the owner to check

The spec settles the design. These are the choices this plan makes where it does not.

  1. Names and places. The library is the crate collab-live; its messages are in protocol::live. The server never depends on the library (only its tests do), so no editor-facing code is built into the server (S6).
  2. The library does no input or output. The host passes in frames and the time; the library returns frames and events. This is how the existing text client is built (web-client's ClientInner) and lets one library serve the browser and the desktop.
  3. A change's content is text (UTF-8 inside a JSON string), at most 262,144 bytes. GridCraft's commands are already JSON. The server stores it as bytes and never reads it.
  4. The format version is a short name such as gridcraft/1: 1 to 64 characters from a-z 0-9 . _ / -. The live protocol has its own number, 1. A session takes the format of its kept entries, or, when none are kept, of its first joiner.
  5. Log positions never restart. They continue for the life of the document, across sessions and server restarts. The text room restarts them for each room lifetime. Continuing them lets a returning client's "position last seen" mean the same thing later (G4).
  6. Participant numbers are never reused within a document, so lasting identities (participant number plus a counter) are unique for the whole document, not only one session. This makes G4's returning clients simpler.
  7. Each change is numbered by its sender: the client id plus a local number from 1. The server takes them strictly in order. A repeat is dropped silently. A refusal is final and uses up its number, so the sender's later changes keep their order.
  8. The server stamps each change with its own clock time in milliseconds and a random 32-bit starting point for random numbers. 32 bits keeps the number exact in JavaScript.
  9. Rate limit: the room accepts at most 30 changes a second from one client, with bursts up to 120; beyond that a change is refused. The library paces itself to 20 a second, so a working editor never meets the limit.
  10. A dropped connection keeps the person's place. Only a "leave" message (the page closing) or the expiry ends it. The heartbeat carries one number, the last log position the client applied; it is still not written to the log.
  11. A server restart continues the session. Everyone who held a place gets a fresh three minutes from the moment the room loads again, because the time the server was down is not their fault.
  12. A database failure ends the room without a message. Clients reconnect and resend; nothing is stored twice, because repeats are dropped.
  13. The cancelling rule in detail.
    • The "editing clients in the session when the entry was sent" are those holding a place with editing rights when the server ordered it. They are stored with the entry.
    • "Moved past it" means any message from that client stating it has applied the entry's position or later (a heartbeat or a change).
    • Reports are kept in memory only. A client re-reports on every join until it hears the verdict.
    • The cancellation is a log entry of its own. Clients that applied the cancelled entry load the base again and replay the log without it.
    • A client that reported an entry that stands is told "this device cannot open the document as it now is" and loses its place.
  14. Confirming your own change normally costs nothing. When nothing else arrived in between, the library does not go back and re-run; it trusts what is shown, up to 64 confirmed changes. It goes back only when another person's change arrives, when 64 have built up, or when the editor says the change read the clock or a random number (its server stamp may differ from the time used to show it).
  15. "Wait for the server" is chosen per change by the fork (C13). The library does not decide which commands are heavy.
  16. Identity tables: an identity is two 32-bit numbers (participant, counter). Participant 0 names the rows that were in the base document, so an untouched sheet is one run. Deleted identities are remembered as runs, with the position they were at and the identity just above them.
  17. How the room is reached. Same address as today; the server picks the live room for documents whose editor is in the new setting Config.live_editors, empty by default. No real document uses the live room until G5 turns it on for GridCraft.
  18. Left out of G2:
    • the limit on editing participants (exclusive check-out in the live room), until a one-seat editor moves to it;
    • large content beside the log, the unsaved-log limit and agreement fingerprints, which go to G4 with checkpoints;
    • the personal undo lists, which go to G3 with GridCraft's undo.
  19. Retention: entries are removed by an hourly sweep 30 days after a verified revision covers them (C18, C22). Nothing marks them covered until G4, so in G2 every entry is kept. Each document's head position is kept for ever (one row), so positions never go back. Purging a document from the bin deletes its log.
  20. The stand-in document is a list of lines, each with a lasting identity. It has five commands (insert before a line, delete, set text, write the stamp, crash on a named device), so it exercises order, a change that does nothing, the stamps and both kinds of crash.
  21. New event kinds (S7):
    • live.session_started
    • live.session_ended
    • live.client_expired
    • live.client_returned
    • live.entry_cancelled
    • live.entry_failed_on_device
    Their details are positions and counts only, never content.

Global constraints

  • Exact values:
    • heartbeat every 60,000 ms; expiry after 3 missed heartbeats, that is 180,000 ms without any message (C21);
    • any message from a client counts as a sign of life;
    • the session ends when the last place holder has left or expired; the 60-second grace rule does not apply to live rooms;
    • entries are kept until a verified revision covers them, then for 30 days (C18, C22);
    • a change's content is at most 262,144 bytes; one WebSocket message stays at most 1 MiB (ws.rs);
    • the live protocol number is 1;
    • a format name is 1 to 64 characters from a-z 0-9 . _ / -;
    • the server allows 30 changes a second per client, bursts up to 120; the library sends at most 20 a second;
    • the library folds at most 64 confirmed changes before going back.
  • The server never reads a change's content (S6, C1). No server code parses, inspects or changes the payload. It is stored and sent byte for byte.
  • Entries are written to PostgreSQL before they are sent to anyone (section 05).
  • Applying a received entry reads nothing that belongs to one person; the library hands the editor only the entry, its server stamp and its sender's participant number (section 03).
  • No computed values cross the wire or are compared by the server; cross-platform agreement uses entered content only (proofs report, section 10).
  • The library depends only on collab-core, protocol, serde, serde_json and thiserror; MIT or Apache 2.0, no copyleft (section 10). It has no clocks, threads, sockets or randomness of its own, and builds for wasm32-unknown-unknown: add collab-live to WASM_CRATES in xtask/src/main.rs.
  • Workspace lints: no unwrap, expect, panic or slice indexing outside tests; unsafe is forbidden.
  • Migration number: 0018 remains the live-log migration; the GitHub source schema follows it in migration 0019.
  • Migrations keep LF line endings and are never edited once applied (BUILDING.html section 02). The new one is crates/records/migrations/0018_live_log.sql.
  • Checks: every task ends with cargo xtask check passing. Database tests run through cargo xtask test (it loads TEST_DATABASE_URL); a database test is never skipped.
  • Commits follow the repository's style (feat:, test:, docs:, fix:) and end with Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>. Nothing is pushed without the owner's go-ahead.

Review focus

The conditions most likely to hurt a person that the happy-path tests would not catch. Each has a named test in the task that owns it.

  1. A hostile or malformed entry. A frame that is not JSON closes only that connection. A payload that is not valid for the editor, or that looks like a server message, is stored and relayed byte for byte and does nothing in every editor alike. Over-long content, a wrong format, a position ahead of the log, a number out of order and a viewer's change are each refused, and the room carries on for everyone else. (Task 8, hostile_entries_are_refused_and_room_carries_on; Task 11, malformed_payload_is_relayed_verbatim_and_does_nothing; Task 3, malformed_payload_has_no_effect.)
  2. A reconnect that resends. A client that drops after sending, possibly after the server stored its change, reconnects, catches up and resends. Each change is in the log exactly once, in the sender's order, and the client's shown state equals everyone else's. (Task 5, reconnect_resends_only_unconfirmed; Task 11, reconnect_resends_without_duplicating.)
  3. Two clients racing. Two people change the same line at the same moment, each against the same position. The server picks one order; both editors end with the same lines, with the later change standing, and neither person's view is left showing a state nobody agreed. (Task 4, racing_changes_converge; Task 6, random_sessions_converge; Task 11, racing_entries_get_one_order.)
  4. A heartbeat expiry while an entry is in flight.
    • An entry that arrives just before the expiry counts as a sign of life.
    • One that arrives after the server ended the place is ignored, not stored.
    • The client rejoins as returning and resends; the change is stored once.
    • An entry stored just before the expiry, whose confirmation was lost, is not stored again when resent.
    (Task 9, entry_in_flight_at_expiry_is_stored_once; Task 11, expiry_with_entry_in_flight_commits_once.)
  5. The log survives a server restart. After a stop mid-session, a new server serves the same entries with the same positions, stamps and content. Positions continue without a gap or a repeat; a client resending what was stored before the stop is not stored twice; places are kept. (Task 7, log_reloads_exactly; Task 9, loaded_session_continues_with_fresh_expiry; Task 11, log_survives_server_restart.)
  6. The database fails during a change. The change is not sent to anyone. The room ends, clients reconnect, and the resent change is stored once. (Task 8, store_failure_ends_room_without_broadcast.)

The state, which the signatures do not determine:

  • agreed: an Option<E::Snapshot>. None means what is shown is exactly the agreed state, so nothing needs copying.
  • folded: own entries confirmed by the server but not yet in the agreed copy (at most 64).
  • pending: own changes not yet confirmed, in order, each with its local number, the seen it was made at, its payload, its mode, whether it was sent, and whether showing it read the stamp.

The rules:

  1. A local change. Refused if not Live (NotLive), if the person may not edit (ReadOnly), or if it is over 262,144 bytes (TooLarge); nothing changes then.
    • If agreed is None, take agreed = snapshot() first.
    • In ShowAtOnce mode, apply it with seq: None and stamp: None. On Crash, restore(agreed), re-run the other waiting changes and return LocalError::Crashed; nothing is sent.
    • Queue it with the next local number and seen = agreed_seq.
  2. An entry must be at agreed_seq + 1, or OutOfOrder is returned and the host reconnects. Then:
    • A cancelled change only moves agreed_seq on.
    • Another person's change, when agreed is None, is applied straight to the editor, between note_applying(Some(seq)) and note_applying(None).
    • Otherwise the library goes back and re-runs: restore(agreed), apply each folded entry and the new entry with their server stamps, agreed = snapshot(), empty folded, then re-apply each waiting ShowAtOnce change with stamp: None.
  3. Own entry confirmed. Its local number must be the first waiting change's (otherwise Desync). Take it off the queue.
    • If it was shown and did not read the stamp, add it to folded. If nothing is waiting now, set agreed = None and empty folded. If folded reaches 64, go back and re-run.
    • Otherwise (it was waiting for the server, or it read the stamp) go back and re-run with it.
  4. A refusal must name the first waiting change (otherwise Desync). Take it off the queue; if it was shown, go back and re-run without it. Emit Event::Refused.
  5. Losing the right to edit (Access { can_edit: false }) drops every waiting change (go back and re-run with none) and emits DroppedPending with the count (S5).
