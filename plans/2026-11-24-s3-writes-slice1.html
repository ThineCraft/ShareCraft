Rulings already made

  • S3 first, store-neutral. The shared write path is built once with S3 as its only store. Store has one arm, Store::S3; the file share adds Store::Share later. Shared names are neutral: source_writes, source_write, stage, write_due.
  • Only administrators choose read and write, when connecting and when switching later. Owners may switch a library back to read-only. A new S3 library is still read-only unless an administrator asks for read and write (this differs from the S3 plan, which made read and write the default).
  • Migration 0025 (0025_source_writes.sql). Main uses up to 0024. The S3 plan's 0023_s3_writes.sql and the file-share plan's 0021_file_share_writes.sql are not written.
  • One PUT per file, at most 512 MiB. Larger files are refused before any byte is stored, in plain words. Multipart is slice 2.
  • Out of slice 1, and refused in a read-and-write S3 library with the code source_action_unavailable: rename, move, delete, restore, copy in, new blank file, new from template. The library node itself keeps its current refusals.
  • Writes are counted by the existing meter (S3::count, class Write), nothing caps them, and the counts are still not saved to source_usage: Phase 1 never calls S3::take_usage (budget work stays deferred).
  • No site quota is used by uploads or saves into an S3 library: the bytes live in the bucket. Staged content lives in the external-content cache (source_cache) until written.
  • The write probe runs before read and write is allowed and leaves nothing. A key that may only read is refused with 422 in plain words. What the probe learns about conditional writes is recorded in source_s3.conditional.
  • A refused write blocks the library ("read-only until fixed"), drops nothing, and a passing probe restores it.
  • Editor saves go through the file session by giving external files a different Checkpointer; live_room.rs does not change, and a bucket file never opens in a live room.
  • Writes are never retried inside the S3 client. The worker's back-off retries them, and every retry starts with a HEAD. Each PUT carries x-amz-meta-sharecraft-sha256 so that a write whose answer was lost is recognised as ours rather than as a conflict.

Review focus

Conditions the happy path never meets. Each has a named test in the task that owns the code; Task 9 checks them again across the branch.

  • A write that destroys something. An outside change overwritten on a store that honours conditions; a 412 or 409 taken for success; a write retried inside the client after an answer was lost; a key built without the prefix or with ..; a probe that leaves its object (Tasks 2, 3).
  • An accepted save that can be lost. A save answered Saved with no pending row; staged content evicted, swept or released while a row names it; a restart, a session end, a mode switch or a blocked library dropping a row; a superseded stage lost by finish_write (Tasks 1, 5, 7).
  • Content written before the scan. Every PUT of user content passes Db::availability first; infected content is never written (Task 5).
  • The guard per mode, route by route. Every guarded route has an S3 read-and-write decision; refused routes stay refused; a person who cannot see the node gets 404; a blocked library refuses writes and still reads (Task 4).
  • Races. The write worker and a listing touching the same library without the source lock; a listing that removes, renames or re-tags a node with a pending row; a mode switch racing a write; two saves from one base (Tasks 4, 5, 7).
  • Echo. The tag recorded after a write not matching what the next listing computes (a phantom change, or a missed one) (Task 5).
  • Quota and counting. An upload or save into an S3 library touching site usage or reservations; a write request not counted (Tasks 2, 5, 6, 7).
  • Nothing else changes. GitHub libraries, file-share libraries, read-only S3 libraries, ordinary uploads and file sessions, and live co-authoring rooms behave exactly as before; live_room.rs is untouched.

Rules

  • set_source_mode refuses read_write for a GitHub source (InvalidSetting) and refuses read_only while the library has pending rows (AccessError::WritesPending, judged in the same transaction with the source row locked FOR UPDATE). A real change advances the generation and answers true.
  • set_write_state cuts the error to 300 characters and answers whether the state changed.
  • stage_write is one transaction: lock the blobs row FOR SHARE (the caller pinned it with pin_cached); upsert the row, keeping the first base_tag and first_staged_at when one exists and replacing content, size, by_user, staged_at and flush (true wins); state scanning, error null, attempts 0, next_try_at null; mint a revision (new_external_revision) and, when the node has a source_items row, write it to source_items.revision too.
  • A pending row is a reference to its content everywhere a cache pin is: release_blob_if_unreferenced, unreferenced_blobs, due_scans and queue_unscanned count source_writes; coldest_cached skips content a pending row names; unpin_cached answers false and removes nothing for such content.
  • due_writes answers rows whose next_try_at is null or passed, that are flush or were first staged COALESCE or more before now, oldest first, and leaves scanning rows alone otherwise. The scan decision is the caller's (Db::availability), not SQL.
  • finish_write is compare-and-set on the staged hash, one transaction. For a tracked node it writes the item's tag (blob_sha), size and modified_at; when the row still holds sha256 it also sets content_sha256, read_at, clears unavailable, missing_since and version_id, keeps the row's revision as source_items.revision, and deletes the row (true). For a new file it inserts the source_items row (path = repository_path = the row's path) with the row's revision. If a newer stage arrived meanwhile it answers false, leaves the row, and sets its base_tag to tag.
  • fail_write sets state failed, the error, attempts + 1 and next_try_at; retry_write makes a row due at once (state back to scanning, error kept until written); flush_write sets flush. Each is refused (false) for other content where it takes a hash.
  • drop_write removes the row if it still holds sha256; for a tracked node it also mints a fresh source_items.revision (the staged revision is withdrawn; the item's content is the bucket's again).
  • Disconnect (disconnect_source, disconnect_source_as) answers WritesPending while rows exist.
