Sharing links and access requests: implementation plan

ShareCraft · Stage 2, platform plan 2B · Written 13 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: people who manage access can share a file or folder by link: a signed-in link for anyone in the organisation, with a role and an optional expiry, and, where an administrator has switched them on, an anyone link that lets people without an account view and download, always read-only and always expiring. Links can be revoked at any time and stop working at once. Someone who reaches an item they cannot open can ask for access; the people who manage it see the request and approve it with a role or decline it.

Architecture: a signed-in link is a hidden link group (plan 2A's groups) with an assignment on the shared item; opening the link while signed in makes the person a member. Everything plan 2A built — the one access decision, locking, live-session rechecks, the explorer — then applies unchanged, and revoking the link deletes the group's assignment and members in one step. An anyone link is not a group: a person without an account has no session, so the link's token is checked on every request it makes, and it only ever reaches the read-only download and view routes below the shared item. Links are stored in PostgreSQL only, like all permissions (D24); their tokens are stored as hashes. Access requests are PostgreSQL rows with events; approval goes through plan 2A's set_node_access, so the "no more than you hold" rule applies.

Tech stack: the existing workspace; no new dependencies.

Spec: scope.html SC-11 ("access requests, authenticated sharing links, expiry, revocation, … and configurable anonymous sharing"), D20, D24, D25; acceptance A04. Plans 1 and 2A are the base. Owner decisions of 13 November 2026: a signed-in link is a hidden group with a role on the item, so sharing by link gives the item its own permissions, as SharePoint does; anyone links allow viewing and downloading only, never an editor; domain restrictions wait for the guests plan.

Not in this plan

  • Domain allow and block lists, guests and inviting outside people (with the identity provider decision).
  • Email or other notifications (SC-13): requests and link use are shown inside ShareCraft only.
  • Opening an editor through an anyone link; previews of files other than plain text (plan 3).
  • Sharing by people who do not manage access (SharePoint lets members share); see the rule below. A maximum expiry for signed-in links. A "shared by link" explorer filter.

Global constraints

  • Who may create, change or revoke a link: a person with manage_access on the item. The link's role must be within their own permissions there (plan 2A's rule, beyond_your_access; administrators exempt as before), and may not include manage_access or manage_site (link_role_too_high): a link never makes anyone a manager, so a link group never counts toward the last-manager rule.
  • Signed-in links: one hidden group per link (groups.purpose = 'link', no name and no site), assigned the link's role on the item through the same path as set_node_access (which breaks inheritance first when the item inherits). Opening the link while signed in adds the person to the group; a person who already has that much access is not added. A link group is never listed among groups, never offered in any group list or filter, and is changed only by the link code: set_node_access, add_member, remove_member and delete_group refuse it (link_group). Its assignment may be copied below when a child breaks inheritance; revoking the link deletes every assignment of the group and all its members. Restoring inheritance on a node that removes a link group's last assignment revokes that link (reason "inheritance restored").
  • Anyone links: only when the organisation setting anyone_links is on (default off). Role is always view. Expiry is required and at most anyone_link_max_days (default 30). They reach only: the landing page, the listing of a shared folder and what is below it, downloads of files at or below the shared item, and the read-only view of plain-text documents (as of their last saved revision; unsaved live edits are not shown). They stop at breaks: a node is reachable only if no node strictly below the link's item and at or above it has its own permissions, and no node at or above it is deleted (plan 2A's DEAD test) — exactly what a signed-in Viewer link's assignment would reach. They never open a session, an editor, the access page, the explorer or any other route. Switching the setting off stops every anyone link at once (checked on every request).
  • Tokens: 32 random bytes from the operating system, written in URLs as 64 lowercase hex characters at /l/<token> (as SessionToken); only a SHA-256 hash is stored. The link's address is shown once, when it is created, built from the address the manager is using; a manager who needs it again makes a new link. While the server listens on the local machine only (development mode), links work only there.
  • Expiry: optional for signed-in links, required for anyone links. An expired link stops working within one minute: a sweeper running every minute revokes expired links exactly as a manager would (events, live-session rechecks), one link per transaction. Anyone-link requests also check the time themselves, so they stop at the expiry instant.
  • Revocation is immediate (S5): revoking a signed-in link deletes its assignment and its group's members in one transaction and rechecks open sessions below the item before answering; revoking an anyone link makes the next request with its token fail.
  • Same answer for unknown, revoked and expired links: a link address that does not work shows one page, "This link does not work. It may have expired or been turned off.", whatever the reason; the server answers 404 link_not_found.
  • Access requests never reveal existence: the "Request access" form is offered wherever an item is not found, and submitting it always answers the same, "If this item exists, the people who manage it will see your request." One open request per person per item. The limit of 20 submissions per person per day counts every submission, recorded or not, and is checked before anything else (too_many_requests, 429), so it says nothing about the item. A person sees their own requests only once decided, and only names items they can now see. Requests go to everyone with manage_access on the item. Approval chooses a role (within the approver's own permissions) and gives it to the requester directly on the item, unless their current access already covers it (already_has; never a downgrade); decline may carry a short message the requester sees.
  • Every change records an event: link.created, link.used (first use per person), link.revoked (with reason: manager, expired, item deleted, setting off), request.created, request.approved, request.declined, setting.changed.
  • Locking follows plan 2A's single order: node rows top-down, then groups by id, then roles by id. A link row is locked after the node chain and before its group (FOR UPDATE to revoke, FOR SHARE to redeem, then revoked_at and expiry are checked again). The request rate limit uses pg_advisory_xact_lock on the requester, never a lock on the users row.
  • Headers: every /l/ page and /api/l/ answer carries Cache-Control: no-store and Referrer-Policy: no-referrer; the server's general security headers are added only where a handler has not set its own. Anonymous downloads reuse the existing download headers (octet-stream, attachment, CSP: sandbox, nosniff). No anonymous answer sets a cookie.
  • Redemption is a POST: the landing page asks a signed-in visitor to confirm ("Open with Editor access") and sends a same-origin POST /api/l/{token}/redeem; a plain visit, a prefetch or a cross-site navigation never joins anyone to a link group.
  • Never print .env, database addresses, passwords or link tokens. Documents are HTML with colour banding on tables and long lists.

Review focus

  1. An anyone link to a folder cannot reach anything outside that folder, nor a subfolder or file below it that has its own permissions, by any route or crafted parameter; nor anything once it is moved out of the link's item, deleted (itself or an ancestor), the link expires, or the setting is switched off. (Task 1, anyone_link_reaches_only_below_its_item; Task 3, anyone_link_stays_inside_its_item.)
  2. Revoking a signed-in link while people who joined through it have a file open removes or downgrades them at once, unless they also have access another way — including on folders below the item that broke inheritance after the link was made and copied its assignment. (Task 1, revoke_removes_copies_below; Task 3, revoke_link_reaches_open_sessions.)
  3. A link created by someone whose own access is later lowered still grants exactly its role, no more; and nobody can create a link above their own access. (Task 1, link_role_within_creator_access.)
  4. The request form and its answer are identical for an item that exists, one that does not, and one the person can already open; the rate limit holds under concurrent submissions. (Task 2, requests_never_reveal_existence.)
  5. The expiry sweeper and a manager revoking the same link at the same moment produce one revocation and one event, without deadlock. (Task 1, sweeper_and_revoke_take_turns.)

  • Db::create_link(&self, actor, node, kind, role: &str, expires_at) -> Result<(Link, LinkToken), AccessError>: manage_access; subset rule; no manager permissions in the role (LinkRoleTooHigh); setting and expiry checks (AnyoneLinksOff, ExpiryRequired, ExpiryTooLong); for a signed-in link creates the hidden group and its assignment through the same path as set_node_access. Db::revoke_link(&self, actor: Option<UserId>, link, reason) -> Result<bool, AccessError> (None actor = the sweeper or the system): locks the item's chain, then the link row FOR UPDATE, then the group; deletes every assignment of the group (copies below included) and all its members, marks the link; idempotent (false when already revoked). Returns the nodes whose assignments it removed, for the server's rechecks.
  • Db::redeem_signed_in(&self, user, token: &LinkToken) -> Result<NodeId, LinkError>: locks the item's chain, then the link row FOR SHARE (checking it is live and unexpired again), then the group FOR UPDATE; adds the person to the link group unless their access already covers the link's role; records link.used on first use; LinkError::NotFound for unknown, revoked, expired or anyone-kind tokens, and for a deleted item.
  • Db::anyone_link(&self, token: &LinkToken, node: Option<NodeId>) -> Result<Option<AnyoneGrant>, DbError> with AnyoneGrant { link: Uuid, root: NodeId, node: Node }: Some only if the setting is on, the link is live and unexpired at this instant, and node (default the item) is at or below the item, with no node at or above it deleted and no node strictly below the item and at or above it having its own permissions. The one check every anonymous route uses; listings filter children by the same rule.
  • Db::expired_links(&self, now) -> Result<Vec<Uuid>, DbError> reads candidates without locks; the sweeper then calls revoke_link(None, id, "expired") for each, one transaction per link. Deleting an item (inside apply_nodes, so Git repairs are covered too) revokes its links with reason "item deleted" and closes its open requests in the same transaction.
  • Db::setting / Db::set_setting(&self, actor, key, value) (administrator; known keys and value types only; setting.changed event). Switching anyone_links off stops every anyone link at once (checked on every request); they are not revoked, and work again if it is switched back on before they expire.
  • Explorer: a link group appears as PrincipalView::Link { link: Uuid, kind, expires_at } in break assignments (never as a group with a name), and Break gains anyone_links: i64 (live anyone links on that node). Anyone links on a node with no break of its own are listed on the access page, not in the explorer, so the explorer's cost still follows breaks.
