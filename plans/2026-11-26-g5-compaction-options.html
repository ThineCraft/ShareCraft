Row and column compaction

Options for the owner, 26 November 2026. The last G5 follow-up that stops editing together from being switched on in production. The owner chose A the same day; how it was built is at the end.

The problem

When people edit a spreadsheet together, every row and column has an identity, so that “Bob edits row 12” still means the right row after Ann inserts a row above it. Identities are kept in runs, and a deleted row keeps its run forever (as a tombstone), so a later change that names it can say “someone deleted that row” instead of landing in the wrong place.

Tombstones are never removed, and each sheet axis allows at most 65,536 runs. A checkpoint carries the runs into the next session, tombstones included. Over months of editing an axis can reach the limit, and from then on every row and column insert, delete or move on that sheet is refused, in every session, for good. A hostile editor could reach it on purpose in one session.

The code already says the way out (collab-live/src/ids.rs): tombstones below a position that every participant has passed can be dropped, because no change still to come can name them. The difficulty is that every editor must drop exactly the same ones at exactly the same point, or their tables differ and the next change can be accepted by one and refused by another.

Recommendation

A first. It removes the permanent build-up that real use would hit, for about a third of the work. B can follow later if one session ever needs it. With A in, the production guard’s list is empty, so production mode can switch editing together on.

The remaining minors from the G5 ledger (a heartbeat during a reload, test gaps for the joiner wait list, presence flooding by a hostile server, and similar) don’t block production. I suggest fixing them after compaction, as one batch.

As built (option A)

PartWhat it does
ServerThe catch-up message carries compact: true when the verified base is the last position before the open session began. It depends only on the base and the session, so everyone loading that base in that session is told the same. A base followed by an earlier session’s unsaved entries is not compacted (those entries may name its deleted rows); the session after compacts instead.
Live protocolVersion 2. A version-1 editor (an old browser tab after an upgrade) is refused, because it would keep ids that everyone else forgets.
collab-liveOrderedIds::compact forgets every deleted id. A client whose state came from another session loads a compacted base again instead of carrying on with its old tables.
GridCraft forkA checkpoint base loaded with compact drops every sheet’s deleted row and column runs and their deletion owners; sheet identities are kept.
Production guardIts list of open work is empty, so production mode accepts SHARECRAFT_LIVE_EDITORS. The guard stays for any later gap.
Browser check (26 Nov)Fork 2f4ea5e0 on a development server, two accounts in two tabs. Session 1: rows and a column deleted, both tabs agree, verified checkpoint at 23 holding 2 deleted row runs and 1 deleted column run. Both left, the session ended. Session 2 loaded that checkpoint through live-base; an insert and a delete agreed in both tabs; its verified checkpoint at 26 holds only session 2’s own deleted rows (the deleted row, and the last sheet row the insert pushed off the end) and no deleted column.
Found on the way (not this change)A document’s first live session starts from an empty workbook, not its stored file: with no live checkpoint the catch-up names no revision, and the page then loads the empty document. The first checkpoint would then store that empty workbook as a new version on top of the uploaded one. Fixed the same day: a log with no verified checkpoint and no entries names the document’s current revision as its base, so the page loads the stored file (with fresh identities). A log already holding entries made on the empty base keeps it. Checked in the browser: a fresh upload opened with its 10 rows and formulas in both tabs, edits agreed, and the first checkpoint was verified.
What changes for peopleA returning person’s change that names a row or column deleted before the compaction does nothing (“not available”) instead of landing as a #REF! or near where the row was. One very long session can still fill an axis; the next session starts clean.
