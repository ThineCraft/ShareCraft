Files: content store, uploads, recycle bin, copy and quotas: implementation plan

ShareCraft · Stage 2, platform plan 3A · Written 13 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: everyday file work at SharePoint's level. Files of many gigabytes upload by drag and drop, resume after an interruption and are checked against their checksum. Deleted items go to a two-stage recycle bin and can be restored for 93 days; after that, or when the bin is emptied, their bytes are truly erased. Files and folders can be copied, and many items moved, copied or deleted at once. Duplicate and invalid names are handled without losing anyone's work. Each site has a storage quota.

Architecture: file bytes move out of Git into a content store in the data folder: one file per distinct content, named by its SHA-256. Git keeps, for each saved version, a small pointer naming that hash and size, so history, attribution, JSON metadata and checkpoints stay in Git exactly as before (S3, S4). Identical bytes are stored once, so a copy costs nothing. PostgreSQL keeps one row per stored blob and one row per version that points at it, written before the Git commit, so nothing can erase a blob that a version is about to name. Uploads and saves stream to disk while being hashed and pass a reference, never the bytes, through the editing session. Deleting stays a soft delete (plan 1); the recycle bin is a view over deleted nodes whose stage and deletion grouping are recorded in Git with the node. Purging marks the node purged and erases each blob no longer named by any version of any item that is live or in a bin.

Tech stack: the existing workspace; sha2 (already used by records and server, MIT/Apache) added to revisions; no other new dependency.

Spec: scope.html SC-02 (drag-and-drop and resumable uploads, bulk operations, copy, deletion with documented permission and history behaviour, duplicates, invalid names, interrupted transfers, checksums, quotas, large files), SC-01 (quotas), SC-21 (binary storage; recoverable deletion versus permanent erasure), SC-23 (resumable uploads, checksums, range downloads); D24. Plans 1, 2A and 2B are the base. Owner decisions of 13 November 2026: plan 3 is split into 3A files, 3B sites and 3C libraries, in that order, with document sets and metadata panels moving to Stage 3; the recycle bin has two stages and keeps items 93 days in total, as SharePoint does; malware scanning (plan 3C) calls an external scanner the organisation runs; file bytes live in a content store named by SHA-256 with pointers in Git (settles the binary-storage part of decision 3).

Not in this plan

  • Previews, image and template libraries, new-from-template, upload rules and file policies, malware quarantine (plan 3C). Site templates, site and library lifecycle, hubs, navigation, language and time zone (plan 3B).
  • Rewriting Git history: bytes already stored inside Git before this plan stay in its history and cannot be erased; only versions saved after the upgrade can be. A history-purge tool is later work.
  • Uploading a new version of a plain-text document (they are edited live in the text room; refused with text_document). Encryption of the content store, object-storage backends, per-library version limits (SC-08, Stage 3).

Global constraints

  • Content store: <data>/blobs/<first two hex digits>/<sha256>, one file per distinct content, never modified. New content is written under <data>/blobs/tmp/ (or arrives there as an upload's part file, on the same volume), flushed, then renamed into place; a blob that already exists is not rewritten. The store lives in revisions (BlobStore); the server holds it in AppState and is the only code that turns a pointer into bytes.
  • Pointer: a saved version's docs/<id>/content in Git holds exactly sharecraft-blob 1\nsha256 <64 lowercase hex>\nsize <decimal bytes>\n. Content that does not start with sharecraft-blob 1\n is an old version whose bytes are inline, read as before. Every version saved after the upgrade is a pointer, plain-text documents included. "Unchanged" is decided by comparing hash and size (an inline old version is hashed to compare), so opening and saving an old document unchanged writes nothing.
  • Blob safety: tables blobs (sha256 pk, size, created_at) and blob_refs (sha256, doc_id, revision text null, pending boolean, primary key (doc_id, sha256, revision)). Before any checkpoint, copy or new file names a hash, a pending blob_refs row is written with the blobs row locked FOR SHARE; after the Git commit the row is completed with its revision (or deleted if the commit failed). Erasure locks the blobs row FOR UPDATE, re-counts every row naming it (pending included) and erases only at zero. A pending row older than one hour with no matching Git revision is cleared by the sweeper.
  • Locking order (extending plans 2A and 2B): node rows top-down, then link rows, then site_usage, then groups by id, then roles by id; blobs rows are locked in their own short transactions, never while holding the others.
  • Streaming: uploads, saves and downloads never hold a whole file in memory. A save streams the body into the store in the request handler and passes a BlobRef through the file session (FileCommand::Save, the seat's waiting save and the write job carry a BlobRef, not bytes). Downloads support one Range (206, Content-Range, Accept-Ranges: bytes; 416 when unsatisfiable) and keep today's download headers. A pointer whose blob file is missing is logged and answers 503.
  • Sizes: SHARECRAFT_MAX_FILE_BYTES stays the largest file allowed, with a new default of 10 GiB. Each person may have at most 5 open upload sessions, and their declared sizes are reserved against the site's quota while open.
  • Checksums: SHA-256 of the whole file, computed as chunks arrive (and recomputed from the part file only after a server restart). Finishing refuses (checksum_mismatch, 422) if the bytes differ from the declared size and checksum, and creates nothing.
  • New versions go through the editing session: an upload that replaces a file (a new-version session, or "replace" on a name conflict) is allowed only for file documents (Editor::is_file) and is saved through the document's file session exactly as an editor's save (Rooms::save_file, the seat rules, S4's base revision); while someone holds the editing seat it answers 409 being_edited.
  • Recycle bin: deleting moves an item (a folder with every live item inside it) to its site's first-stage bin; every open editing session on a deleted document ends with deleted (S5), for a folder as for a file. Restoring or removing from the first stage needs delete on the item, judged by a defined function Db::access_as_if_live(user, node) (the one access decision with the deleted flags of the node and its deleted_with group ignored). Removing from the first stage moves the item to the second stage, which only people with manage_site on the site see, restore from and remove from. 93 days after the original deletion, or when removed from the second stage, an item is purged. The bin page lists the entries the viewer could restore (so a person sees nothing whose name they could not see when it was live). The stage and the deletion grouping (deleted_with) are recorded in the node's Git record, with "purged", so reconcile rebuilds them.
  • Restore puts an item back where it was, with its own permissions as they were. If a folder above it is in the bin, that folder node alone is restored too (never what was deleted with it), and only if the person may restore it; otherwise the answer is 409 parent_in_bin. If a folder above it has been purged, the item is restored to the top of its library. Items deleted with a folder come back with it; items deleted separately before the folder stay in the bin. A name now taken gets  (2),  (3) … before its extension (plan 1's unique_name, shared) and the answer says so. Links revoked by the deletion stay revoked.
  • Purge and erasure: purging an item purges what was deleted with it; items inside it deleted separately keep their own bin entries. A purged node stays as a tombstone (Git record marked "purged", PostgreSQL row kept, never listed) so sync clients learn it is gone (SC-23); its assignments, link groups and open requests are removed. Its versions' blob_refs rows are deleted and each hash with no rows left is erased (the blob file deleted after the commit). Bytes stored inline in Git before the upgrade are not erasable.
  • Copy: copying a file or folder (to any library or folder the person may add to) makes new items with new identifiers and the same bytes, the latest saved version only (unsaved live edits in an open text room are not included; history is not copied), and the destination's permissions (a copy inherits; own permissions and links are not copied). An old inline latest version is written to the store first. Needs view on the source and add on the destination. A folder's copy is one tree commit, and the first versions of all its documents one checkpoint commit.
  • Bulk: move, copy, delete and restore accept up to 500 items per request; each item is one operation with its own result (ok or an error code), in the order given.
  • Names on upload and copy: refused characters are replaced by _ (plan 1's clean_name, shared) and the answer says so. A name taken in the destination: an upload answers 409 name_taken {suggested} until the person chooses replace (a new version as above; needs edit), keep both or skip. Copies always keep both.
  • Quotas: each site has a storage quota in bytes (default none; set by administrators). Usage is the sum of the sizes of every version of every item in the site, live and in its bins, inline old versions included (their size is known from Git). A save, upload or copy first reserves its bytes in its own transaction (site_usage locked FOR UPDATE, checked, reservation added), then commits to Git, then turns the reservation into usage; a failure releases it. Over the quota it is refused (quota_exceeded, 507) before anything is committed. Checkpoints of the live text room and of co-authoring are never refused for quota (they would retry for ever); deleting, restoring and purging always work. At 90% the site page warns its owners.
  • All existing rules stand: the one access decision, S4 base revisions, S5 rechecks, events for every change (node.restored, node.binned (to the second stage), node.purged (with bytes freed), node.copied, quota.changed, upload.completed), no printing of .env, addresses, passwords or tokens, HTML documents with colour banding.

Review focus

  1. Erasure never removes bytes a version points at or is about to point at: a purge racing a save of the same bytes, a copy, an old version of another file. (Task 4, erasure_keeps_shared_bytes, purge_racing_a_save_of_the_same_bytes.)
  2. An interrupted upload resumed from where it stopped produces exactly the declared bytes; a wrong checksum, a short or long upload, or chunks out of order create nothing. (Task 2, resume_after_interruption, bad_uploads_create_nothing.)
  3. Restoring a folder brings back what was deleted with it, not what was deleted separately before it, with the same permissions; it never restores someone else's deleted folder the person may not restore; it never resurrects a revoked link. (Task 3, restore_folder_brings_back_its_own, restore_never_beyond_your_rights.)
  4. Two uploads finishing at the same moment cannot take a site over its quota together. (Task 5, concurrent_finish_respects_quota.)
  5. After the upgrade, a live checkpoint writes a pointer and is still refused when stale; an editor's save of a large file streams through the file session; old inline versions still download byte for byte; a replace upload while someone edits is refused. (Task 1, checkpoint_writes_pointer_and_stays_s4, old_inline_versions_still_read; Task 2, replace_while_being_edited_refused.)
