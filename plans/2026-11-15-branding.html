Plan 4A, branding: themes, logos, headers and footers: implementation plan

ShareCraft · Stage 2, platform track · Written 15 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: an organisation can keep approved themes and brand images in one brand centre. Each site can then have its own look: a theme that works in light and dark, a logo and logo thumbnail, a header layout, a navigation style and a footer. Owners preview a look before applying it and can go back to an earlier one. ShareCraft's own controls stay neutral, and status colours and warnings are never recoloured.

Architecture:

  • Records: the brand centre is a Git JSON record, org/brand.json. A site's look is a new look field on its existing site record. Both follow the established pattern: one commit per change, mirrored to PostgreSQL afterwards, taken back if the database refuses, and repaired at start.
  • Images: brand images are snapshots. Applying an image pins its content in the content store, so later changes to the library file do not touch the brand. A new route serves the image to anyone signed in.
  • Pages: each page fetches the site's effective look (with the hub rule already applied). siteChrome then sets the theme's colour variables through the CSS object model, which the current Content Security Policy allows, and builds the header and footer. Previews use the same function on a draft.
  • Contrast: the contrast check and the dark-colour derivation exist twice, in Rust (authoritative) and in JavaScript (live feedback). Both are tested against one shared table of test values.

Tech stack: the existing workspace (axum, sqlx, gix and the image crate for image sizes), and plain HTML and JS pages with node tests. No new dependency.

Spec: scope.html:

  • SC-25, organisation and site branding;
  • D13 (own identity, not SharePoint's look);
  • D23 and D31 (plan 4 is branding);
  • D39 (asset libraries hold logos and brand images);
  • acceptance test A18.

Proposals in this plan for the owner to check

The owner asked for the plan to be written without stopping for questions. These are the choices it makes. Each is cheap to change before the build starts.

  1. Plan 4 is split in two:
    • This plan, 4A, covers the brand centre (themes and brand images), site looks, Change the look with preview, history and rollback, the hub rule, and the look carried into the editor frame.
    • 4B covers font packages, copying branding from another site, branding in site templates and the API, limiting site owners to approved options (including hiding the default themes), mega menus, the browser-tab icon, and branded emails and portals.
  2. Brand images are snapshots seen by anyone signed in.
    • Applying an image copies a reference to its exact content.
    • Everyone signed in can see it, even without access to the asset library it came from.
    • A changed or deleted library file does not change the brand until the image is chosen again.
  3. The hub rule:
    • A site in a hub uses the hub's theme.
    • Its own logo, header, navigation style and footer stay its own.
    • Its own theme is kept, unused, and comes back when it leaves the hub.
    • The owner can still edit it while the site is in a hub; the page says the hub's theme is in use.
  4. Unreadable colours are refused.
    • A look whose text or buttons fall below WCAG AA contrast (4.5:1) in light or dark mode cannot be applied.
    • The page shows which pair fails and suggests the nearest passing shade.
  5. Themes are copied into the look.
    • A site look holds its theme's colours, plus a note of where the theme came from.
    • Editing or deleting a brand-centre theme never breaks a site.
    • Change the look marks a theme whose source has changed since it was applied.
  6. Brand managers: administrators name the brand managers. Brand managers and administrators look after the brand centre.

Not in this plan

  • Everything listed for 4B above.
  • A branded sign-in page.
  • Theming inside the editors themselves: their own pages are not restyled, only the frame around them.
  • Custom style sheets or scripts, which SC-25 excludes.
  • Page-editor section backgrounds, which wait for SC-09.

Global constraints

  • Colours are #rrggbb. Input is accepted in upper or lower case and stored in lower case.
  • A theme is {name (1–60), primary, secondary, primary_dark?, secondary_dark?}:
    • primary is the accent: links, buttons, the focus ring and the bar stripe.
    • secondary is the background of a strong header or footer.
    • When a dark value is left out, it is derived (see Contrast).
    • The page reference colours, from web/style.css, are: light paper #ffffff, dark paper #202a2e, light background #f5f7f8 and dark background #141c20.
  • Contrast (WCAG 2.x relative luminance), shared by Rust and JS. All of these must reach 4.5:1:
    1. primary on light paper and on light background;
    2. white button text on primary;
    3. primary_dark on dark paper and on dark background;
    4. the button text on primary_dark (white or #141c20, whichever is higher);
    5. the header text on secondary, and on secondary_dark (each takes white or #141c20, whichever is higher).
    • Deriving a dark value: keep the hue and saturation in HSL.
      • For primary_dark, raise the lightness in steps of 1% until checks 3 and 4 pass.
      • For secondary_dark, use secondary unchanged if check 5 passes. Otherwise lower the lightness in steps of 1% until it passes.
      • If nothing passes, the dark value is reported as failing.
      • For the built-in themes, this gives dark accents between 4.51:1 and 4.70:1. For example, ShareCraft's #3156c9 gives #748ddd.
    • Suggestions: a failing light colour gets the passing HSL lightness nearest to its own, searched 1% at a time in both directions.
    • Refusal: 422 low_contrast {"pairs":[{"check","ratio","suggestion"}]}, with ratios rounded to 2 decimals.
    • Shared test values: web/look-vectors.json, read by the Rust tests through include_str! and by web/look.test.mjs.
  • Built-in themes (light primary / secondary; dark values derived):
    IdNamePrimarySecondary
    builtin:sharecraftShareCraft#3156c9#233239
    builtin:harbourHarbour#1f5f8b#163447

    Each one passes every check. A test proves it.
  • Brand images:
    • Types: png, jpeg, webp, gif and svg, judged by the file's content and not by its name. The image crate's format guess is used for raster images; SVG must parse as XML whose root element is svg.
    • Size limits: logo, thumbnail and icon at most 1 MiB; background at most 5 MiB.
    • Raster images: at most 8,000 × 8,000 pixels, read from the header only.
    • The image's content must be available (D37) when it is chosen.
    • Chosen from a document id the person can view: any image in an asset library they can view, or any image in the site's own libraries (for that site's look).
    • ImageRef = {sha256, media_type, bytes, width?, height?, name, from_doc}.
  • Serving brand images: GET /api/brand/images/{sha256}.
    • Signed in only.
    • 404 unless the content is named by the brand centre or by a current site look. 423 held if the content is no longer available, for example after a rescan found it infected.
    • Headers: the recorded media_type, X-Content-Type-Options: nosniff, Content-Security-Policy: sandbox; default-src 'none'; style-src 'unsafe-inline', Cache-Control: private, max-age=31536000, immutable, and no Content-Disposition.
    • Pages only ever show these images through <img>.
  • Pinning images:
    • Table brand_refs (sha256 references blobs, owner text), where owner is org or a site id.
    • It is written in the same transaction as the mirror change, with the blobs row locked FOR SHARE, following the claim pattern in records::blobs.
    • release_blob_if_unreferenced also counts brand_refs.
    • A purged site loses its rows.
    • Reconcile rebuilds the table from Git.
  • The brand centre record, org/brand.json:
    • Shape: {schema:1, managers:[uuid], themes:[{id, ...theme, changed_at}], images:[{id, kind: logo|icon|background, image: ImageRef}]}.
    • Limits: at most 50 themes, 100 images and 20 managers.
    • Theme names are unique, ignoring case.
  • A site's look, SiteRecord.look: Option<Look> (absent means the built-in ShareCraft theme with the defaults below), and SiteRecord.themes: Vec<Theme with id> (at most 20, site-only). A Look holds:
    • theme: a copy of the theme, plus from: "builtin:<id>" | "org:<id>" | "site:<id>" | "custom".
    • logo?, thumbnail? (both ImageRef), and logo_alt, 0–120 characters; empty means the site name.
    • header: {layout: minimal|compact|standard|extended, background: none|soft|strong|image, image?: ImageRef, align: left|centre|right, hide_title: bool}.
      • The default is compact with none.
      • image and align apply only to extended.
      • hide_title needs a logo.
    • navigation: horizontal|vertical. Vertical puts the local bar in a left column at 900 pixels and wider, and in the existing Menu at narrower widths.
    • footer: {enabled, layout: simple|extended, logo?: ImageRef, name (0–80), background: none|soft|strong, groups:[{heading (0–40), links:[{label (1–60), url}]}]}.
      • Simple: one group, at most 8 links, no heading.
      • Extended: at most 4 groups of 8 links.
      • Each url is https://, http:// or a path starting with a single /.
    All text is trimmed. Control and invisible format characters are refused, using the same cleaning as names (3C).
  • Who may do what:
    • Reading the brand centre: anyone signed in.
    • Changing themes and images: brand managers and administrators.
    • Changing managers: administrators.
    • A site's look and site themes: manage_site.
    • On an archived site, look and theme changes answer 403 archived, but the look is still shown.
    • Branding never grants or removes access.
  • Effective look, GET /api/sites/{id}/look (view on the site): {theme: {light:{accent, accent_ink, header_bg, header_ink}, dark:{...}}, logo_url?, thumbnail_url?, logo_alt, header, navigation, footer, theme_from: "site"|"hub", hub?: {id, name, thumbnail_url?}}.
    • A site in a hub takes the theme of the hub's own look.
    • Everything else comes from the site.
  • Never themed: --ok, --warn-*, --stop-*, --text, --muted, --line, --bg, --paper, the account bar, permission warnings and the held or quarantine marks. The focus ring stays at least 2 pixels and uses --accent-ink, which the contrast checks cover.
  • History:
    • Every look change records site.look_changed {before, after}.
    • GET /api/sites/{id}/look/history (manage_site) lists the last 50 changes, newest first: {event_id, at, by, look}.
    • POST /api/sites/{id}/look/rollback {event_id} applies that entry's before or after as the new look, checked again. An image whose content is gone answers 409 image_gone {"slots"}; the page then loads that look as a draft without those images.
  • Events: brand.theme_changed (created, updated or deleted, with the theme), brand.image_changed (added or removed), brand.managers_changed, site.look_changed and site.theme_changed.
  • Errors (each with a plain-English message in common.js):
    • low_contrast 422
    • invalid_look 422 {"reason"}
    • invalid_theme 422 {"reason"}
    • not_an_image 422
    • image_too_large 413
    • held 423
    • image_gone 409
    • too_many 409 {"limit"}
    • name_taken 409
  • Locking order: unchanged from 3C. The brand-centre record is a single row, org_brand, locked before node rows when a change touches both (only reconcile does). brand_refs rows are written after blobs are locked.
  • Upgrade: migration 0015_brand.sql adds the following and is one way:
    • org_brand (id boolean primary key check (id), record jsonb);
    • sites.look jsonb null and sites.themes jsonb not null default '[]';
    • brand_refs.
    Existing sites read with no look, so they look as they do today.

Review focus

  1. Branding cannot run code or load anything from outside. Covered by Task 2, brand_inputs_never_run:
    • an SVG logo containing a script, an onload handler or an external href;
    • a theme name or footer label holding HTML;
    • a footer link with javascript:, data:, //evil.example or /\evil;
    • a colour such as red;background:url(x);
    • a PNG that is really HTML.
    Each is refused or shown as text, and nothing reaches the page as markup or as a style.
  2. A brand image never outlives its last reference or disappears while still used. Covered by Task 2, brand_images_pinned_until_unreferenced:
    • the source file is deleted and its bin emptied while a look uses its image;
    • a look switches logos;
    • a site is purged;
    • a theme is deleted while a site uses a copy.
  3. Unreadable looks are refused on every path that sets colours. Covered by Task 1, every_check_on_every_path, and Task 3, rollback_rechecks_contrast. The paths are:
    • brand-centre themes;
    • site themes;
    • a custom theme in a look;
    • a rollback to an older look, re-checked in case the rules change later;
    • a derived dark value that cannot pass.
  4. The hub rule holds through every hub change: joining, leaving, the hub changing its theme, the hub being unregistered, and the hub being archived or deleted. The effective look is right after each, and the site's own theme is never overwritten. (Task 3, hub_rule_through_every_change.)
  5. Looks survive the records model's failure paths: a look change refused by the database is taken back from Git; a start after a crash between commit and mirror shows the committed look; reconcile rebuilds org_brand, sites.look and brand_refs from Git. (Tasks 2 and 3, look_change_refused_by_database_is_taken_back, reconcile_rebuilds_brand_from_git.)
