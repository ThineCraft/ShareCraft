Production mode: ShareCraft at a public HTTPS address, behind a reverse proxy or tunnel: implementation plan

ShareCraft · Stage 2, platform track · Written 15 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Why: the owner installed the Windows package on another computer, put it behind a proxy at a public address, and could not sign in. That is the development build working as designed: it refuses any Host that is not a loopback name, and any Origin that is not http://<that host>. A production mode was always planned (scope section 06, “Deployment & upgrades”; BUILDING section 21) but never built.

Goal: one setting, SHARECRAFT_PUBLIC_URL, turns on production mode. An installation can then be used safely at an address such as https://share.example.com, with a reverse proxy or tunnel in front that handles HTTPS. Production mode adds:

  • an origin check against the configured public address, keeping the cross-site request protection the loopback check gives today;
  • forwarded headers trusted only from configured proxy addresses;
  • Secure cookies with the __Host- prefix, HSTS, and the existing Content Security Policy and security headers;
  • sign-in protection fit for the internet: limits per account and per address, a lock with a stated wait, answers that take the same time whether or not an account exists;
  • anyone links and access-request pages that work at the public address;
  • a way to turn it on in the Windows package, with the README guide updated;
  • a new installer zip, built from the finished branch, that the owner can install over the copy on the other computer with -Reinstall.

Architecture:

  • One description of the deployment. A new module, crates/server/src/deployment.rs, holds Deployment::Development (today's behaviour, byte for byte) or Deployment::Production {public, proxies, hsts}. Config builds it, AppState carries it, and every check that today assumes loopback asks it instead.
  • Where a request came from is worked out once. A middleware reads the connection's peer address (axum's ConnectInfo) and, only when that peer is a trusted proxy, the forwarded headers. It stores a Source {client_ip, https, host_ok} in the request's extensions. The origin check, the sign-in limits and the plain-HTTP refusal all read Source, never the raw headers.
  • HTTPS lives in the proxy. ShareCraft never terminates TLS itself and never answers the internet directly: in production it accepts requests only from its trusted proxies, and only those the proxy says arrived over HTTPS.
  • Development mode does not change. With SHARECRAFT_PUBLIC_URL unset, every existing test passes untouched, the cookie keeps its name, and the server still refuses a non-loopback address.

Tech stack: the existing workspace, the pages in web/, and the Windows package scripts in packaging/windows (Windows PowerShell 5.1, Pester tests). The server needs no new dependency: CIDR matching is a few lines over std::net::IpAddr. The browser check's local HTTPS proxy is a choice for the owner (proposal 10).

Spec: scope.html:

  • section 06, Security (encryption in transit, authorisation at every boundary) and Deployment & upgrades (self-hosted reference deployment, configuration and secrets);
  • SC-11, sharing links, access requests and session handling;
  • BUILDING.html section 04 (the loopback rule and its variables), section 21 (known limits) and section 24 (links and access requests).

Proposals in this plan for the owner to check

These are the choices the plan makes. Each is cheap to change before the build starts.

  1. Production mode is turned on by one setting, SHARECRAFT_PUBLIC_URL, for example https://share.example.com.
    • It must start with https://. It may carry a port (https://share.example.com:8443), but no path, query, fragment, user name or password.
    • One public address only. A second name for the same installation (for example www.) is the proxy's job to redirect.
    • Serving ShareCraft under a path (https://example.com/share/) is not supported: the pages, the API and the editors all assume they sit at /.
  2. Trusted proxies are named by address, in SHARECRAFT_TRUSTED_PROXIES: a comma-separated list of IP addresses or ranges (127.0.0.1, ::1, 10.0.0.0/24).
    • When it is unset in production mode, it means 127.0.0.1, ::1: a proxy or tunnel on the same computer. That is the Windows package's case.
    • Ranges wider than /8 (IPv4) or /32 (IPv6), and 0.0.0.0/0 or ::/0, are refused at start: trusting everyone would let anyone forge their address.
  3. Which forwarded headers are read: X-Forwarded-For, X-Forwarded-Proto and X-Forwarded-Host, and only when the connection comes from a trusted proxy. From anyone else they are ignored.
    • The client is found by reading X-Forwarded-For from the right and skipping trusted proxies; the first address that is not a trusted proxy is the client. A client cannot forge its address by sending its own X-Forwarded-For, because its own entries sit to the left of the one the proxy adds.
    • The standard Forwarded header (RFC 7239) is not read in this plan. Caddy, nginx, IIS and the common tunnels all send the X-Forwarded-* ones.
  4. In production mode, the server answers only through its proxies.
    • A request from an address that is not a trusted proxy gets 403 for everything except GET /healthz from loopback (the Windows Start shortcut uses it).
    • Using ShareCraft directly at http://127.0.0.1:8787 on the server computer stops working in production mode; people there use the public address too. This keeps one cookie, one origin and one set of rules.
  5. Plain HTTP stays refused.
    • A request the proxy says arrived over plain HTTP (X-Forwarded-Proto is not https, or is missing): a GET or HEAD for a page is redirected (308) to the same path at the public address; anything else gets 403 https_required.
    • The server refuses to start with an http:// public address, or with a non-loopback SHARECRAFT_ADDR in development mode (as today).
  6. The session cookie in production mode is __Host-sharecraft_session=…; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=….
    • The __Host- prefix makes browsers refuse it unless it is Secure, has Path=/ and no Domain, so another site on a neighbouring subdomain cannot plant or overwrite it.
    • SameSite stays Lax: links from email or chat to a ShareCraft page must arrive signed in. The origin check, not SameSite, is what stops cross-site changes.
    • Switching modes signs everyone out once, because the cookie's name changes. That is intended.
  7. HSTS: Strict-Transport-Security: max-age=31536000 on every production answer, without includeSubDomains or preload, because ShareCraft cannot know what else runs under the owner's domain.
    • SHARECRAFT_HSTS_SECONDS can shorten it (for example 300 while trying production mode for the first time) or set it to 0, which sends max-age=0 to withdraw it.
  8. Sign-in limits:
    • Per account (kept from today): 5 failures within 15 minutes lock that email address until the oldest failure is 15 minutes old. While locked, even the right password is refused. The answer is 429 too_many_attempts with Retry-After in seconds, and the sign-in page says when to try again.
    • Per address (new): 30 failures within 15 minutes from one client address lock that address out of signing in, for any account, the same way. An IPv6 client counts as its /64, since one person usually holds a whole /64.
    • Everyone at once (new): at most as many password checks run together as the computer has processor cores (at least 2). Others wait up to 10 seconds, then get 503 busy. This stops a flood of guesses from taking the whole computer, because each check (Argon2) is deliberately slow.
    • The counts stay in memory and reset on restart, as today. An attacker cannot restart the server, and keeping them in memory needs no database write per guess.
    • No lock is permanent, and nothing is sent to the account holder. An administrator sees each lock as a sign_in.locked event, recorded once per lock.
  9. The Windows package turns production mode on with one command, run from the installed program folder: 
    "%LOCALAPPDATA%\Programs\ShareCraft\Set public address.cmd" https://share.example.com
    • It checks the address, writes it to settings.cmd, restarts ShareCraft and says what the proxy must send. -Off goes back to this-computer-only use.
    • The package keeps listening on 127.0.0.1 only, so the proxy or tunnel runs on the same computer. Listening on the network would need a Windows Firewall rule, which needs administrator rights; the package avoids that.
    • The README gives worked examples for two setups: a tunnel run by the Windows user (no open ports, no administrator rights), and Caddy on the same computer. It names no tunnel provider as the right one.
  10. The browser check needs a local HTTPS proxy. Two ways, for the owner to choose:
    • (a, proposed) a small cargo xtask tls-proxy command for development only: HTTPS on 127.0.0.1:8443 with a self-signed certificate for sharecraft.localhost, adding the forwarded headers. It adds tokio-rustls and rcgen to xtask only, never to the server, and installs nothing on the computer.
    • (b) Caddy installed on the build computer, which needs the owner's go-ahead to install.
    Either way, the owner checks once on the real installation at the real public address; the build computer cannot do that.

Not in this plan

  • TLS inside ShareCraft itself (certificates, ACME). The proxy or tunnel does it.
  • Single sign-on, multi-factor sign-in and password reset by email (SC-11). Production mode makes them more urgent; each is its own plan.
  • A Windows service, or starting before anyone signs in to Windows.
  • Serving under a path, or at more than one public address.
  • Rate limits on routes other than sign-in and anyone-link lookups. The API's other routes all need a session.
  • Linux and macOS packages. The server settings work there unchanged; only the Windows scripts are updated here.

Global constraints

  • Settings (read in Config::from_env; none is a secret, all are safe to print):
    VariableDefaultMeaning
    SHARECRAFT_PUBLIC_URLunsetUnset: development mode, exactly as today. Set: production mode at this https:// origin.
    SHARECRAFT_TRUSTED_PROXIES127.0.0.1, ::1 in production; ignored in developmentAddresses and ranges whose forwarded headers are believed.
    SHARECRAFT_HSTS_SECONDS31536000The HSTS max-age; 0 withdraws it.
    SHARECRAFT_ADDR127.0.0.1:8787Unchanged in development (loopback only). In production any address is allowed, because untrusted peers are refused anyway.
  • Refusals at start (each a ConfigError with a plain-English message, and the process exits):
    • PublicUrlNotHttps: the public address starts with anything but https://.
    • BadPublicUrl: not a URL, or it has a path other than /, a query, a fragment, a user name or password, or a host that is not lowercase ASCII (international names must be given in their xn-- form).
    • BadTrustedProxies: an entry is not an address or range, or a range is wider than allowed (proposal 2).
    • ProxiesWithoutPublicUrl: SHARECRAFT_TRUSTED_PROXIES is set but the public address is not, so the owner meant production mode and missed a setting.
    • NotLoopback: as today, in development mode only.
  • Start-up message: development mode prints today's two lines unchanged. Production mode prints ShareCraft server listening on <addr>, then Production mode: public address https://share.example.com, trusted proxies 127.0.0.1, ::1.
  • The source of a request (Source, set by one middleware in front of every route, including the static files and the WebSocket):
    • Development: client_ip is the peer; https is false; nothing forwarded is read.
    • Production, peer is a trusted proxy: client_ip comes from X-Forwarded-For as in proposal 3 (the peer itself if the header is missing or unreadable); https is true only if the last X-Forwarded-Proto value is exactly https; the host is X-Forwarded-Host if present, otherwise Host.
    • Production, peer is not a trusted proxy: 403 with a plain-text body, except GET /healthz from loopback.
    • Several X-Forwarded-Host or X-Forwarded-Proto headers, or a list in one, are read from the last value, which is the one the nearest proxy wrote.
  • The origin check (same_origin becomes Deployment::same_origin(&HeaderMap, &Source); used by require_same_origin in api/mod.rs, by ws.rs and by editors.rs):
    • Development: unchanged, byte for byte.
    • Production: the host (port included, default 443 left out on both sides) must equal the public address's host, ignoring case; Source.https must be true; and, if Origin is present, it must equal the public origin exactly, ignoring case. Origin: null is refused.
    • As today, every /api request other than GET must carry Origin. That rule, with the exact-origin match, is the cross-site request protection, and it does not change.
    • The WebSocket refusal message changes from “only local, same-origin connections are allowed” to “only same-origin connections are allowed” in both modes.
  • Cookies (auth.rs): the name and attributes come from Deployment.
    • Development: sharecraft_session=…; HttpOnly; SameSite=Lax; Path=/; Max-Age=…, as today.
    • Production: proposal 6. The cleared cookie uses the same name and attributes with Max-Age=0.
    • Production reads only __Host-sharecraft_session; a leftover development cookie is ignored, never accepted.
  • Security headers (security_headers in lib.rs):
    • Kept in both modes, with the same rule that an answer's own value wins: Content-Security-Policy (default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; frame-src 'self'; frame-ancestors 'none'), an editor's own policy, a download's sandbox, X-Content-Type-Options: nosniff, Referrer-Policy: same-origin, and no-referrer on link pages.
    • Production adds Strict-Transport-Security on every answer, errors and the 308 redirect included, but not on 403 answers to untrusted peers (they never came over HTTPS).
    • 'self' in the policy already means the public origin when the page is loaded from it; no address is written into the policy.
  • Addresses the server writes: every address built from Host today is built from the public address in production. Known: link_url in api/links.rs. Task 5 greps for http:// and HOST across crates/server/src and web/ to find any other. Development keeps http://<Host>.
  • Sign-in (api/session.rs, auth.rs, records/src/accounts.rs):
    • The order of checks is: the address limit, then the account limit, then a slot from the password-check pool, then the password. Each limit refusal answers the same 429 too_many_attempts with Retry-After, whether or not the account exists.
    • Timing: an unknown email already pays for one Argon2 check against the dummy hash. The remaining difference, the sign_in.failed event written only for a known account, moves to a task spawned after the answer is decided, so the answer's time does not depend on whether the account exists.
    • The address limit is keyed by Source.client_ip, so in development every attempt counts against 127.0.0.1. The development limit stays at 30, which tests and a single person never reach.
    • Password rules are unchanged: 10 to the maximum length in accounts.rs, Argon2 hashing, longer passwords checked against the dummy hash.
    • Both throttle tables keep today's bound (10,000 entries) and today's eviction rule.
  • Anyone-link lookups: an address that gets 60 404 link_not_found answers within 15 minutes gets 429 too_many_attempts for /api/l/ until the oldest is 15 minutes old. Tokens are long and random, so this only slows mass guessing; working links are never counted.
  • Events: sign_in.locked {by: "account" | "address", until}, recorded once when a lock starts, with the account as subject when known. The client address is recorded in it, and nowhere else new.
  • Errors (each with a plain-English message in common.js):
    • too_many_attempts 429 (kept; now with Retry-After)
    • busy 503 with Retry-After: 10
    • https_required 403
    • forbidden 403 (kept, for a failed origin check)
  • Upgrade: no database migration. An installation that sets nothing behaves exactly as before.

Review focus

  1. Nobody can forge where a request came from. Covered by Task 2, forwarded_headers_only_from_trusted_proxies:
    • an untrusted peer sending X-Forwarded-For, X-Forwarded-Proto: https and X-Forwarded-Host;
    • a client behind the trusted proxy adding its own X-Forwarded-For: 1.2.3.4 before the proxy's entry;
    • a chain of two trusted proxies;
    • repeated and comma-joined header values, empty values, and values that are not addresses.
    Each gives the right client address, or a refusal, never the forged one.
  2. Cross-site requests stay refused at the public address. Covered by Task 2, public_origin_check: Origin of another site, of http:// the public host, of the public host with another port, of null, and missing on a POST; a Host of another name (DNS rebinding); and the same for the WebSocket and editor routes.
  3. Nothing works over plain HTTP in production, and development mode is unchanged. Covered by Task 2, plain_http_refused, and the existing tests, which run in development mode and must pass untouched.
  4. The cookie is never sent or accepted unsafely. Covered by Task 3, production_cookie_attributes and development_cookie_ignored_in_production.
  5. Sign-in reveals nothing and cannot be hammered. Covered by Task 4: limits_per_account_and_address, locked_even_with_right_password, same_work_for_unknown_and_known_accounts (counts Argon2 checks and database writes before the answer, rather than timing them) and password_checks_are_pooled.
