File share surfacing: a library that shows the files of a file share: implementation plan

ShareCraft · Stage 2 platform plan 6, phase A2 of SC-27 (storage-source libraries) · Written 17 November 2026 · Draft for the owner

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes. In this plan Codex writes all code and runs all tests; each task card is the brief for one Codex run, and the controller only commits, writes one ledger line and dispatches the next run (section "How this plan is executed").

Goal: an administrator approves folders the ShareCraft server may read, and a site manager connects a library to one of them: a UNC path (\\server\share\folder) or a path on the server. The share's folders and files appear in the library within minutes. Permissions, inheritance, sharing links, previews, thumbnails, malware scanning and file-type limits work on them. The files are not copied to the server: bytes are read from the share when someone opens, previews or downloads a file, scanned on that first read, kept in a size-bounded cache, and never counted against the site's quota. The library cannot be changed in ShareCraft (read-only; the share stays the source of truth).

Architecture:

  • The same connected-library attribute as GitHub. library_sources gains kind share; source_items maps each node to its path on the share. The read-only guard, the advisory lock, generation compare-and-set, the worker with backoff, the events and the pages are reused.
  • Items are real tree nodes; their content is external. Each folder and file is an ordinary nodes row and each file an ordinary documents row, created with the existing tree::create_document, but with no stored revision. Its source_items row records where the bytes are: size, modified time, and the SHA-256 once the file has been read. Code that does not know about external content sees a file that was never saved (HTTP 204, no thumbnail), so nothing can serve unscanned bytes by accident. See proposal 1.
  • Fetch on first use. One function, external::materialise, is the only way bytes leave a share: it checks the path is still approved, asks the share for the file's size and time, reads it once into the content store while hashing it (single flight per file, four reads at a time), pins it in a least-recently-used cache, waits for the scan, and hands back the stored content. Download, preview, thumbnail and link routes call it where they find no stored revision.
  • A listing engine walks the share by size and modified time under a budget (files, time, folders at once), and feeds the existing planner and apply step through a small StorageSource trait that the GitHub source also implements (proposal 3).
  • No credentials are stored. The server reads the share as the account it runs under. A stored, sealed account can be added later through the existing secrets.rs and the unused token_secret column; nothing here closes that door.

Tech stack: the existing workspace. No new dependency. File access uses std::fs (and std::os::windows::fs::MetadataExt for attributes) inside tokio::task::spawn_blocking; hashing uses the content store's existing writer. No unsafe, so native change notifications (ReadDirectoryChangesW) are not possible here and are a later optimisation.

Spec: s3-surfacing-design.html v0.3 (sections 03 to 11, the file-server table in section 13, phase A2 in section 14), scope.html SC-27 and D61 to D64, the GitHub surfacing plan and BUILDING.html section 33 (what it delivered and deferred). Owner decisions of 17 November 2026 (binding): file share is the next source; no versioning; read-only first; files are not copied and do not count against quota; the server's own account, with administrator-approved root paths; polling by size and modified time; every member of a case-colliding group is numbered; reuse, do not duplicate; DriveCraft sees ordinary nodes.

Proposals in this plan for the owner to check

Choices the owner's decisions did not settle. Approving the plan approves them; any can be changed before building. The six marked open question are repeated at the end with the alternative.

  1. External content is "a file with no stored revision plus a record of where its bytes are". Nothing changes in Git's document records, the revisions crate or the collaboration spine. The pages are told a revision of the form x<size>-<modified time> (the external tag), which can never be a Git revision, so their existing download and "newer version" logic works. The alternative, a real Git revision holding an external pointer (a new Content variant), would add a Git commit per file per change, touch the spine that co-authoring is changing, and make every missed case a compile error rather than a safe "no content"; it was rejected for size and risk.
  2. The cache lives in the content store (files named by SHA-256), pinned by a new source_cache table so the sweeper does not erase it and scans find it. Default size 10 GiB, least recently used first out; content being read is never evicted. External files have no revisions rows, so site usage and quota are untouched by construction.
  3. The StorageSource trait is extracted now, small: "look at the source", "which bytes to fetch before applying", "limits", "mirrored or external". The GitHub code moves behind it without behaviour change. The design's larger trait (put, copy, delete, change feed) waits for write-back and S3.
  4. Only document and image libraries can be connected to a share in this release. Template and asset libraries copy stored content into other places (new-from-template, brand images) and are refused with a plain message.
  5. Copying out of a share library is refused in this release (HTTP 409, "download it instead"). Open question 3.
  6. Disconnecting empties the library. There are no bytes to keep, so the listed items go to the recycle bin and the library becomes an ordinary empty one. Nothing on the share is touched. Open question 2.
  7. A file missing from one listing is kept for one more poll before it goes to the recycle bin, so a save in progress or a brief outage does not lose the file's permissions and links. A bin entry from a share holds no content.
  8. Who may connect: anyone who may create a library in the site, but only inside an administrator-approved root. The full path is shown to library owners; others see only that it is a file share. Open question 1.
  9. Hidden and counted, never followed or shown: symbolic links and junctions; files with the Windows Hidden or System attribute; Thumbs.db, desktop.ini, .DS_Store, ~$* lock files; cloud placeholders (files marked offline or recall-on-open); names ShareCraft or Windows refuses; paths over 400 characters; folders the server may not read. Open question 4 (a per-library switch).
  10. Freshness: every open asks the share for the file's size and modified time (one cheap call). If they differ from the listing, the fresh file is read and a new listing is started. If the share cannot be reached, a cached copy is still served and other files answer a plain "the share cannot be reached".
  11. Scan on first read. With a scanner configured, the first open waits up to 20 seconds for the verdict and otherwise answers the existing held state; the page tries again. The verdict belongs to the content hash, so it survives eviction only while the content stays stored.
  12. Limits: the existing source_max_files (default 50,000) caps files per library; listing time is capped (default 10 minutes); a file larger than half the cache, or than the server's largest file, is hidden as too big. Open questions 5 and 6.

Not in this plan

  • Write-back (upload, rename, delete, editor saves written to the share with temporary-file-and-rename). A later plan; the tag recorded per item is the base it needs.
  • A stored account for shares the server's own account cannot read. The token_secret column and secrets.rs stay available for it.
  • Native change notifications, and any incremental listing. Every poll is a full listing, which is also the reconcile.
  • Reading NTFS or share permissions. ShareCraft permissions govern; the settings page says so.
  • DriveCraft sync (phase B) and search. What they must do about external content is recorded in Task 14 and below, not built.
  • Copying out, template and asset kinds, version history, a per-library switch for hidden files, a cost panel, S3 and Azure.

DriveCraft advisory (owner item 8). A share library is ordinary nodes for the SC-23 feed. DriveCraft keeps every file whole on disk, so syncing a share library reads the whole share through ShareCraft once, loads the file server, and turns the cache over. When SC-23 is built: the library must advertise that its content is fetched on demand and its total size, so DriveCraft asks before syncing it and offers folder selection; an item with no SHA-256 yet is normal (the hash is stated in the download answer); an unavailable item (denied, gone, too large, held) carries its reason and DriveCraft must keep its local copy and list it under Problems. The numbering of case-colliding names protects Windows clients here exactly as for GitHub.

Review focus

Conditions the happy path never meets. Each has a named test in the task that owns the code; the final review (Task 12) checks them again across the branch.

  1. Escaping the approved root. .., a junction or symbolic link pointing out, \\?\ and \\.\ prefixes, device names (CON, NUL, COM1), alternate data streams (file.txt:secret), an administrative share (C$) nobody approved, the ShareCraft data folder itself, and a root whose approval was withdrawn while content is cached (Tasks 1, 5, 7, 9).

  4.   5. The read-only guard is complete. Every new route is classified in the route-list test; share libraries refuse what GitHub libraries refuse, and copying out as well (Tasks 8, 9).
  6. Nothing counts against quota, and nothing is written to the share. Asserted, not assumed (Tasks 6, 7).

Rules. parse is pure string work and behaves the same on every operating system. It accepts \\server\share[\folder…] (also written with /), X:\folder…, and /folder…. It refuses: an empty or relative path; anything starting \\?\, \\.\ or //?/, //./ (DevicePrefix); a . or .. segment (Traversal); an empty segment; a control character or any of " * < > ? |, and a : anywhere but after a drive letter (Stream for a colon inside a segment); a segment that is a Windows device name with or without an extension, any case (CON, PRN, AUX, NUL, COM1–COM9, LPT1–LPT9); a segment ending in a dot or a space; more than 1,000 characters. Trailing separators are dropped. Comparison (is_within, approved_root) ignores case for UNC and drive paths (Unicode lower-case) and is exact for POSIX paths, and is by whole segments (\\s\share\ab is not within \\s\share\a). valid_root refuses a bare drive (C:\) and a bare administrative share (\\s\C$) as WholeDrive: an administrator approves a folder, not a whole drive. An administrative share is therefore usable only below a root an administrator typed in full. windows_safe_name is false for the device names, a trailing dot or space, and the characters above. hidden_by_default is true, ignoring case, for Thumbs.db, desktop.ini, .DS_Store and names starting ~$. validate accepts share_roots only as an array of at most 20 strings that each parse and pass valid_root. share_settings skips a stored root that no longer parses (logged), never panics.
