File share libraries: a library whose files are stored on a file share: implementation plan

ShareCraft · Stage 2 platform plan 6, phase A2 of SC-27 (storage-source libraries) · Written 17 November 2026, revised the same day for read and write · Draft for the owner

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes. In this plan Codex writes all code and runs all tests; each task card is the brief for one Codex run, and the controller only commits, writes one ledger line and dispatches the next run (section "How this plan is executed").

Two phases in one document. Phase 1 (Tasks 1 to 14) connects a library to a share, lists it, reads files on first use into a bounded cache, and is read-only; it is usable on its own and ends with a controller check. Phase 2 (Tasks 15 to 27) makes the share the library's storage: every write in ShareCraft is written through to the share, with soft delete, conflicts, editor saves and a per-library read-only switch; it ends with its own controller check. Phase 2 starts only after Phase 1's check has passed.

Goal: an administrator approves folders the ShareCraft server may use, and a site manager connects a library to one of them: a UNC path (\\server\share\folder) or a path on the server. The share is the storage for the library's files. Its folders and files appear in the library within minutes; permissions, inheritance, sharing links, previews, thumbnails, malware scanning and file-type limits work on them. Files are not copied to the server: bytes are read from the share when someone opens a file, scanned on that first read, kept in a size-bounded cache, and never counted against the site's quota. By default the library is read and write: creating a folder, uploading, replacing, renaming, moving, deleting and saving from an editor all change the share, safely and without overwriting anyone's outside change. An owner can make a library read-only when connecting it or later.

Architecture:

  • The same connected-library attribute as GitHub. library_sources gains kind share and a mode (read and write, or read-only); source_items maps each node to its path on the share. The advisory lock, generation compare-and-set, the worker with backoff, the events and the pages are reused. The read-only guard becomes mode-aware in Phase 2.
  • Items are real tree nodes; their content is external. Each folder and file is an ordinary nodes row and each file an ordinary documents row, created with the existing tree::create_document, but with no stored revision in Git. Its source_items row records where the bytes are (size, modified time, the SHA-256 once read) and a revision id of its own: 40 hexadecimal characters, made new whenever the content is seen to change. The pages, the file sessions and the spine rules (S3, S4: a change names the revision it is based on) use that id exactly as they use a Git revision. Code that does not know about external content sees a file that was never saved (HTTP 204, no thumbnail), so nothing can serve unscanned bytes by accident. See proposal 1.
  • Fetch on first use. One function, external::materialise, is the only way bytes are read from a share: it checks the path is still approved, asks the share for the file's size and time, reads it once into the content store while hashing it (single flight per file, four reads at a time), pins it in a least-recently-used cache, waits for the scan, and hands back the stored content.
  • Write-through (Phase 2). New content is first staged in the cache and scanned; only then is it written to the share: a temporary file in the same folder, flushed, checked, the target compared with the revision the change was based on, then one rename over the target. If the share's file changed meanwhile it is never overwritten: the change is saved beside it as name (edited by <person> <time>).ext. One module, share_write.rs, is the only code that changes anything on a share.
  • A listing engine walks the share by size and modified time under a budget, and feeds the existing planner and apply step through a small StorageSource trait that the GitHub source also implements (proposal 3).
  • No credentials are stored. The server uses the share as the account it runs under; that account's rights on the share are the outer limit, and ShareCraft permissions decide who may do what inside it. A stored, sealed account can be added later through secrets.rs and the unused token_secret column.

Tech stack: the existing workspace. Phase 1 adds no dependency. Phase 2 adds none except, in Task 22 only and only if its checks pass, the trash crate (MIT) for the Windows Recycle Bin on local folders. File access uses std::fs (and std::os::windows::fs::MetadataExt for attributes) inside tokio::task::spawn_blocking. No unsafe, so native change notifications are not possible here.

Proposals in this plan for the owner to check

Choices the owner's decisions did not settle. Approving the plan approves them; any can be changed before building. Those marked open question are repeated at the end with the alternative.

  1. External content is "a file with no stored Git revision, plus a record of where its bytes are and a revision id of its own". Nothing changes in Git's document records or the revisions crate. The alternative, a real Git revision holding an external pointer, would add a Git commit per file per change and touch the spine that co-authoring is changing; it was rejected for size and risk.
  2. The cache lives in the content store (files named by SHA-256), pinned by a source_cache table so the sweeper does not erase it and scans find it. Default 10 GiB, least recently used first out; content being read or waiting to be written is never evicted. External files have no revisions rows, so site usage and quota are untouched by construction; uploads into a share library reserve nothing.
  3. The StorageSource trait is extracted now, small: "look at the source", "which bytes to fetch before applying", "limits", "mirrored or external". The GitHub code moves behind it without behaviour change. Writing is not in the trait yet: the share's write module is concrete, and the trait grows when S3 needs the same.
  4. Only document and image libraries can be connected to a share. Template and asset libraries are refused with a plain message.
  5. Phase 1 is read-only for every share library; Phase 2 makes read and write the default for new connections and lets an owner switch an existing library either way.
  6. Staged content is the current revision. Once a save or upload is accepted, the file shows as saving, its new revision id is the current one, and people with access read the staged bytes from the cache (after the scan), while the share still holds the previous content until the write lands. Open question 3.
  7. Writes to the share are coalesced: at most one write per file every 30 seconds while it is being edited, and at once when an upload finishes or the editing session ends. A failed write is retried (30 seconds doubling to 10 minutes) and shown with a Retry button; the staged content is kept until it is written, replaced or discarded by its author.
  8. Moving between libraries is refused; copying is allowed in every direction, within limits: a copy out of a share library is read and stored as ordinary files that count against the destination's quota; a copy into one is written through. Open question 4.
  9. A file that vanishes from the share (deleted there by someone else) is kept for one more poll, then goes to ShareCraft's recycle bin marked "deleted on the share; ShareCraft holds no copy" and cannot be restored. A delete made in ShareCraft records where the real file went and can be restored.
  10. Disconnecting removes the items from ShareCraft and touches nothing on the share, the holding folder included. Open question 5.
  11. Who may connect: anyone who may create a library in the site, but only inside an administrator-approved root. The full path is shown to library owners; others see only that it is a file share. Open question 2.
  12. Hidden and counted, never followed or shown: symbolic links and junctions; files with the Windows Hidden or System attribute; Thumbs.db, desktop.ini, .DS_Store, ~$* lock files; cloud placeholders; names ShareCraft or Windows refuses; paths over 400 characters; folders the server may not read. ShareCraft's own .sharecraft-bin folder and .sharecraft-tmp-* files are skipped and not counted.
  13. Freshness: every open asks the share for the file's size and modified time. If they differ from the listing, the fresh file is read and a new listing is started. If the share cannot be reached, a cached copy is still served and other files answer a plain "the share cannot be reached".
  14. Scan gates both directions. A file is scanned on its first read before it is served, and new content is scanned before it is written to the share. With no scanner configured both pass, as uploads do today.
  15. Limits: the existing source_max_files (default 50,000) caps files per library; listing time is capped (default 10 minutes); a file larger than half the cache, or than the server's largest file, is hidden as too big and cannot be uploaded. Open question 6.

Not in this plan

  • A stored account for shares the server's own account cannot use. The token_secret column and secrets.rs stay available for it.
  • Native change notifications, and any incremental listing. Every poll is a full listing, which is also the reconcile.
  • Versioning. A share keeps one version; ShareCraft does not invent a history it cannot restore.
  • Reading NTFS or share permissions to decide who sees what. ShareCraft permissions govern inside what the server's account can reach.
  • The SC-23 sync API and search. DriveCraft uploads reach a share library through the same guarded routes and the same staged-write path when SC-23 is built (Stage 4); what SC-23 must carry is recorded below and in Task 27.
  • Moving items between libraries, template and asset kinds, new-from-template into a share library, a cost panel, a per-library switch for hidden files, S3 and Azure.

DriveCraft (owner item 8). A share library is ordinary nodes for the SC-23 feed. DriveCraft keeps every file whole on disk, so syncing a share library reads the whole share through ShareCraft once; the library must advertise that its content is fetched on demand, its total size, and whether it is read-only, so DriveCraft asks before syncing and never queues an upload to a read-only library. An item's etag is its revision id; an upload that replaces a file names that id and gets a conflict if it is stale, which DriveCraft already turns into a conflict copy. An item with no SHA-256 yet is normal. An item that is saving is not offered until it is written; an unavailable item carries its reason and DriveCraft keeps its local copy and lists it under Problems. The numbering of case-colliding names protects Windows clients exactly as for GitHub.

Review focus

Conditions the happy path never meets. Each has a named test in the task that owns the code; the final review (Task 12) checks them again across the branch.

  1. Escaping the approved root. .., a junction or symbolic link pointing out, \\?\ and \\.\ prefixes, device names (CON, NUL, COM1), alternate data streams (file.txt:secret), an administrative share (C$) nobody approved, the ShareCraft data folder itself, and a root whose approval was withdrawn while content is cached (Tasks 1, 5, 7, 9).
  2. A listing that is cut short must delete nothing. Share offline, time budget passed, too many files, one unreadable sub-folder: the library keeps what it had (Tasks 5, 6).
  3. Bytes served without the scan gate, or from the wrong file. Every route that hands out bytes goes through materialise; a file that changed, vanished or was swapped between listing and read is detected; a torn read is never cached (Tasks 7, 8).
  4. Races the GitHub work met: a sync finishing after a change or disconnect (generation compare-and-set), two first reads of one file (single flight), eviction during a read (hold), a read finishing after the listing moved the tag (compare-and-set on the tag), a long first listing blocking disconnect (the apply loop stops when the generation moves), stale syncing recovery only with the lock free (Tasks 6, 7, 9, 10).
  5. The read-only guard is complete. Every new route is classified in the route-list test; share libraries refuse what GitHub libraries refuse, and copying out as well (Tasks 8, 9).
  6. Nothing counts against quota, and Phase 1 writes nothing to the share. Asserted, not assumed (Tasks 6, 7).
  7. Phase 2: a write that destroys something. An outside change overwritten; a rename that lands on an existing file; a file open in another program; a write to a share that went offline half way; a temporary file left behind; a delete that was meant to be soft and was not; content written before its scan; a save accepted and then lost on a restart (Tasks 16, 19, 20, 21).
  8. Phase 2: the guard per mode. A read-only share library and every GitHub library refuse exactly what they refuse today; a read and write library either writes through or refuses with a stated code, route by route, and a route added later fails the test until it is decided for both modes (Task 17).

Rules. parse is pure string work and behaves the same on every operating system. It accepts \\server\share[\folder…] (also written with /), X:\folder…, and /folder…. It refuses: an empty or relative path; anything starting \\?\, \\.\ or //?/, //./ (DevicePrefix); a . or .. segment (Traversal); an empty segment; a control character or any of " * < > ? |, and a : anywhere but after a drive letter (Stream for a colon inside a segment); a segment that is a Windows device name with or without an extension, any case (CON, PRN, AUX, NUL, COM1–COM9, LPT1–LPT9); a segment ending in a dot or a space; more than 1,000 characters. Trailing separators are dropped. Comparison (is_within, approved_root) ignores case for UNC and drive paths (Unicode lower-case) and is exact for POSIX paths, and is by whole segments (\\s\share\ab is not within \\s\share\a). valid_root refuses a bare drive (C:\) and a bare administrative share (\\s\C$) as WholeDrive: an administrator approves a folder, not a whole drive.   3. Unless the library is marked offline, stat the path on a blocking thread with a STAT_WAIT time limit. A time-out or an unreachable error marks the library offline for OFFLINE_FOR.

Phase 2: the share as storage (read and write)

Phase 2 starts after Task 13 has passed. It changes Phase 1 in three stated places: the guard becomes mode-aware (Task 17), the copy refusal of Task 8 is replaced (Task 23), and bin entries from a share gain a record of where the real file went (Tasks 15 and 21).

How a write flows. Every ShareCraft write to a share library is one of two kinds. A structure change (new folder, rename, move, delete, restore) is made on the share first and, when that succeeds, in the tree and the tracking rows; if the tree step fails the share step is undone, and if that fails too the next listing repairs it. A content change (new file, replaced file, editor save) is staged: the bytes go into the cache and are pinned, a source_writes row records them with the revision they were based on, the file shows as saving, and a worker writes them to the share once the scanner has passed them. Both kinds name the revision they are based on (S3, S4); a stale base is an explicit conflict, never an overwrite.

What is atomic. std::fs::rename on Windows is one MoveFileExW call with replace-existing (newer Rust tries the POSIX-semantics rename first). On a local NTFS folder, and on a share served by Windows from NTFS, the client sends one rename request and other readers see either the old file or the new one, never a mixture; a rename of a folder within one share is likewise one operation, whatever the folder holds. On a NAS or Samba server it is as atomic as that server's own file system makes a rename, which is normally the same. Not atomic: "compare the target with the base, then rename" is two steps, so an outside program that writes the target in the instant between them is overwritten; and a rename fails, rather than waits, when another program holds the target open without sharing delete access (Office does), which is reported as locked. Creating a file that must not exist uses create_new, which is atomic, to reserve the name.

Someone who can create a junction on the share in that instant could make the server read or write outside the root, within what its account may reach. Closing it needs a handle-based check, which needs unsafe or a new crate.
  • Locked files. Office keeps documents open without sharing delete access, so replacing or deleting a file someone has open on the share fails and waits for a retry. This is the right outcome but will be common where people use both ways in.
  • The Windows Recycle Bin (Task 22). I did not verify the trash crate's current licence set, its Windows list and restore support, or its behaviour for a service account or a mapped drive; the task verifies them first and may end "not adopted". A drive letter that is really a network mapping would delete for good, which is why the canary exists.
  • The holding folder is visible on the share as .sharecraft-bin: std offers no safe way to set the Windows Hidden attribute. People using the share directly can see and empty it; restore then says the file is gone.
  • Staged content lives only in the cache until written. It is pinned and survives a restart, but a lost data folder before the write loses the change. A share that stays offline keeps changes waiting indefinitely, visible as "saving" or failed.
  • One Git commit per listed or created file. A first listing of 50,000 files may take tens of minutes and shares the tree lock with people working. Task 6 measures the rate.
  • Blocked threads on a dead share. A Windows call to an unreachable server can hang for a minute; requests time out and the library is marked offline, but the blocked thread stays until Windows returns.
  • Moves are guessed by the listing from equal size and modified time; same-size edits with a restored timestamp are not seen until the content is read again. Both are the design's stated limits.
  • Large files wait on first read (read whole, then scanned) and on write (scanned, then copied, then read back up to 256 MiB to verify).
  • Not verified: how std::fs::canonicalize answers for DFS paths and NAS shares; whether FileType::is_symlink covers every junction form; the projection and adoption code on documents that keep a null Git revision for good; the exact error codes Windows returns for a sharing violation over SMB from a NAS (the Locked and Denied mapping is tested on the fake and on local NTFS only); the pages' behaviour with revision ids that are not Git commits (Task 8's editor test and the controller checks cover it).
  • Exposure and reach are by design: the server's account reads and now writes everything under an approved root, and ShareCraft permissions decide who may. A carelessly approved root is exposed, and writable, to whoever a site manager chooses.

Open questions for the owner

  1. Local-folder deletes. Decided direction: the Windows Recycle Bin. It needs the trash crate (and the Windows API crate it brings), is the server account's bin, and may not exist when the server runs as a service. Proposed: build the holding folder for every library first (Task 21) and add the Recycle Bin for local folders as Task 22, adopted only if its checks and canary pass, falling back to the holding folder otherwise. Alternative: the holding folder everywhere and no new crate. Recommendation: as proposed; be ready to accept "holding folder everywhere" if Task 22 reports badly.
  2. Who may connect a share? Proposed: anyone who may create a library in the site, inside an approved root. Alternative: administrators only. Recommendation: as proposed for read-only; for read and write the stakes are higher, so consider administrators only until a first site has used it.
  3. May people read a change before it reaches the share? Proposed: yes; once accepted and scanned, the staged content is the file's current content in ShareCraft while it shows "saving". Alternative: show the share's old content until the write lands. Recommendation: as proposed; otherwise an author saves and sees their change disappear.
  4. Between libraries: proposed copy allowed (500 files and 2 GiB at a time; a copy out counts against the destination's quota), move refused. Alternative: allow move as copy then delete. Recommendation: as proposed; add move once copy has been used.
  5. Disconnect. Proposed: the items leave ShareCraft, the share and its holding folder are untouched, and it is refused while changes are waiting. Alternative: also empty the holding folder. Recommendation: as proposed; never delete from a share on disconnect.
  6. Default limits. Proposed: 50,000 files per library, a 10 GiB cache, a 10 minute listing limit, a file over half the cache refused, one write per file per 30 seconds while editing, 93 days in the holding folder. Recommendation: accept, and revisit the file cap after Task 6 reports the measured rate.
