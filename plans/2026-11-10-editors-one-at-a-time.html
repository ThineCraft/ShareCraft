Editors, One Person at a Time: Implementation Plan

ShareCraft · Stage 1, part 3 of 3 · Written 10 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps are checkbox items. Do not tick them in this file; the execution ledger is the record.

Needs the owner's go-ahead before execution. This plan does three things outside the ShareCraft repository: it creates four public forks in the ThineCraft organization on GitHub (Tasks 7 to 10), pushes a sharecraft branch to each, and installs the trunk build tool for the current user with cargo install (Task 6, no administrator rights). Approving the plan approves these and nothing else outside the repository.

Goal: a GridCraft, WordCraft, PdfCraft and SolidCraft file each opens in the browser from ShareCraft, in the real editor, and saves back as a Git revision credited to the person who saved it. One person edits at a time. Removing someone's access closes the file on their screen at once.

Architecture: a document gains an editor: the built-in text editor, or one of the four forks. A file document's content is opaque bytes to ShareCraft. Opening one joins a file session over the same WebSocket route, account check and access commands as a text document; the session has one editing seat and holds no content. Bytes travel over HTTP: the page downloads the current revision, and a save is an upload that the document's room accepts only from the seat holder, based on the room's current revision. Each editor is the fork's own browser build, served by ShareCraft as static files from the same origin, inside a frame page that ShareCraft owns. The frame page talks to the editor through the bridge the editor already has.

Tech stack (added): trunk (builds the editors; not a dependency of the server), toml in xtask. No new server dependencies are expected; if one is needed, add it with cargo add at its current stable release with the fewest features that work.

Spec: scope.html (D12, D14 to D19, SC-15, SC-24, A17), sequencing.html (Stage 1; spine rules S3, S4, S6), editor-readiness.html and docs/editor-frame.html. Read them, and BUILDING.html, before starting.

Global constraints

  • Everything in plan 2's global constraints still holds: Rust for server code (D14); MIT OR Apache-2.0 and no copyleft dependencies (D17); no organization identifiers (D18); secrets never printed, logged or committed; SQL with bind parameters only; every route through the Signed extractor and Db::role; 404 for no access; loopback only; workspace lints (no unsafe, unwrap, expect, panic! or panicking indexing outside tests); tests use the real PostgreSQL in TEST_DATABASE_URL and are never skipped.
  • No save path around the spine (D15): after a document is created, its content changes only through its room. RevisionStore::checkpoint stays the only code that writes content (S3), and every write states the revision it was based on (S4).
  • ShareCraft never interprets a file document's bytes (S6). It never serves them in a way a browser will render: always Content-Type: application/octet-stream, Content-Disposition: attachment, X-Content-Type-Options: nosniff, Content-Security-Policy: sandbox and Cache-Control: no-store.
  • Events never contain file content.
  • Editor builds are not committed to ShareCraft. They live in editors/ at the repository root, which is git-ignored. Fork source is not copied into ShareCraft.
  • In the forks: work on a branch named sharecraft cut from the base commit in Task 6; leave the fork's default branch equal to upstream. Keep LICENSE-MIT, LICENSE-APACHE, NOTICE, ATTRIBUTION.md and every other licence or attribution file. Change as little as the task names. Never push to, or open a pull request against, an upstream repository. Follow each fork's own lint and test commands for the files touched.
  • Fork changes are stated in the fork's NOTICE under a heading Changes made for ShareCraft: one line per change, with the date. Apache 2.0 asks that modified files be marked; this is where.
  • A fork must not present itself as ArtCraft or imply endorsement by Tangency Labs. Plain text "based on GridCraft by the ArtCraft team" (and likewise) is allowed and is used.
  • Page scripts hold no permission logic: what a person may do is decided by the server and told to the page.
  • Work in ShareCraft on branch stage-1-editors. Run cargo xtask check before each commit. Commit after each task with the message given. Do not push ShareCraft; push a fork's sharecraft branch only in the step that says so.
  • Editor builds are slow and large. Use one shared CARGO_TARGET_DIR per fork outside the repository, build one editor at a time, and run builds in the background.

Review focus

Conditions the scope implies that are most likely to hurt a real person. Each has a test in the task named.

  1. A save that ShareCraft refuses after the editor has marked the file saved. The person must be told, the bytes must be kept in the page, and they must be able to try again or download their copy. Leaving the page must warn. (Task 5: refused_save_keeps_the_bytes; browser check in Task 7.)
  2. Access removed while the file is open. The editor must leave the screen within a second, a later save with the old seat must be refused, and the content must answer 404. (Task 3: removed_holder_loses_the_seat; Task 4: save_after_removal_is_refused.)
  3. Two people, or one person in two tabs, with the same file open. Only the seat holder's save is accepted; a save based on an older revision is refused and overwrites nothing. (Task 3: second_editor_does_not_get_the_seat; Task 4: save_without_the_seat_is_refused, save_on_an_old_revision_is_a_conflict.)
  4. An export mistaken for a save. A PDF or CSV the editor "saves" must become a download, never the stored workbook. (Task 5: exports_are_not_saves.)
  5. A hostile or oversized file. An uploaded HTML or SVG file must never run on ShareCraft's origin; a file over the limit is refused before it is stored; a bad name is refused. (Task 4: content_is_never_rendered, oversized_upload_is_refused, bad_file_names_are_refused.)

    Taken { by: Participant },

// server
pub(crate) enum SaveReply { Saved(RevisionId), Unchanged(RevisionId), NotHolder, Conflict { current: Option<RevisionId> }, Failed }
impl Rooms {
    // Asks doc's room to store `bytes`. NotHolder if no room is open.
    pub(crate) async fn save_file(&self, doc: DocId, user: UserId, token: &str,
                                  base: Option<RevisionId>, bytes: Vec<u8>) -> SaveReply;
}

Rules:

  • One WebSocket route, /ws/docs/{id}. The connection looks the document up as it does now and starts a file session when editor.is_file(). A text client's messages on a file document, and the reverse, close the connection.
  • The registry stays one entry per document: Rooms opens either kind, and send_to, send_all, link, order_access and the three access commands work on both without the callers knowing which. The hooks in api/mod.rs are not duplicated. Restructure room.rs as little as that needs; the text room's behaviour and tests do not change.
  • The room holds the document's current revision and stored fields, never its bytes. It reads them when it starts, as the text room does.
  • The seat. At most one connection holds it. A joining connection whose role can edit takes it if it is free. When the holder leaves, is removed, or loses the right to edit, the seat becomes free and everyone is sent Seat { free }; nobody is given it. A connection takes a free seat only by joining again, because its copy of the file may be old. The token changes every time the seat is given.
  • Saving. save_file is answered NotHolder unless user and token are the current holder's (compare the token in constant time). base must equal the room's revision, else Conflict. The write is one Checkpoint with the holder as the only author, run on a blocking task; everyone is sent Save { saving }, then Save { saved, revision }, and the revision is recorded as the text room records it. A store answer of Stale puts the room in conflict exactly as the text room: Save { conflict }, every later save Conflict, and the room ends when empty. Any other error is Save { failed } and Failed; the room carries on.
  • While a write runs, access commands are still handled at once and further saves wait their turn. A write that has started finishes even if the holder is removed meanwhile; its reply still goes back.
  • Access commands behave as in the text room: removal sends Removed as the last frame and drops the connection; a role change sends Access on every change of role. A join that races a removal gets Removed and no Joined (plan 2, finding F2).
  • Events: editing.joined, editing.left, save.written, save.failed, save.conflict as the text room reports them, plus seat.taken and seat.freed with the actor.
  • The room stays open for the configured grace period after the last connection leaves, then ends. There is nothing to save at the end.

Task 4: Content over HTTP

Files: create crates/server/src/api/content.rs, crates/server/tests/content.rs; modify crates/server/src/{api/mod.rs,lib.rs}.

Consumes: Rooms::save_file, SaveReply, Checkpointer, Editor, Config::max_file_bytes. Produces:

GET  /api/docs/{id}/content[?revision=<id>]
     200 bytes; headers from the global constraints, plus X-ShareCraft-Revision and a
     Content-Disposition file name taken from the stored name (RFC 6266, filename* for non-ASCII)
     204 when the document has no revision yet
PUT  /api/docs/{id}/content?base=<id>          header X-ShareCraft-Seat: <token>; body: the bytes
     200 {"revision": …, "changed": bool} | 403 not the seat holder | 409 {"current": …}
     | 413 over the limit | 503 the write failed
POST /api/docs/upload?name=<file name>           body: the bytes
     201 the document, as POST /api/docs answers

Rules:

  • Download needs any role on the document; a revision that is not one of this document's is 404. It works for text documents too.
  • Save needs a role that can edit, checked before the body is read, then goes through Rooms::save_file and nothing else. base absent means "no revision yet". It is refused with 400 for a text document. The handler's work runs to completion if the caller disconnects (plan 2, finding F1): the room owns the write, and the handler only waits for its answer.
  • Upload creates a new document and its first revision in one request: the editor comes from the name (400 if no editor opens it), the caller becomes owner, and the bytes are written with base: None through Checkpointer::write. This is creation, not an edit: nobody can have the document open. If the write fails after the row is made, the document stays, empty, and the answer is 503 naming it; an empty body is 400.
  • The body limit is max_file_bytes on these two routes only and is enforced while reading, not after. Other routes keep their limit.
  • Events: content.downloaded is not recorded (too frequent); upload records document.created with {"editor": …, "uploaded": true, "bytes": n}.

Write failing tests: upload_then_download_round_trips (bytes with every value 0 to 255); content_is_never_rendered (upload x.docx whose bytes are an HTML page with a script: the download has application/octet-stream, attachment, nosniff and sandbox); download_needs_access (404 for a stranger and when signed out); revision_of_another_document_is_not_found; empty_document_answers_no_content; save_with_the_seat_writes_a_revision (open a socket, take the token, save, download); save_without_the_seat_is_refused (no socket; a second editor; a viewer); save_on_an_old_revision_is_a_conflict (the answer names the current revision and nothing is written); save_after_removal_is_refused (revoke, then save with the token just held: 404, and the content answers 404); oversized_upload_is_refused and oversized_save_is_refused (limit set to 1 KiB by the harness; 413; no document or revision made); bad_file_names_are_refused (no extension, an unknown one, a separator, 300 characters); non_ascii_file_name_survives_download; save_is_refused_for_a_text_document; cross_origin_save_is_refused.

Rules:

  • file.html?doc=<id> is the frame from the concept, reduced to what a session of one needs: a slim bar with the way back, the document name, one status, a Save button, a Download link, and Share for owners (the Sharing panel from doc.js, moved to common.js so both pages use one copy); one banner line under it; the editor in an <iframe> filling the rest, with allow="clipboard-read; clipboard-write". The home page opens a file document here and a text document in doc.html.
  • Order of opening: fetch the document; if its editor is not in GET /api/editors, say "The … editor is not installed on this server." and offer Download only. Otherwise open the socket and join; on Joined download the content at revision (none if there is no revision); load the editor; on its ready, send open with the document's name and the bytes (no open for a document with no revision: the editor starts empty). An editor that sends failed, or no ready within 60 seconds, gets a banner with its error and Download.
  • Messages from the editor are accepted only when event.source is the frame's window and event.origin is the page's origin. The page posts to that origin only.
  • A save from the editor: classifySave is "save" only when the name ends with the document's native extension (ASCII case-insensitive); the editor's name is otherwise ignored. An export becomes a browser download under the editor's name and never touches the document. A save is uploaded with the seat token and the revision the page last knew; while it is in flight a newer save from the editor replaces any one waiting, so at most one waits.

People without the seat get the full editor under a banner, not a locked one.No editor has a view-only mode. Nothing they do can be stored.Someone may type for a while before reading the banner. A view-only switch in each fork is the fix, planned with Stage 2.
