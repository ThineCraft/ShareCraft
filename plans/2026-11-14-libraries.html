Libraries: kinds, any file type, malware scanning, previews and file policies: implementation plan

ShareCraft · Stage 2, platform plan 3C · Written 14 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: libraries at SharePoint's level for everyday files:

  • A library holds files of any type, not only the editors' four. Each new file is checked by the organisation's own malware scanner before anyone can open it, and infected files are quarantined.
  • Files that a browser can show safely get a preview, and image libraries show thumbnails.
  • A library is a document, image, template or asset library, and has settings: folders on or off, the file types it accepts, and the largest file it takes. Template libraries give the site its "New from template" choices.
  • Administrators can block file types for the whole organisation.

Architecture:

  • Library records: each library gets a second Git record, libraries/<xx>/<id>.json, beside its tree record. It holds the library's kind and settings and is mirrored into PostgreSQL as site records are (plan 3B: one commit per change, mirrored after it, taken back when refused, compared at every start).
  • Files without an editor: a file that no editor opens is a document with the new editor value other. It has versions, a recycle bin entry, sharing and quotas like any file, and opens as a preview or a download.
  • Scanning: the result belongs to the content, not the document. The blobs row records it, so the same bytes are scanned once. A scan worker sends each new upload to the scanner over ICAP. Until the content is clean, every route that would hand out its bytes refuses.
  • Previews: they come from a separate route that serves only a short list of safe types, with the same sandboxing as downloads. Thumbnails are made on the server, are kept beside the content store and are erased with it.

Tech stack: the existing workspace, plus the image crate (MIT or Apache 2.0), built with only its PNG, JPEG, GIF and WebP decoders and its PNG encoder, for thumbnails. The ICAP client is written in the server; it is small and has no dependency.

Spec: scope.html SC-02 (document, asset, image and template libraries; optional folder-free organisation; new-from-template; preview and unsupported previews; malware quarantine; library settings, upload validation and configurable file policies), SC-21, D28, D30 (a pluggable external scanner the organisation runs), D36 (any file type arrives in 3C with scanning). Plans 1 to 3B are the base. Owner decisions of 14 November 2026: the scanner is reached over ICAP; a new file is held until the scanner says it is clean (with no scanner configured, files are available at once; if the scanner is down files wait, unless an administrator lets them through); previews are what a browser can show safely, plus thumbnails made on the server for image libraries; the four kinds are as proposed (document as today; image: thumbnail grid and image-only uploads; template: its files are the site's "New from template" choices; asset: a library administrators mark for logos and brand images, used by branding in plan 4).

Proposals in this plan for the owner to check

These are choices the plan makes that the owner's answers did not settle. Approving the plan approves them; any can be changed before building.

  1. Saves from the editors are scanned afterwards, not held. Holding them would stop people reopening a spreadsheet they have just saved. An infected save is quarantined as soon as the scanner reports it. Uploads, new-version uploads and "New from template" copies are held until clean.
  2. Only administrators release or delete quarantined files. Site owners and the uploader see that a file is quarantined, and why, but cannot release it. A released file is marked clean for that content, and the release is recorded with the person and the reason.
  3. Files that existed before the upgrade are not scanned automatically. They were all files from the four editors, so they stay available and are marked "not scanned". An administrator can press "Scan existing files" to queue them.
  4. No file type is blocked by default, as in SharePoint today. Administrators can add types to an organisation block list, and a library can narrow what it accepts further.
  5. SVG images are shown only as images. They appear through an <img> element, which runs no script, and get no thumbnail. Text previews show at most the first 1 MiB. Files over the scanner's size limit wait for an administrator, unless an administrator lets large files through.

Not in this plan

  • Document sets, metadata panels and missing-information views (Stage 3, with columns and content types).
  • Previews converted on the server (other office formats, video thumbnails), and editing images.
  • Branding that uses asset libraries (plan 4).
  • Scanners other than ICAP; scanning the bytes stored before the upgrade without an administrator asking; re-scanning on a schedule when signatures change.
  • A tool that moves pre-3A bytes out of Git history (later work, see BUILDING section 25).

Global constraints

  • Library record in Git: libraries/<first two hex digits>/<library id>.json, two-space indent, one line per field, in this order: 
    {"schema": 1, "id", "kind": "document"|"image"|"template"|"asset",
 "description": 0–500 characters,
 "folders": true|false,
 "allowed_types": [extension] or null,
 "blocked_types": [extension],
 "max_file_bytes": number or null}
    • An extension is written lower case with its leading dot (".png", ".tar.gz"). Lists hold at most 100 extensions, each 2–20 characters of letters, digits and dots.
    • A library made before this plan has no file. It is read as document, empty description, folders on, all types allowed, nothing blocked and no limit; its file is written at its first change.
    • The commit moves refs/sharecraft/sites, as site records do.
    • Site templates (plan 3B) carry each library's kind and settings. A package with none is read as document libraries with the defaults.
  • Kinds:
    • image: accepts only .png .jpg .jpeg .gif .webp .svg .avif .bmp .tif .tiff .heic. A library's allowed_types may narrow this list further but never widen it.
    • template: its live files, those the person can view, are the "New from template" choices in every library of its site.
    • asset: only administrators set this kind, or change a library away from it. Asset libraries are listed at GET /api/assets to people who can view them.
    • Changing kind never touches files already in the library. A file that the new settings would refuse stays, and is shown with a mark.
  • Folders off: new folders, and moves or copies of a folder into the library, answer 409 folders_off. Existing folders stay and can be emptied, deleted and restored.
  • Any file type: Editor::Other, id "other", for any name that no editor's native extension ends. It is added to the migration's check constraint, and is_file() is true for it. Rename rules:
    • An editor's file keeps its extension, as today.
    • An other file may take any extension except an editor's native one, which answers wrong_extension.
    • Every new name is checked against the file policies.
    New versions of an other file come through upload sessions, as for editors' files.
  • File policies: a name is refused with 422 blocked_file_type {"extension"} when:
    • its extension is in the organisation's blocked_file_types setting (a list, empty by default, set by administrators), or
    • it is not allowed by its library (allowed_types, blocked_types, or the image list).
    A size over the library's max_file_bytes answers 413 file_too_large {"limit"}. Both are checked when an upload session starts, and again at finish, at a copy or move into the library, and at a rename. A file's extension is the longest suffix that is in the list being checked, matched without regard to case (so .tar.gz matches before .gz).
  • Scan states (column blobs.scan):
    • pending: waiting for the scanner.
    • clean.
    • infected: with scan_detail (the scanner's threat name, at most 200 characters).
    • failed: scanner error, retried.
    • too_large: over the scanner limit.
    • unscanned: content stored before the upgrade, or stored while no scanner was configured.
    • released: an administrator let infected or held content through.
    New content is pending when a scanner is configured and unscanned when not.

    Content is available when it is clean, released or unscanned; when it is failed or too_large and the matching setting lets it through; or when it is pending and came from an editor's save.

    Every route that hands out bytes answers 423 held {"scan"} for content that is not available: content download, ranged download, preview, thumbnail, anyone-link download, opening in an editor, copy, new-from-template, and the text room loading a revision. Listing, renaming, moving, deleting and sharing still work.

  • Quarantine: a document whose current version is infected is quarantined. Every person who can see it sees the mark and the threat name. Only administrators see the organisation's quarantine list (GET /api/admin/quarantine), and they release it (POST /api/admin/quarantine/{sha256}/release {reason}, at least 3 characters) or delete it (POST /api/admin/quarantine/{sha256}/delete). Delete purges every document whose current version names that content, skipping the bin, and erases the content once nothing names it.
  • ICAP:
    • Settings: scanner_url (icap://host[:port]/service, default port 1344; empty means no scanner), scanner_timeout_seconds (default 120, 5–3600), scanner_max_bytes (default 2 GiB), scanner_unavailable ("hold" default, or "allow") and scanner_too_large ("hold" default, or "allow"). Administrators set them.
    • A scan sends RESPMOD with the file as a chunked HTTP response body, streaming from the content store, never whole in memory. It honours Preview and 100 Continue when the server's OPTIONS asks for them.
    • 204, or 200 with no infection header, means clean. 200/403 with X-Infection-Found, X-Violations-Found or X-Virus-ID means infected. Anything else, a timeout or a refused connection means failed.
    • Failed content is retried after 1, 5, 15 and then every 60 minutes.
    • The worker runs at most 2 scans at once. Each scan records content.scanned {"sha256", "result", "detail"}.
  • Previews: GET /api/docs/{id}/preview (view needed; content available), with the download's headers except Content-Disposition: inline and a fixed safe Content-Type chosen by extension:
    KindTypes
    Imagespng, jpeg, gif, webp, avif, bmp, svg (image/svg+xml, with the CSP sandbox header that every answer carries)
    Audiomp3, ogg, wav, m4a, flac
    Videomp4, webm, mov, served as video/mp4 for .mov
    Texttext/plain; charset=utf-8, the first 1 MiB, for .txt .md .csv .tsv .log .json .xml .yaml .yml .toml .ini .rs .js .ts .py .java .c .h .cpp .cs .go .rb .php .sh .ps1 .sql .css .html .htm, and only if valid UTF-8
    Every other type answers 415 no_preview. PDF previews open in PdfCraft as today. HTML is only ever previewed as text.
  • Thumbnails: GET /api/docs/{id}/thumbnail answers a PNG at most 256 pixels on its longer side, made from png, jpeg, gif (first frame) and webp.
    • Making one: it is made the first time it is asked for. A decode limit of 12,000 × 12,000 pixels and 256 MiB guards against oversized images. At most 2 are made at once, each in spawn_blocking.
    • Storing it: it is kept at <data>/thumbs/<xx>/<sha256>.png. Erasing a blob erases its thumbnail.
    • When there is none: other types, and images that fail to decode, answer 415 no_thumbnail.
  • New from template: GET /api/libraries/{id}/templates lists the template files of the library's site that the person can view: files whose content is available, in every template library of the site. POST /api/libraries/{id}/from-template {template, parent?, name?} copies one into the library, or into folder parent, through the existing copy path. That path brings the quota, name cleaning, policies and add checks. The copy starts as the template's latest version, with no history.
  • Locking order (unchanged from 3B, with library rows after site rows): node rows top-down, then sites rows by id, then libraries rows by id, then link rows, then site_usage, then groups by id, then roles by id. The blobs row for a scan result is locked in its own short transaction, never while holding the others (as 3A).
  • Events: library.changed (fields changed, with old and new values), content.scanned, content.released (who, reason), content.deleted (who, how many documents), setting.changed for the new settings.
  • Errors (each with a plain-English message in common.js): blocked_file_type 422, file_too_large 413, folders_off 409, held 423, no_preview 415, no_thumbnail 415, invalid_library_settings 422 (with {"reason"}), invalid_scanner_url 422.

Review focus

  1. No route hands out the bytes of held or infected content. That includes ranged downloads, anyone links, previews, thumbnails, opening in an editor, copies and new-from-template, the text room, and a version history download of an older version whose content is infected. (Task 3, held_content_is_never_served, a table of every byte-serving route.)
  2. A preview or download of a file that contains a web page or script never runs it. This covers an .html file, an .svg with a script, a .png that is really HTML, and a name with quotes or line breaks in the Content-Disposition. (Task 4, previews_never_run_content.)
  3. A hostile image cannot exhaust the server. This covers a decompression bomb, a 50,000-pixel-wide PNG, a truncated JPEG and a GIF with 10,000 frames. Each answers no_thumbnail quickly and the server keeps serving. (Task 4, hostile_images_refused_quickly.)
  4. Scanner trouble never loses a file or lets one through by accident. This covers a scanner that refuses the connection, times out halfway, answers garbage or restarts during a scan: the content stays held and is retried, and only scanner_unavailable: allow lets it through. The same bytes uploaded twice are scanned once. (Task 3, scanner_failures_hold_and_retry, same_content_scanned_once.)
  5. Policies hold on every path into a library: upload session start and finish, single-request upload, copy, move, bulk, rename, restore from the bin (a restored file whose type is now blocked is restored but marked), and new-from-template. (Task 2, policies_hold_on_every_path.)
