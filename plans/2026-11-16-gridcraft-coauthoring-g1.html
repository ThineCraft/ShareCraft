GridCraft live co-authoring, plan G1: the proofs: implementation plan

ShareCraft · Stage 2, editor track · Written 16 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: before anything is built for live co-authoring in GridCraft, prove the things the agreed design depends on, or show where they fail. The proofs are:

  • Two copies of the spreadsheet engine, given the same ordered changes, end in the same workbook.
  • The engine in the browser (WebAssembly) and on the desktop give the same results.
  • Saving and reopening loses nothing.
  • Rolling back and re-applying changes is fast enough on large workbooks.
G1 ends with a go/no-go report.

Why first: the co-authoring approach (co-authoring-approach.html, adopted 11 November 2026, decision C16) puts these proofs before any building. Every later plan rests on them. If they fail, the design changes before money is spent on the rest.

Proposals in this plan for the owner to check

  1. Plan the editor track in five plans (G1 to G5), and start with the proofs alone.
  2. The candidate shared commands for Stage 2 are the ones the design names:
    • cell content (set, clear);
    • number format, font, fill, borders and alignment;
    • insert and delete rows and columns;
    • add, rename and delete sheets;
    • set and clear a filter.
    The proofs use only these, with explicit targets. Every other command stays one-person-at-a-time until a later plan.
  3. Go/no-go thresholds:
    • Two engines agree on every step of 10,000 random sequences.
    • Desktop and browser agree on entered content always, and on computed values except listed last-digit differences.
    • Save and reopen is lossless for everything the shared commands can make.
    • Re-applying 10 pending changes on a 100,000-cell workbook takes at most 50 ms on the desktop and 150 ms in the browser, judged by the 95th percentile (the time that 95 % of runs come in under). Above that, the design's "wait for the server" mode covers those commands.
  4. Small determinism fixes are made in G1 (ordered maps where order leaks into results, the fixed clock and random seed). Larger ones are listed for G3.
  5. Codex builds two well-bounded tasks (Tasks 4 and 6), at your request. Claude reviews every task the same way.
  6. The fork branch stays local until you approve pushing it and opening a pull request into the fork's sharecraft branch (house rule 8).

Not in this plan

  • Any server, protocol or page change in ShareCraft.
  • Making commands target-explicit beyond what the proofs need.
  • Identities, the apply loop, undo, presence and checkpoints (G2 to G5).
  • Desktop GridCraft joining sessions.

Global constraints

  • Fingerprint (engine::fingerprint): two SHA-256 digests over a canonical walk of the workbook, sheets in order.
    • entered covers, for each sheet:
      • the name and hidden state;
      • each non-empty cell's row, column, formula text (normalised by the existing formula printer) or literal value, and its resolved style (number format, font, fill, borders, alignment as values, never style ids);
      • row heights and column widths that differ from the default, and hidden rows and columns;
      • merges, sorted;
      • the filter range and criteria.
      It also covers defined names, sorted.
    • computed covers each cell's computed value. Numbers are written as their IEEE-754 bits; errors by code.
    • Excluded: active sheet, selection, scroll, zoom, frozen panes, the undo history and the command journal.
    • The walk never iterates a hash map without sorting first.
  • Determinism inputs:
    • Every run sets fixed_now (calc/src/recalc.rs) and a RAND seed taken from the sequence's seed.
    • Two engines in one process already use different hash-map seeds, so in-process comparisons do exercise hash order.
  • Sequences:
    • A sequence is a JSON file {seed, now, steps:[{id, params}]} of shared commands with explicit sheet and range parameters (never relying on the selection).
    • Generated by a seeded generator: 1 to 6 sheets, up to 200 rows by 30 columns of content, formulas drawn from a list of 40 common functions including cross-sheet references, and structural changes in about 15 % of steps.
    • Stored fixtures go in crates/engine/tests/fixtures/coauthor/, with 20 checked in. CI runs 500 random sequences; a long run of 10,000 is done once and reported.
  • Measurement: rollback and re-run is timed as clone the agreed workbook, apply N pending commands, and rebuild calculation. Native times are measured with std::time::Instant in a release test (#[ignore] by default). Browser times are measured with performance.now() under the wasm test runner. Each run gives p50 and p95 over 30 repetitions.
  • House rules (fork):
    • No panics or unsafe in non-test code.
    • New test dependencies come from the licence allowlist and are recorded.
    • Commits and pull requests carry no agent attribution.
    • cargo fmt, cargo clippy and the existing tests stay green: cargo test -p gridcraft-engine and the workspace check the fork's CI runs.

Review focus

  1. The fingerprint really covers what a co-author would see. A test changes each covered property alone (a style, a merge, a hidden row, a filter, a defined name) and the fingerprint must change. A test changes only view state, and it must not change. (Task 1, fingerprint_sensitivity.)
  2. A "pass" cannot come from both engines being wrong the same way. The replay compares with independent expectations for a fixed set of hand-written sequences (known final cells and values), not only engine against engine. (Task 2, replay_matches_hand_written_expectations.)
  3. Browser runs use the same sequences and compare the same digests. The fixtures are byte-identical inputs. A mismatch prints the first differing cell, not just "differs". (Task 4, wasm_matches_native_fixtures.)
  4. Save and reopen covers what shared commands make, including edge cases: formulas with sheet names that need quoting, a renamed and a deleted sheet referred to by formulas (#REF!), very large and very small numbers, empty strings versus empty cells, merged areas, and filters. (Task 5, save_reload_lossless.)
  5. Timings are honest: release builds, a warm-up excluded, the workbook sizes stated, and the machine noted. A threshold miss is reported as a finding, not tuned away. (Task 6.)

Task 1: the fingerprint

Files: create crates/engine/src/fingerprint.rs (exported) and crates/engine/tests/it/fingerprint.rs.

  • pub fn fingerprint(session: &Session, doc: DocId) -> Fingerprint, where Fingerprint { entered: [u8; 32], computed: [u8; 32] }.
  • pub fn first_difference(a: &Session, b: &Session, doc) -> Option<String> describes the first differing item, for test messages.
  • Use the existing SHA-256 the workspace already depends on. If there is none, use a licence-allowlisted crate and record it.
  1. Write failing tests:
    • fingerprint_sensitivity (each covered property changes the digest; view state does not)
    • fingerprint_is_order_independent (two sessions built through different hash seeds give equal digests)
    • first_difference_names_the_cell
  2. Run them: they fail. Implement. Run the engine tests: they pass.
  3. Commit test: workbook fingerprint for co-authoring proofs.

Task 2: the two-engine replay and the sequence generator

Files: create crates/engine/tests/it/coauthor_replay.rs and crates/engine/tests/support/sequences.rs (generator and JSON form); modify crates/engine/tests/it/main.rs or its module list. Add fixtures under crates/engine/tests/fixtures/coauthor/.

  • The generator emits only the candidate shared commands, with explicit targets.
  • Before any run, a command that still reads the selection when given explicit parameters is recorded in a list, selection_readers.md in the fixtures folder, as input for G3, and left out of generation.
  1. Write failing tests:
    • two_engines_agree_on_random_sequences (500 seeds in CI; fingerprints compared after every step)
    • replay_matches_hand_written_expectations (6 hand-written sequences with known cells and values)
    • fixtures_round_trip_as_json
    • volatile_functions_agree_with_fixed_now_and_seed (NOW, TODAY, RAND, RANDBETWEEN)
  2. Run them: they fail. Implement. Fix small determinism problems found (ordered maps, sorted iteration, a fixed clock and seed) in the engine with a test each, and list larger ones in the task report. Run the engine tests: they pass.
  3. Commit test: two-engine replay of shared commands, plus one fix: commit per determinism fix.

Task 3: the long run and the determinism audit

Files: a #[ignore] test long_replay in coauthor_replay.rs; a written audit at docs/coauthor-determinism.md in the fork (the fork's documents are Markdown).

  • Run 10,000 sequences.
  • Audit every HashMap and HashSet in engine, model, calc, formula, functions and xlsx for iteration whose order can reach a result, a written file or the fingerprint. Classify each as safe, fixed in G1, or left for G3, with a reason each.
  1. Run long_replay in release. Record seeds that fail. Turn each failure into a fixture and a fix, or into an audit entry for G3.
  2. Commit docs: determinism audit for co-authoring.

Task 4 (Codex): desktop versus browser

Files: create crates/engine/tests/wasm_replay.rs, compiled for wasm32-unknown-unknown with wasm-bindgen-test in Node mode; a native test write_native_digests that records each fixture's digests to fixtures/coauthor/native-digests.json; and a short README in the fixtures folder saying how to run both.

  • The browser test replays the same fixtures and compares the digests with the native file.
  • On a mismatch it prints the first differing cell (Review focus 3).
  • Computed-value differences in the last bits of a float are reported by function name with the inputs.
  1. Write the tests: wasm_matches_native_fixtures and native_digests_are_current, which fails when the fixtures change and the digests weren't regenerated.
  2. Run the native side, then cargo test --target wasm32-unknown-unknown -p gridcraft-engine --test wasm_replay with CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER=wasm-bindgen-test-runner.
  3. Record the results: agree, or a list of differences.
  4. Commit test: browser engine matches desktop on shared-command fixtures.

Task 5: save and reopen

Files: create crates/engine/tests/it/coauthor_save_reload.rs (using the xlsx crate's writer and reader through the engine's existing save and open paths).

  1. Write failing tests:
    • save_reload_lossless: entered and computed digests are equal after save and reopen, for every fixture and the edge cases in Review focus 4.
    • save_is_deterministic: two engines in the same state write identical bytes.
    • save_reload_save_is_stable: writing, reopening and writing again gives identical bytes.
  2. Run them. Fix small losses with a test each, and list larger ones for G3/G4, noting whether the "reload at every checkpoint" fallback would be needed.
  3. Commit test: save and reopen are lossless for shared commands.

Task 6 (Codex): rollback and re-run timings

Files: create crates/engine/tests/it/coauthor_timing.rs (#[ignore], release only), with a browser counterpart in wasm_replay.rs behind its own ignored test. Generated workbooks have 10,000, 100,000 and 1,000,000 cells, about 20 % of them formulas, including whole-column sums and cross-sheet references.

  1. For each size, time p50 and p95 over 30 repetitions of: cloning the agreed workbook; applying 1, 10 and 50 pending commands; rebuilding calculation.
  2. Run native and browser. Write the table into the task report with the machine and build details.
  3. Commit test: timings for rollback and re-run.
