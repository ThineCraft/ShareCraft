Collaboration Spine Implementation Plan

ShareCraft · Stage 1, part 1 of 3 · Written 9 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Each step below is a checkbox item; tick it by changing ☐ to ☑ in this file as you complete it.

Goal: two people edit the same plain-text document at once from two browsers, see who else is there, reach the same text, survive a dropped connection, and have the result saved as a Git revision with a JSON metadata file.

Architecture: a Rust server holds one ordered change log per open document. Every client change is sent with the log position it was based on; the server adjusts it against changes committed since, appends it, and broadcasts it to everyone, including the sender. Clients apply changes in log order and adjust their own unconfirmed changes when others arrive first. The same Rust merging code runs in the server and, compiled to WebAssembly, in the browser. When a document goes quiet the server writes a checkpoint: one Git commit with the content and its JSON metadata.

Tech stack: Rust (stable, edition 2024), Cargo workspace; tokio, axum (WebSocket), serde/serde_json, uuid, thiserror, git2 (default features off), proptest, tokio-tungstenite (tests), wasm-bindgen + wasm-bindgen-cli. Add each with cargo add at its current stable release; Cargo.lock records the versions.

Spec: scope.html (D09, D14–D18, SC-15, SC-21, A07, A13) and sequencing.html (Stage 1, spine rules S1–S7). Read both before starting.

What this plan does not cover

Stage 1 is three plans. This is the first; each ends in working, tested software.

Until plan 2, identity is a name typed into the page and anyone who can reach the server can edit. The server therefore binds to 127.0.0.1 only and prints a warning at start. Do not add a way to bind to other addresses in this plan.

Global constraints

  • Language: Rust only for server and merging code (D14). No JavaScript merging logic; the page script only wires the text box to the WebAssembly client.
  • Licence: every crate has license = "MIT OR Apache-2.0" (D17). No copyleft dependencies (GPL, LGPL, AGPL, MPL): the merging crates will be linked into the editor forks, whose upstreams forbid them.
  • One organization per installation (D18). Do not add organization or tenant identifiers to types, paths or messages.
  • One write path (S2, S3): content reaches Git only through RevisionStore::checkpoint. No other code writes to a repository.
  • Live changes never go to Git individually (S3). No commit per change.
  • Every checkpoint states the revision it was based on and is refused if stale (S4).
  • The merging core does not know what a change means (S6): collab-core must not depend on collab-text or mention text.
  • Library crates (collab-core, collab-text, protocol, revisions): #![forbid(unsafe_code)], and no unwrap, expect, panic! or indexing that can panic outside #[cfg(test)]. Input from a client must never be able to stop the server.
  • collab-core, collab-text and protocol must compile for wasm32-unknown-unknown: no tokio, file or clock use in them.
  • Text positions are counted in Unicode scalar values (Rust char), never bytes or UTF-16 units. Conversion from the browser's UTF-16 offsets happens inside the WebAssembly client.
  • Work on branch stage-1-spine, created from main before Task 1. Commit after each task with the message given. Do not push.
  • .gitignore and .env may be edited by another session installing PostgreSQL. Append to .gitignore; never rewrite it. Do not touch .env.

Review focus

Conditions the spec implies that are most likely to hurt a real user. Each has a test in the task named.

  1. Text beyond ASCII: emoji and combining characters typed by two people at the same spot must converge and never split a character. Task 3 (converges_with_astral_and_combining_chars) and Task 8 (utf16_offsets_convert_at_astral_chars).
  2. Reconnect with unconfirmed changes: a client that drops and returns must not lose or duplicate what it typed. Task 2 (duplicate_op_id_is_not_applied_twice) and Task 6 (reconnect_resends_without_duplicating).
  3. Malformed or hostile change from a client: wrong length, position past the end, base position in the future. The server refuses it, tells that client, and every other participant is unaffected. Task 2 (rejects_base_ahead_of_log), Task 3 (apply_rejects_length_mismatch), Task 6 (invalid_op_is_refused_and_room_survives).
  4. Checkpoint cannot be written (repository locked, disk full): editing continues, the save status says saving failed, and the next checkpoint includes everything. Task 7 (failed_checkpoint_is_retried_and_reported).
  5. Server restarts mid-session: changes after the last checkpoint are gone; returning clients must be told plainly and reset to the saved text, not left silently diverged. Task 6 (unknown_since_gets_reset) and Task 8 (page shows the count of changes that could not be kept).

Task 2: Document trait and server log

Files: create crates/collab-core/src/document.rs, src/server_log.rs; modify src/lib.rs.

Consumes: Task 1 ids. Produces:

pub trait Document: Clone {
    type Op: Clone + PartialEq + std::fmt::Debug + Serialize + DeserializeOwned;
    type Error: std::error::Error + Send + Sync + 'static;
    fn apply(&mut self, op: &Self::Op) -> Result<(), Self::Error>;
    /// `first` and `second` were both made against the same state. Returns (first2, second2) such that
    /// applying first then second2 gives the same state as applying second then first2.
    /// Where the two compete for the same place, `first` takes it.
    fn transform(first: &Self::Op, second: &Self::Op) -> Result<(Self::Op, Self::Op), Self::Error>;
}

pub struct Entry<Op> { pub seq: Seq, pub client: ClientId, pub op_id: OpId, pub op: Op }   // Clone, Serialize, Deserialize
pub enum Submitted<Op> { Committed(Entry<Op>), Duplicate(Seq) }
pub enum SubmitError { BaseAhead { base: Seq, head: Seq }, BaseTooOld { base: Seq, oldest: Seq }, Invalid(String) }

impl<D: Document> ServerLog<D> {
    pub fn new(doc: D, head: Seq) -> Self;        // log starts empty at `head`
    pub fn head(&self) -> Seq;
    pub fn doc(&self) -> &D;
    pub fn submit(&mut self, client: ClientId, op_id: OpId, base: Seq, op: D::Op) -> Result<Submitted<D::Op>, SubmitError>;
    pub fn since(&self, seq: Seq) -> Option<&[Entry<D::Op>]>;   // None if `seq` is older than the oldest kept entry or ahead of head
    pub fn truncate_through(&mut self, seq: Seq);  // forget entries with seq <= given; head unchanged
}

submit: if an entry with the same client and op_id is still in the log, return Duplicate(its seq) and change nothing. Otherwise transform the incoming op against each entry after base, in order, with the logged entry as first; apply the result; append it with seq = head.next(). A transform or apply error becomes SubmitError::Invalid and leaves the log and document exactly as they were.

Normalized means: no zero-length components, adjacent components of the same kind merged, and an insert next to a delete ordered insert first. An op covers the whole document: apply fails with LengthMismatch unless base_len() == len_chars(). transform(first, second) requires equal base_len; when both insert at the same position, first's text comes before second's. This is the standard retain/insert/delete operation transform; walk both component lists together.

Task 4: Client state

Consumes: Document, Entry, ids. Produces:

pub struct Outgoing<Op> { pub op_id: OpId, pub base: Seq, pub op: Op }      // Clone, PartialEq, Debug
pub enum ClientError<E> { Document(E), OutOfOrder { expected: Seq, got: Seq } }

impl<D: Document> ClientState<D> {
    pub fn new(client: ClientId, doc: D, seq: Seq) -> Self;
    pub fn client(&self) -> ClientId;
    pub fn doc(&self) -> &D;                 // includes unconfirmed local changes
    pub fn seq(&self) -> Seq;                // last log position applied
    pub fn pending(&self) -> usize;          // unconfirmed local changes (in flight + waiting)
    /// Apply a local change. Returns what to send now, or None if one is already in flight.
    pub fn local(&mut self, op_id: OpId, op: D::Op) -> Result<Option<Outgoing<D::Op>>, ClientError<D::Error>>;
    /// Handle one committed entry from the server, in order. If it is this client's in-flight change it is
    /// confirmed; otherwise it is adjusted past local unconfirmed changes and applied.
    pub fn committed(&mut self, entry: &Entry<D::Op>) -> Result<Applied<D::Op>, ClientError<D::Error>>;
    pub fn in_flight(&self) -> Option<Outgoing<D::Op>>;   // to resend after reconnecting
    /// Drop unconfirmed changes and adopt a server snapshot. Returns how many were dropped.
    pub fn reset(&mut self, doc: D, seq: Seq) -> usize;
}
pub struct Applied<Op> { pub remote: Option<Op>, pub send_next: Option<Outgoing<Op>> }
// remote: the change as it must be applied to the caller's own view (None when it was our own confirmation)

State: at most one change in flight, plus a queue of changes waiting. A remote entry is transformed past the in-flight change and then each waiting change in order, with the remote entry as first; each local change is replaced by its transformed form. When the in-flight change is confirmed, the next waiting change goes in flight with base equal to the confirming entry's seq. committed with entry.seq != seq().next() returns OutOfOrder and changes nothing.

Files: create crates/server/{Cargo.toml,src/main.rs,src/config.rs,src/room.rs,src/ws.rs,tests/two_sessions.rs,tests/common/mod.rs}. The crate is a library plus a thin main.rs so tests can start it in-process.

Consumes: ServerLog<TextDoc>, ClientState<TextDoc> (tests), protocol messages. Produces:

pub struct Config { pub addr: SocketAddr, pub data_dir: PathBuf, pub web_dir: PathBuf,
                    pub checkpoint_idle: Duration, pub checkpoint_max: Duration }
impl Config { pub fn from_env() -> Result<Self, ConfigError> }
// SHARECRAFT_ADDR (default 127.0.0.1:8787; any non-loopback address is a ConfigError),

One room per open document, owned by a single task that receives commands over a channel, so the log is never touched concurrently. A room is created on first join, loading the document from the revision store or starting empty, with the log at Seq(0). Log positions restart at 0 whenever a room is created; that is why a returning client can be asked to reset. name is trimmed, limited to 60 characters, and defaults to "Guest". On Join: with since the room can honour (ServerLog::since is Some), send Joined with no snapshot and then the missed entries; otherwise, for a first join send Joined with the snapshot, and for a reconnect send Reset. Every committed entry is sent to every participant including its sender. SubmitError produces Refused to that client only. A second Join with a ClientId already in the room replaces the older connection. Send People to all on join, leave and cursor change. Frames over 1 MiB, non-text frames and unparseable JSON close that connection only. The room ends when its last participant leaves (Task 7 adds a final checkpoint first).

tests/common/mod.rs provides spawn_server() -> TestServer { addr, data_dir (TempDir) } on port 0 with checkpoint_idle 100 ms, and TestClient wrapping a tokio-tungstenite socket and a ClientState<TextDoc> with connect(addr, doc, name), type_at(pos, &str), pump_until(|c| ..) with a 5 s timeout, text(), people(), disconnect(), reconnect().

Decisions made in this plan

These were not specified by the scope and were chosen here. Change them before execution if they are wrong.

  • Changes are adjusted against each other by operation transform on a retain/insert/delete form, with one change in flight per client.
  • Text positions are Unicode scalar values.
  • One bare Git repository per library; content and metadata are stored under the document identifier, with a per-document reference used for the stale-write check.
  • Checkpoints are written 2 seconds after typing stops, at least every 30 seconds while it continues, and when the last person leaves. Changes made after the last checkpoint are lost if the server stops.
  • Git is accessed through git2 (libgit2). Web framework is axum.
  • The browser is tested by hand in Task 8; the automated two-session test drives the same Rust client code over real WebSockets without a browser. Automated browser testing is left to a later plan.
