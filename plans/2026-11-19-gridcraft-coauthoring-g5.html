GridCraft live co-authoring, plan G5: the host bridge, presence, notices, switching it on and the two-browser acceptance run: implementation plan

ShareCraft · Stage 2, editor track · Written 19 November 2026 · The last plan of the G1–G5 road

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: make GridCraft live co-authoring something two people can actually use. A GridCraft file clicked in a library opens in the browser, both people edit it at the same time, each sees the other's changes and where the other is working, notices about changes that could not be applied appear in ShareCraft's own frame, the file is saved and checked automatically, and the whole thing is proved with two real browsers against acceptance tests A07 and A17.

In plain words. G2 built the server's "chat session" for a document and the shared library that every editor uses to take part in it. G3 taught the GridCraft engine to send and apply changes in that session. G4 taught the session to save checked revisions. All of that works only inside automated tests. G5 connects the pieces to the screen: the ShareCraft page around the editor carries the messages between the server and the editor, the editor draws the other people's selections, ShareCraft shows who is here and what happened, and a setting switches GridCraft documents from "one editor at a time" to "together". It also clears the items that the earlier reviews said must be fixed before anyone uses it.

Architecture:

  • The ShareCraft page owns the connection; the editor owns the session logic. The frame page (file.html, file.js) opens the one WebSocket to /ws/docs/{id}, as it does today for the file session, and passes every live frame unchanged to the GridCraft editor in its <iframe> and back, over same-origin postMessage. Inside the editor, GridCoauthor (G3/G4) is the live client. The page only looks at a short, named list of server messages (who is here, access, removal, pause, saved) so it can draw the bar and the notices. The server is unchanged in kind: it still orders opaque entries and never reads a GridCraft command, presence or session data.
  • Live work runs from messages, not from drawing. The page sends the editor a tick every minute and hands over each frame as it arrives. The editor answers from its message handler, so a tab in the background keeps its heartbeat, applies other people's changes and can still write a checkpoint, even though the browser has stopped drawing it.
  • Presence is a small opaque note beside the log. Each editor sends "where I am" (sheet, active cell, selection, and whether it is typing in a cell) named by lasting identity. The room passes it to the others, keeps only the latest one per person in memory, never stores or logs it, and drops it when the person's connection drops. ShareCraft shows only people who are connected.
  • Notices live in the frame page, which is ordinary HTML. The editor reports what happened ("your change to B5 was not applied: the row was deleted; your text is kept") as a structured notice; ShareCraft shows it as one banner under the bar, readable by a screen reader (approach §12). The editor draws only other people's selections, in colours ShareCraft assigns, always with initials, never by colour alone.
  • GridCraft's bridge is Rust. The fork adds its live messages in apps/gridcraft-web with web-sys, beside the existing craft-web-host bridge, so no handwritten JavaScript enters the fork. The screen (ui-egui) sends shared commands through GridCoauthor and keeps view commands personal.
  • The switch is explicit and checked. A new setting, SHARECRAFT_LIVE_EDITORS, fills Config.live_editors, which stays empty by default. The server also refuses to route a document to the live room unless the installed GridCraft build says it speaks the live protocol, so an old editor build can never be put into a live session by mistake.

Tech stack: both existing Rust workspaces; ShareCraft's protocol, collab-live, server, records, xtask and the plain JavaScript modules in web/ with node --test; GridCraft's engine, ui-egui and apps/gridcraft-web (eframe, web-sys, craft-web-host). No new third-party dependency in either repository. The fork's dependency on ShareCraft's crates changes from a sibling folder path to a pinned git revision of the same public repository (Task 7).

Proposals for the owner

The binding paper settles the behaviour. These are the choices it leaves open, made here so the work can go ahead. Each can be changed before or after the build.

  1. The page carries the connection. The ShareCraft frame page opens the one WebSocket and passes frames to and from the editor; the editor does not open its own. This keeps one connection per open tab, keeps sign-in and the editors' security policy as they are, and lets ShareCraft see who is here without asking the editor. The alternative, the editor opening its own socket, would need a second connection for the page's bar.
  2. GridCraft's live messages are its own, for now. They are a small set of gridcraft:live-* messages in apps/gridcraft-web, written in Rust with web-sys, beside the shared craft-web-host contract rather than inside it. Adding them to craft-web-host would mean a change and a release in another organisation's repository (storytold/craft-libs), which can follow once the messages have settled.
  3. A hidden tab stays a full participant. Ticks and frames are handled when they arrive, not when the editor draws, so a tab in the background keeps its place, applies changes and may write checkpoints. The "bring this tab forward" request (C19) is shown only when changes are paused and this tab is the only editor that could save.
  4. Reconnecting after an error waits longer each time. After a closed socket or an error the library cannot follow, the page waits 1 second, then doubles the wait up to 60 seconds, with up to 20% random spread so several tabs do not retry together. After five identical errors in a row it stops and shows "This document can't be opened together right now" with a Reload button. Reaching the live state resets the count.
  5. What presence carries. The sheet, the active cell, one selected range and whether the person is typing in a cell, all named by identity; at most 1,024 bytes; at most 10 updates a second from one tab (the room drops the rest); the latest kept in memory per person and sent to people who join; never stored, logged or put in events. Showing "typing in this cell" is the middle way the paper kept open in Q2; nobody sees the typed text before Enter.
  6. Viewers are shown, marked read only. Viewers send presence too. The bar lists them with "(read only)" and the canvas draws their selection with a dashed outline.
  7. People without a connection are hidden. A person whose connection has dropped keeps their place for up to three minutes (C21), but neither the bar nor the canvas shows them during that time. They reappear when they reconnect.
  8. Colours and names. ShareCraft gives each person the colour it already uses for their avatar, and passes name, initials and colour to the editor. The editor draws an outline with an initials tag, and the name on hover.
  9. Bounds on identity tables (I7). The library indexes its identity runs so a lookup takes a few steps rather than a scan. One structural change may touch at most 1,024 separate blocks of rows or columns, and one axis may hold at most 65,536 runs (live and deleted together). A change over either limit does nothing on every machine and its author is told, in the same way as other rule failures (C8). The automated test counts steps; a separate timing run is recorded.
  10. The fork pins ShareCraft by git revision. collab-core, collab-live and protocol come from https://github.com/ThineCraft/ShareCraft at a full commit hash, as the fork already does for craft-libs. Nothing is published to crates.io. This needs that ShareCraft commit to be pushed, which waits for your yes. For work across both checkouts, a command-line --config patch points the build at the local folder without committing it.
  11. Session data for a joining editor comes over HTTP. A new read-only route hands the editor the identity tables for its starting revision. They can be up to 8 MiB, which does not fit in a 1 MiB socket message.
  12. Desktop GridCraft is refused for now. The paper keeps desktop editors out of shared sessions until both builds use one maths library (§12, C5, C16). The room therefore refuses a desktop build joining a GridCraft session with a clear message. Desktop sign-in and a desktop bridge are not built in G5.
  13. How it is switched on. SHARECRAFT_LIVE_EDITORS=gridcraft turns it on; the built-in default stays empty. Only GridCraft is accepted, since the other editors keep the one editing seat (C17). A document goes to the live room only when the installed GridCraft build declares the live protocol in its manifest. The development .env turns it on for the acceptance run; turning it on anywhere else is your decision after A07 and A17 pass.
  14. Save and Download in a live document. There is no Save button and the editor's own Save does not upload a file, because checkpoints are automatic and a whole-file upload would race them. The status reads Saved, Saving… or Unsaved changes kept. Download gives the last stored revision and says when it is behind the live document.
  15. When the editor stops. The editor notes the entry it is applying in the tab's session storage, so a reloaded editor reports it (C3). If the editor does not answer a tick within 15 seconds while the tab is shown, the page offers "Reload editor"; it reloads automatically at most three times.
  16. Faults shown to the owner. When a checkpoint could not be verified because two editors wrote different files (C6), people who own the document see a notice in the frame, and the Activity feed records it. Editors and viewers see nothing.
  17. Others are told about a return. The room sends everyone else a short "this person's changes made while away are arriving" message when a returning client's batch starts, so the frame can say that the version before is kept (§04).
  18. Commands GridCraft does not share yet. In a live document they are refused with "Not available while editing together", rather than greyed one by one; the menu stays as it is.
  19. Which browsers. No Playwright or similar tool exists in either repository, and none is added. The acceptance run uses the assistant's built-in browser (Chromium) for one person at http://localhost:8787 and Claude in Chrome (Google Chrome) for the other at http://127.0.0.1:8787, which keeps their sign-ins apart and keeps both tabs drawn. The proofs' Edge and Firefox runs need you to open a page and read out its result; no browser driver is downloaded without your yes.
  20. Branches. The acceptance run installs the GridCraft build from coauthor-g5, recorded in editors.toml with that branch name. Merging the fork's co-authoring branches into its sharecraft branch, and pushing either repository, wait for your go-ahead.

Not in this plan

  • Desktop GridCraft in shared sessions, desktop sign-in to ShareCraft and the common maths library (C5, C16; after G5).
  • Large content beside the log and large shared paste (C20), and any new shared command families: sort, cut and paste, fill, objects, charts, pivots, macros and scripts stay refused in a live document.
  • Seeing typing live inside a cell (Q2: after Enter in Stage 2), personal filter views (C10) and following another person's view.
  • "Who is in it now" on the library page (the concept's library presence), SC-08 version numbering and a version-history screen.
  • Moving the plain-text editor onto the live room (C15) and any change to WordCraft, PdfCraft or SolidCraft, which keep the one editing seat (C17).
  • Adding the live messages to craft-web-host or offering the work to upstream GridCraft.
  • Any CI workflow change in either repository, and pushing or merging without the owner's yes.

Global constraints

  • The server stays a relay (C1, C4, S6). It never reads an entry payload, a presence note, GridCraft session data or XLSX content. It may count bytes and compare fixed-size hashes. Presence is not written to PostgreSQL, not put in events and not logged.
  • Nothing new reaches a log or a Debug form. Names, account ids, payloads, presence notes and typed text are kept out of Debug output, eprintln!, log:: calls and the browser console. Events carry positions, counts and kinds only.
  • Applying a received change reads nothing personal (approach §03). Filling in a target from the sender's selection happens on the sender's side, before the entry is made. View state (active sheet, scroll, active cell, zoom, frozen panes, gridlines) stays per person (C11).
  • The screen changes the shared workbook only through GridCoauthor. In a live document every direct write the paper lists (the filter menu, view state written before commands, the screen's own trimming of the undo list) goes through the entry point or is switched off.
  • Hostile input is bounded on both sides of postMessage. The page checks the message's origin and source; the editor checks its parent's origin, every size (frame 1 MiB, base file 512 MiB as today, session data 8 MiB, people list 256) and every field before use.
  • The room stays off by default. Config.live_editors stays empty unless SHARECRAFT_LIVE_EDITORS names gridcraft and the installed editor declares the live protocol.
  • GridCraft fork rules (AGENTS.md): no panic primitives and no unsafe in non-test code; input treated as hostile and allocations bounded; Rust only, no handwritten JavaScript or TypeScript (the web build stays an eframe app using web-sys); the existing web build and the craft-web-host contract keep working; no CI changes; no agent attribution in commits or pull requests; one task id per commit; cargo xtask ci before each commit, reporting the four failures known to exist at the G3 base separately from anything new.
  • ShareCraft rules (BUILDING.html): page scripts keep their pure parts in exported functions tested with node --test; no inline script is added to a page (the hashed security policy, section 20, stays as it is); every new table and long list in a document is banded in light and dark; cargo xtask check before each commit; builds use CARGO_TARGET_DIR=J:\cargo-target\sharecraft-g5, and CARGO_BUILD_JOBS=1 if the paging file runs out.
  • Report only what ran. Each step that runs a browser check records what was seen; anything not run is listed as not checked.
