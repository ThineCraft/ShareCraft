Content tree and inherited permissions: implementation plan

ShareCraft · Stage 2, platform plan 1 of 4 · Written 11 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: ShareCraft's flat list of documents becomes a tree of sites, libraries, folders and files. Permissions are given at any level and inherited downwards; inheritance can be broken and restored at any level, whatever the size of the library. One access check serves every route, including downloads, the editors and live sessions. People can create folders, create and upload files into them, rename, move and delete, and find their way with site navigation and breadcrumbs. Existing documents move into a default site without losing anyone's access.

Architecture: every site, library, folder and file is a node with a lasting identifier (a file's node identifier is its existing document identifier). The tree is recorded in Git as one small JSON file per node, tree/<id>.json, and mirrored into a PostgreSQL nodes table; Git is the authority and the table is rebuilt from it on start. Permissions are kept only in PostgreSQL: a node either inherits or is a scope with its own assignments; a person's role on a node is the assignment on the nearest scope at or above it, found by walking up the parent chain. Breaking inheritance copies the parent's assignments onto the node; restoring deletes them. Neither touches the node's descendants, so neither depends on how many files are below.

Tech stack: the existing workspace: axum server, sqlx and PostgreSQL (records), gix (revisions), plain HTML and JavaScript pages in web/. No new dependencies.

Spec: scope.html SC-01, SC-02, SC-11, decisions D10, D18 and D19; sequencing.html Stage 2 and spine rules S1–S7. Owner decisions of 11 November 2026: Stage 2 begins with the platform track, in four plans (this one; groups, roles, sharing links, access requests, the inheritance explorer and the 100,000-file test; the rest of libraries and sites; branding), with single sign-on and guests after an identity provider is chosen; the tree is recorded in Git and mirrored into PostgreSQL, permissions are recorded in PostgreSQL only, with every change in the event log.

Not in this plan

  • Groups, configurable roles, sharing links, access requests, the inheritance explorer, background processing and the 100,000-file test (plan 2). Roles stay viewer, editor and owner.
  • Copy, recycle bin and restore, resumable uploads, previews, templates, document sets, metadata panels, quotas, site types, site templates, hubs, site archive and deletion, library deletion (plan 3). Delete here only marks a node deleted in Git and PostgreSQL; plan 3 lists and restores them.
  • Branding (plan 4). Single sign-on and guests (after the identity provider decision). Search.

Global constraints

  • Lasting identity (S1). A node's identifier never changes. A file's node identifier is its DocId. Rename and move never change an identifier, never break a link, and never end a live session.
  • Git for the tree, PostgreSQL for access (owner decision, 11 November 2026). Every tree change (create, rename, move, delete) is one Git commit on main credited to the person who made it, then mirrored into PostgreSQL. Permission changes are written only to PostgreSQL, each with an event.
  • Checkpoints are unaffected (S4). A tree commit never moves a document's ref refs/sharecraft/docs/<id>, so a live session's next checkpoint is never refused because the file was renamed or moved.
  • No size limit on inheritance (D10). Breaking and restoring inheritance cost the same for an empty folder and for a library of 100,000 files: they read and write only the node's own assignments. Nothing is done per descendant.
  • One access decision. Db::effective_role is the only code that decides a role. Disabled or unknown accounts get nothing; an enabled administrator is owner of everything (today's rule); a node with a deleted ancestor-or-self is not found.
  • Revocation is immediate (S5). Any change that lowers someone's role on an open file (an assignment, break, restore, move or delete anywhere above it) reaches that file's live session before the request answers.
  • Every change is an event (S7): node.created, node.renamed, node.moved, node.deleted, inheritance.broken, inheritance.restored, access.granted, access.changed, access.revoked, tree.adopted.
  • Names: 1 to 120 characters after trimming; no control characters and none of " * : < > ? / \ |; no trailing dot. Unique among a node's undeleted siblings, ignoring case. A file's name keeps its editor's extension (existing rule).
  • One installation is one organization (D18): no organization table; sites are the top level.
  • Never print .env, database addresses or passwords. Documents are HTML with colour banding on tables and long lists.

  2. Two people renaming or moving into the same folder at once with the same name: one succeeds and the other gets 409 name_taken; Git and PostgreSQL agree afterwards. (Task 4, concurrent_same_name_one_wins.)
  3. Moving a folder into itself or below itself is refused, and a move never makes a cycle even when two moves cross. (Task 4, move_into_descendant_refused, crossing_moves_make_no_cycle.)
  4. Task 2: inherited access

Files: create crates/records/src/scopes.rs, crates/records/tests/scopes.rs; modify crates/records/src/documents.rs (reachable, role, grants, set_access go through the tree; documents_for is removed), crates/records/tests/documents.rs.

Interfaces consumed: Task 1. Produced:

  • Db::effective_role(&self, user: UserId, node: NodeId) -> Result<Option<Role>, DbError>: the one access decision (Global constraints). Finds the nearest node at or above with unique_scope by a recursive walk up parent_id, then the person's row in scope_access. Db::role(user, doc) calls it.
  • records::Crumb { id: NodeId, kind: NodeKind, name: String, role: Option<Role> }; Db::path(&self, user: UserId, node: NodeId) -> Result<Option<Vec<Crumb>>, DbError>: the site down to the node; None unless the person has a role on the node or limited access to it.
  • Db::sites_for(&self, user: UserId) -> Result<Vec<(Node, Option<Role>)>, DbError>: sites with a role, and sites with limited access (None), by name.
  • records::Listed { node: Node, role: Option<Role>, editor: Option<Editor>, revised_at: Option<OffsetDateTime> }; records::Cursor { kind_rank: i16, name: String, id: NodeId } (folders before files, then name ignoring case, then id); Db::children(&self, user: UserId, parent: NodeId, after: Option<&Cursor>, limit: u32) -> Result<Option<(Vec<Listed>, Option<Cursor>)>, DbError>: None if the parent is not reachable; otherwise the visible undeleted children, keyset-paged. With a role on the parent, every child that inherits is visible with the parent's role, and a child that is a scope is visible if the person has a role on it or below it. With limited access to the parent, only the children that lead to something the person can reach.
  • records::NodeAccess { inherits: bool, source: Crumb, grants: Vec<Grant> }; Db::access(&self, actor: UserId, node: NodeId) -> Result<NodeAccess, AccessError> (owner only; grants are those of source).
  • Db::set_node_access(&self, actor: UserId, node: NodeId, user: UserId, role: Option<Role>) -> Result<(Option<Role>, Option<Role>), AccessError>: as today's set_access (lock, re-check under the lock, last owner, events, before and after), but on a node; if the node inherits, it first breaks inheritance in the same transaction. Db::set_access(actor, doc, ...) becomes a call to it.
  • Db::break_inheritance(&self, actor: UserId, node: NodeId) -> Result<bool, AccessError> and Db::restore_inheritance(&self, actor: UserId, node: NodeId) -> Result<bool, AccessError>: false when already so; restore on a site is IsSite. Both lock the node row and judge the actor under the lock. Restore needs the actor to be owner of the node and of the parent's scope (otherwise Forbidden), so nobody can restore themselves out of their own access by accident without owning above.
  • Locking. Every access change (set_node_access, break, restore) locks the chain from the node up to its source scope, top-down: FOR UPDATE on the scope it writes and FOR SHARE on the rest, then judges the actor under those locks. A move or delete locks the moved node's row FOR UPDATE the same way, so a move cannot change the chain while an access change is judged. The chain is a handful of rows, whatever the library size.
  • Db::scope_users(&self, node: NodeId) -> Result<Vec<UserId>, DbError>: everyone with a grant on the node's scope (used in Task 5).

Limited access is computed from the person's grants: the set of nodes at or above any scope where they have a row. The number of a person's grants is small; nothing scans a library. Write it as one recursive query from scope_access where user_id = $1 upwards, skipping scopes with a deleted node at or above them, so a grant inside a deleted folder exposes no names.
