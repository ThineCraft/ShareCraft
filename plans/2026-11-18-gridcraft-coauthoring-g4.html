GridCraft live co-authoring, plan G4: checkpoint tickets, verification, returning clients and bounded logs: implementation plan

ShareCraft · Stage 2, editor track · Written 18 November 2026

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: turn GridCraft's ordered live log into durable, bounded and independently checked file revisions: a participant writes a checkpoint at an exact agreed position, another participant verifies the bytes, later joiners load a fully recalculated checkpoint without row-height drift, expired clients create the adopted major-version history, and the room pauses before its unsaved log or catch-up can grow without limit.

Architecture:

  • ShareCraft remains the coordinator, not a spreadsheet engine. The live room chooses a capable editing participant, issues a one-use ticket for one log position and base revision, accepts the resulting file through the existing content-store/checkpointer path, and asks a different participant for a SHA-256 of bytes independently written at the same position. The room never parses an XLSX file, a GridCraft command or GridCraft's session data.
  • collab-live exposes the agreed state without folding in waiting work. A ticket can be honoured only at LiveClient::agreed_seq(). If optimistic changes are shown, the library returns its saved agreed snapshot; otherwise the editor itself is the agreed state. This is the mechanical guarantee that a checkpoint base never covers a waiting change.
  • GridCraft owns checkpoint fidelity. Its adapter writes deterministic XLSX bytes and serialised WorkbookIds from an agreed GridSnapshot, loads a checkpoint through a checkpoint-specific open path, performs a full recalculation, and uses only Fingerprint.entered for room agreement. Ordinary File › Open keeps its existing imported-row fitting behaviour.
  • PostgreSQL records the durable live facts. Migration 0020_live_checkpoints.sql, after this branch's 0019_github_sources.sql, stores each checkpoint's revision, log position, byte hash, verification state, session-data bytes and major-version reason/person. The one-use ticket stays in the room: restart cancels it and issues another.

Tech stack: both existing Rust workspaces; ShareCraft's protocol, collab-live, records, server, revisions, PostgreSQL/sqlx, content store and Axum API; GridCraft's engine, xlsx, serde_json, sha2 and existing co-author test fixtures. No new third-party dependency.

Spec:

  • co-authoring-approach.html v1.2 (binding), especially section 04's returning-client sequence, section 05's participant checkpoints and second hash, section 12's save/reopen and version risks, and adopted decisions C1–C23;
  • gridcraft-coauthoring-proofs.html section 10: checkpoint loads fully recalculate and preserve row heights; cross-platform agreement compares entered content only;
  • plan G2 and its built collab-live/live_room/live_store/records::live foundation; plan G3 and the fork's GridCoauthor, GridLiveEditor, WorkbookIds and entered fingerprint;

Proposals for the owner

The binding paper settles the behaviour. These are the concrete values and implementation choices it deliberately left to the Stage 2 plan.

  1. Checkpoint cadence: ask after 15 seconds without a new change or 120 seconds after the first unsaved change, whichever comes first. Ask immediately when the last editing participant is leaving, when the room reaches its warning threshold, before a returning-client batch, and after that batch. This is slower than text's 2/30 seconds because each checkpoint is a whole workbook.
  2. Bounded unsaved work: warn and issue an urgent ticket at 4,000 changes or 48 MiB of payload since the verified base; pause new changes at 5,000 changes or 64 MiB, whichever comes first. Cancel records count as entries but contribute only their encoded size. The limits apply to retained in-memory catch-up as well as new work, so a room that loads over the hard limit starts paused.
  3. Bounded session data: GridCraft identity JSON is at most 8 MiB. It is opaque to ShareCraft but validated by GridCraft before use. An oversize or invalid table cannot become a catch-up base; the checkpoint stays unverified and the room keeps its earlier verified base.
  4. Verification status is durable database state. The Git revision's immutable JSON fields record verified: false when stored without a matching second hash, plus its live position. A later match marks that same revision verified in live_checkpoints and advances live_logs.verified_through; it does not rewrite Git history merely to change a flag. History/API answers overlay the durable verification state.
  5. Tickets are short-lived room capabilities. A UUID ticket is one-use, belongs to one participant, position, base revision and purpose (write or verify), and expires after 2 minutes or immediately on access loss, heartbeat expiry, departure, room restart or a stale base. The next eligible participant is then asked.
  6. A different writer verifies. The second hash must come from a different participant and, when both kinds are present, prefer the other build kind (browser versus desktop). G4 proves the protocol without allowing desktop co-authoring; C16's desktop admission remains blocked until the common maths library after G5.
  7. Agreement reports every 64 ordered changes. An editing client reports the 32-byte entered digest at the exact agreed position. A mismatch makes the odd client resync from the last verified checkpoint and records live.agreement_mismatch; computed values and view state never cross the wire.
  8. Retain a minimal return tombstone. Session identity data and entries still expire by the adopted 30-day rule, but the session id, participant/client ownership, end time and final position remain as small tombstone rows. That is the only way to recognise the same in-memory client after 30 days and apply C22's “archive its copy under the current file” path without retaining the old identities forever.
  9. Large-content side-channel remains deferred. G3 refuses large paste and over-limit Undo, and the G1 road row for G4 names checkpoints, verification, returning clients/major versions and the log limit. G4 therefore bounds ordinary payloads but does not add C20's per-document large-content upload. It must be planned before any large-paste command is admitted.

Not in this plan

  • No browser or desktop transport bridge, frame-page status UI, “bring this tab forward” prompt, read-only editor shell, presence drawing or real-browser run. G5 consumes the host APIs and message/event variants prepared here.
  • No enabling Config.live_editors for GridCraft. The unsaved limits are required before that switch, but G5 owns the switch and end-to-end browser acceptance.
  • No common native/WASM maths library and no desktop admission. Computed values remain native diagnostics only.
  • No large-content side-channel, large shared paste, shared macros/scripts/import/Solver, objects or new shared command families. C20 remains required before one of those commands needs content beyond MAX_PAYLOAD_BYTES.
  • No SC-08 version numbering or publishing UI. G4 stores the adopted interim major, reason and person metadata.
  • No change to text rooms, file-seat rooms, their checkpoint schedule or their save protocol.

Global constraints

  • The server never reads an entry payload, GridCraft identity JSON or XLSX content. It may count bytes, compute SHA-256 over uploaded bytes and compare fixed-size hashes (C1, C4, S6).
  • A checkpoint is one existing Git/content-store revision with all contributors since the preceding checkpoint; the uploader alone is not credited (S3). Every write names the current revision it was based on and stale writes take the adopted S4 recovery path.
  • A ticket names one Seq. GridCraft writes exactly the agreed snapshot at that sequence. A shown but unconfirmed change is never included, and a ticket ahead of or behind agreed_seq is refused.
  • Entries are retained until a verified revision covers them and then for 30 days. Db::mark_live_verified is called only after a matching independent hash, never merely after the primary upload.
  • Checkpoint session data and file bytes are one logical result: the room does not advance its base unless both are durably associated with the same position/revision. A malformed identity table cannot be loaded by GridCraft.
  • Cross-platform agreement is Fingerprint.entered only. It includes entered content, explicit formatting, row heights/column widths, merges, filters and names; it excludes computed values, active sheet, selection, scroll, zoom and personal history.
  • Checkpoint load performs a full recalculation under the log's deterministic stamp state. It does not apply File › Open's imported-row auto-fit a second time. Ordinary user-open behaviour remains unchanged.
  • At either hard log limit the room refuses/pause-notices new entries before writing them; heartbeats, leave, report, resync, hash, ticket and access messages still work so the room can recover.
  • A role loss or heartbeat expiry cancels that participant's ticket before another is issued (S5). A viewer never receives a write or verify ticket.
  • The returning-client sequence is two barriers: store/mark the current state major before accepting the saved late batch, then store the result major immediately after the last local number that existed at return. Ordinary entries made later are not mistaken for the return batch.
  • ShareCraft migration 0020_live_checkpoints.sql uses LF endings and is never edited after application. GridCraft production code follows its AGENTS.md: no panic primitives, no unsafe, checked hostile input, no CI changes, no agent attribution.
  • No new third-party dependency in either repository. ShareCraft finishes with cargo xtask check; GridCraft finishes with cargo xtask ci. Report only gates that actually ran.
