S3 libraries: a library whose files are stored in an S3 bucket: implementation plan

ShareCraft · Stage 2 platform plan 7, phase A3 of SC-27 (storage-source libraries) · Written 18 November 2026 · Draft for the owner

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes. In this plan Codex writes all code and runs all tests; each task card is the brief for one Codex run, and the controller only commits, writes one ledger line and dispatches the next run (section "How this plan is executed").

Two phases in one document. Phase 1 (Tasks 1 to 17) connects a library to a bucket and prefix, lists it, reads objects on first use into the bounded cache the file-share work built, shows a request budget, and is read-only; it ends with a controller check against Cloudflare R2. Phase 2 (Tasks 18 to 31) makes the bucket the library's storage: every write in ShareCraft is written through with a conditional request, with deletes, conflicts, editor saves and a per-library read-only switch; it ends with its own controller check. Phase 2 starts only after Phase 1's check has passed and the file-share plan's Phase 2 is on this branch (Task 18).

What this plan stands on. The branch s3-surfacing was cut from fileshare-surfacing at f4b2e6f, which holds file-share Tasks 1 to 9. File-share Tasks 10 (worker), 11 (pages) and the whole of its Phase 2 are not on this branch yet. Each card names the file-share task it needs; Tasks 1 and 18 are the controller's gates that bring that work in first. Signatures of file-share Tasks 1 to 9 were read from the code; signatures of Tasks 10 to 27 were read from that plan only and are marked so.

Goal: an administrator approves the S3 endpoints the ShareCraft server may talk to, and a site manager connects a library to a bucket (and optional prefix) with an access key. The bucket is the storage for the library's files. Keys appear as folders and files within minutes; permissions, inheritance, sharing links, previews, thumbnails, malware scanning and file-type limits work on them. Objects are not copied to the server as the record: bytes are fetched when someone opens a file, scanned on that first read, kept in the shared size-bounded cache, and never counted against the site's quota. The secret key is stored only as AES-256-GCM ciphertext. Every request ShareCraft makes is counted against a per-library monthly budget the owner can see. Phase 1 is read-only; Phase 2 makes read and write the default with a per-library read-only option. First checked against Cloudflare R2, then AWS S3 and MinIO.

Architecture:

  • The same connected-library attribute as GitHub and file shares. library_sources gains kind s3; a side table source_s3 holds where the bucket is; the sealed secret key goes in the existing token_secret column through secrets.rs. The advisory lock, generation compare-and-set, worker with backoff, events, the read-only guard and the pages are reused.
  • Items are real tree nodes; their content is external, exactly as for a file share: a nodes row and a documents row with no stored Git revision, created in batches of up to 1,000 nodes per Git commit by the existing tree::create_external_nodes, and a source_items row whose tag now also carries a digest of the object's ETag.
  • One fetch path. external::materialise stays the only way external bytes are read. Task 8 splits its file-share specifics from its shared part (single flight, cache pin, compare-and-set on the tag, scan gate, eviction, offline memory) without changing file-share behaviour; Task 9 adds the S3 arm: HEAD, then one GET with If-Match on the ETag just seen, streamed into the content store.
  • A small S3 client of our own (s3_sign.rs, s3_xml.rs, s3.rs): Signature Version 4 with the hmac and sha2 crates the server already uses, over the existing operating-system-TLS reqwest client. No AWS SDK, no new crate (decision recorded below).
  • A listing engine pages ListObjectsV2 under a time, count and request budget, turns keys into paths, and feeds the existing planner through the existing StorageSource trait as a third implementation, S3Source.
  • Write-through (Phase 2) reuses the file-share staging path (stage in the cache, scan, then write): the write is one conditional PUT (If-Match on the ETag the change was based on, or If-None-Match: * for a new key), multipart for large content. One module, s3_write.rs, is the only code that changes a bucket.

Tech stack: the existing workspace. No new crate in either phase. HTTP is reqwest 0.13 with native-tls (already a dependency); signing uses hmac 0.13 and sha2 0.11 (already direct dependencies of server); dates use time. Cargo.lock holds no XML crate (no quick-xml, serde-xml-rs, roxmltree, xml-rs), so Task 3 writes a minimal parser for the few S3 documents. Hex and percent-encoding are written by hand in the signer (SigV4 has its own encoding rule; api/sources.rs already has a hex helper to move).

Spec: s3-surfacing-design.html v0.3 (sections 03 to 11, 12 for costs, 13), scope.html SC-27 and D61 to D64, the file-share plan and its ledger, BUILDING.html section 33. Owner decisions of 18 November 2026 (binding): S3 follows the file share and precedes Azure; first test on Cloudflare R2, then AWS S3 and MinIO, and nothing billed or created without the owner's go-ahead and a stated cost; no versioning required, used when present; read and write with a per-library read-only option, in two phases; files are not copied as the record and never count against quota; the secret key only as AES-GCM ciphertext, write-only in the pages; custom endpoints from administrators only, HTTPS only, private and link-local addresses blocked unless an administrator allows a range; polling with a cost budget, notifications and Inventory later; a budget panel and per-source request budget; the numbered-names rule for case collisions; no network in tests.

Proposals in this plan for the owner to check

Choices the owner's decisions did not settle. Approving the plan approves them; any can be changed before building. Those marked open question are repeated at the end with the alternative.

  1. SigV4 by hand, not aws-sdk-s3. The signer is about 250 lines of pure code over two crates already in use, proven by the four published AWS examples (Task 2). The SDK would add well over a hundred crates (the Smithy runtime, its own HTTP stack, and by default rustls with ring or aws-lc, which D64 excludes), must be fetched by the controller because Codex cannot download, and gives us nothing we use beyond signing, ten operations and XML. What we give up: the SDK's credential chain (ambient credentials, later work either way), its retry policy (ours is in Task 6) and automatic handling of new AWS features. Open question 1.
  2. A minimal XML reader of our own (Task 3), because the lockfile has none: elements and text only, the five named entities and numeric references, no DTD, no attributes kept, hard limits on size and depth. Listings are requested with encoding-type=url so a key with characters XML cannot carry still arrives intact.
  3. Approved endpoints, like approved roots. Administrators keep a list of named endpoints under Sharing settings: address (https:// only, no path), region, path-style or virtual-host addressing, and the private address ranges it may resolve to (none by default). AWS's own regional endpoints (https://s3.<region>.amazonaws.com) are built in and need no entry. A site manager chooses an endpoint by name and never types an address.
  4. The private-address block is enforced at connection time, on every address a name resolves to, not once at save time, so a DNS answer that later changes to an internal address is still refused. Redirects are never followed.
  5. The change tag is x{size}-{modified, whole seconds as ns}~{16 hex of SHA-256 of the ETag}, with !a appended for an object in an archive class. The ETag is used only to detect change, never as a content hash; the SHA-256 comes only from our own read. The raw ETag is not stored: each read and write takes it from a fresh HEAD.
  6. One cache for file shares and S3, the existing source_cache and its size setting (default 10 GiB). An object larger than half the cache, or than the server's largest file, is listed as too big and never fetched.
  7. Hidden and counted, never shown: keys with an empty segment, a . or .. segment, a control character, bytes that are not UTF-8, a segment over 255 bytes, a path over 400 characters, a name Windows refuses; zero-byte folder markers (name/) become folders, not files; a marker with content is counted as unnameable; ShareCraft's own .sharecraft-bin/ and .sharecraft-tmp-* keys are skipped and not counted.
  8. A file and a folder with one name (a and a/b both exist in S3): the folder keeps the plain name and the file is numbered a (1), because renaming the folder would rename every path below it. Files that differ only in case are all numbered, as decided.
  9. Archive classes (GLACIER, DEEP_ARCHIVE, and INTELLIGENT_TIERING objects reported as archived) are listed, marked "In archive storage: restore needed", and never fetched. A "Request restore" action is not in this plan.
  10. The request budget is per library and per calendar month (UTC), in three counts: list and write requests (default 100,000), read requests (default 1,000,000) and bytes downloaded (default no limit, shown). At 80 % the library's owners see a warning; at 100 % of the list count, listing pauses until the month ends or an owner raises it; at 100 % of the read count or bytes, uncached files answer "over this month's budget" and cached files still open. The polling interval is never shorter than the budget allows for the bucket's size. ShareCraft counts only its own requests; the provider's bill is the authority, and the panel says so. Open question 3.
  11. Who may connect: anyone who may create a library in the site, on an approved endpoint, with a key pair they supply. Only library owners and administrators see the bucket, prefix and the access key id's last four characters; nobody sees the secret after saving. Open question 2.
  12. Phase 2: holding prefix by default. In a bucket with versioning, a delete writes a delete marker and restore removes it. Without versioning, a delete copies the object to .sharecraft-bin/<date>/<node>/<name> and then deletes the original, kept 93 days in step with the recycle bin; an owner may choose "permanent" with a typed confirmation. Open question 4.
  13. Phase 2: where the store has no conditional writes (the probe finds out), ShareCraft does HEAD then PUT. A write by another system in that instant is overwritten; the Source section says so in plain words, and each such write is counted. Open question 5.
  14. Phase 2: a rename or move is a server-side copy then a delete, one pair per object; a folder of more than 1,000 objects is refused with the count. It is not atomic: a failure part way is rolled back where it can be and otherwise repaired by the next listing.
  15. History (Task 13): for a versioned bucket the file's page lists its S3 versions (time, size, "current", "deleted"); otherwise one line, "This storage keeps no earlier versions." Phase 2 adds "Restore this version" as a copy forward. Downloading a past version is not in this plan (it needs its own scan-gate path).

Not in this plan

  • Ambient credentials (an instance profile, ECS or EKS role, web identity, AssumeRole) and anonymous buckets. Later work: it needs the instance-metadata and STS calls, short-lived session tokens (the signer already takes a session token) and a refresh loop; the metadata address is link-local, so it also needs a deliberate exception to the address block.
  • Event notifications. Not built. They would need: the customer to create an SQS queue (or R2 queue, or a webhook through SNS) and a bucket notification policy; a long-poll consumer per source; ordering by the event's sequencer; treating events only as hints that bring one key's check forward; and the polling of this plan kept as the reconcile. S3 Inventory likewise: it needs a second bucket to read manifests from, a CSV reader, and is a day old at best.
  • Request restore for archived objects, Object Lock, object tags and user metadata as columns, pre-signed URLs (never issued), UploadPartCopy (so an object over 5 GB cannot be renamed), additional checksums (x-amz-checksum-sha256), requester-pays buckets, per-person S3 identities, a bill estimate in money.
  • The SC-23 sync API and search (Stage 4 and 5). What SC-23 must carry is recorded below and in Tasks 17 and 31.
  • Template and asset libraries on S3, moving items between libraries, downloading a past version, Azure Blob Storage.

DriveCraft. An S3 library is ordinary nodes for the SC-23 feed, the same as a file-share library: the item's etag is its revision id, an item with no SHA-256 yet is normal, an unavailable item carries its reason (archived and budget are new) and DriveCraft keeps its local copy and lists it under Problems. The library must advertise that content is fetched on demand, its total size, whether it is read-only, and that each computer's first sync is served from ShareCraft's cache after the first fetch, so thirty computers cost the bucket one download, not thirty. The numbered names protect Windows clients from A.md and a.md.

Global constraints

  • Rust 2024; workspace lints deny unwrap_used, expect_used, panic, indexing_slicing; unsafe_code is forbidden. New code follows them; test files carry #![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::indexing_slicing)] as the existing ones do.
  • No new crates. git diff f4b2e6f -- Cargo.lock must show no added package from this plan. If a task seems to need one, stop and report; do not add it. (Licences must be MIT or Apache-2.0; no ring, no rustls; Codex cannot download crates.)
  • Operating-system TLS only (D64): every S3 request goes through reqwest built with native-tls, certificate checks on. https only, with one exception that exists for tests: Config::s3_plain_loopback (default false, no environment variable, set only by test configuration) lets an endpoint be http://127.0.0.1:<port>.
  • Windows features must not need per-machine administrator work: no installer step, no service change, no certificate store change.
  • Migrations: never edit an applied migration; LF line endings (.gitattributes pins them). On this branch 0020 is applied and 0021 is reserved by the file-share plan (0021_file_share_writes.sql). This plan adds 0022_s3_sources.sql (Task 5) and 0023_s3_writes.sql (Task 19). Once its task is committed a migration is not edited; a later need is a new numbered file.
  • The secret key exists in plain text only in the request that supplies it and in memory at the moment of signing, wrapped in secrets::Secret. It is stored only through SecretBox::seal with the context source_sync::token_context(library). It never appears in Git, an event, a log line, an error, a Debug output, a URL, or any API answer; Authorization headers are never logged. The pages show "set" and offer "replace". A standing test plants a secret and searches every answer and every event for it (Task 11).
  • Events carry counts and library-relative paths only; never the endpoint address, bucket, prefix or key id. last_error and every API message is a plain sentence of ours, at most 300 characters; text from an S3 error body is written to the server log only (its Code word, never its Message), never stored or returned.
  • Phase 1 never changes a bucket. The Phase 1 client has no method that sends PUT, POST or DELETE; the fake records every request and tests assert none was a write. In Phase 2 every change to a bucket goes through crates/server/src/s3_write.rs and nowhere else. A read-only library is never written to.
  • Never overwrite an outside change knowingly, never drop a write silently, never leave an unfinished multipart upload.
  • Real services cost the owner money. No Codex run and no test touches a real endpoint. Only controller Tasks 16 and 30 do, and only after the owner's explicit yes to a stated cost. The controller never creates a bucket, an API token or a Cloudflare or AWS resource on its own initiative, and never types or reads a secret key: the owner types it into the page.
  • Web pages are plain HTML and JavaScript in web/, no build step, light and dark, 375 px wide up, keyboard and screen-reader usable; tables and long lists carry alternating row shading. Documents are HTML, never Markdown, with the same shading.
  • Commits end with Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>. The controller commits; Codex never runs a Git command that changes state. Work stays on s3-surfacing; nothing is merged into main or pushed without the owner.

How this plan is executed

Roles. For each task the controller starts one new Codex run with write access in H:\Source\repos\ThineCraft\ShareCraft-s3, pasting the task card together with the sections Global constraints, How this plan is executed and Shared types. When Codex reports, the controller commits exactly the files Codex names (never git add -A), writes one ledger line, and starts a read-only Codex review of that commit range with the task card and its Review focus. Findings go to a Codex fix run; at most five fix rounds per task. The controller does not read code: it decides from the reports, and records any decision as a ruling.

Every fix round is a new Codex run, never a resumed one. Codex resumes its latest thread, and after a review that thread is read-only and refuses to write (this cost an hour in the file-share work).

The report file. Every run writes .superpowers/sdd/2026-11-18-s3-surfacing.html/task-N-report.md (fix rounds: task-N-fix-k-report.md; reviews: task-N-review.md). Its first line is Status: done or Status: stopped and nothing else. Then: files created and changed; each command run with its pass and fail counts copied from the output; anything outside the card's file list and why (see the seams below); any place the code departs from the card and why; anything not run. A run must not say a suite passed unless it ran it. A known load-sensitive test that fails under load and passes alone is reported with both results and is Status: done, not stopped.

How the controller waits. It notes the time of dispatch and waits for the report file to exist with a modification time newer than that; it does not poll Codex's output or trust a launch notice. A finished job's text can also be read with the Codex companion's result <job-id> command.

Seams every card allows (a run does not stop on the card's file list for these; it lists each under "Outside the file list"):

  • Changing test-support files: crates/server/tests/common/*.rs and crates/records/src/test_support.rs, including new faults and counters on fake_s3.rs and fake_share.rs.
  • Test-only setters on the S3 and Shares handles for waits, timeouts, page size, part size and cache size, named set_* or *_for_tests, that change no production default.
  • New ApiError, AccessError, SyncError or ExternalError variants, mapped wherever the existing variants are mapped.
  • Additive, read-only plumbing in crates/records/src/sources.rs (and its tests) to expose a field the card's answer names.
  • Adding the new kind to an exhaustive match anywhere the compiler demands it, with the arm the card's rules imply (or the same arm as Share when the card is silent, said in the report).

Anything else outside the file list, a signature here that does not fit the code, or a need for a crate: stop and report instead of redesigning.

Review focus

Conditions the happy path never meets. Each has a named test in the task that owns the code; the review waves (Tasks 15 and 29) check them again across the branch.

  1. The secret key anywhere it must not be: a log line, a Debug or Display, an error text, an event, an API answer, a URL, the database outside secrets.ciphertext, a test snapshot; a signature computed over a header that is not sent, or a header sent that should have been signed (Tasks 2, 6, 11).
  2. Reaching an address nobody approved (SSRF): an endpoint typed by a non-administrator; http; an address with a path, credentials or a port trick; a name that resolves to loopback, a private range, link-local (the cloud metadata address 169.254.169.254), an IPv4-mapped or NAT64 IPv6 form of one; a name that resolves publicly at save time and privately later; a redirect; a bucket name that changes the host (a.b, a/b, a@b, a:1) (Tasks 4, 6, 11).
  3. A listing that is cut short must delete nothing. A failed page, a throttle that outlasts the retries, the time, count or request budget passed, a truncated or malformed page, a continuation token that repeats, credentials withdrawn part way: the library keeps what it had (Task 7).
  4. Bytes served without the scan gate, from the wrong object, or half an object. Every byte goes through materialise; an object replaced between HEAD and GET is refused by If-Match; a body shorter or longer than its length, or a hung body, is never cached; an archived object is never requested (Tasks 9, 10).
  5. Races the earlier work met: a sync finishing after a change or disconnect (generation compare-and-set), two first reads of one file (single flight), eviction during a read (hold), a read finishing after the listing moved the tag (compare-and-set on the tag), approval withdrawn while waiting on a flight (re-check after the wait), a long first listing blocking disconnect, a lost compare-and-set still serving stale bytes (it must not), stale syncing recovery only with the lock free (Tasks 7, 9, 11, 12).
  6. Keys that are not names: a//b, ../x, a leading /, control characters, percent-encoded oddities, non-UTF-8, CON, a trailing dot, a 1,024-byte key, A.md with a.md, a file a with a folder a/, a key equal to the prefix, a key outside the prefix returned by a careless store (Task 7).
  7. File-share behaviour unchanged. Tasks 5, 8 and 22 touch shared code; every share_* and source_* suite keeps its pass count, reported side by side.
  8. The budget cannot be bypassed and cannot strand a library: every request is counted where it is sent; counts survive a restart; a paused library still opens cached files and resumes by itself (Tasks 6, 12).
  9. Phase 2: a write that destroys something. An outside change overwritten where conditional writes exist; a precondition answer taken for success; a multipart upload left unfinished (it is billed until aborted); a copy-then-delete that deletes before the copy is confirmed; a delete meant to be soft that was not; content written before its scan; an accepted save lost on a restart (Tasks 20, 21, 25, 26).
  10. Phase 2: the guard per mode, route by route, for the new kind (Task 23).

How a write flows. As for a file share. A structure change (new folder, rename, move, delete, restore) is made in the bucket first and then in the tree and tracking rows. A content change (new file, replaced file, editor save) is staged: pinned in the cache, recorded in source_writes with the revision it was based on, shown as saving, and written by the worker once the scanner has passed it. Both name the revision they are based on; a stale base is an explicit conflict, never an overwrite.

What is atomic in S3. One PUT is atomic: readers see the old object or the new one. A PUT with If-None-Match: * creates a key only if it does not exist, and with If-Match: <etag> replaces an object only if it is still that one; where the store honours these, "compare then write" is a single step and the file-share plan's residual window does not exist. Not atomic: a rename or move (a copy and then a delete, per object; a folder is as many pairs as it has objects); a delete into the holding prefix (copy, then delete); and, on a store without conditional writes, HEAD then PUT. A multipart upload is invisible until completed, and its completion is one atomic step that can carry the same conditions; an upload never completed is billed until aborted.

Task 8's split is described from reading its first 330 lines and its function list, not every line. If the shared tail cannot be separated as one function without changing behaviour, Task 8 stops and the alternative is a parallel S3 function that calls the same small helpers.
  • The address check depends on a reqwest 0.13 hook I did not verify (a custom resolver on the client builder, or pinning resolved addresses). Task 6 names both and stops if neither works without a new crate. A check only at save time would leave DNS rebinding open and is not acceptable.
  • What each real store supports is not verified: whether R2 honours If-Match and If-None-Match on PutObject and on completing a multipart upload; whether R2 answers the versioning call at all (I believe it has no object versioning); R2's ETag for multipart objects; which error codes R2 and MinIO use for a refused key or a wrong region; whether every store accepts encoding-type=url. The probe and Tasks 16 and 30 are how we find out; the fake encodes AWS's documented behaviour.
  • Prices are recalled, not checked. The R2 and AWS figures in Tasks 16 and 30 must be re-read from the providers' pages before the owner is asked.
  • The unconditional fallback can overwrite. On a store without conditional writes, a change made in the bucket between ShareCraft's HEAD and PUT is lost (or, with versioning, becomes an earlier version). The window is one round trip. It is stated in the Source section and counted, not closed.
  • Rename, move and soft delete are not atomic and cost requests. A folder rename is two requests per object, capped at 1,000 objects. A failure part way can leave duplicates until the next listing. An object over 5 GB cannot be renamed, moved or held (no UploadPartCopy).
  • Every pass lists everything. A library at the 50,000-file cap costs 50 list requests a pass; with the default budget that is a pass about every 27 minutes at best. Larger buckets need a higher cap and budget, or event notifications, which are later work. Change in the bucket is seen only at the next pass or when a file is opened.
  • The meter is an estimate. It counts ShareCraft's requests, loses up to a minute of counts in a crash, knows nothing of other users of the bucket, and does not turn counts into money. A provider may bill a retried or failed request differently.
  • Large objects wait on first read (fetched whole, then scanned; ranges are served only afterwards) and on write (scanned, then sent). An object over half the cache or the server's largest file cannot be opened at all.
  • A hung store ties up a read permit until the idle limit (30 seconds). Unlike a file share the request can be dropped, so the permit does come back.
  • Clock. Signatures fail when the server's clock is more than about fifteen minutes off; ShareCraft reports it in plain words and cannot fix it.
  • The XML reader is ours. It is small and bounded, but it is new parsing code facing a network. Its tests include truncations and hostile shapes; the review waves look at it again.
  • Migration numbering across two branches. 0022 may be applied to a developer database before the file-share 0021 exists there. I did not verify how the migration runner treats a lower number appearing later; throwaway schemas avoid the question, and Task 18 runs the suites after the merge.
  • Not verified in the code: that shown_names numbers a file that collides with a folder (Task 7 adds it if not); that time parses the HTTP date form with GMT through a format description (Task 3 tests it); that Blobs::write_reader with a channel reader applies back-pressure rather than buffering a whole object; the exact share-specific sentences in shared failure paths.
  • Exposure is by design: everyone reaches the bucket through one key. ShareCraft's permissions decide who sees what; anyone with the key, or the provider's console, is outside them and outside ShareCraft's audit trail. A key that can do more than read one prefix is a risk the connect dialog warns about and cannot check.

Open questions for the owner

  1. Signing by hand, or the AWS SDK? Proposed: our own Signature Version 4 (about 250 lines, proven by AWS's published examples) and a minimal XML reader, with no new crate. Alternative: aws-sdk-s3, which brings well over a hundred crates, its own TLS choice to be forced onto the operating system's, and a fetch the controller must do for Codex. Recommendation: by hand. Revisit only if ambient credentials (the SDK's strongest part) become a near-term need.
  2. Who may connect a bucket? Proposed: anyone who may create a library in the site, on an endpoint an administrator approved, with a key they supply. Alternative: administrators only. Recommendation: as proposed for read-only; administrators only for read and write until a first site has used it, since a writable key and a mistaken prefix can change a bucket other systems depend on.
  3. Default budgets. Proposed per library per month: 100,000 list and write requests, 1,000,000 read requests, no limit on bytes downloaded (shown, with a limit an owner can set); warning at 80 %; at 100 % listing pauses and uncached opens are refused while cached files still open. Alternative: no pause, warnings only. Recommendation: as proposed: ten libraries then fit inside R2's free allowance as I recall it, and on AWS the request ceiling is under one US dollar a library a month at the rates I recall.
  4. Deletes in a bucket without versioning. Proposed: the holding prefix .sharecraft-bin/ by default, 93 days, so the recycle bin works; "permanent" by explicit choice. Alternative (the design document's original default): permanent unless an administrator turns the holding prefix on. Recommendation: holding by default, consistent with file shares; it costs two requests a delete and the storage of what is held.
  5. Read and write on a store with no conditional writes. Proposed: allowed, with the overwrite risk stated in the Source section and each such write counted. Alternative: refuse read and write there and offer read-only. Recommendation: allow, because MinIO and other on-premises stores are where people most want this; revisit if Task 30 shows a common store silently ignores the conditions.

Proposed: a local merge of fileshare-surfacing into s3-surfacing at Task 1 and again at Task 18, each with the owner's yes, nothing pushed.
