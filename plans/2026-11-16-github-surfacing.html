GitHub surfacing: a library whose files live in a GitHub repository: implementation plan

ShareCraft · Stage 2 platform plan 5, phase A1 of SC-27 (storage-source libraries) · Written 16 November 2026 · Draft for the owner

For agentic workers: REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or superpowers:executing-plans. Steps are checkboxes.

Goal: an administrator connects a library to a branch of a GitHub repository (public, or private with a read-only token). The repository's documents appear in the library as folders and files, kept in step with the branch within minutes (seconds when a webhook is set up). Everything ShareCraft already does over a file works on them: permissions and inheritance, sharing links, previews, thumbnails, malware scanning and file-type limits. They cannot be changed in ShareCraft yet (read-only, section "Not in this plan").

Architecture:

  • The connection is an attribute of a library, not a fifth kind. A library_sources row marks a library as connected and holds the repository, branch, folder, state and sync bookmark. library_sources and source_items (which node holds which repository path and Git blob ID) are new PostgreSQL tables. The kind stays document, image, template or asset, so kinds, settings and templates are untouched.
  • Items are real tree nodes. Each repository folder and file becomes an ordinary nodes row, and each file an ordinary document with a stored revision. Listings, access checks, scan gates, previews, links and the DriveCraft feed all key on those rows, and the survey of the code (16 November 2026) found no cheap way to feed them virtual items. This is a deliberate change from the design's cache model (s3-surfacing-design.html, section 10): for a repository of documents the bytes are mirrored into the content store, and the repository stays the authority. See proposal 2.
  • A sync engine reads the branch through GitHub's REST API: the branch head with a conditional request (an unchanged branch costs no rate limit), the tree, then the changed files, by a single tarball when many changed and by single blob requests when few. A pure function plans the difference (add, change, remove, move); an apply step writes it using the existing upload and tree functions, as a system sync attributed to the person who connected the library.
  • A worker and a webhook trigger syncs: the worker polls due libraries on the sweeper's pattern; POST /hooks/github/{library}, verified by HMAC-SHA256, wakes the worker at once.
  • Secrets (the token, the webhook secret) are stored only as AES-256-GCM ciphertext, under a key file in the data folder. No secret appears in Git, events, logs, API responses or error text.

Tech stack: the existing workspace, plus new dependencies, each of which approving this plan approves (proposal 5): reqwest with rustls (no native TLS and, to avoid a C build tool on Windows, the ring provider) for the HTTPS client; tar and flate2 for the tarball; aes-gcm for secret storage; hmac for webhook signatures. Licences must be MIT or Apache 2.0 (D17). The server has no HTTPS client today, and gix is built here without a network transport, so cloning with Git is not available; the GitHub API is both simpler and cheaper.

Spec: s3-surfacing-design.html v0.3 (sections 03 to 11 and 14, and the Git table in section 13) and scope.html SC-02, SC-11, SC-21, D09, D24, D28, D39. Plans 1 to 4B are the base. Owner decisions of 16 November 2026: sources are built in the order GitHub, file share, S3 (first on Cloudflare R2); saves to a Git repository will be direct commits; no versioning is required of a store.

Proposals in this plan for the owner to check

These are choices the plan makes that the owner's answers did not settle. Approving the plan approves them; any can be changed before building.

  1. Read-only first. The design puts write-back in phase C. This plan ends with a library that mirrors GitHub and refuses changes. Direct commits (decided) follow in a separate plan, 5B, which needs the version and lock work of Stage 3 only for check-out, not for commits (see "Not in this plan").
  2. The bytes are mirrored into the content store. A connected library holds a copy of each allowed file (up to caps), so every existing feature works unchanged. The copy is rebuildable from GitHub, and the library's size and file count are capped (default 50,000 files, 2 GiB, both settable by an administrator). The lazy cache model of the design stays the plan for S3, where buckets are far larger.
  3. Source settings are kept in PostgreSQL and the event log, not as a Git record. The sync bookmark is operational, and the repository, branch and folder are small. Putting the settings into the library's Git record (D24) can follow without changing behaviour.
  4. Who may connect. Anyone who may create a library in the site (a site owner or an administrator). The token field is write-only: it can be replaced or cleared, never shown.
  5. New dependencies as listed under Tech stack.
  6. Attribution. Synced files and versions are credited to the person who connected the library, with the commit ID and the GitHub author's name in the revision's note. Crediting each GitHub author needs a mapping to ShareCraft accounts, which does not exist.
  7. Removed files go to the recycle bin (D29), so a repository mistake can be undone in ShareCraft for 93 days. Only the sync can remove files from a connected library; people cannot.
  8. Disconnecting keeps the files. The library becomes an ordinary library holding the last synced copy, and can then be edited. Reconnecting starts again and does not merge.
  9. Symbolic links and submodules are hidden and counted, not followed.

Not in this plan

  • Plan 5B, write-back as direct commits. An upload, rename, delete or editor checkpoint in a connected library becoming a commit through the Git Data API (blob, tree, commit, then a branch update that GitHub refuses if the branch moved). The sync engine here already records the commit each node came from, which is the base 5B needs; the replay-on-new-head rule and the sibling-copy conflict rule are written in the design (sections 06 and 13).
  • The file-share source (phase A2) and the S3 source (A3). The RepoRef/GithubClient split here is the point where a general StorageSource trait is extracted when the second source is built, not before (YAGNI), and the design's trait stays the target.
  • DriveCraft sync (phase B). Connected libraries are ordinary nodes, so they appear in the SC-23 feed when it exists; the capabilities block (read-only flag) is added then.
  • GitHub Apps, OAuth sign-in, GitHub Enterprise Server hosts other than through the configured API address, pull requests, LFS pointer resolution, per-author attribution, and any full-text search.
  • Putting the connection settings in Git (proposal 3).

Global constraints

  • Rust 2024; workspace lints deny unwrap_used, expect_used, panic, indexing_slicing; unsafe_code is forbidden. New code follows them, tests included (the existing tests carry #![allow(clippy::unwrap_used, ...)] at the top).
  • Build output goes to J: (CARGO_TARGET_DIR=J:\cargo-target\sharecraft). Tests: cargo xtask test -p server --test <name> and cargo xtask test -p records --test <name>; they need TEST_DATABASE_URL (PostgreSQL 18, port 5433). Never print .env, database URLs, tokens or passwords.
  • No secret in plain text anywhere: not in PostgreSQL, Git, events, logs, API responses, panics or error strings. A token-bearing type has a redacting Debug, as DatabaseUrl does in config.rs.
  • Migrations are immutable once applied: this plan adds 0017_sources.sql and edits no earlier migration.
  • Windows features must not need per-machine administrator work: the secret key is a file in the data folder, created on first use, with no installer step.
  • HTTPS only to GitHub. The API base address comes from configuration (default https://api.github.com); a plain http address is accepted only when SHARECRAFT_GITHUB_API is set explicitly, which the tests do for their fake server. A user can never choose the address.
  • Web pages are plain HTML and JavaScript in web/, no build step, light and dark, 375 px wide up, keyboard and screen-reader usable; tables and long lists carry alternating row shading.
  • Documents are HTML, never Markdown, with alternating row shading (BUILDING.html).
  • Commits end with Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>. Work on a branch; do not merge or push without the owner.
  • Subagents use Opus 5.5 or Sonnet, with the model named on each dispatch.

Review focus

Inputs and conditions the design implies but the happy path never meets. Each has a test in the task that owns the code.

  1. Names that cannot be ShareCraft names. Git allows A.md and a.md together, names ending in a dot, and names over 255 characters. Expected: the first path in sort order keeps its name, the other is shown with a visible suffix and counted, and nothing is silently dropped (Task 4).
  2. Symbolic links and submodules. A tree entry of mode 120000 or type commit must not become a file with the link target as its content. Expected: hidden and counted (Task 4).
  3. A sync that fails or is cut short must not delete anything. A truncated tree, a dropped connection, a repository over the caps: the library keeps what it had and the status says why (Task 4).
  4. A deleted branch, a revoked token, a renamed or deleted repository. Expected: state not connected with a plain message, files still readable, no retry loop (Task 7).
  5. A secret leaking. Plant a token and a webhook secret and scan every API response, event row and captured log line for them (Task 6).

Rules the engine follows. One sync at a time per library (a PostgreSQL advisory lock keyed on the library; a second caller returns Ok(None)). Read the head with the stored etag; NotModified or an unchanged commit only updates last_checked_at. Read the tree; filter to the folder; apply file policy per file with tree::check_policies and the largest file (D39), counting hidden. A repository over source_max_files or source_max_bytes fails with a plain message before anything is written. Names: split on /; a segment that ShareCraft refuses (empty, ., .., control characters, over 255 characters) hides the file as unnameable; two siblings equal ignoring case keep the first in byte order and give the others name (2).ext, name (3).ext and count them. Plan: same path and same blob ID is unchanged; same path, different blob ID is a change (a new version of the same document, same id); a vanished path and a new path with the same blob ID, exactly one each, is a move (same node, same document, renamed or re-parented); everything else is add or remove. Fetch: more than 20 files to read means one tarball to a temp file in data_dir/uploads and one pass through it, otherwise one blob request per file, four at a time. Every byte read is checked with git_blob_id against the tree's ID; a mismatch fails the sync. Write: folders first (shallowest first), then files, through the existing upload functions, as the connecting user, with the commit ID and the GitHub author's name in the revision note; removals go to the recycle bin and folders left empty are removed after the files. Nothing is applied until every wanted byte has been read and checked; apply then runs file by file and records each in source_items as it goes, so a crash leaves a state the next sync repairs (items not in source_items but present as nodes are found by path and adopted, not duplicated). Sync bytes do not count against the site's quota. Event kinds: source.synced with the counts and commit, source.failed with a plain reason; neither carries a token or a response body.

Task 7: the worker, backoff and the webhook

Files: modify crates/server/src/source_sync.rs (worker), crates/server/src/lib.rs (serve_state starts it; the webhook route is registered next to /l/{token}, outside /api, because GitHub sends no Origin; re-export source_tick_once), crates/server/Cargo.toml (hmac); create crates/server/src/webhooks.rs, crates/server/tests/source_worker.rs.

Interfaces. Produces pub fn start_worker(state: AppState) -> Worker (abort on drop, tokio::select! on a Notify and a 60 s tick, as scan::start_worker), pub async fn tick_once(state: &AppState, now: OffsetDateTime) -> usize (syncs every due library, returns how many ran; tests call it with a chosen now), and POST /hooks/github/{library}. A wake handle lives in AppState: state.sources().wake(library).

Rules. Due means: state is ok, failed or connecting; last_checked_at + poll_seconds <= now; and retry_at is not in the future. After RateLimited(t): state rate_limited, retry_at = t. After Unauthorized, NotFound or a missing branch: state not_connected with the plain message, no further automatic attempts until an owner changes the source or presses Sync (which clears the state). After a network failure or other error: state failed, back off min(60 s × 2^n, 1 h) with n counted in memory per library; a success resets it. At most two libraries sync at once. Webhook: X-Hub-Signature-256: sha256=<hex> is the HMAC-SHA256 of the raw body with the unsealed secret, compared in constant time; ping answers 200; push for refs/heads/<branch> wakes the library and answers 202, other pushes and events answer 204; an unknown library, a library with no webhook secret, and a bad signature all answer 404 and 401 respectively without telling which part was wrong beyond that; body limit 5 MiB, read in full before the check; failures count towards the existing per-address throttle (extend lib.rs::source, which counts 404s under /api/l/, to cover /hooks/). The delivery's content is never trusted for anything but the branch name.

Self-review

  • Design coverage: read-only surfacing, folders from paths, versions (the repository's blob and commit IDs; history shown is ShareCraft's own, because Git history in the UI is part of 5B), change detection by conditional polling and webhook, credentials sealed, permissions over the tree, scanning and previews and file-type limits and recycle bin through real nodes, and the DriveCraft path by being ordinary nodes.
