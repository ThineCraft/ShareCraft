01 / Purpose & scope status

Develop ShareCraft as the open-source shared-content foundation of ThineCraft: a platform for sites, intranets, libraries, structured records, publishing, knowledge, governance and collaboration. Organizations must be able to own their information, deploy the platform on infrastructure they control, and connect it to other applications.

The SharePoint capability catalogue below establishes breadth. ShareCraft also includes cross-application co-authoring, hybrid continuity, controlled public intake and a foundation for specialized services.

This is a proposed scope of works, not an implementation claim or a fixed-price agreement. Established product direction is distinguished from newly proposed detail. All functionality remains planned until implemented and verified. Release allocation, costs, dates and service levels require separate agreement.

“Comprehensive” means a broad functional baseline with explicit boundaries. It does not promise every historical SharePoint feature, every Microsoft 365 service, or automatic Microsoft API compatibility.

03 / SharePoint functional baseline

The following modules expand the requested baseline into reviewable requirements. Detailed behaviors are proposed unless explicitly established above. These are ShareCraft requirements, not assertions that every listed behavior is native to every SharePoint edition.

Proposed baseline detail

SC-01 · Organizations, sites & navigation

  • Create and administer organizations, site collections or equivalent boundaries, team sites, communication sites, departmental portals and hub-style groupings.
  • Provide site templates, reusable provisioning packages, branding, logos, themes, language settings, time zones, global navigation, local navigation, breadcrumbs and site discovery.
  • Manage site ownership, lifecycle, quotas, archival, restoration and deletion. Audience targeting personalizes navigation; permissions independently control access.
Proposed baseline detail

SC-02 · Libraries & file operations

  • Create document, asset, image and template libraries; support folders, optional folder-free organization and document sets with shared metadata.
  • Provide drag-and-drop and resumable uploads, bulk operations, new-from-template, preview, download, rename, copy, move and deletion with documented permission and history behavior.
  • Use durable content identifiers and links; handle duplicates, invalid names, interrupted transfers, checksums, quotas, large files, malware quarantine and unsupported previews.
  • Provide metadata panels, missing-information views, library settings, upload validation and configurable file policies.
Proposed baseline detail

SC-03 · Lists & structured information

  • Create custom lists and reusable list templates for contacts, tasks, issues, assets, registers, events and operational records.
  • Support item creation, editing, attachments, comments, bulk grid editing, CSV import/export, relationships, uniqueness and validation.
  • Support indexed columns, paging, large datasets, calculated values with a documented formula subset, and safe handling of referenced or deleted records.
Explicit requirement

SC-04 · Site columns & metadata

  • Define reusable organization/site columns and local list/library columns, with stable internal identifiers, descriptions, grouping and controlled display names.
  • Cover text, rich text, number, currency, date/time, Boolean, choice, multiple choice, person/group, lookup, hyperlink, image, calculated and managed-metadata fields.
  • Configure required/optional/hidden fields, defaults, validation, unique values, indexing, display formatting and column-level edit behavior where authorized.
  • Support bulk metadata editing and folder/location defaults. Plan schema changes, field conversion and deletion without silently losing existing values.
Explicit requirement

SC-05 · Managed metadata & taxonomy

  • Provide a term store with groups, term sets, hierarchical terms, stable IDs, descriptions, synonyms, multilingual labels and taxonomy owners.
  • Support closed and open term sets, single/multiple term selection, enterprise keywords and scoped reuse across sites and content types.
  • Allow authorized import/export, reparenting, merging, deprecation and replacement. Preserve references when labels change; expose affected content before destructive changes.
  • Use taxonomy consistently in forms, navigation, filtering, search and DriveCraft metadata displays. Record taxonomy changes in an audit trail.
Explicit requirement

SC-06 · Content types

  • Provide a content-type gallery with inheritance, stable identifiers, names, descriptions, categories, document templates and reusable site-column assignments.
  • Allow multiple content types per library/list; configure defaults, field ordering, required/optional/hidden fields and type-specific forms.
  • Support publication across selected sites and controlled propagation of parent changes. Preview downstream effects, preserve local overrides according to policy and support rollback.
  • Associate workflow, retention and document-generation behavior with content types through explicit rules. Include document-set types and reusable business record types.
Proposed baseline detail

SC-07 · Views, forms & everyday usability

  • Provide personal/public saved views with column selection, sorting, filtering, grouping, totals and metadata navigation.
  • Include table, grid, gallery, calendar and board views where compatible with the schema; provide reusable, accessible formatting rules.
  • Provide configurable create/edit/display forms with conditional fields, validation, help text and read-only states; integrate richer forms through FormCraft.
  • Preserve keyboard navigation, responsive layouts, clear empty/error states, bulk-selection feedback and localization.
Explicit requirement

SC-08 · Version history, publishing & locking

  • Version files, metadata, list items and pages with actor, timestamp, change comment and revision ID. Define which changes create a version.
  • Support major/minor document revisions, drafts, publication, approval status, draft visibility and configurable version limits/expiry.
  • Inspect historical metadata and retrieve prior file bytes; restoration creates a new current version while preserving the historical record. Show text/field differences where supported; binary comparison depends on the editor.
  • Provide check-out/check-in, exclusive locks, lock expiry/recovery and optimistic concurrency. Exclusive editing and live co-authoring require explicit coordination.
  • Keep version pruning subordinate to retention and hold rules. Document history behavior for moves, copies, migration and deletion.

SharePoint reference: Microsoft’s versioning, draft visibility and checkout documentation.

Proposed baseline detail

SC-09 · Pages, news & knowledge publishing

  • Provide a visual page editor with sections, layouts, templates and reusable components for text, images, files, links, lists, libraries, news, events, people and approved embeds.
  • Support draft saving, preview, version history, review, scheduling, publish/unpublish, page ownership, translations and expiry/review reminders.
  • Provide home pages, knowledge articles, news posts, announcements, comments, reactions and aggregated content rollups subject to permissions.
  • Maintain asset references and navigation links; sanitize authored content and embedded components. Public publishing requires deliberate configuration.
Proposed baseline detail

SC-10 · Search & discovery

  • Search sites, pages, list records, document metadata and supported file contents, with scoped queries, refiners, sorting, highlights and saved searches.
  • Map site columns/content types into a configurable search schema, with indexed/queryable/refinable fields and taxonomy-aware filtering.
  • Enforce current access rights for results, counts, snippets, suggestions and previews; handle permission revocation and index delays without exposing content.
  • Provide crawl/index status, extraction failures, rebuild controls and relevance configuration. OCR and people-directory search are separately configurable extensions.

Reference baseline: Microsoft’s SharePoint search overview.

Proposed baseline detail

SC-11 · Identity, permissions & sharing

  • Support users, guests, groups, service identities, owners/members/visitors and configurable permission roles, with delegated administration.
  • Provide inheritance at site, library/list, folder and item levels; show effective access, broken inheritance and the reason access was granted.
  • Support access requests, authenticated sharing links, expiry, revocation, domain restrictions and configurable anonymous sharing. Apply authorization consistently to APIs, downloads, previews and co-authoring.
  • Integrate an agreed identity provider and single sign-on; define session revocation, MFA responsibility, account deactivation and tenant isolation.
Proposed baseline detail

SC-12 · Retention, records & audit

  • Define retention schedules, record declaration, preservation holds, archival and authorized disposition review for files, items and associated versions.
  • Ensure normal deletion, version cleanup and administrator actions cannot silently bypass active preservation rules; define hold release and post-hold disposal.
  • Record content, permission, sharing, administrative and workflow changes in an access-controlled audit trail with export and integrity controls.
  • Provide classification labels, review reminders, retention reports and case-based search/export. Specify jurisdictional rules before claiming regulatory compliance.

Microsoft 365 reference: Purview retention for SharePoint. Equivalent ShareCraft controls are separate implementation work; a Microsoft Purview dependency is not implied.

FlowCraft integration

SC-13 · Workflows, approvals & notifications

  • Expose triggers for creation, content changes, metadata changes, submission, publication, approval, deadlines and permission changes.
  • Support serial/parallel approval, delegation, escalation, rejection, resubmission, reminders and an auditable decision history through FlowCraft.
  • Provide in-app notifications, subscriptions, mentions and configurable email delivery; links must recheck permissions when opened.
  • Specify retry, idempotency, cancellation, timeout, workflow versioning and service-identity permissions. A published approval must reference the exact approved revision.
Proposed baseline detail

SC-14 · Administration & extensibility

  • Provide organization and site administration for settings, storage, identities, sharing, content types, taxonomy, search, workflows, audit and lifecycle.
  • Expose documented, versioned APIs, event subscriptions, webhooks and scoped application credentials with paging, rate controls and change tracking.
  • Provide reusable templates and approved extension points for page components, content handlers and business applications; isolate extensions from privileged operations.
  • Report storage, activity, stale content, orphaned ownership, sharing exposure and failed background jobs. Provide import/export of configuration.

04 / Beyond SharePoint

These capabilities express ShareCraft’s broader role in ThineCraft. The product direction is established; protocols and detailed acceptance behavior below are proposed.

Established direction · Detail proposed

SC-15 · Cross-application co-authoring

  • Provide shared document identity, editing sessions, participant presence, authorization, reconnect behavior and revision checkpoints for WordCraft, GridCraft, PdfCraft, SolidCraft and DeckCraft.
  • Define an editor integration contract covering capabilities, supported formats, autosave, comments, user attribution, conflicts and durable saves.
  • Negotiate collaboration by content type: text operations, cells, slide objects, PDF annotations or CAD operations require appropriate application-specific strategies. Generic file storage does not merge arbitrary binaries.
  • Show session state and save status; preserve concurrent work during disconnects and enforce revocation during active sessions. Editors own rendering and document semantics.
DriveCraft · Established direction

SC-16 · Hybrid continuity & organization-owned copies

  • Support hosted, self-hosted and hybrid deployments with organization-controlled server/NAS copies of organizational files and their necessary metadata, identities and permissions.
  • Expose incremental synchronization, checkpoints, checksums, tombstones and conflict information to DriveCraft. Show mirror coverage, last successful sync, missing data and recovery readiness.
  • Define whether offline copies are recovery-only, readable during outages, or writable with later reconciliation. Writable offline operation is an open decision, not an assumed guarantee.
  • Provide authorized export and recovery without depending solely on the hosted service. Synchronization is not a substitute for independent backups and tested restoration.
DriveCraft / Microsoft interoperability

SC-17 · Migration & coexistence

  • Inventory source files, sites, libraries, schemas, content types, taxonomy, users, permissions and versions before transfer. Produce a supported/unsupported mapping report.
  • Support resumable migration, dry runs, staged batches, throttling, delta passes, checksums, reconciliation and exception reports through DriveCraft.
  • Preserve content and metadata to the extent supported by each source/destination API; explicitly report unpreserved author identities, timestamps, versions, links and permissions.
  • Use Microsoft Graph where supported; define additional supported APIs or tools for gaps. Do not promise complete SharePoint migration or continuous two-way sync before a connector capability assessment.
Established direction · Detail proposed

SC-18 · Controlled public portals & submission

  • Provide branded public/guest submission surfaces that write into a controlled intake boundary without granting access to private libraries or administrative functions.
  • Support authenticated or anonymous submissions by policy, file uploads, validation, consent capture, receipts, tracking references and permitted status updates.
  • Separate incoming/quarantined records from approved internal content, with abuse controls, upload inspection, workflow routing and owner review.
  • Provide public read-only previews where explicitly authorized. Prevent visitors from enumerating other submissions or resolving private document links.
FormCraft / PdfCraft · Established direction

SC-19 · Electronic forms & paper-to-digital records

  • Store and publish form templates, template revisions, fillable PDFs, browser views, submissions and source evidence. FormCraft owns field logic; PdfCraft owns PDF viewing/editing and capture.
  • Resolve a QR-coded document-instance identifier to its authorized template, template version and field map; distinguish instance identity from a human or cryptographic signature.
  • Receive progressively extracted fields, assembled page imagery, confidence information and capture history from PdfCraft’s streamed phone-scanning workflow.
  • Support human review of uncertain extraction, correction history, finalization and controlled read-only access to completed records. Define evidence/video retention separately; do not assume indefinite raw-stream storage.
Requested ecosystem extension · Design open

SC-20 · Signatures, integrity & timestamp evidence

  • Store finalized document bytes, cryptographic hashes, detached signatures, signer-key information, verification results and optional public-ledger timestamp proof bundles.
  • Associate evidence with an exact immutable revision; any edited document becomes a different revision requiring its own evidence.
  • Keep signer identity verification separate from proof of document integrity and time of existence. Bitcoin timestamping alone does not identify the signer.
  • Define provider, privacy, pending/confirmed/failed states, verification tooling, key revocation and retention before implementation. OpenTimestamps was proposed in the continuation, but provider and signing roles remain unresolved.
Historical direction · Architecture open

SC-21 · Git-oriented history & portable storage

  • Evaluate Git-backed history as part of the document-management direction while maintaining a normal library experience for nontechnical users.
  • Specify how content, metadata, permissions, schemas and revision identifiers map into repositories or an equivalent portable history model.
  • Resolve binary/object storage, large files, repository growth, encryption, tenancy isolation, retention, deletion and recovery before selecting Git, Git LFS or another design.
  • Branching, forks, pull requests and automated merges are candidate extensions requiring explicit scope decisions; they are not implied by Git storage.
Established platform direction

SC-22 · Services assembled on the platform

  • Provide reusable site, library, content-type, form, permission and workflow packages that can be assembled into specialized services.
  • Allow ThineWedding, ThineMemorial and ThineCapture to use independent branding, URLs, users and service-specific configuration on ShareCraft.
  • Keep service-specific schemas and behavior modular. Their detailed commercial/event workflows require separate scopes and do not redefine ShareCraft core.

07 / Delivery framework & acceptance

Recommended delivery order; no phase is yet assigned a contractual date, cost or release commitment.

  1. Definition: approved requirements register, feature classification, compatibility matrix, information architecture, sample schemas, tenancy/security model, deployment choices and measurable service targets.
  2. Content foundation: identities, sites, libraries, lists, reusable columns, content types, taxonomy, permissions, history and APIs.
  3. Knowledge & governance: pages, search, publishing, approval integration, retention, audit, administration, migration and backup/restore.
  4. Broader platform: editor co-authoring, DriveCraft hybrid continuity, public intake, form capture integration, evidence verification and service templates.
  5. Production readiness: realistic migration rehearsal, accessibility/security/performance checks, disaster recovery exercise, operational documentation, administrator training and release handover.

Required handover outputs

Application source and build/deployment instructions; schema and API documentation; configured sample sites/libraries/lists/content types/taxonomies; migration and reconciliation reports; verification evidence; security and recovery runbooks; user/admin guidance; known limitations; dependency/license inventory; and an HTML requirements register mapping each scope item to its release and acceptance evidence.

08 / Decisions to resolve

These remain open rather than being silently chosen by this document.

  1. Release breadth: which baseline and extension modules belong in the first usable release, and which are later deliverables?
  2. Tenancy & identity: single organization or multitenant service; identity provider; federation; external users; delegated administration.
  3. Storage & Git: canonical content model, metadata database, object storage, Git role, binary history and recoverable deletion versus permanent erasure.
  4. Hybrid authority: recovery mirror, offline read service or fully writable offline deployment; conflict ownership and reconciliation policy.
  5. Co-authoring: editor protocol, supported formats, per-editor collaboration semantics and release order.
  6. Compatibility: modern SharePoint baseline, selected classic capabilities, import/export guarantees and supported Microsoft API coverage.
  7. Trust & evidence: signing parties, verified identity, timestamp provider, key management, public verification and evidence retention.
  8. Scale & operations: infrastructure, volume, concurrency, availability, indexing, backups, recovery, support and accessibility targets.
  9. Commercial handover: budget, milestones, acceptance owner, support period, open-source license and change-control procedure.

Additional features: record each requested addition with an ID, user outcome, owner application, data/permission impact, dependencies, acceptance scenario and release assignment. AI-assisted tagging/search, mandatory data-loss prevention, native mobile clients, Microsoft Office integration and legacy SharePoint runtime compatibility are not silently included by the phrase “everything”; each needs an explicit scope entry.
