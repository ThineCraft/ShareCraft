01 / Purpose & scope status

Develop ShareCraft as the open-source shared-content foundation of ThineCraft: a platform for sites, intranets, libraries, structured records, publishing, knowledge, governance and collaboration. Organizations must be able to own their information, deploy the platform on infrastructure they control, and connect it to other applications.

The SharePoint capability catalogue below establishes breadth. ShareCraft also includes cross-application co-authoring, hybrid continuity, controlled public intake and a foundation for specialized services.

This is a proposed scope of works, not an implementation claim or a fixed-price agreement. Established product direction is distinguished from newly proposed detail. All functionality remains planned until implemented and verified. Release allocation, costs, dates and service levels require separate agreement.

“Comprehensive” means a broad functional baseline with explicit boundaries. It does not promise every historical SharePoint feature, every Microsoft 365 service, or automatic Microsoft API compatibility.

D26Metadata is hierarchical. A content type defines a tree of field groups, each single or repeating and nested to any depth, so a document can describe an order and also hold its items. Detailed in SC-26.Explicit user requirement, 12 November 2026: “A document can be about an order but it can also contain items. D27Sharing by link (plan 2B, D25) works as follows. A signed-in link is a hidden group with a role on the item, so sharing by link gives the item its own permissions and breaks inheritance, as in SharePoint. Anyone links allow viewing and downloading only, never editing; they are off by default, always expire, and stop at any folder or file with its own permissions. Domain allow and block lists wait for the guests plan, which depends on the identity provider decision. Two choices in the plan were accepted when the owner approved it: only people who manage access can share by link (SharePoint also lets members share), and a link's address is shown once, when it is made, because only a hash of it is kept.Owner decisions, 13 November 2026, and the owner's approval of plans/2026-11-13-links-and-requests.html. Progress is in sequencing.html and what was built is in section 24 of BUILDING.html. Refines D25 and SC-11.
D28Binary storage is settled. File bytes are kept in a content store on disk, named by their SHA-256 hash, and Git holds a small pointer to them in place of the bytes. Settles the binary-storage part of decision 3 and SC-21. Built in plan 3A (plans/2026-11-13-files.html); what was built is in section 25 of BUILDING.html. Refines D09.

03 / SharePoint functional baseline

The following modules expand the requested baseline into reviewable requirements. Detailed behaviors are proposed unless explicitly established above. These are ShareCraft requirements, not assertions that every listed behavior is native to every SharePoint edition.

Proposed baseline detail

SC-01 · Organizations, sites & navigation

  • Create and administer organizations, site collections or equivalent boundaries, team sites, communication sites, departmental portals and hub-style groupings.
  • Provide site templates, reusable provisioning packages, site branding as specified in SC-25, language settings, time zones, global navigation, local navigation, breadcrumbs and site discovery.
  • Manage site ownership, lifecycle, quotas, archival, restoration and deletion. Audience targeting personalizes navigation; permissions independently control access.
Proposed baseline detail

SC-02 · Libraries & file operations

  • Create document, asset, image and template libraries; support folders, optional folder-free organization and document sets with shared metadata.
  • Provide drag-and-drop and resumable uploads, bulk operations, new-from-template, preview, download, rename, copy, move and deletion with documented permission and history behavior.
  • Use durable content identifiers and links; handle duplicates, invalid names, interrupted transfers, checksums, quotas, large files, malware quarantine and unsupported previews.
  • Provide metadata panels, missing-information views, library settings, upload validation and configurable file policies.
Proposed baseline detail

SC-03 · Lists & structured information

  • Create custom lists and reusable list templates for contacts, tasks, issues, assets, registers, events and operational records.
  • Support item creation, editing, attachments, comments, bulk grid editing, CSV import/export, relationships, uniqueness and validation.
  • Support indexed columns, paging, large datasets, calculated values with a documented formula subset, and safe handling of referenced or deleted records.
Explicit requirement

SC-04 · Site columns & metadata

  • Define reusable organization/site columns and local list/library columns, with stable internal identifiers, descriptions, grouping and controlled display names.
  • Columns can be arranged in nested and repeating groups, as defined by content types (SC-26), so a document can carry items as well as single values.
  • Cover text, rich text, number, currency, date/time, Boolean, choice, multiple choice, person/group, lookup, hyperlink, image, calculated and managed-metadata fields.
  • Configure required/optional/hidden fields, defaults, validation, unique values, indexing, display formatting and column-level edit behavior where authorized.
  • Support bulk metadata editing and folder/location defaults. Plan schema changes, field conversion and deletion without silently losing existing values.
  • Detect metadata changes from supported application, API, synchronization and repository inputs. Read the current metadata/revision, validate changes and update the associated JSON files and PostgreSQL representation as specified in SC-21.
Explicit requirement

SC-05 · Managed metadata & taxonomy

  • Provide a term store with groups, term sets, hierarchical terms, stable IDs, descriptions, synonyms, multilingual labels and taxonomy owners.
  • Support closed and open term sets, single/multiple term selection, enterprise keywords and scoped reuse across sites and content types.
  • Allow authorized import/export, reparenting, merging, deprecation and replacement. Preserve references when labels change; expose affected content before destructive changes.
  • Use taxonomy consistently in forms, navigation, filtering, search and DriveCraft metadata displays. Record taxonomy changes in an audit trail.
Explicit requirement

SC-06 · Content types

Explicit architecture · Synchronization detail proposed

SC-21 · Git version control, JSON metadata & PostgreSQL

  • Confirmed foundation: ShareCraft is based on Git and PostgreSQL. Git is the version-control system for content revisions and JSON metadata files, while users retain a normal library experience without needing Git commands.
  • Versioned metadata: store metadata in JSON files associated with stable content identifiers. Define a versioned JSON schema for field values, content-type references and managed-metadata term IDs. Metadata-only changes must be traceable in Git, including attribution and the associated content revision.
  • Change-aware updates: when metadata changes through a supported application, API or synchronization path, read the current JSON and revision, validate the requested changes, update the JSON as needed and commit the change to Git. Avoid creating commits for unchanged values.
  • PostgreSQL role — proposed: maintain validated, queryable operational records and indexes in PostgreSQL, linked to Git revision IDs. Use committed JSON as the durable versioned metadata record; PostgreSQL must be reconcilable with that record rather than becoming an unrelated metadata silo.
  • Repository reads — proposed: detect supported Git/JSON changes through change events or revision polling, read and validate the changed files, then update PostgreSQL and notify dependent search/sync services. Support initial import, replay and rebuilding the metadata projection from versioned records.
  • Consistency — proposed: track pending, committed, indexed and failed updates; provide idempotent retries and reconciliation after interruption. Reject or surface malformed JSON, stale writes and concurrent conflicts without silently overwriting another user’s metadata. Do not claim a single atomic transaction across Git and PostgreSQL.
  • Enforce authorization and tenant boundaries for every metadata write and repository import. Repository access must not provide a route around ShareCraft permissions; permission-related records and inheritance changes must remain auditable.
  • Binary storage is settled as a SHA-256 content store with pointers in Git (D28). Resolve repository layout/growth, encryption, retention, deletion and recovery within this confirmed Git/PostgreSQL foundation.
  • Branching, forks, pull requests and automated merges are candidate extensions requiring explicit scope decisions; they are not implied by Git storage.

Explicit requirement · Detail proposed

SC-26 · Hierarchical metadata

  • Requirement: a document's metadata is a structure, not only a flat set of columns. An order document describes the order in header fields (order number, customer, date) and also holds its items (product, quantity, price) as repeating records. Items can hold items of their own, to any depth: an order, its shipments, their lines, each line's serial numbers.
  • Content types define the structure: a content type (SC-06) is a tree of field groups, not only a collection of columns. Each group uses site columns (SC-04) and is either single or repeating. Proposed: minimum and maximum counts for repeating groups, required fields and validation at every level, and rules across levels, such as an order total that must equal the sum of its line amounts.
  • Lasting identity: every group and every item has an identifier that does not change when items are reordered or others are removed (spine rule S1). History, workflows, links and the API name an item by it.
  • Storage: the structure is kept in the document's JSON metadata in Git, with a versioned schema (SC-21), and mirrored in PostgreSQL in a form that can be indexed and queried per item. A change to metadata alone is a revision credited to the person who made it. A change to a content type's structure migrates existing values, or flags the documents it cannot migrate; values are never silently dropped.
  • Entry and extraction: people add, edit, reorder and remove items at any depth in the metadata panel and in type-specific forms (SC-07). A content type can map parts of the file to its structure, such as a table in a spreadsheet to a repeating group, PDF form fields, or document properties. On upload or save, the mapping fills in values or proposes them for a person to review. Extraction here is rule-based; AI-assisted extraction is not included unless it is added by its own scope entry (section 08).
  • Search, views and reports: filter and search documents by item fields. Conditions on one item are matched within the same item: "product is Chair and quantity is more than 1" finds a document only if one line meets both, not one line each. Views can show items as rows under their document, with counts and totals across items.
  • Workflows, API and DriveCraft: FlowCraft can trigger on and test item fields (SC-13), for example when an item over a set amount is added. The API reads and changes items by their identifiers, and the change feed reports item-level changes (SC-14, SC-23). DriveCraft shows and edits the structure.
  • Permissions: items share their document's permissions. Item fields appear in search, views, exports, the API and the change feed only to people who may read the document.
  • Open: whether an item can be turned into a separate record (a list item, SC-03) and linked back; how deep forms nest before they switch to a separate page; limits on the number of items per document.
Owner-approved direction · Phase A1 built

SC-27 · Storage-source libraries

  • Shape: create a connected library of one of the existing kinds. The connection is an attribute of the library, not a fifth kind (D61); its document, image, template or asset kind and its ordinary permissions, sharing, scanning, previews and file policies still apply.
  • Order: build GitHub first, then a file share, then S3 tested first on Cloudflare R2, then Azure Blob Storage (D62). This is a platform-track module beside the editor track and does not change the delivery stages or put co-authoring second.
  • Git authority and mirror: for a Git source, the selected repository branch remains authoritative while ShareCraft mirrors the allowed files into its content store as ordinary tree nodes (D63). Migration 0019 creates the final source records, generation checks and separate original repository path after the live-log migration 0018. Tracking replacement is atomic, and tracked nodes are verified by parent and name. The mirror is rebuildable and is bounded by file and byte caps whose defaults are 50,000 files and 2 GiB. This release has no settings API or page for those caps; they are set in the database. The S3 design keeps its separate lazy-cache model.
  • Case-collision safety: by owner decision on 17 November 2026, every file in a same-folder, case-insensitive collision group is numbered from (1) in original repository-path byte order; none keeps the plain name. This prevents case-insensitive DriveCraft on Windows from overwriting one file with another and avoids presenting one member as the “real” file. The original repository path remains its identity while displayed names change.
  • Read-only first: phase A first provides browse, download, preview, permissions, links, scanning and DriveCraft-feed-compatible nodes while ShareCraft refuses content changes. Removed repository paths go to ShareCraft’s recycle bin; symbolic links and submodules are hidden and counted. If an initial connection fails, its new library is purged only while empty and otherwise left in the recycle bin. A worker stop can interrupt a tree mutation; recovery repairs it on the next sync. A path purged through malware quarantine stays absent until a new repository commit.
  • Write-back: plan 5B will make Git saves direct commits. Repository history display, per-author account attribution, protected-branch behaviour and conflict replay belong to that later work.
  • Credentials and operation: connection credentials are write-only and encrypted at rest; key installation does not delete a key another process installed. Polling and source webhooks detect changes. Poll-only and webhook-secret changes preserve an active rate-limit wait; token, branch and folder changes reset it. The library page reloads its current folder when the synchronized commit changes. Webhooks accept JSON, not form-encoded deliveries. Source settings are operational PostgreSQL records and events rather than Git records.
  • Approval record: on 16 November 2026 the owner replied “Approve plan” to plan 5, approving its nine proposals: read-only first; mirroring Git bytes with caps; keeping source settings in PostgreSQL and events; allowing site library creators to connect with a write-only token; the named dependencies; connector attribution until account mapping exists; recycle-bin removals; keeping files on disconnect; and hiding and counting symbolic links and submodules.

07 / Delivery framework & acceptance

Delivery order following D15: co-authoring first, the platform formed alongside it. The order is the owner's direction; the stage contents are proposed and detailed in sequencing.html. No stage is yet assigned a contractual date, cost or release commitment.

  1. Definition and editor inspection: decisions needed to start, including how concurrent edits are merged; a read-only inspection of the four upstream editors; the editor integration contract; tenancy/security model and measurable service targets.
  2. Collaboration spine: in Rust, document identity, shared editing sessions, presence, reconnect, checkpoints saved as Git revisions with JSON metadata and PostgreSQL records, and permission checks that can end a live session. Proven with two browsers editing one plain-text document. The four editor forks are created and each opens from ShareCraft and saves back, one person at a time.
  3. Libraries and access, with GridCraft: sites, libraries, file operations, permissions, the inheritance explorer and site branding; the first real editor co-authoring from a library.
  4. Metadata and history, with WordCraft: lists, reusable columns, taxonomy, content types, views, versions, publishing and locking.
  5. API and change feed, with PdfCraft: administration, extensibility and the DriveCraft integration API.
  6. Knowledge and governance, with SolidCraft: pages, search, retention, audit, workflow integration, hybrid continuity and migration.
  7. Intake, forms, evidence and services: public portals, form capture, evidence verification and service templates; can run alongside the previous stage.
  8. Production readiness: realistic migration rehearsal, accessibility/security/performance checks, disaster recovery exercise, operational documentation, administrator training and release handover.

An automated two-session co-authoring test runs on every build from the end of stage 1, so later work that breaks co-authoring is caught when it is made.

Required handover outputs

Application source and build/deployment instructions, including the designated editor forks, upstream mapping, reproducible browser builds and collaboration-service deployment; schema and API documentation, including the DriveCraft OpenAPI contract, authentication guidance, examples and interoperability verification; configured sample sites/libraries/lists/content types/taxonomies; migration and reconciliation reports; verification evidence; security and recovery runbooks; user/admin guidance; known limitations; dependency/license inventory; and an HTML requirements register mapping each scope item to its release and acceptance evidence.

08 / Decisions to resolve

These remain open rather than being silently chosen by this document. Git-source quota accounting and GitHub TLS are settled in D63 and D64.

  1. Source-cap administration: accept database-only configuration of source_max_files and source_max_bytes for this release, or add a settings API and page. The defaults are 50,000 files and 2 GiB.
  2. Release breadth: which baseline and extension modules belong in the first usable release, and which are later deliverables?
  3. Tenancy & identity: tenancy is decided (D18: one organization per installation). Stage 1 signs people in with ShareCraft’s own accounts and passwords, as proposed in plans/2026-11-10-accounts-and-permissions.html; that is a starting point, not a decision against an outside provider. Still open are the identity provider; federation; external users; delegated administration.
  4. Git / JSON / PostgreSQL implementation: repository and JSON schema layout, synchronization/commit boundaries, PostgreSQL schema and projection strategy, conflict handling, and recoverable deletion versus permanent erasure (binary storage and the two-stage recycle bin are settled: D28, D29). Git version control, JSON metadata and PostgreSQL are settled requirements, not open technology choices; the proposed consistency details in SC-21 still require design review.
  5. Hybrid authority: recovery mirror, offline read service or fully writable offline deployment; conflict ownership and reconciliation policy.
  6. Browser editors and forks: fork names and base revisions (D21) and the hosting and embedding model (D20) are decided. The session, transport and message approach for the ordered change log decided in D16 is settled in D22 (co-authoring-approach.html v1.3). G3 is built in the GridCraft fork but is not yet user-facing. Open implementation items include G4 checkpoints and saved deletion ownership (I8); G5 host/UI integration and identity-table growth under fragmentation (I7); one cross-platform maths library for last-digit agreement; and four GridCraft gates that reproduce at the fork base: clippy at apps/gridcraft-cli/src/check.rs:281, complex_numbers, caret_after_typing_arabic_is_drawn_at_its_left_end, and the stale keytips table. Browser opening, live co-authoring and extending the designated forks are settled requirements; these status items add no product decision.
  7. DriveCraft API design: agree authentication protocol, endpoint/schema definitions, cursor and tombstone retention, notification transport, offline cache policy, compatibility window and measurable synchronization targets. A documented API is required; these implementation details remain open.
  8. Compatibility: modern SharePoint baseline, selected classic capabilities, import/export guarantees and supported Microsoft API coverage. Includes whether any classic branding capability excluded by SC-25 is wanted, and the hub branding inheritance rule.
  9. Trust & evidence: signing parties, verified identity, timestamp provider, key management, public verification and evidence retention.
  10. Scale & operations: infrastructure, volume, concurrency, availability, indexing, backups, recovery, support and accessibility targets.
  11. Commercial handover: budget, milestones, acceptance owner, support period and change-control procedure. The open-source license is decided (D17).

Additional features: record each requested addition with an ID, user outcome, owner application, data/permission impact, dependencies, acceptance scenario and release assignment. AI-assisted tagging/search, mandatory data-loss prevention, native mobile clients, Microsoft Office integration and legacy SharePoint runtime compatibility are not silently included by the phrase “everything”; each needs an explicit scope entry.

For AI contributors and implementers

  • This repository file is the current scope record. Publishing it does not turn every proposed implementation detail into an approved design. Git version control, JSON metadata, PostgreSQL, inheritance breaks independent of library size and an inheritance explorer are explicit user requirements; do not downgrade them to optional ideas or reintroduce count-based restrictions. Rust (D14) and building co-authoring first (D15) are likewise explicit: do not introduce a save or edit path that bypasses the collaboration spine, and do not defer co-authoring behind the baseline modules.
  • Preserve the distinction between explicit user direction, proposed detail and unresolved design choices. Do not label planned features as implemented.
  • Keep editors, sync clients, workflows and specialized services within their stated application boundaries. Record agreed changes in HTML.
  • Use stable requirement IDs in implementation plans, issues and acceptance evidence. Do not claim SharePoint parity, regulatory compliance or production readiness without defined criteria and verification.
