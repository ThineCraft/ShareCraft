01 / Purpose & scope status

Develop ShareCraft as the open-source shared-content foundation of ThineCraft: a platform for sites, intranets, libraries, structured records, publishing, knowledge, governance and collaboration. Organizations must be able to own their information, deploy the platform on infrastructure they control, and connect it to other applications.

The SharePoint capability catalogue below establishes breadth. ShareCraft also includes cross-application co-authoring, hybrid continuity, controlled public intake and a foundation for specialized services.

This is a proposed scope of works, not an implementation claim or a fixed-price agreement. Established product direction is distinguished from newly proposed detail. All functionality remains planned until implemented and verified. Release allocation, costs, dates and service levels require separate agreement.

“Comprehensive” means a broad functional baseline with explicit boundaries. It does not promise every historical SharePoint feature, every Microsoft 365 service, or automatic Microsoft API compatibility.

03 / SharePoint functional baseline

The following modules expand the requested baseline into reviewable requirements. Detailed behaviors are proposed unless explicitly established above. These are ShareCraft requirements, not assertions that every listed behavior is native to every SharePoint edition.

Proposed baseline detail

SC-01 · Organizations, sites & navigation

  • Create and administer organizations, site collections or equivalent boundaries, team sites, communication sites, departmental portals and hub-style groupings.
  • Provide site templates, reusable provisioning packages, site branding as specified in SC-25, language settings, time zones, global navigation, local navigation, breadcrumbs and site discovery.
  • Manage site ownership, lifecycle, quotas, archival, restoration and deletion. Audience targeting personalizes navigation; permissions independently control access.
Proposed baseline detail

SC-02 · Libraries & file operations

  • Create document, asset, image and template libraries; support folders, optional folder-free organization and document sets with shared metadata.
  • Provide drag-and-drop and resumable uploads, bulk operations, new-from-template, preview, download, rename, copy, move and deletion with documented permission and history behavior.
  • Use durable content identifiers and links; handle duplicates, invalid names, interrupted transfers, checksums, quotas, large files, malware quarantine and unsupported previews.
  • Provide metadata panels, missing-information views, library settings, upload validation and configurable file policies.
Proposed baseline detail

SC-03 · Lists & structured information

  • Create custom lists and reusable list templates for contacts, tasks, issues, assets, registers, events and operational records.
  • Support item creation, editing, attachments, comments, bulk grid editing, CSV import/export, relationships, uniqueness and validation.
  • Support indexed columns, paging, large datasets, calculated values with a documented formula subset, and safe handling of referenced or deleted records.
Explicit requirement

SC-04 · Site columns & metadata

  • Define reusable organization/site columns and local list/library columns, with stable internal identifiers, descriptions, grouping and controlled display names.
  • Cover text, rich text, number, currency, date/time, Boolean, choice, multiple choice, person/group, lookup, hyperlink, image, calculated and managed-metadata fields.
  • Configure required/optional/hidden fields, defaults, validation, unique values, indexing, display formatting and column-level edit behavior where authorized.
  • Support bulk metadata editing and folder/location defaults. Plan schema changes, field conversion and deletion without silently losing existing values.
  • Detect metadata changes from supported application, API, synchronization and repository inputs. Read the current metadata/revision, validate changes and update the associated JSON files and PostgreSQL representation as specified in SC-21.
Explicit requirement

SC-05 · Managed metadata & taxonomy

  • Provide a term store with groups, term sets, hierarchical terms, stable IDs, descriptions, synonyms, multilingual labels and taxonomy owners.
  • Support closed and open term sets, single/multiple term selection, enterprise keywords and scoped reuse across sites and content types.
  • Allow authorized import/export, reparenting, merging, deprecation and replacement. Preserve references when labels change; expose affected content before destructive changes.
  • Use taxonomy consistently in forms, navigation, filtering, search and DriveCraft metadata displays. Record taxonomy changes in an audit trail.
Explicit requirement

SC-06 · Content types

  • Provide a content-type gallery with inheritance, stable identifiers, names, descriptions, categories, document templates and reusable site-column assignments.
  • Allow multiple content types per library/list; configure defaults, field ordering, required/optional/hidden fields and type-specific forms.
  • Support publication across selected sites and controlled propagation of parent changes. Preview downstream effects, preserve local overrides according to policy and support rollback.
  • Associate workflow, retention and document-generation behavior with content types through explicit rules. Include document-set types and reusable business record types.
Proposed baseline detail

SC-07 · Views, forms & everyday usability

  • Provide personal/public saved views with column selection, sorting, filtering, grouping, totals and metadata navigation.
  • Include table, grid, gallery, calendar and board views where compatible with the schema; provide reusable, accessible formatting rules.
  • Provide configurable create/edit/display forms with conditional fields, validation, help text and read-only states; integrate richer forms through FormCraft.
  • Preserve keyboard navigation, responsive layouts, clear empty/error states, bulk-selection feedback and localization.
Explicit requirement

SC-08 · Version history, publishing & locking

  • Version files, metadata, list items and pages with actor, timestamp, change comment and revision ID. Define which changes create a version.
  • Support major/minor document revisions, drafts, publication, approval status, draft visibility and configurable version limits/expiry.
  • Inspect historical metadata and retrieve prior file bytes; restoration creates a new current version while preserving the historical record. Show text/field differences where supported; binary comparison depends on the editor.
  • Provide check-out/check-in, exclusive locks, lock expiry/recovery and optimistic concurrency. Exclusive editing and live co-authoring require explicit coordination.
  • Keep version pruning subordinate to retention and hold rules. Document history behavior for moves, copies, migration and deletion.

SharePoint reference: Microsoft’s versioning, draft visibility and checkout documentation.

Proposed baseline detail

SC-09 · Pages, news & knowledge publishing

  • Provide a visual page editor with sections, layouts, templates and reusable components for text, images, files, links, lists, libraries, news, events, people and approved embeds.
  • Support draft saving, preview, version history, review, scheduling, publish/unpublish, page ownership, translations and expiry/review reminders.
  • Provide home pages, knowledge articles, news posts, announcements, comments, reactions and aggregated content rollups subject to permissions.
  • Maintain asset references and navigation links; sanitize authored content and embedded components. Public publishing requires deliberate configuration.
Proposed baseline detail

SC-10 · Search & discovery

  • Search sites, pages, list records, document metadata and supported file contents, with scoped queries, refiners, sorting, highlights and saved searches.
  • Map site columns/content types into a configurable search schema, with indexed/queryable/refinable fields and taxonomy-aware filtering.
  • Enforce current access rights for results, counts, snippets, suggestions and previews; handle permission revocation and index delays without exposing content.
  • Provide crawl/index status, extraction failures, rebuild controls and relevance configuration. OCR and people-directory search are separately configurable extensions.

Reference baseline: Microsoft’s SharePoint search overview.

Inheritance requirements explicit · Other detail proposed

SC-11 · Identity, permissions & sharing

  • Support users, guests, groups, service identities, owners/members/visitors and configurable permission roles, with delegated administration.
  • Provide inheritance at site, library/list, folder and item levels; show effective access, broken inheritance and the reason access was granted.
  • No library-size restriction on breaking inheritance: always allow users with permission-management rights to break inheritance at library/list, folder or file/item level, regardless of the number of files in the library or existing unique permission scopes. Do not impose a file-count or unique-scope threshold that disables this capability.
  • Keep large permission changes available through resumable background processing where needed, with progress, failure details and an auditable result. Processing must preserve correct access checks and must not temporarily expose content.
  • Inheritance explorer: provide an expandable site → library/list → folder → file/item tree, with clear inherited/unique indicators and an exceptions-only view retaining the ancestor paths to every break. Nested breaks must remain discoverable without inspecting each file manually.
  • For each break, show its full path, direct assignments, effective permissions, nearest permission source, and who changed it and when where recorded. Provide search/filter by location, principal and scope type, counts of breaks, direct navigation to permission settings and an exportable report.
  • Allow authorized restoration of inheritance with a preview of access changes, including the effect on descendants and independent nested breaks. Tree expansion, counts and reports must obey the viewer’s permission-management scope.
  • Support access requests, authenticated sharing links, expiry, revocation, domain restrictions and configurable anonymous sharing. Apply authorization consistently to APIs, downloads, previews and co-authoring.
  • Integrate an agreed identity provider and single sign-on; define session revocation, MFA responsibility, account deactivation and tenant isolation.
Proposed baseline detail

SC-12 · Retention, records & audit

  • Define retention schedules, record declaration, preservation holds, archival and authorized disposition review for files, items and associated versions.
  • Ensure normal deletion, version cleanup and administrator actions cannot silently bypass active preservation rules; define hold release and post-hold disposal.
  • Record content, permission, sharing, administrative and workflow changes in an access-controlled audit trail with export and integrity controls.
  • Provide classification labels, review reminders, retention reports and case-based search/export. Specify jurisdictional rules before claiming regulatory compliance.

Microsoft 365 reference: Purview retention for SharePoint. Equivalent ShareCraft controls are separate implementation work; a Microsoft Purview dependency is not implied.

FlowCraft integration

SC-13 · Workflows, approvals & notifications

  • Expose triggers for creation, content changes, metadata changes, submission, publication, approval, deadlines and permission changes.
  • Support serial/parallel approval, delegation, escalation, rejection, resubmission, reminders and an auditable decision history through FlowCraft.
  • Provide in-app notifications, subscriptions, mentions and configurable email delivery; links must recheck permissions when opened.
  • Specify retry, idempotency, cancellation, timeout, workflow versioning and service-identity permissions. A published approval must reference the exact approved revision.
Proposed baseline detail

SC-14 · Administration & extensibility

  • Provide organization and site administration for settings, storage, identities, sharing, content types, taxonomy, search, workflows, audit and lifecycle.
  • Expose documented, versioned APIs, event subscriptions, webhooks and scoped application credentials with paging, rate controls and change tracking. The DriveCraft integration API is a required platform interface defined in SC-23.
  • Provide reusable templates and approved extension points for page components, content handlers and business applications; isolate extensions from privileged operations.
  • Report storage, activity, stale content, orphaned ownership, sharing exposure and failed background jobs. Provide import/export of configuration.

04 / Beyond SharePoint

These capabilities express ShareCraft’s broader role in ThineCraft. The product direction is established; protocols and detailed acceptance behavior below are proposed.

Browser opening and co-authoring explicit · Protocol detail proposed

SC-15 · Browser editors & live co-authoring

  • Open from ShareCraft: clicking a supported WordCraft, GridCraft, PdfCraft or SolidCraft file in a library must launch the corresponding browser application in the ShareCraft site experience. Users must not need to download the file or install a desktop editor to open and collaborate. Define the supported native/import/export format matrix for each application.
  • Collaborative editing: multiple authorized users must edit the same document concurrently with live updates, participant presence, attribution, save status and durable shared results. A viewer, presence indicator or exclusive file lock alone is insufficient. Preserve the existing co-authoring requirement for DeckCraft and future compatible applications.
  • Provide shared document identity, secure editor launch, session authorization, read-only/edit modes, reconnect behavior and revision checkpoints. Enforce permission changes while sessions are active and return users to the originating ShareCraft library/context.
  • Define an editor integration contract covering capabilities, supported formats, autosave, comments, user attribution, conflicts and durable saves. Fork and extend the designated upstream editor repositories under SC-24 to implement the required capabilities.
  • Application-specific collaboration — proposed: synchronize appropriate operations for text, spreadsheet cells/formulas, PDF editing/forms/annotations and CAD models. Define consistency and conflict handling per editor; generic file storage cannot substitute for document-aware co-authoring.
  • Persistence — proposed: turn collaboration checkpoints into coherent Git-backed content revisions and associated JSON metadata updates through ShareCraft. Coordinate with PostgreSQL and DriveCraft revision/conflict handling. Do not treat Git file merges or a commit on every keystroke as the live editing protocol.
  • Preserve concurrent work during disconnects; surface failed saves and unresolved conflicts. Editors own rendering and document semantics; ShareCraft owns governed content, permissions, session integration and durable history.
DriveCraft · Established direction

SC-16 · Hybrid continuity & organization-owned copies

  • Support hosted, self-hosted and hybrid deployments with organization-controlled server/NAS copies of organizational files and their necessary metadata, identities and permissions.
  • Expose incremental synchronization, checkpoints, checksums, tombstones and conflict information to DriveCraft. Show mirror coverage, last successful sync, missing data and recovery readiness.
  • Define whether offline copies are recovery-only, readable during outages, or writable with later reconciliation. Writable offline operation is an open decision, not an assumed guarantee.
  • Provide authorized export and recovery without depending solely on the hosted service. Synchronization is not a substitute for independent backups and tested restoration.
DriveCraft / Microsoft interoperability

SC-17 · Migration & coexistence

  • Inventory source files, sites, libraries, schemas, content types, taxonomy, users, permissions and versions before transfer. Produce a supported/unsupported mapping report.
  • Support resumable migration, dry runs, staged batches, throttling, delta passes, checksums, reconciliation and exception reports through DriveCraft.
  • Preserve content and metadata to the extent supported by each source/destination API; explicitly report unpreserved author identities, timestamps, versions, links and permissions.
  • Use Microsoft Graph where supported; define additional supported APIs or tools for gaps. Do not promise complete SharePoint migration or continuous two-way sync before a connector capability assessment.
Established direction · Detail proposed

SC-18 · Controlled public portals & submission

  • Provide branded public/guest submission surfaces that write into a controlled intake boundary without granting access to private libraries or administrative functions.
  • Support authenticated or anonymous submissions by policy, file uploads, validation, consent capture, receipts, tracking references and permitted status updates.
  • Separate incoming/quarantined records from approved internal content, with abuse controls, upload inspection, workflow routing and owner review.
  • Provide public read-only previews where explicitly authorized. Prevent visitors from enumerating other submissions or resolving private document links.
FormCraft / PdfCraft · Established direction

SC-19 · Electronic forms & paper-to-digital records

  • Store and publish form templates, template revisions, fillable PDFs, browser views, submissions and source evidence. FormCraft owns field logic; PdfCraft owns PDF viewing/editing and capture.
  • Resolve a QR-coded document-instance identifier to its authorized template, template version and field map; distinguish instance identity from a human or cryptographic signature.
  • Receive progressively extracted fields, assembled page imagery, confidence information and capture history from PdfCraft’s streamed phone-scanning workflow.
  • Support human review of uncertain extraction, correction history, finalization and controlled read-only access to completed records. Define evidence/video retention separately; do not assume indefinite raw-stream storage.
Requested ecosystem extension · Design open

SC-20 · Signatures, integrity & timestamp evidence

  • Store finalized document bytes, cryptographic hashes, detached signatures, signer-key information, verification results and optional public-ledger timestamp proof bundles.
  • Associate evidence with an exact immutable revision; any edited document becomes a different revision requiring its own evidence.
  • Keep signer identity verification separate from proof of document integrity and time of existence. Bitcoin timestamping alone does not identify the signer.
  • Define provider, privacy, pending/confirmed/failed states, verification tooling, key revocation and retention before implementation. OpenTimestamps was proposed in the continuation, but provider and signing roles remain unresolved.
Explicit architecture · Synchronization detail proposed

SC-21 · Git version control, JSON metadata & PostgreSQL

  • Confirmed foundation: ShareCraft is based on Git and PostgreSQL. Git is the version-control system for content revisions and JSON metadata files, while users retain a normal library experience without needing Git commands.
  • Versioned metadata: store metadata in JSON files associated with stable content identifiers. Define a versioned JSON schema for field values, content-type references and managed-metadata term IDs. Metadata-only changes must be traceable in Git, including attribution and the associated content revision.
  • Change-aware updates: when metadata changes through a supported application, API or synchronization path, read the current JSON and revision, validate the requested changes, update the JSON as needed and commit the change to Git. Avoid creating commits for unchanged values.
  • PostgreSQL role — proposed: maintain validated, queryable operational records and indexes in PostgreSQL, linked to Git revision IDs. Use committed JSON as the durable versioned metadata record; PostgreSQL must be reconcilable with that record rather than becoming an unrelated metadata silo.
  • Repository reads — proposed: detect supported Git/JSON changes through change events or revision polling, read and validate the changed files, then update PostgreSQL and notify dependent search/sync services. Support initial import, replay and rebuilding the metadata projection from versioned records.
  • Consistency — proposed: track pending, committed, indexed and failed updates; provide idempotent retries and reconciliation after interruption. Reject or surface malformed JSON, stale writes and concurrent conflicts without silently overwriting another user’s metadata. Do not claim a single atomic transaction across Git and PostgreSQL.
  • Enforce authorization and tenant boundaries for every metadata write and repository import. Repository access must not provide a route around ShareCraft permissions; permission-related records and inheritance changes must remain auditable.
  • Resolve binary storage, Git LFS or object-storage integration, repository layout/growth, encryption, retention, deletion and recovery within this confirmed Git/PostgreSQL foundation.
  • Branching, forks, pull requests and automated merges are candidate extensions requiring explicit scope decisions; they are not implied by Git storage.
Established platform direction

SC-22 · Services assembled on the platform

  • Provide reusable site, library, content-type, form, permission and workflow packages that can be assembled into specialized services.
  • Allow ThineWedding, ThineMemorial and ThineCapture to use independent branding, URLs, users and service-specific configuration on ShareCraft.
  • Keep service-specific schemas and behavior modular. Their detailed commercial/event workflows require separate scopes and do not redefine ShareCraft core.
Explicit API requirement · Contract detail proposed

SC-23 · DriveCraft integration API

Provide a first-class, versioned ShareCraft API for DriveCraft on Windows, macOS and Zorin OS/Linux, and for organization-controlled synchronization/mirror services. The same contract must work with hosted, self-hosted and hybrid ShareCraft deployments. DriveCraft must not depend on UI scraping, direct PostgreSQL access or unrestricted Git credentials.

  • Discovery and identity: expose server capabilities, API/schema versions, stable organization/site/library/folder/item IDs and authorized roots. Support delegated user access and separately authorized unattended mirror/migration identities, scoped credentials, renewal, revocation and tenant isolation; select the exact authentication protocol during design.
  • Files and folders: enumerate with stable paging; read properties; create, rename, move, copy and delete authorized resources; download with range/resume support; provide resumable upload sessions, checksums, quota/status responses and atomic finalization of completed uploads. Stable IDs must survive supported renames and moves.
  • Metadata and schemas: read/update typed metadata and expose site columns, content types, validation rules, term sets and term IDs. Preserve JSON metadata identity and Git revision references. Route writes through SC-21 so API edits update versioned JSON and PostgreSQL rather than bypassing either.
  • Versions and conflicts: list/retrieve supported historical revisions and restore with permission checks. Expose revision tokens for conditional writes; return explicit stale-write/conflict results. Retries must not duplicate successful operations or silently overwrite concurrent edits.
  • Initial and incremental synchronization: provide resumable inventory plus durable scoped change cursors covering content, metadata, schema/taxonomy changes, renames, moves, deletion tombstones and permission/access changes. Define a consistent initial-inventory-to-delta handoff so changes during enumeration are not missed; expose cursor expiry and bounded rescan/recovery behavior.
  • Notifications and reconciliation: offer change notifications or polling without making notifications the sole source of truth. Support replay, duplicate handling, retry/backoff, explicit rate-limit responses and reconciliation against the authoritative change feed. Retain checkpoints per client/library and document deletion-feed retention.
  • Permissions and inheritance: expose the caller’s effective capabilities and permission source. Authorized permission managers can inspect the inheritance structure and break/restore inheritance through the API with the same no-library-size restriction as the UI. Permission loss must revoke subsequent server access and be signaled to the client; define local cache cleanup and offline-access policy without promising erasure of copies already taken outside managed clients.
  • Offline and migration services: expose mirror coverage/checkpoint reporting, transfer job progress, failed items and integrity verification. Support migration workflows from SC-17 through this interface. Offline writes and continuous two-way reconciliation remain subject to the unresolved hybrid-authority decision in SC-16.
  • Errors and operational behavior: provide machine-readable error codes, request/correlation IDs, documented retryability, idempotency support and progress/cancellation for long-running jobs. Apply permission and retention checks to every transfer, history request, metadata write and deletion.
  • Contract and compatibility: deliver an OpenAPI description, data schemas, authentication setup, examples, synchronization/recovery guidance and a compatibility/deprecation policy. Verify the API with a DriveCraft client or representative contract harness, including inventories exceeding 100,000 files. Microsoft Graph interoperability remains a separate DriveCraft connector concern; this API does not claim Graph compatibility.

Site branding explicit · Control detail proposed

SC-25 · Organization & site branding

  • Independent identity: retain familiar content-management navigation patterns while giving ShareCraft its own typography, spacing, components and product identity. A green/teal SharePoint-style application bar is not the default design requirement.
  • Brand layers — proposed: distinguish ShareCraft product chrome, organization branding and individual site branding. Provide neutral application chrome so a department, client, project or public portal can express its own identity without recoloring every application control.
  • Site controls — proposed: configure site name, logo/wordmark, thumbnail/favicon where applicable, accent palette, approved font package, header layout, optional banner/background, navigation placement and footer. Keep site identity visible in libraries, lists, access views and browser-editor context.
  • Reusable themes — proposed: support organization-approved brand kits, inheritance from organization/hub defaults, permitted site overrides and reusable templates. Allow different sites to use different brands without changing content, permissions or application behavior.
  • Safe administration — proposed: provide an authorized branding editor with responsive preview, draft/apply/cancel, version history and reset/rollback. Record branding configuration as Git-versioned JSON with the PostgreSQL representation governed by SC-21.
  • Accessibility — proposed: check foreground/background contrast, keyboard focus, readable typography, logo alternatives, mobile layout and light/dark appearance. Brand choices must not hide status, controls or permission warnings; prevent unsafe script/style injection through branding inputs.
  • SharePoint baseline controls — proposed detail. The items that follow set out the branding functions SharePoint provides, as the functional floor for the controls above. They describe capability, not appearance: ShareCraft’s own identity governs how they look.
  • Change the look: give site owners one place to set the site's theme, fonts, header, navigation style and footer, with a preview before applying and the ability to return to the previous look.
  • Themes: supply a set of default themes. Provide a theme designer in which brand colors are entered as primary and secondary colors and combined into named background/accent pairs (SharePoint allows up to 16 per theme). An applied theme must carry consistently through pages, lists, libraries, forms, search and system screens, and supply the section background colors used by the page editor (SC-09).
  • Fonts: provide a brand font library accepting .ttf, .otf, .woff and .woff2 files, and font packages that pair a display font with a content font and map them to defined text roles (title, heading, body, interactive). Preview a package before applying it.
  • Header: offer minimal, compact, standard and extended header layouts; a header background drawn from the theme; a background image and logo alignment in the extended layout; a site logo and a separate logo thumbnail used in cards, search results and site lists; and the option to hide the site title.
  • Navigation style: choose horizontal or vertical placement where the site type allows, and cascading or mega-menu presentation. Navigation links themselves are managed under SC-01.
  • Footer: enable or disable a site footer with simple and extended layouts, a logo, a display name, grouped links and a background choice.
  • Organization brand centre: provide a central place where designated brand managers maintain the organization's themes, font packages and brand images such as logos, icons and backgrounds. Organization themes and font packages are offered to every site; brand images are offered in the page editor's image picker. Administrators can hide the default themes and limit site owners to approved brand options.
  • Site-level branding: site owners can create themes and font packages that exist only in their site, rename or delete them, and copy branding from another site they are permitted to read.
  • Hub inheritance: sites associated with a hub-style grouping (SC-01) take the hub's theme, and the hub's name and logo appear in shared navigation. Site-level branding does not override hub branding. Define what a site looks like when it joins or leaves a hub; Microsoft's own documentation is inconsistent on this point, so ShareCraft must state its own rule.
  • Provisioning and API: include theme, fonts, logo, header and footer settings in site templates and provisioning packages, and expose them through the API (SC-14) so branding can be applied to many sites at once.
  • Reach — proposed: apply a site's branding to its public portals (SC-18), to independently branded services with their own URLs (SC-22), to notification emails (SC-13) and to the frame around browser editors launched from the site (SC-15). A browser tab icon per site and a branded sign-in page are candidate extensions; neither is part of the SharePoint baseline.
  • Boundary: classic SharePoint master pages, composed looks, and arbitrary custom style sheets or scripts are not included. Deeper visual customization goes through the approved extension points in SC-14. Branding and audience targeting never grant or remove access.
  • Self-contained assets — proposed: serve fonts and brand images from the deployment itself so self-hosted and offline-capable installations do not depend on a public content network. The organization is responsible for the licence of any font it uploads.

07 / Delivery framework & acceptance

Delivery order following D15: co-authoring first, the platform formed alongside it. The order is the owner's direction; the stage contents are proposed and detailed in sequencing.html. No stage is yet assigned a contractual date, cost or release commitment.

  1. Definition and editor inspection: decisions needed to start, including how concurrent edits are merged; a read-only inspection of the four upstream editors; the editor integration contract; tenancy/security model and measurable service targets.
  2. Collaboration spine: in Rust, document identity, shared editing sessions, presence, reconnect, checkpoints saved as Git revisions with JSON metadata and PostgreSQL records, and permission checks that can end a live session. Proven with two browsers editing one plain-text document. The four editor forks are created and each opens from ShareCraft and saves back, one person at a time.
  3. Libraries and access, with GridCraft: sites, libraries, file operations, permissions, the inheritance explorer and site branding; the first real editor co-authoring from a library.
  4. Metadata and history, with WordCraft: lists, reusable columns, taxonomy, content types, views, versions, publishing and locking.
  5. API and change feed, with PdfCraft: administration, extensibility and the DriveCraft integration API.
  6. Knowledge and governance, with SolidCraft: pages, search, retention, audit, workflow integration, hybrid continuity and migration.
  7. Intake, forms, evidence and services: public portals, form capture, evidence verification and service templates; can run alongside the previous stage.
  8. Production readiness: realistic migration rehearsal, accessibility/security/performance checks, disaster recovery exercise, operational documentation, administrator training and release handover.

An automated two-session co-authoring test runs on every build from the end of stage 1, so later work that breaks co-authoring is caught when it is made.

Required handover outputs

Application source and build/deployment instructions, including the designated editor forks, upstream mapping, reproducible browser builds and collaboration-service deployment; schema and API documentation, including the DriveCraft OpenAPI contract, authentication guidance, examples and interoperability verification; configured sample sites/libraries/lists/content types/taxonomies; migration and reconciliation reports; verification evidence; security and recovery runbooks; user/admin guidance; known limitations; dependency/license inventory; and an HTML requirements register mapping each scope item to its release and acceptance evidence.

08 / Decisions to resolve

These remain open rather than being silently chosen by this document.

  1. Release breadth: which baseline and extension modules belong in the first usable release, and which are later deliverables?
  2. Tenancy & identity: tenancy is decided (D18: one organization per installation). Stage 1 signs people in with ShareCraft’s own accounts and passwords, as proposed in plans/2026-11-10-accounts-and-permissions.html; that is a starting point, not a decision against an outside provider. Still open are the identity provider; federation; external users; delegated administration.
  3. Git / JSON / PostgreSQL implementation: repository and JSON schema layout, synchronization/commit boundaries, PostgreSQL schema and projection strategy, binary storage, conflict handling, and recoverable deletion versus permanent erasure. Git version control, JSON metadata and PostgreSQL are settled requirements, not open technology choices; the proposed consistency details in SC-21 still require design review.
  4. Hybrid authority: recovery mirror, offline read service or fully writable offline deployment; conflict ownership and reconciliation policy.
  5. Browser editors and forks: fork names and base revisions (D21) and the hosting and embedding model (D20) are decided. The session, transport and message approach for the ordered change log decided in D16 is settled in D22 (co-authoring-approach.html v1.0). Still open: current browser capability and gaps; supported formats, document/CAD operation semantics and editor order, and the risks and open questions in section 12 of that paper. Browser opening, live co-authoring and extending the designated forks are settled requirements; source selection and implementation detail remain open.
  6. DriveCraft API design: agree authentication protocol, endpoint/schema definitions, cursor and tombstone retention, notification transport, offline cache policy, compatibility window and measurable synchronization targets. A documented API is required; these implementation details remain open.
  7. Compatibility: modern SharePoint baseline, selected classic capabilities, import/export guarantees and supported Microsoft API coverage. Includes whether any classic branding capability excluded by SC-25 is wanted, and the hub branding inheritance rule.
  8. Trust & evidence: signing parties, verified identity, timestamp provider, key management, public verification and evidence retention.
  9. Scale & operations: infrastructure, volume, concurrency, availability, indexing, backups, recovery, support and accessibility targets.
  10. Commercial handover: budget, milestones, acceptance owner, support period and change-control procedure. The open-source license is decided (D17).

Additional features: record each requested addition with an ID, user outcome, owner application, data/permission impact, dependencies, acceptance scenario and release assignment. AI-assisted tagging/search, mandatory data-loss prevention, native mobile clients, Microsoft Office integration and legacy SharePoint runtime compatibility are not silently included by the phrase “everything”; each needs an explicit scope entry.

For AI contributors and implementers

  • This repository file is the current scope record. Publishing it does not turn every proposed implementation detail into an approved design. Git version control, JSON metadata, PostgreSQL, inheritance breaks independent of library size and an inheritance explorer are explicit user requirements; do not downgrade them to optional ideas or reintroduce count-based restrictions. Rust (D14) and building co-authoring first (D15) are likewise explicit: do not introduce a save or edit path that bypasses the collaboration spine, and do not defer co-authoring behind the baseline modules.
  • Preserve the distinction between explicit user direction, proposed detail and unresolved design choices. Do not label planned features as implemented.
  • Keep editors, sync clients, workflows and specialized services within their stated application boundaries. Record agreed changes in HTML.
  • Use stable requirement IDs in implementation plans, issues and acceptance evidence. Do not claim SharePoint parity, regulatory compliance or production readiness without defined criteria and verification.
