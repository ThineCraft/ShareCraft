01 / Summary

Stage 1 proved co-authoring on plain text. There, the server itself merges the changes. The real editors are far larger, and the same method would put each editor's code inside the server. This paper tests three ways of doing it against the code and recommends one.

  • Recommendation. The server only puts changes in order. It does not look inside them. Every person's editor applies the same ordered list and so reaches the same document. This is option C below. It is the plainest reading of decision D16, and it keeps spine rule S6.
  • What a change says. A change names the things it touches by a lasting identity, not by a position. "Row 5" becomes "the row with this identity", so it still means the same row after someone inserts a row above it.
  • The evidence supports this, with five amendments. They are listed in the note below. None of them points to a different option. Two of them add a part the provisional recommendation did not have: a way to cancel a bad change for everyone, and a small server-side helper process for the saved file.
  • The saved file. While people are connected, one person's editor uploads the file at a stated point in the list of changes. The server keeps the list on disk until the file is stored. A helper process that runs the editor's engine without a screen finishes the job when the last person leaves too early.
  • GridCraft. Sheets, rows and columns get identities that last for the session. A cell is its row and its column. GridCraft's existing code already keeps every stored formula right when rows and columns move. What is new is the same care for the change that is still on its way.

Status. Decided by the owner and not reopened here: live co-authoring in the four forked editors (D12), co-authoring built first (D15), one shared ordered list of changes that every editor applies in order, with a live connection required (D16), editors served by ShareCraft from the ThineCraft forks (D20, D21), and the editor order GridCraft, WordCraft, PdfCraft, SolidCraft. Everything else in this paper is proposed. Nothing here is decided until the owner says so. Section 14 lists each decision asked. No code was changed and nothing was built or run for this paper.

Where the evidence changed the provisional recommendation.

  1. GridCraft does not need text merging inside a cell. A cell's text is a private draft until Enter, then it is one whole change. Text merging is first needed for WordCraft.
  2. GridCraft's existing reference adjustment covers the stored document only. It does not cover a change in flight. Lasting identities do that job. Sorting, cut-and-paste and "insert cells" move contents without moving rows, so they need one more rule.
  3. Option C alone has no defence against a change that crashes the editor. In a browser the editor cannot recover from such a crash. The proposal adds a rule for cancelling the change for everyone.
  4. Some changes cannot be re-run safely on every machine, for example ones that fetch data or run a script in a PDF. For these the editor sends the result of the change, not the instruction.
  5. Rolling back and re-running is cheap for a workbook's cells but its cost for the calculation data is not measured. For SolidCraft it is the wrong default. The library needs a second mode that waits for the server before showing a change.

02 / What exists today

Words used in this paper. The log is the ordered list of changes the server keeps for one open document. A log position is a change's number in that list. A room is the server's record of one open document and the people in it. A checkpoint is the moment the live document is stored as one Git revision. A snapshot is a complete copy of the document at one moment. A command is one named action in an editor with its parameters, such as "insert rows". File references are written path:line; the repository is named where it is not ShareCraft.

03 / Who reconciles concurrent changes

Two people change the same document within the same moment. Each made their change without seeing the other's. Something must make both documents end up the same. There are three candidates.

Option A

The server merges

The server holds the document. It adjusts each incoming change against the ones it missed, as it does for text today. Each editor's merge code is compiled into the server.

Option B

The server orders and refuses; the sender tries again

The server holds no document. It accepts a change only if the sender had seen every earlier change. Otherwise it refuses, and the sender's editor reworks the change on the newer document and sends it again. The ProseMirror editor's collaboration module works this way.

Option C · Recommended

The server only orders; every editor applies the same list

The server holds no document and refuses nothing for being late. Each change names its targets by lasting identity. Every editor applies the changes in the server's order and gets the same result. To hide the delay, an editor shows a person's own changes at once. When someone else's change arrives first, the editor goes back to the last agreed state, applies the arrival, and re-runs the person's waiting changes.

What the code says about each test

  • Commands are data in three of the four editors. GridCraft: crates/engine/src/lib.rs:670. WordCraft: crates/engine/src/session/run.rs:55, a name and JSON parameters. SolidCraft: crates/engine/src/lib.rs:1663. PdfCraft's edit type cannot be written out as data yet (crates/engine/src/edit.rs:20-21 has no serialisation). So "send the command" is natural for three editors. Option A would throw that away and ask for a second, smaller vocabulary.
  • Rolling back is cheap for the workbook. A copy shares everything unchanged (GridCraft crates/model/src/store.rs:1-4). The calculation data is a separate structure (crates/engine/src/lib.rs:188-190). Undo rebuilds it from scratch after a swap (crates/engine/src/cmd/edit.rs:212). What that costs on a large workbook was not measured. It is the first thing the Stage 2 plan should measure.
  • The same build for everyone. ShareCraft serves each editor itself and records its version and fork commit in a manifest (editors.html, section 02). Everyone in a room can therefore be held to the same WebAssembly build (the compiled form of the editor that runs in a browser). The room must refuse a person whose browser still holds an older build, and tell them to reload.
  • Arithmetic. The same WebAssembly build gives the same arithmetic on every machine, except for details of invalid numbers that do not reach the document. A native build can differ in the last digit for functions such as sine and logarithm, because it uses the machine's own maths library. This is why option A, where a native server must match browser clients exactly, carries a risk that option C between browsers does not. It was reasoned, not tested.
  • Clock and random numbers. NOW() reads the local clock (GridCraft crates/calc/src/recalc.rs:178-183). The engine already accepts a fixed time (:47). RAND() draws from a sequence stored beside the workbook (:45, :100), which stays the same on two machines only if both recalculate exactly the same number of times. Local actions such as undo rebuild the calculation data, so they would drift. Proposed: the server stamps each change with its time, and the editor takes both the time and the random starting point from the change it is applying.
  • Counters. GridCraft gives a new chart, picture or table "one more than the largest number in use" (crates/model/src/workbook.rs:511-513). SolidCraft gives new items the next number from a counter in the document (SolidCraft crates/doc/src/document.rs:3217, :3938-3939). Applied in the server's order these give the same numbers on every machine. They go wrong only while a person's change is shown early, because a later change of theirs may name a number that turns out different. So the person's editor must choose the identity of anything it creates and send it with the change.
  • Other per-person inputs. A command can depend on the clipboard, which is a private copy of the source workbook (GridCraft crates/engine/src/lib.rs:130-134), on the person's name (:386), and on ranges that person has unlocked with a password (:204). Each must be written into the sent command or left out of shared commands.
  • Order of unordered collections. The calculation data uses hash tables with a fixed hash function (GridCraft crates/calc/src/recalc/graph.rs:9, :31), so their order does not vary between machines. No use of parallel calculation was found in the crates. Other hash tables in the engine were not audited.
  • A crashing change. GridCraft catches a panic inside a command and restores the workbook (crates/engine/src/lib.rs:725). Rust's standard browser target stops the whole program on a panic and cannot catch it. The fork sets nothing to change that (its Cargo.toml:94-96 and .cargo/config.toml). So in a browser, a change that panics would stop every participant's editor at the same log position. This was read, not run.
  • Commands that reach outside the document. Editors run with the signed-in person's rights on ShareCraft (D20). A command can ask to open a web address (GridCraft crates/engine/src/lib.rs:450), read files or run stored scripts. A change arriving from another person must never do these on my machine. GridCraft already separates trusted and untrusted content (crates/engine/src/lib.rs:156-175, :212-217). Shared commands must be an explicit list, and everything not on it stays local or is refused.

Conclusion on question 1

Option C fits the editors as they are: commands are data, one entry point, cheap copies. Option A gives the best protection and the easiest checkpoint, but it breaks S6, ties the server to four large codebases and asks for the most new code in each fork. Option B has no advantage once changes carry lasting identities, and it starves slow connections.

The evidence does call for a hybrid in two places. Both keep the server out of the edits. First, a helper process per editor, outside the server, runs the engine without a screen for the jobs the server cannot do (section 05). Second, inside WordCraft's paragraphs, each editor adjusts text positions the classic way (operational transformation: shifting a typing position to allow for text another person typed first). That is the part the plain-text spine already has.

04 / How the proposal works

  1. A change is an opaque entry. The editor sends bytes the server does not read. The server adds the log position, the sender, and the time, and sends the entry to everyone, including the sender.
  2. An entry is either an instruction or a result. Normally it is a command with its parameters. Where re-running the command on other machines is unsafe or cannot give the same answer, the sender's editor runs it and sends what changed. Examples: importing data from outside, a script in a PDF form. Each fork decides per command.
  3. Targets are named by identity. The sender's editor turns every position in the command into identities before sending: the target cells, and every reference inside a typed formula. The receiving editor turns them back into positions in its current document. A target that no longer exists has a stated outcome (section 07).
  4. Every editor keeps two states. The agreed state has exactly the entries the server has sent, in order. The shown state is the agreed state plus the person's own changes still waiting. When another person's entry arrives, it is applied to the agreed state, and the shown state is rebuilt from it. When nothing is waiting, the two are the same and nothing is re-run.
  5. Two modes. Show at once is the above, for GridCraft, WordCraft and PdfCraft. Wait for the server applies a person's change only when it comes back from the server. It costs one round trip of delay and needs no re-running. It is for editors where applying a change is slow (SolidCraft), and for single commands a fork marks as heavy.
  6. A rule failure is not an error for the room. If an entry's target is gone, the entry does nothing, on every machine alike. The sender's editor tells the sender and keeps what they typed so they can put it somewhere else.
  7. Cancelling a bad entry. An editor notes which entry it is about to apply. If the editor stops and comes back, it reports that entry. The server marks the entry as cancelled when the helper process confirms it fails, or when enough different participants report it. Everyone then skips it. The server acts on reports and positions only. Limits on entry size and rate stop the simpler abuses.
  8. Checking that everyone agrees. Every so many entries, each editor sends a short fingerprint of its agreed state (a hash: a small number computed from the content, which differs if the content differs). If two fingerprints for the same position differ, the room knows at once and the odd one reloads. This turns a silent divergence into a visible, counted fault. The fingerprint covers what people entered, not computed values.
  9. Large content travels beside the log. A paste of a big range does not fit in one message. The editor uploads the content over HTTP and the entry names it by its fingerprint.

05 / Who writes the checkpoint

Under option C the server cannot produce the file. Three ways to get one:

WayForAgainst
1 · A participant's editor uploads the file at a stated log positionNo server knowledge of the format. No server computing. The file is exactly what people saw. The upload path exists already (BUILDING.html section 15).Nobody connected means nobody to ask. The server must trust or check what it is given. The editors save only while their tab is shown (BUILDING.html section 14).
2 · The server runs the editor's engine without a screenAlways available. No trust question.Inside the server it is option A's coupling again. 3 · Both: participants while anyone is connected; a helper process when nobody isEach covers the other's gap. The helper is a separate program, so the server still does not understand edits and an engine fault cannot stop the server.Two paths to build and test. The helper must be rebuilt with each fork update.

Proposed: way 3. In detail:

  1. The log is kept on disk. Entries after the last stored revision are written to PostgreSQL before they are sent out. A server restart or a failed room then loses nothing. This is live session state outside Git, as rule S3 says.
  2. The server asks one participant. When a checkpoint is due, it picks a connected person who may edit and whose tab is showing, and sends a one-time ticket naming a log position. That editor writes the file from its agreed state at that position and uploads it with the ticket and the base revision. This replaces the editing seat and its token. Everyone who may edit now edits.
  3. The existing save path does the rest. The role is checked before the upload is read. A wrong base is refused with 409, a file over the limit with 413, a busy store with 503. Unchanged bytes write nothing. The revision is one Git commit with its JSON metadata.
  4. Credit. The room already tracks who contributed since the last checkpoint (crates/server/src/room.rs:441). The revision credits all of them, not the uploader. This meets S3.
  5. Session data beside the file. The identity tables of section 06 are not in the .xlsx. The uploader sends them as a second, small item. The server keeps it with the room and gives it to people who join later. It is discarded when the room ends.
  6. Checking the upload. A person who may edit can already change anything, so a false file gives them no new power over content. It could, though, credit others with words they did not write, or drop their work unseen. Check: the uploader states the fingerprint of its state at that position, and the server accepts the file as verified only if it matches the fingerprint other participants reported for the same position (step 8 of section 04). With one person left there is nobody to compare with. The revision is then stored and marked unverified in its metadata, or the helper process checks it.
  7. When nobody is connected. If the last person leaves and entries remain after the last revision, the helper process loads the last revision, applies the remaining entries and writes the checkpoint. Since nobody is connected, there is no one for its result to disagree with. If the helper is absent or fails, the document is marked as having unsaved live changes. The next person to open it applies the entries and is asked for a checkpoint at once. Downloads and the change feed must say that the stored file is behind.
  8. Rule S4. Every checkpoint, by a participant or by the helper, states its base revision and is refused if stale. A stale checkpoint means the stored file was changed outside the room. The room then stops, as it does today.

How often to checkpoint is open. Text is stored two seconds after the last change. A workbook is a whole file of up to 64 MiB by default (crates/server/src/config.rs:44), and each revision adds to the Git repository. A longer interval is likely, and it is safe once the log is on disk.

What gets an identity

ThingProposed identityNote
SheetA session identity given when the sheet is first seen or created.Formulas keep naming sheets by name in the file. The existing per-program counter (crates/model/src/sheet.rs:62-68) is replaced for shared use.

Identities are made by the person's editor from a participant number the room hands out on joining, plus a counter. Two people can never make the same one. Identities of deleted rows are remembered for the life of the room, with where they were, so a late change naming one gets a defined answer. Identities are not written into the .xlsx. A new room starts fresh from the file.

What the existing reference adjustment already does

Under option C, structural changes run one after another on every machine, exactly as they do for one person today. So everything GridCraft already does when a row is inserted or deleted is reused unchanged:

  • Positions through an insert or delete, and ranges that shrink or become #REF!: crates/formula/src/adjust.rs:147-162, :165-196, :198-224.
  • Cut-and-paste, insert cells, delete cells, move to another sheet: crates/formula/src/adjust.rs:225-272.
  • Sheet rename and sheet delete in every formula: crates/formula/src/adjust.rs:277-302, :306-328.
  • Every stored formula, sparkline source and pivot source rewritten: crates/engine/src/cmd/sheet.rs:220-250; crates/engine/src/cmd/edit/paste_special.rs:555.
  • Everything else with a position: row and column settings, merged cells, conditional formats, validation, tables, the filter, comments, links, floating objects, print area, pivots: crates/engine/src/cmd/sheet.rs:122-216.

What it does not do

It adjusts what is stored in the workbook. It does not adjust a command that was made against an older workbook and has not been applied yet. Commands name cells as text such as B5 (crates/engine/src/cmd.rs:296-303). If someone inserts a row above first, B5 is the wrong cell, and a formula typed as =A5 points at the wrong row. Identities fix both: the sender converts B5 and A5 to identities, and the receiver converts them back.

The closest existing code is the macro runner. It keeps a range outside the workbook and moves it with each structural change a step makes, or reports that the step deleted it (crates/engine/src/macros/run.rs:763-784, :888-910). That proves the hook works. It was not chosen as the method here because it works on positions. When a person has their own structural change waiting and another person's lands in between, positions need the pairwise adjusting that option C avoids. Identities do not.

The identity tables are kept up to date from the list of structural changes each command already records (crates/engine/src/cmd.rs:377, :429-431). No second bookkeeping of "what moved" is needed.

07 / GridCraft: conflict rules

Three principles, then the cases. One: a change is never silently written somewhere other than where its author meant. Two: where two changes compete for the same cell, the one later in the log stands. Three: a change that cannot be applied does nothing, and its author is told and keeps what they typed.

08 / GridCraft: per-person undo

Today Undo puts back a whole earlier workbook (crates/engine/src/cmd/edit.rs:194-215). In a shared session that would remove everyone else's work since.

Proposed rule. Undo reverses your own last action, and only where the document is still as your action left it. Anything someone has changed since is left alone, and you are told how much was left.

  • How. When a person's command is applied, their editor works out its reverse from the workbook before and after: for each changed cell, the earlier content; for a structural change, the opposite structural change plus the cells it altered. The engine already has both workbooks and the list of changed cells (crates/engine/src/cmd.rs:367, :393-457), and unchanged parts are shared, so finding the difference is cheap.
  • Undo is a new entry. Pressing Undo sends the reverse as an ordinary change. It is ordered and applied like any other, so everyone agrees on the result.
  • The stack is personal. Each person's editor keeps its own list. It is not in the file. It lasts while the room lasts.
  • Redo is the same in the other direction.
  • First scope, proposed. Cell content and format, row and column insert and delete, and sheet add and rename get full undo in Stage 2. Sort, large paste and sheet delete are undone only if nothing they touched has changed since. Otherwise Undo is refused with a reason.

09 / How it carries to the other editors

Stage 3

WordCraft · two people typing in one paragraph

  • Commands are already a name with JSON parameters (WordCraft crates/engine/src/session/run.rs:55). So the order-only log fits.
  • A paragraph is a text string with formatting runs (crates/doc/src/para.rs:28-30). A position is a path of indexes and an offset (crates/doc/src/position.rs:60-64). Blocks need identities. The same ordered-identity table as GridCraft's rows serves.
  • Inside a paragraph, identity is not enough: offsets shift with each keystroke. A typing change carries the paragraph's identity and the log position it was made at. Each editor shifts its offset past the typing that landed first. The plain-text spine has this code (crates/collab-text/src/transform.rs). It moves from the server into the shared library.
  • Hard case to design in Stage 3: one person splits or joins paragraphs while another types in them. Formatting runs must shift with the text.
Stage 4

PdfCraft · the object overlay

  • The edit type is not data yet (PdfCraft crates/engine/src/edit.rs:20-21). That is the first piece of work.
  • PDF object numbers are lasting identities already (editor-readiness.html, section 04). New objects need numbers that two people cannot both pick.
  • Edits can run form scripts. Re-running those on every machine is the unsafe case of section 04. PdfCraft is the main user of "send the result": the set of changed objects, which the editor already knows how to merge. Not re-read for this paper beyond the edit type.
Stage 5

SolidCraft · counters and rebuild time

  • Commands are a name with JSON parameters (SolidCraft crates/engine/src/lib.rs:1663).
  • New items take the next number from a counter in the document (crates/doc/src/document.rs:3217, :3938-3939). In the "wait for the server" mode every editor applies commands in the same order, so the counter gives the same numbers everywhere and need not change. Only showing changes early would need the collision-free scheme.
  • Every participant's editor rebuilds the model for every change, on one thread in the browser. Re-running waiting changes would multiply that. "Wait for the server" avoids it. Separating "change the timeline" from "rebuild" so several arrivals cause one rebuild is fork work. Rebuild times were not measured.

11 / What changes in the spine

  • A room for opaque entries. It orders, numbers, stamps and sends. It keeps the checks that need no knowledge of content: role (crates/server/src/room.rs:429), duplicate resends (crates/collab-core/src/server_log.rs:61-67), size and rate.
  • The log on disk until its entries are covered by a stored revision.
  • Joining gives the stored file over HTTP, the session data, and the entries since. Today it gives the text itself (crates/protocol/src/lib.rs:105-123).
  • The editor build is pinned per room. A person with another build is told to reload. Installing a new editor build must wait for open rooms and unsaved entries, or end them.
  • Presence becomes opaque. Today it is a text cursor position (crates/protocol/src/lib.rs:43).
  • Checkpoint by ticket replaces the editing seat for file documents.
  • Cancelled entries and fingerprint reports, as positions and counts only.
  • A place to hold large content named by an entry.
  • The plain-text editor. It works today with the server merging. Proposed: leave it until GridCraft co-authoring works, then move it onto the opaque room so there is one kind of room. Until then the server still understands text, which S6 does not strictly allow.

13 / Out of scope

  • Offline editing. D16 requires a live connection to edit together. A person who loses the connection keeps their waiting changes and resends them on return, within the same room. Editing for hours offline and merging later is not designed here and stays with the SC-16 decision.
  • Merging two saved revisions of a file, branches and pull requests (SC-21 lists these as candidate extensions).
  • Co-authoring of list items, pages and metadata (sequencing section 03, a Stage 3 decision).
  • DeckCraft.
  • Comment threads, tracked changes and "show changes" as review features. Co-authoring does not depend on them.
  • Scale and performance targets (scope decision 9).
