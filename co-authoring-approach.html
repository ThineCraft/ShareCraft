01 / Summary

Stage 1 proved co-authoring on plain text. There, the server itself merges the changes. The real editors are far larger, and the same method would put each editor's code inside the server. This paper tests three ways of doing it against the code and recommends one.

  • The session model is decided. Owner decision, 11 November 2026 Each open document has one "chat session". The editors in it, in the browser and on the desktop, send their changes to the server. The server passes each change, in order, to everyone else in the session. It does not look inside them, and no editor process runs on the server for a document. This is the ordered log, option C below. Every person's editor applies the same ordered list and so reaches the same document. It is the plainest reading of decision D16, and it keeps spine rule S6.
  • Heartbeat and returning clients are decided. Owner decision, 11 November 2026 Every client sends an empty heartbeat message every minute. A client whose heartbeat has expired loses its place in the session, and any editing seat it held is freed, so a file is never locked for good. A client that sends changes after its heartbeat expired creates a new major version, as SharePoint does. How this paper reads that rule is in section 04; the owner is asked to confirm it.
  • What a change says. A change names the things it touches by a lasting identity, not by a position. "Row 5" becomes "the row with this identity", so it still means the same row after someone inserts a row above it.
  • The evidence supports this, with five amendments. They are listed in the note below. None of them points to a different option. One adds a part the provisional recommendation did not have: a way to cancel a bad change for everyone.
  • Revised after an independent review, then after the owner's decisions. Version 0.2 kept the recommendation and corrected how it is carried out. Version 0.3 records the owner's decisions, drops the server-side helper process that version 0.2 proposed, and adds desktop editors to the sessions. Section 15 lists what changed.
  • The saved file. While people are connected, one person's editor uploads the file at a stated point in the list of changes, and a second editor confirms it. The server keeps the list on disk until the file is stored. If everyone leaves before that, the changes stay on disk, and the next person to open the document has their editor apply them and save.
  • GridCraft. Sheets, rows and columns get identities that last for the session. A cell is its row and its column. GridCraft's existing code already keeps every stored formula right when rows and columns move. What is new is the same care for the change that is still on its way.

Status. Decided by the owner and not reopened here: live co-authoring in the four forked editors (D12), co-authoring built first (D15), one shared ordered list of changes that every editor applies in order, with a live connection required (D16), editors served by ShareCraft from the ThineCraft forks (D20, D21), and the editor order GridCraft, WordCraft, PdfCraft, SolidCraft. On 11 November 2026 the owner also decided: one chat session per open document, through which browser and desktop editors exchange their changes (C1, C5); no editor process on the server (C4); a heartbeat every minute, after which an absent client loses its place and its seat (C21); and a new major version when a client returns after its heartbeat expired (C22). These are marked Owner decision, 11 November 2026 where they appear. Everything else in this paper is proposed. That includes how this paper works the owner's decisions out in detail, such as the expiry time and the reading of "major version". Nothing else here is decided until the owner says so. Section 14 lists each decision. Section 02 is the evidence from the code and can be skipped on a first reading. No code was changed and nothing was built or run for this paper.

Where the evidence changed the provisional recommendation.

  1. GridCraft does not need text merging inside a cell. A cell's text is a private draft until Enter, then it is one whole change. Text merging is first needed for WordCraft.
  2. GridCraft's existing reference adjustment covers the stored document only. It does not cover a change in flight. Lasting identities do that job. Sorting, cut-and-paste and "insert cells" move contents without moving rows, so they need one more rule.
  3. Option C alone has no defence against a change that crashes the editor. In a browser the editor cannot recover from such a crash. The proposal adds a rule for cancelling the change for everyone.
  4. Some changes cannot be re-run safely on every machine, for example ones that fetch data or run a script in a PDF. For these the editor sends the result of the change, not the instruction.
  5. Rolling back and re-running is cheap for a workbook's cells but its cost for the calculation data is not measured. For SolidCraft it is the wrong default. The library needs a second mode that waits for the server before showing a change.

02 / What exists today

Words used in this paper. The log is the ordered list of changes the server keeps for one open document. A log position is a change's number in that list. A room is the server's record of one open document and the people in it. The owner calls it the document's chat session; this paper uses "session" and "room" for the same thing. A client is one connected editor, in a browser or on the desktop. A heartbeat is an empty message a client sends to say it is still there. A checkpoint is the moment the live document is stored as one Git revision. A major version is a revision marked as a milestone in the version history, as in SharePoint; every other checkpoint is a minor version. A snapshot is a complete copy of the document at one moment. A command is one named action in an editor with its parameters, such as "insert rows". File references are written path:line; the repository is named where it is not ShareCraft.

03 / Who reconciles concurrent changes

Two people change the same document within the same moment. Each made their change without seeing the other's. Something must make both documents end up the same. There are three candidates.

Option A

The server merges

The server holds the document. It adjusts each incoming change against the ones it missed, as it does for text today. Each editor's merge code is compiled into the server.

Option B

The server orders and refuses; the sender tries again

The server holds no document. It accepts a change only if the sender had seen every earlier change. Otherwise it refuses, and the sender's editor reworks the change on the newer document and sends it again. The ProseMirror editor's collaboration module works this way.

Option C · Owner decision, 11 November 2026

The server only orders; every editor applies the same list

This is the owner's "chat session" for the open document: editors in the browser and on the desktop send their changes to the server, and the server passes them on to everyone else in the session. The server holds no document and refuses nothing for being late. Each change names its targets by lasting identity. Every editor applies the changes in the server's order and gets the same result. To hide the delay, an editor shows a person's own changes at once. When someone else's change arrives first, the editor goes back to the last agreed state, applies the arrival, and re-runs the person's waiting changes.

What the code says about each test

  • Commands are data in three of the four editors. GridCraft: crates/engine/src/lib.rs:670. WordCraft: crates/engine/src/session/run.rs:55, a name and JSON parameters. SolidCraft: crates/engine/src/lib.rs:1663. PdfCraft's edit type cannot be written out as data yet (crates/engine/src/edit.rs:20-21 has no serialisation). So "send the command" is natural for three editors. Option A would throw that away and ask for a second, smaller vocabulary.
  • Rolling back is cheap for the workbook. A copy shares everything unchanged (GridCraft crates/model/src/store.rs:1-4). The calculation data is a separate structure (crates/engine/src/lib.rs:188-190). Undo rebuilds it from scratch after a swap (crates/engine/src/cmd/edit.rs:212). What that costs on a large workbook was not measured. It is the first thing the Stage 2 plan should measure.
  • The same command format for everyone. ShareCraft serves each browser editor itself and records its version and fork commit in a manifest (editors.html, section 02). Version 0.2 proposed holding everyone in a room to one exact WebAssembly build (the compiled form of the editor that runs in a browser). Owner decision, 11 November 2026 Desktop editors join the same sessions as browser editors. A desktop program is installed and updated on its own schedule, so one exact build cannot be required. Proposed instead: each session is pinned to a version of the protocol and command format. Any editor build, browser or desktop, that states that version may join, and must apply every entry of that version exactly as the others do. A person whose editor speaks another version is told to reload or update.
  • Arithmetic. The same WebAssembly build gives the same arithmetic on every machine, except for details of invalid numbers that do not reach the document. A native build can differ in the last digit for functions such as sine and logarithm, because it uses the machine's own maths library. Version 0.2 used this to argue that option C between browsers carries no such risk. With desktop editors in the same sessions it does: a desktop GridCraft and a browser GridCraft could compute a different last digit from the same entries, and a later command that depends on that value (a sort, a condition) could then act differently. Proposed: both builds use one maths library written in Rust rather than the machine's, and the native-against-browser replay test of C16 compares computed values as well as entered content. This was reasoned, not tested.
  • Clock and random numbers. NOW() reads the local clock (GridCraft crates/calc/src/recalc.rs:178-183). The engine already accepts a fixed time (:47). RAND() draws from a sequence stored beside the workbook (:45, :100), which stays the same on two machines only if both recalculate exactly the same number of times. Local actions such as undo rebuild the calculation data, so they would drift. Proposed: the server stamps each change with its time, and the editor takes both the time and the random starting point from the change it is applying.
  • Counters. GridCraft gives a new chart, picture or table "one more than the largest number in use" (crates/model/src/workbook.rs:511-513). SolidCraft gives new items the next number from a counter in the document (SolidCraft crates/doc/src/document.rs:3217, :3938-3939). Applied in the server's order these give the same numbers on every machine. They go wrong only while a person's change is shown early, because a later change of theirs may name a number that turns out different. So the person's editor must choose the identity of anything it creates and send it with the change.
  • Other per-person inputs. A command can depend on the clipboard, which is a private copy of the source workbook (GridCraft crates/engine/src/lib.rs:130-134), on the person's name (:386), on ranges that person has unlocked with a password (:204), and on whether the command is enabled in that person's session (:672). The rule: whatever a change needs is written into it by the sender, and applying a received change reads nothing that belongs to one person. Permission to make the change is checked once, on the sender's side and by role on the server.
  • Order of unordered collections. The calculation data uses hash tables with a fixed hash function (GridCraft crates/calc/src/recalc/graph.rs:9, :31), so their order does not vary between machines. No use of parallel calculation was found in the crates. About 27 other engine files use the standard hash table. In a native program its order is random on every run, so anything in a desktop editor that walks one and writes the result into the document or the file can differ from the browsers, and from another desktop editor. These must be audited, and fixed to a stable order, before desktop editors join shared sessions.
  • A crashing change. A panic is a crash inside the editor's own code. GridCraft catches a panic inside a command and restores the workbook (crates/engine/src/lib.rs:725). Rust's standard browser target stops the whole program on a panic and cannot catch it. The fork sets nothing to change that (its Cargo.toml:94-96 and .cargo/config.toml). So in a browser, a change that panics would stop every participant's editor at the same log position. The page around the editor survives and can load the editor again. A desktop editor catches the same panic and puts the workbook back, so it would carry on without the entry while the browsers stopped. To keep everyone equal, a desktop editor that catches a panic in a received entry must treat it as a crash: stop applying entries and report it, as in section 04. This was read, not run.
  • Commands that reach outside the document. Editors run with the signed-in person's rights on ShareCraft (D20). A command can ask to open a web address (GridCraft crates/engine/src/lib.rs:450), read files or run stored scripts. A change arriving from another person must never do these on my machine. GridCraft already separates trusted and untrusted content (crates/engine/src/lib.rs:156-175, :212-217). Shared commands must be an explicit list, and everything not on it stays local or is refused.

Conclusion on question 1

Option C fits the editors as they are: commands are data, one entry point, cheap copies. Option A gives the best protection and the easiest checkpoint, but it breaks S6, ties the server to four large codebases and asks for the most new code in each fork. Option B has no advantage once changes carry lasting identities, and it starves slow connections. Owner decision, 11 November 2026 The owner has chosen option C, as one chat session per open document.

The evidence calls for a hybrid in one place, and it keeps the server out of the edits. Inside WordCraft's paragraphs, each editor adjusts text positions the classic way (operational transformation: shifting a typing position to allow for text another person typed first). That is the part the plain-text spine already has. Version 0.2 also proposed a helper process per editor, outside the server, to run the engine without a screen. The owner has ruled that out: there is no editor process per open document (section 05).

04 / How the proposal works

  1. A change is an opaque entry. The editor sends bytes the server does not read. Beside them it states two things the server can read: the last log position the sender had seen, and the version of the protocol and command format the entry is written in, reported by the loaded editor itself. The server adds the log position, the sender, and the time, and sends the entry to everyone in the session, including the sender. An entry in another format version than the session's is refused. Browser and desktop editors send and receive entries in exactly the same way.
  2. An entry is either an instruction or a result. Normally it is a command with its parameters. Where re-running the command on other machines is unsafe or cannot give the same answer, the sender's editor runs it and sends what changed. Examples: importing data from outside, a script in a PDF form. Each fork decides per command.
  3. Targets are named by identity. The sender's editor turns every position in the command into identities before sending: the target cells, and every reference inside a typed formula. The receiving editor turns them back into positions in its current document. A target that no longer exists has a stated outcome (section 07).
  4. Every editor keeps two states. The agreed state has exactly the entries the server has sent, in order. The shown state is the agreed state plus the person's own changes still waiting. When another person's entry arrives, it is applied to the agreed state, and the shown state is rebuilt from it. When nothing is waiting, the two are the same and nothing is re-run.
  5. Two modes. Show at once is the above, for GridCraft, WordCraft and PdfCraft. Wait for the server applies a person's change only when it comes back from the server. It costs one round trip of delay and needs no re-running. It is for editors where applying a change is slow (SolidCraft), and for single commands a fork marks as heavy.
  6. A rule failure is not an error for the room. If an entry's target is gone, the entry does nothing, on every machine alike. The sender's editor tells the sender and keeps what they typed so they can put it somewhere else. To tell that an edit is late (made before its sender saw a sort or a move), every editor compares the position the sender had seen with a short list it keeps of the areas recent entries moved.
  7. Limits on what a command may do. A limit on bytes does not stop a thirty-byte command that inserts a million rows or fills a whole column. Each fork sets limits on the parameters of shared commands (how many rows, how large a fill). An entry over a limit does nothing, everywhere.
  8. Cancelling a bad entry. An editor notes which entry it is about to apply. If the editor stops and comes back, it reports that entry. A desktop editor that catches a panic in a received entry reports it in the same way (section 03). Only people who may edit can report; a viewer's report is ignored, because cancelling is a way of changing the document. With no helper process on the server (the owner's decision), the rule rests on the editors alone. Proposed: an entry is cancelled when every editing client that was in the session when the entry was sent has reported it, and none has sent a fingerprint from a position after it. A client whose heartbeat expires before it reports or moves past the entry no longer counts. If even one editor applied the entry and moved on, the entry stands: it is not malformed, it fails only on some devices. The editors that keep failing on it are told that this device cannot open the document as it now is, and they leave the session; the fault is recorded. One person cannot cancel another's entry alone, because every other editor that reached the entry must report it too. The cancellation is itself written to the log, with who reported. Some editors may have applied part of the entry before they stopped. So after a cancellation every editor rebuilds its agreed state from the last stored revision and the log without that entry. People's waiting changes are kept and re-run. Limits on entry size and rate stop the simpler abuses.
  9. Checking that everyone agrees. Every so many entries, each editor sends a short fingerprint of its agreed state (a hash: a small number computed from the content, which differs if the content differs). If two fingerprints for the same position differ, the room knows at once and the odd one reloads. This turns a silent divergence into a visible, counted fault. The fingerprint covers what people entered, not computed values and not per-person view settings. It shows that editors agree with each other, browser and desktop alike. It is not a check on a stored file; section 05 has that.
  10. Large content travels beside the log. A paste of a big range does not fit in one message. The editor uploads the content over HTTP and the entry names it by its fingerprint. The content belongs to one document. Fetching it needs the right to read that document, so knowing a fingerprint gives no way into another document. It is deleted when the entries that name it are no longer kept (section 05), and it counts against a size limit per document.

The session and the heartbeat

Owner decision, 11 November 2026 The owner's words: "The goal is to have a chat session for the open document into which the editors both in the browser and desktop can send their changes to the server to be disseminated to the other viewers in that 'chat' session." And: "each client must also send a heartbeat every 1 minute as a 'empty' message to ensure that the file doesn't get locked permanently."

  • One session per open document. Owner decision The session is the room of this paper. It lasts while any client is in it. Viewers are in the session too, and receive every entry, but cannot send one.
  • Desktop editors join it. Owner decision A desktop GridCraft connects to the same session as the browsers, with the same entries. This is new compared with version 0.2. It needs three things, all proposed: sessions pinned to a protocol and command-format version rather than one exact build (C14); a proof that the native and browser engines apply the same entries identically, joining the opening proofs (C16); and the audit of hash-table order and maths functions in section 03, since a native program walks the standard hash table in a different order on every run.
  • A heartbeat every minute. Owner decision Every client sends an empty heartbeat message every minute, whatever else it sends. The heartbeat carries no change and is not written to the log.
  • When a heartbeat expires. Owner decision A client whose heartbeat has expired loses its place in the session. Others see that the person has left. If it held the editing seat of an editor that cannot co-author yet (C17), the seat is freed, so another person can take it. Proposed: a client counts as gone after three missed heartbeats, that is, when nothing has been heard from it for three minutes. Proposed also: any other message from the client counts as a sign of life, so the expiry is never shorter than the heartbeat promises. One minute matches the slowest timer a browser allows a tab in the background (general knowledge, not checked), so a hidden tab still keeps its place.
  • When a session ends. Proposed: the session ends when the last client has left or expired. This replaces today's rule that a room stays open 60 seconds after the last person leaves (crates/server/src/config.rs:146). Entries not yet stored stay on disk (section 05).
  • A client that drops and comes back within the expiry. It still holds its place. It resends its waiting changes, which are ordered like any other change. Nothing special happens.

A client that returns after its heartbeat expired

Owner decision, 11 November 2026 The owner's words: "The client to send a message after the expiration of the heartbeat causes a major version to be created." And: "When a client comes back, they create a new major version. SharePoint does this as well."

This paper's reading of the rule (proposed, for the owner to confirm). SharePoint keeps a version history in which some versions are major (whole numbers) and some minor. When someone who was away brings back changes to a document others kept editing, their changes are added to the current document, and the history keeps the version from before. Read the same way here:

  1. The point before is kept. When the returning client sends its first change, the current document, with everyone else's work up to that moment, is stored as a checkpoint and marked as a major version. If there is no session any more, the last stored revision is that point and is marked major.
  2. The late changes go on top of the current document. The returning client rejoins as a new participant and builds the current document. Its editor then sends its waiting changes as ordinary entries, stating the old log position it had last seen. They are applied by the normal rules: targets by identity (section 06) and the conflict rules (section 07). An edit to a row someone deleted, or into a range someone sorted, does nothing; the returning person is told and keeps what they typed. Their changes are not applied to the old document they last saw.
  3. The result is a new major version. When the late changes are applied, a checkpoint is stored at once and marked major. It credits the returning person.
  4. Nothing is lost. Everything others did is in both major versions. The returning person's changes are in the second, apart from those that could not apply, which their editor keeps to copy from. Anyone can open or restore the version from before the return.
  5. What everyone sees next. The others see the late changes arrive like anyone else's, with a notice that they were made while the person was away and that the version before them is kept as a major version. The returning person sees the current document with their changes on top, and a list of any that did not apply. Everyone carries on in the same session.
  6. Placing changes from an earlier session. The late changes name rows and columns by identities of the session they were made in. If that session has ended, those identities mean nothing to the new one. Proposed: the entries and session data of a session are kept on disk for 30 days after they are stored, so the late changes can still be placed. A client returning after that cannot have its changes placed. Its own copy, as it last saw it with its changes, is stored as a major version, and the current document is stored again on top of it, so the current document is unchanged and the returning work is in the history.
  7. Editors with one editing seat. For WordCraft, PdfCraft and SolidCraft until their stage (C17), a change is a whole file, so nothing can be placed on top. A returning seat holder's file is stored as a new major version on top of whatever others stored meanwhile; their work stays in the version before, which is marked major. The returning person is told whose saved work their version follows.

The alternative reading. The rule could also mean that the returning client's own document, as they last saw it plus their changes, becomes the new major version and the current document, as a whole-file save would in SharePoint. Others' work since then would then be only in the version before, to be copied back by hand. Owner decision, 11 November 2026: the first reading holds (everyone's work, plus the late changes on top). This paper reads the rule the first way for co-authoring editors because it keeps everyone's work in the current document. The second way is what happens for one-seat editors (item 7). The owner is asked which is meant (Q1 in section 14).

How a major version is stored before SC-08. "Major version" here is the same concept as SC-08 (versions, Stage 3). Until SC-08 exists, proposed: a major version is an ordinary Git revision whose JSON metadata carries "major": true, with the reason ("returning client") and the person. Every other checkpoint is minor. SC-08 then numbers and shows them without changing what is stored.

Owner decision, 11 November 2026 Way 1, with no editor process on the server. The details below are proposed:

  1. The log is kept on disk. Entries after the last stored revision are written to PostgreSQL before they are sent out. A server restart or a failed room then loses nothing. This is live session state outside Git, as rule S3 says.
  2. The unsaved log has a limit. Checkpoints need a participant who can save: a browser editor whose tab is showing, or a desktop editor. A save can also keep failing (too large, for example). Without a limit the log and the catch-up for people joining would grow without end. Proposed: at a set number of entries or bytes since the last revision, the room asks more insistently, then pauses new changes with a notice until a checkpoint is stored.
  3. The server asks one participant. When a checkpoint is due, it picks a connected person who may edit and who can save, and sends a one-time ticket naming a log position. That editor writes the file from its agreed state at that position and uploads it with the ticket and the base revision. Per-person view state (active sheet, scroll position, active cell, zoom) is set to the values of the last stored revision before writing, so the file does not depend on who wrote it. If the ticket holder's role is lowered or removed, or their heartbeat expires, the ticket is cancelled at once and another person is asked (rule S5). This replaces the editing seat only for an editor that can co-author. In Stage 2 that is GridCraft. WordCraft, PdfCraft and SolidCraft keep the one editing seat until their own stage, or two people would overwrite each other's whole files.
  4. The existing save path does the rest. The role is checked before the upload is read. A wrong base is refused with 409, a file over the limit with 413, a busy store with 503. Unchanged bytes write nothing. The revision is one Git commit with its JSON metadata.
  5. Credit. The room already tracks who contributed since the last checkpoint (crates/server/src/room.rs:441). The revision credits all of them, not the uploader. This meets S3.
  6. Session data beside the file. The identity tables of section 06 are not in the .xlsx. The uploader sends them as a second, small item. The server keeps it in PostgreSQL beside the log, with the format version, and gives it to people who join later. It lives as long as any kept entry does, not only as long as the room: an entry left behind names identities that only this data explains. Entries are kept until they are covered by a verified revision, and then for 30 days so that a returning client can still be placed (section 04). The session data is discarded with the last of them.
  7. People who join later. They build their state from the last verified revision plus the entries since. Everyone else built theirs in memory. If saving and reloading does not give back exactly the same document, including style numbers, object numbers, the order of names and the random-number position, the joiner drifts from the rest on every later entry. This was missed in version 0.1. GridCraft's existing random-sequence test already checks a save and reload (section 02). It must be extended to prove that loading a checkpoint and applying the rest equals applying everything in memory, in a browser build and a desktop build alike. If that cannot be made exact, the fallback is that every editor reloads from the file at each checkpoint, which is slower but keeps everyone equal.
  8. Checking the upload. A person who may edit can already change anything, so a false file gives them no new power over content. It could, though, credit others with words they did not write, or drop their work unseen. Version 0.1 proposed comparing a fingerprint stated by the uploader. The review showed that this checks nothing: a dishonest uploader can state the honest fingerprint and upload other bytes, and the fingerprint leaves out computed values, which are in the file. Corrected check: the server computes the hash of the uploaded bytes itself. It asks a second editor to write the file at the same log position and send only its hash. If the two match, the revision is verified. This needs two editors to write byte-identical files from the same state, including a desktop editor and a browser editor. The view-state step above and the fixed times in the writer point that way, but it is not proven and belongs in the first tests (C16).
    Unverified. With one person connected, or if the hashes differ, the revision is stored as unverified. An unverified revision is stored and current like any other: people can open and download it, and it is in the history. Its JSON metadata says "verified": false, and the entries it covers are kept rather than discarded, so it can be checked later. It is verified when another editor re-derives it. The next editing client to open the document, in this session or a later one, builds from the last verified revision plus the kept entries. When it reaches the unverified revision's log position it writes the file there and sends only the hash. If the hash matches, the revision becomes verified and the entries before it can go. If it differs, a fault is recorded and shown to the document's owner, both files stay in the history, and the session carries on from the log, which is the agreed record. The next checkpoint is then written from it as usual.
  9. When nobody is connected. If the last person leaves, or the last heartbeat expires, and entries remain after the last revision, the entries stay on disk with their session data. Nothing runs on the server. The document is marked as having unsaved live changes, and downloads and the change feed say that the stored file is behind. The next person to open it has their editor load the last verified revision, apply the leftover entries using the kept session data, and save the checkpoint at once. A viewer's editor applies the entries to show the document but does not save; the document stays marked until someone who may edit opens it.
  10. Rule S4. Every checkpoint states its base revision and is refused if stale. A stale checkpoint means the stored file was changed outside the room, for example by an upload or, later, by the API or a sync client. The room then stops, as it does today. Today the unsaved changes are lost at that point (crates/server/src/room.rs:276). With the log on disk they need not be. Version 0.2 proposed a recovered copy for the people who made them to download. Proposed now, in line with the owner's rule for returning clients: nothing is merged into the newer file, and nothing is offered as a separate download. A connected editor writes the room's last state from its agreed state; if nobody is connected, the next person to open the document does so from the kept entries. That file is stored as a major version, and the file from outside is then stored again on top of it, unchanged, as the current version. Both are in the history, and the room's work can be restored from it.

How often to checkpoint is open. Text is stored two seconds after the last change. A workbook is a whole file of up to 64 MiB by default (crates/server/src/config.rs:44), and each revision adds to the Git repository. A longer interval is likely, and it is safe once the log is on disk.

The identity tables are kept up to date from the list of structural changes each command already records (crates/engine/src/cmd.rs:377, :429-431). No second bookkeeping of "what moved" is needed.

08 / GridCraft: per-person undo

Today Undo puts back a whole earlier workbook (crates/engine/src/cmd/edit.rs:194-215). In a shared session that would remove everyone else's work since.

Proposed rule. Undo reverses your own last action, and only where the document is still as your action left it. Anything someone has changed since is left alone, and you are told how much was left.

  • How. When a person's command is applied, their editor works out its reverse from the workbook before and after: for each changed cell, the earlier content; for a structural change, the opposite structural change plus the cells it altered. The engine already has both workbooks and the list of changed cells (crates/engine/src/cmd.rs:367, :393-457), and unchanged parts are shared, so finding the difference is cheap.
  • Undo is a new entry. Pressing Undo sends the reverse as an ordinary change. It is ordered and applied like any other, so everyone agrees on the result.
  • The stack is personal. Each person's editor keeps its own list. It is not in the file. It lasts while the room lasts.
  • Redo is the same in the other direction.
  • The screen's own edits to the undo list. The screen trims and merges undo steps directly, for a dragged control and for a drag of an object (crates/ui-egui/src/form_controls.rs:224-229, crates/ui-egui/src/grid/interact.rs:939-948). These must be moved onto the personal list, or they will corrupt it.
  • First scope, proposed. Cell content and format, row and column insert and delete, and sheet add and rename get full undo in Stage 2. Sort, large paste and sheet delete are undone only if nothing they touched has changed since. Otherwise Undo is refused with a reason.

Stage 3

WordCraft · two people typing in one paragraph

11 / What changes in the spine

  • A room for opaque entries. It orders, numbers, stamps and sends. It keeps the checks that need no knowledge of content: role (crates/server/src/room.rs:429), duplicate resends (crates/collab-core/src/server_log.rs:61-67), size and rate.
  • The log on disk until its entries are covered by a stored revision.
  • Joining gives the last verified revision over HTTP, the session data, and the entries since. Today it gives the text itself (crates/protocol/src/lib.rs:105-123).
  • The protocol and command-format version is pinned per room and stated on every entry. The loaded editor reports its own version, since the editor's files can be cached apart from the page and a desktop editor is updated on its own. A person whose editor speaks another version is told to reload or update. Installing an editor build that changes the format must wait for open rooms and kept entries, or end them. A build that keeps the format can be installed at any time.
  • Desktop clients. The room accepts desktop editors on the same connection and terms as browser editors, signed in as the same person with the same role (D20). How a desktop editor signs in to ShareCraft is for the Stage 2 plan.
  • Heartbeat and expiry. The room records when it last heard from each client, removes a client after three minutes without a heartbeat or any other message (proposed), frees its editing seat, and cancels its checkpoint ticket. The room ends when the last client has gone; today's 60-second rule (crates/server/src/config.rs:146) is replaced.
  • Major versions. A returning client's first change, and the S4 case, cause revisions marked "major": true in their JSON metadata (section 04), until SC-08 provides versions.
  • Presence becomes opaque. Today it is a text cursor position (crates/protocol/src/lib.rs:43).
  • Checkpoint by ticket replaces the editing seat for editors that co-author. The seat stays for the others. Rule S2 says exclusive check-out is the same mechanism with a limit on who may join. So the opaque room takes a limit on the number of editing participants. A limit of one is exclusive check-out, for any editor.
  • Permission changes (S5). A person whose role is lowered has their waiting entries refused and their ticket cancelled. Their editor drops the changes it was showing early.
  • A limit on the unsaved log, and entries kept until verified, after a conflict, and for returning clients (section 05).
  • New events (S7): entry cancelled, checkpoint stored unverified, checkpoint verified, checkpoint did not match, stored file is behind, changes paused at the log limit, client expired, editing seat freed, major version created.
  • Cancelled entries and fingerprint reports, as positions and counts only.
  • A place to hold large content named by an entry, per document, read with the document's permission, deleted with the entries.
  • The plain-text editor. It works today with the server merging. Proposed: leave it until GridCraft co-authoring works, then move it onto the opaque room so there is one kind of room. Until then the server still understands text, which S6 does not strictly allow.

13 / Out of scope

  • Offline editing. D16 requires a live connection to edit together. A person who loses the connection keeps their waiting changes and resends them on return. Within the heartbeat expiry they keep their place. After it, their return creates a new major version and their changes go on top of the current document (section 04, the owner's rule). Designing for hours of offline work, with merging beyond that rule, is not done here and stays with the SC-16 decision.
  • Merging two saved revisions of a file, branches and pull requests (SC-21 lists these as candidate extensions).
  • Co-authoring of list items, pages and metadata (sequencing section 03, a Stage 3 decision).
  • DeckCraft.
  • Comment threads, tracked changes and "show changes" as review features. Co-authoring does not depend on them.
  • Scale and performance targets (scope decision 9).
