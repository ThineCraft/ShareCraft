ThineCraft / ShareCraft Stage 0

Editor readiness

What the four upstream editors already provide for browser opening and live co-authoring, and what has to be built.

01 / Summary

  • All four editors are written in Rust and already run in a browser. Each has a WebAssembly build of the full editor, so the "open in the browser" requirement (D12) is largely met upstream.
  • All four can already be embedded by a host page that supplies the document and receives saves as bytes. Launching an editor from a ShareCraft library and saving back through ShareCraft is integration work, not editor development.
  • None has any co-authoring code. WordCraft and GridCraft list it as a known gap awaiting an owner decision; PdfCraft has marked shared review out of scope; SolidCraft has no plans recorded.
  • The same three things are missing in every editor: lasting identities for the things being edited, a record of each change that can be sent to other people, and an undo that reverses one person's work without discarding everyone else's.
  • Every editor routes changes through a single entry point, which is the one place co-authoring needs to attach. That is the most favourable finding for the co-authoring-first plan.

Effect on the plan. No editor needs to be rewritten or ported to the browser. Real editors can be opened from ShareCraft, one person at a time, much earlier than planned. The co-authoring work is the same shape four times, which supports one shared Rust collaboration library used by all four forks.

02 / Method and confidence

Each repository was shallow-cloned at the commit below and its source read. Nothing was built, run, forked or modified. Four separate read-only inspections were made, one per editor; their main claims were then spot-checked directly against the source (web apps present, licence, host bridge, single entry point, snapshot undo, brand terms, stated gaps) and held.

04 / Each editor

WordCraft

Word processor

  • Document: a list of blocks (paragraphs and tables); a paragraph is a text string plus formatting runs. Positions are a path of indexes plus a byte offset. No block has a lasting identity.
  • Changes: over a thousand commands (per the project's own documentation) that alter the document directly and leave no description of what changed.
  • Helps: blocks are shared between snapshots, so finding which blocks a command touched is cheap. Comments, tracked changes with authors, and document compare already exist. The native format is plain structured data.
  • Hardest part: two people typing in the same paragraph. Byte offsets shift with every keystroke, so text needs either lasting character positions or position adjustment.
  • Formats: opens and saves DOCX, DOC, ODT, RTF, Markdown, HTML, plain text and others; exports PDF.
GridCraft

Spreadsheet

  • Document: workbook, sheets, cells. Cells, rows and columns are coordinates only. Formulas refer to cells by coordinate and to sheets by name. Charts, images and tables do have identifiers.
  • Changes: commands are named and carry structured parameters, with a command journal already present. Many read their target from the current selection, which differs per person and must be made explicit.
  • Helps: inserting and deleting rows and columns is already represented as data, and the code that adjusts every formula reference after such a change exists. That is most of what is needed to reconcile one person's edit against another's structural change. Recalculation is incremental.
  • Hardest part: concurrent structural changes, such as two people inserting rows at once.
  • Formats: XLSX, XLSB, ODS, CSV and others; XLS import only.
  • Upstream's own estimate for co-authoring and related review features is 35 to 55 hours, with scope left to the owner. That figure is theirs and was not assessed here.
PdfCraft

PDF reader and editor

  • Document: the original file plus an overlay of changed objects keyed by PDF object number. Saves are normally appended to the file.
  • Changes: one command type with 118 kinds of edit. Commands address pages and annotations by position, and the type cannot yet be written out as data.
  • Helps: object numbers are a lasting identity the other editors lack, and code to merge one set of changed objects into another already exists. Annotations already receive a unique name when created. Comment threads with replies and status exist.
  • Hardest part: edits can run embedded form scripts and regenerate appearances as side effects, so the same edit must produce the same result for every participant.
  • Gaps against the scope: QR-code fields are only planned upstream (SC-19 depends on them). One signing method is unavailable in the browser build (relevant to SC-20). Scanner hardware support is not done; camera-photo straightening and text recognition are present.
SolidCraft

Parametric CAD

  • Document: parameters plus a timeline of features that is replayed to produce geometry. Saved as structured data inside a ZIP container.
  • Changes: about 580 named commands with structured parameters, shared by the interface, command line and automation.
  • Helps: features have identifiers; references to edges and faces use persistent names that survive a rebuild; the embedded mode already has export, import and "saved" messages for a host page; a change notification exists, though it does not say what changed. A scheme for collision-free identifiers is written and awaiting adoption upstream.
  • Hardest parts: identifiers are currently handed out by counters, so two people adding features at once would collide. Rebuilding is done inside each command on a single thread in the browser, so another person's change early in the timeline would freeze everyone's screen while it replays.

06 / Consequence for the merge approach

This is a recommendation for the Stage 0 decision, not a decision.

All four editors are built the same way: a document that changes only through commands, with cheap snapshots. None stores its document in a form designed for automatic merging, so adopting a ready-made merging library would mean rebuilding each editor's document model around it. The findings instead favour a shared ordered change log: the collaboration service puts every participant's changes into one agreed order, each editor applies them in that order, and a participant's own not-yet-confirmed changes are adjusted when someone else's change arrives first.

  • It uses what the editors already have: the single entry point, commands as data, and snapshots to roll back and reapply.
  • It keeps the spine unaware of what the changes mean (spine rule S6); each editor supplies only its own adjustment rule.
  • GridCraft already contains its adjustment rule for structural changes; PdfCraft's object overlay makes most changes independent of each other.
  • It requires a connection to the service to edit together. Editing while disconnected and merging later would be limited to what each editor's adjustment rule can handle, which bears on the offline decision in SC-16.

Suggested editor order: GridCraft, WordCraft, PdfCraft, SolidCraft. GridCraft moves ahead of WordCraft because its commands are already structured data and its adjustment rule largely exists, making it the lowest-risk first proof on a real editor. The owner approved this order on 9 November 2026 and the sequencing plan (v0.3) now follows it.

07 / Fork obligations

  • Licence: all four are MIT or Apache 2.0. Keep the licence files, each NOTICE, and the attribution files (ATTRIBUTION.md; PdfCraft's LICENSES.toml; SolidCraft's THIRD-PARTY-LICENSES.txt).
  • ArtCraft brand (WordCraft, GridCraft, PdfCraft): the ArtCraft name and logos in docs/brand/ are trademarks and are not open source. A distributed fork must remove them and must not present itself as ArtCraft. It may state in plain text that it is "based on WordCraft by the ArtCraft team", and likewise for the others.
  • Product names: no rule was found restricting the names WordCraft, GridCraft, PdfCraft or SolidCraft themselves. That is an absence of a stated rule, not legal clearance.
  • SolidCraft: its geometry kernel in solidcore/ is Apache 2.0 with its own notice that must be kept. Its disclaimer forbids using the Tangency Labs name to imply endorsement.
  • Contributor terms: no contributor licence agreement or sign-off requirement was found in any of the four.
  • Dependencies: the storytold projects forbid copyleft dependencies. A fork that wants to send changes back upstream should hold to the same rule in the collaboration library.

The ThineCraft "Craft" names sit alongside ArtCraft's own "Craft" product family. Whether that needs any agreement with the upstream teams is a question for the owner, not something the source answers.

08 / Not yet checked

  • Accessibility. All four draw their interface to a canvas. How well that works with screen readers and keyboard-only use in a browser was not examined, and it bears directly on the WCAG 2.2 AA target in the scope.
  • Performance in the browser: download size (PdfCraft's is reported as about 13 MB), start-up time, large documents, and SolidCraft rebuild times.
  • Whether the web builds work as well as the desktop ones. Nothing was run.
  • DeckCraft. The scope names it for co-authoring but no upstream source has been identified.
  • Upstream intentions. Whether the upstream teams would accept co-authoring changes, which would greatly reduce the cost of keeping forks current.
  • Phone scanning. The streamed capture workflow in SC-19 was not traced in PdfCraft beyond noting camera-photo straightening.
