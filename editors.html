ThineCraft / Editor forks

The editors ShareCraft opens files in

ShareCraft opens spreadsheets, word documents, PDFs and 3D designs in four editors: GridCraft, WordCraft, PdfCraft and SolidCraft. Each one is a copy (a fork) of another project's open-source editor, changed a little for ShareCraft. This page records where each comes from, what was changed and why, how it is built, what it stores, and what has been checked in a browser.

00 / Where things stand

All four editors open from ShareCraft and save back as Git revisions. On 10 November 2026, GridCraft, WordCraft, PdfCraft and SolidCraft were each built from their fork, opened from ShareCraft in a browser, edited, saved, and reopened from the saved Git revision. Each check covered the main path only; section 08 lists what was not checked, and sections 03 to 07 what does not work yet. Stage 1 was merged into main on 10 November 2026 (commit 28479e7).

Since then, on 11 November 2026, each editor was changed to keep the document ShareCraft opened. When an editor is hosted by ShareCraft, its own New, Open and Close are refused, so a person cannot swap the document inside the frame and have a later Save store the other one. The new GridCraft, WordCraft and PdfCraft commits were pushed to the sharecraft branch of each fork on 11 November 2026. Sections 02 to 07 give the detail, and section 08 what was not checked.

The browser checks were done by the project owner's assistant using the browser built into its tools, one browser engine only. Section 08 lists what was not checked. One person edits a file at a time; editing a file together is Stage 2 work.

01 / How an editor opens from ShareCraft

This is the short version; BUILDING.html has the detail.

  • ShareCraft serves the editor itself. Each editor is built on the ShareCraft machine into a folder of web files (editors/<id>/) and served by the ShareCraft server under /editors/<id>/, from the same address as the rest of the site. This matters because three of the editors only talk to a page that comes from their own address (decision D20 in scope.html).
  • A ShareCraft page holds the editor. Opening a file document goes to /file.html?doc=<id>, the frame page. It has a slim bar (back to documents, the file name, a status, Save, Download and, for owners, Share) and shows the editor inside it in an <iframe>.
  • The page and the editor talk through a bridge the editor already had. GridCraft, WordCraft and PdfCraft share one bridge (the craft-web-host crate from storytold's craft-libs): the page hands the editor the file, and the editor hands back what it saves. SolidCraft has a different one: the page asks it for its design as JSON text and tells it when the server has stored it.
  • One person edits at a time. The first person who may edit and opens the file holds the one editing seat. Everyone else sees the editor under a banner saying their changes are not saved. The editors have no read-only mode, so they can still type; nothing they do is stored.
  • Saving is on demand. The person presses Save in the frame bar (or the editor's own Save). The page uploads the whole file; the server stores it as a new Git revision credited to that person.
  • ShareCraft never looks inside the file. It stores the bytes as they come and serves them back only as a download.

Sizes are in millions of bytes, read from the installed folders. The du -sh figures are from the 10 November builds. du -sh shows 26M, 49M, 49M and 153M for the same folders, because it counts in units of 1,048,576 bytes. The editors are sent compressed (table below). A browser downloads the editor the first time it opens it; after that it asks the server whether the files changed.

Each installed editor has a manifest, editor.json, that records its version, its fork and upstream commits and its build date. The build date is written in UTC, so the PdfCraft, WordCraft and SolidCraft builds made on the evening of 10 November 2026 are dated 2026-11-11 there.

The build command is the same for each editor, run from the ShareCraft repository with the fork cloned beside it: cargo xtask editors build gridcraft (or wordcraft, pdfcraft, solidcraft). BUILDING.html explains what it needs and what it does.

03 / GridCraft

Opens and saves from ShareCraft

Where it comes from and what was changed

Upstream storytold/gridcraft by the ArtCraft team, base e9addf52fe68847e6c1310fcfa5d42b7aa8b9650. Fork ThineCraft/GridCraft, branch sharecraft, ending at 017d0b9d5d167096bcba7d7216569476f80b9046. The hosted lock (below) was added on 11 November 2026.

Why there are changes at all: the fork must not present itself as ArtCraft's product or suggest ArtCraft endorses it, but it must still credit where it came from. So the changes remove the upstream brand from what a person sees, and say plainly what the fork is based on.

  • The About dialog said "Part of ArtCraft." It now says "Based on GridCraft by the ArtCraft team." Its links to the ArtCraft website and chat server were removed, with the translations used only by those links.
  • The ArtCraft logo and mark files and their licence text (docs/brand/) were deleted, with their rows in ATTRIBUTION.md and their references in README.md and AGENTS.md.
  • NOTICE gained a section "Changes made for ShareCraft" saying this is a modified version maintained by ThineCraft, not the original and not endorsed by the ArtCraft team or Tangency Labs, with one dated line per change.

Locked to its document when hosted (11 November 2026)

Why: GridCraft's own File tab offered New, Open and Close, and using them replaced the workbook inside the frame, so a later Save stored that other workbook as this document. Now, when the host bridge is present:

  • There is no File tab. New, Open and Close are refused from the menus, from Ctrl+N, Ctrl+O and Ctrl+W, from the keytips and from command search. A short "not available here" note appears.
  • Files dropped on the sheet are ignored, and a workbook picked in a file dialog is refused.
  • Data ▸ Get Data is refused with the same note (the button is still drawn). The start dialog shows no Open…; its Blank workbook and template buttons are refused with the "not available here" note.
  • ShareCraft's file always ends as the one workbook shown, even if the blank workbook was edited first, and also after a password prompt for a protected file. Anything typed on the blank is lost.
  • Save, Save As, Print and Export stay. ShareCraft's own open, which hands the editor the stored file, still works.
  • GridCraft opened on its own, without the host bridge, behaves as before.

Nothing else was changed in how GridCraft edits or saves.

Formats

According to the fork's README, GridCraft's own format is .xlsx, it also reads and writes CSV and TSV, opens older .xls workbooks with values, formulas and number formats, imports data from .xlsb and .ods, and exports PDF. ShareCraft stores a GridCraft document only as .xlsx. A save from the editor whose name ends in .xlsx becomes a new revision; anything else it saves (CSV, PDF and so on) is treated as an export and becomes a download for the person, leaving the stored file as it was. New spreadsheets can be made from the home page, and .xlsx files can be uploaded.

What was checked in the browser, 10 November 2026

  • "New" with the kind Spreadsheet made Budget.xlsx and opened the frame page. The editor loaded inside it under its security policy, with no policy violations in the browser console.
  • Typing a label in A1 and the formula =40+2 in B1 (through the editor's page interface) changed the status to "Unsaved changes". The frame's Save changed it to "Saved" and stored a new revision. The stored file was a real .xlsx (4,066 bytes), served as a download with the protective headers. After a reload the sheet showed Total and 42, and the editor's title was Budget.xlsx.
  • Exporting CSV from the editor's own File menu downloaded Budget.csv. The stored revision did not change and the status stayed "Unsaved changes", which is right: the spreadsheet itself was not saved.
  • Git held two commits named "Checkpoint Budget.xlsx", both credited to the person who saved, and git fsck on the library repository was clean.
  • A second person with the editor role opening the same file saw "View only" and "Ann Tester is editing this file. You can read it; changes you make here are not saved.", and no Save button.
  • When the owner removed that second person, within about a second the editor disappeared from their screen, the page said "Your access to this document was removed.", the file's content answered 404, and no name was left on the page.
  • With the server stopped, the status read "Connection lost. Saving is paused." and the editor stayed. A Save made then was held. When the server came back, the held save was stored as a further commit (4,100 bytes).

What was checked in the browser, 11 November 2026

With the follow-up build, opening Budget.xlsx from ShareCraft (signed in as an owner, in the browser built into the assistant's tools):

  • There was no File tab. The title bar's "More commands" menu listed Save As, Sort, Calculate and Print, and no New or Open.
  • Ctrl+N, Ctrl+W and Ctrl+O were each refused with "not available here", and the workbook was unchanged. Pressing Alt then F opened nothing (the F was typed into the cell).
  • Editing cell D6 to "Lock check" and pressing Save gave "Saved", and after a reload the cell showed it.

After the final fix on 11 November 2026, with the build made just before the commits were pushed (the files in the pushed commits are the same):

  • The start dialog had no Open…. Its Blank workbook and template buttons were refused with "not available here", and one workbook remained.
  • Data ▸ Get Data was refused with the same note, and no file picker appeared. Opening the open dialog through the editor's page interface returned no dialog, and file.open and file.new through its command interface were refused.

What does not work, or works differently

  • The frame's Save button does nothing while the browser tab is hidden (section 07).
  • The File menu finding of 10 November 2026 is fixed when hosted (section 07). Not tried in a browser: dropping a file on the sheet, which the browser tools cannot do.
  • Cancelling the password prompt, then saving, stores an empty file. If the stored file is password protected and the person cancels the prompt, the blank workbook stays, and Save stores it as a new revision of the document. The earlier revision stays in Git history. Known, not fixed.
  • Not checked: see section 08.

04 / WordCraft

Opens and saves from ShareCraft

Where it comes from and what was changed

Upstream storytold/wordcraft by the ArtCraft team, base 2922fe566b575794f896077467cf92825ccba7c9. Fork ThineCraft/WordCraft, branch sharecraft, ending at 35551cebbaa854a9cfd9bf7da66a49505ec39ad2. The blank start and hosted lock (below) were added on 11 November 2026.

  • The About dialog now ends "Based on WordCraft by the ArtCraft team." Its links to the ArtCraft site and chat server were removed. The link to the upstream source code and the copyright line were kept, as credit.
  • The ArtCraft brand files (docs/brand/) were deleted, with their rows in ATTRIBUTION.md. In README.md the logo and mark images were removed, and the trademark paragraph was replaced by a note that this is a modified version maintained by ThineCraft that includes no ArtCraft marks.
  • A "Join the ArtCraft community on Discord" button, shown by default in the title bar, the File (backstage) menu and the Review ribbon, was removed with its command, its keyboard tip and its Options checkbox. Why: people using ShareCraft would see it and be sent to the upstream's chat as if it were this product's. The setting behind the checkbox is kept but does nothing, so settings saved by an earlier version still load.
  • NOTICE: the trademark paragraph now says this version includes no ArtCraft marks, and a "Changes made for ShareCraft" section lists each change with its date.

Blank start and locked to its document when hosted (11 November 2026)

Why: a new, empty document showed WordCraft's start screen, and its File tab offered New, Open and Close, which could swap the document inside the frame. Now, when the host bridge is present:

  • WordCraft starts on a blank page, with no start screen. This is the fork's own behaviour; ShareCraft no longer sends file.new or presses Escape for it.
  • The File tab keeps Info, Save, Save As, Print, Export and Options. It hides Home, New, Open, Close, Recover and the recent-documents list.
  • New, Open and Close are refused from shortcuts, the toolbar and command search. Mail merges that would open a new document are refused. Documents dropped on the page or picked in a file dialog are refused. Pictures, fonts and recipient lists still work.
  • The stored file always replaces the blank page when ShareCraft opens it, even if someone typed on the blank page first, and also after a password prompt for a protected file. That typing is lost.
  • WordCraft opened on its own, without the host bridge, behaves as before.

Formats

According to the fork's README, WordCraft's own format is .docx; it also opens and saves .odt, .rtf, .html, .md, .tex and .txt, opens older .doc files and exports PDF. ShareCraft stores a WordCraft document only as .docx; any other save from the editor becomes a download. New documents can be made from the home page, and .docx files can be uploaded.

What was checked in the browser, 10 November 2026

  • A new Policy.docx opened the editor in the frame with no policy violations.
  • Text in Latin script, with accents, and in Japanese was typed in (through the editor's page interface). The status changed to "Unsaved changes"; the frame's Save changed it to "Saved" and stored a real .docx (6,620 bytes).
  • After a reload the document reopened with its text intact, and its "last modified by" property was the signed-in person's name, which the frame passes to the editor.
  • The community button no longer appears in the title bar.

What was checked in the browser, 11 November 2026

With the follow-up build, opening a new Lock test.docx from ShareCraft:

  • It opened on a blank page with no start screen. The File tab showed only Info, Save, Save As, Print, Export and Options.
  • Ctrl+N, Ctrl+W and Ctrl+O changed nothing. Typed text saved ("Saved"), and after a reload one document reopened under its stored name with the text.
  • A small finding: the first typing right after the three refused shortcuts did not land. One click on the page restored input. This was not investigated.

After the final fix on 11 November 2026 (build made just before the commits were pushed; the files are the same):

  • A stored Lock test.docx opened as one document with its stored text.
  • A new Blank two.docx, never saved, opened as one blank document (Document1), with no start screen and no dialog.

What does not work, or works differently

  • A new, empty document showed WordCraft's start screen (New, Open and templates) instead of a blank page. Fixed 11 November 2026: hosted, WordCraft starts on a blank page (see above). On 10 November the frame had worked around it by asking for a new document and pressing Escape; that stopgap was removed, and ShareCraft sends neither. Not tried in a browser: a host open after typing on the blank page (covered by an automated test only).
  • The start screen lists recent documents by name. WordCraft keeps a "Recent" list in the browser's own storage, and since every editor is served from ShareCraft's address, that list holds the names of other documents opened in WordCraft in the same browser, whoever opened them. Only names are kept there, not content. This no longer applies while hosted: the start screen and the File tab's recent list are not shown. WordCraft opened on its own still keeps and shows the list.
  • The web build has no font for Chinese, Japanese or Korean text. Japanese text was stored correctly but drawn as empty boxes, and the editor reported "1 font not installed". The upstream's optional extra font set was not built in.
  • The frame's Save button does nothing while the tab is hidden (section 07).
  • The File tab's New, Open and Close finding of 10 November 2026 is fixed when hosted (section 07). Not tried in a browser: the mail merge buttons, Insert Picture with a .docx chosen in the picker, and dropping a file on the page.
  • Cancelling the password prompt, then saving, stores an empty file. Found in GridCraft and likely the same here (not tried): if the stored file is password protected and the person cancels the prompt, the blank document stays, and Save stores it as a new revision. The earlier revision stays in Git history. Known, not fixed.
  • Not checked: see section 08.

05 / PdfCraft

Opens and saves from ShareCraft

Where it comes from and what was changed

Upstream storytold/pdfcraft by the ArtCraft team, base a71b5124bc388e6b86ec0ee5ec16d31fa1955117. Fork ThineCraft/PdfCraft, branch sharecraft, ending at 343edd8045970651a37bafaf78ac7a747cfdda2a. The hosted lock (below) was added on 11 November 2026.

PdfCraft drew the ArtCraft wordmark and mark from image files compiled into the program, on its home screen and in About, and promoted the ArtCraft community in several places. The changes:

  • The wordmark and mark were removed from About and the home screen; About now says "Based on PdfCraft by the ArtCraft team." The home screen's community card, the title bar's Discord button and the Discord and website links in the Help menu, the command list and the command-line tool were removed. The Help menu keeps a link to the upstream source code, as credit.
  • The brand files (docs/brand/) and the licence that covered only them were deleted, with their entries in ATTRIBUTION.toml, ATTRIBUTION.md and LICENSES.toml and their images in README.md.
  • The upstream's tests for the removed buttons and links were replaced by tests that they are gone.
  • NOTICE: the paragraph about the marks now says this version does not include them, and a "Changes made for ShareCraft" section says it is a modified version, not made or endorsed by the ArtCraft team or Tangency Labs, and lists each change with its date.

Locked to its document when hosted (11 November 2026)

Why: PdfCraft opens extra documents in extra tabs, and its Save stores the tab in front, so a second tab's bytes could be stored as this document. Now, when the host bridge is present, PdfCraft has one tab:

  • Open, New blank PDF, Open Recent, Create, Close file and Close all are greyed out or refused: in the menus, from shortcuts, in the command palette, on the tab strip, in the recent list on the home screen, and for dropped files.
  • Some views may still open as extra tabs: attachments, portfolios, revisions, signed versions, comment summaries and Combine results. They can be closed.
  • Save always stores the document ShareCraft opened, whichever tab is in front. On such an extra tab, Save and Save As store the original document and show no message. Export is the way to keep the view as a file.
  • PdfCraft opened on its own, without the host bridge, behaves as before.

Formats

PdfCraft opens and saves PDF. ShareCraft stores a PdfCraft document only as .pdf. The home page cannot make a new, empty PDF (an empty PDF is not a file); a PDF has to be uploaded.

What was checked in the browser, 10 November 2026

  • The PDF was drawn by the editor inside the frame. Duplicating a page (through the editor's page interface) changed the status to "Unsaved changes"; Save changed it to "Saved" and stored a new revision, a PDF with two pages.

What was checked in the browser, 11 November 2026

  • Ctrl+W, Ctrl+O and Ctrl+N changed nothing.
  • Rotating a page (through the editor's page interface) showed "Unsaved changes"; the frame's Save gave "Saved", and after a reload the page was rotated.

  • Text recognition (OCR) cannot work: its worker is built and installed, but the recognition models are not installed.
  • The File menu finding of 10 November 2026 is fixed when hosted (section 07). Extra tabs for derived views are still possible (above). Not tried in a browser: a Combine result tab and saving from it, and closing a derived tab. If the close prompt of a changed derived tab is answered with Save, nothing happens and the tab stays changed, with no message.
  • The frame's Save button does nothing while the tab is hidden (section 07).
  • Not checked: see section 08.

06 / SolidCraft

Opens and saves from ShareCraft

Where it comes from and what was changed

Upstream tangency-labs/solidcraft by Tangency Labs, base f232e4a40c9d1d3088c758e393b7db43048eac22. Fork ThineCraft/SolidCraft, branch sharecraft, one commit: dd8724aeaa10d50de232d7be44864683fdfc508f.

  • The web page no longer registers its service worker (an offline cache) when it is opened inside ShareCraft. Why: a cached copy of the editor could outlive an upgrade and keep running an old version.
  • The social-preview tags (used when a link is shared on social media) that pointed at the upstream's website were removed.
  • The loading animation of the SolidCraft mark was replaced by a plain pulsing square, drawn for the fork. The original file stays in the repository.
  • About gained the line "Based on SolidCraft by Tangency Labs. This is a modified version, not endorsed by Tangency Labs." Upstream's DISCLAIMER.md forbids using Tangency Labs' name to suggest endorsement; a plain statement of origin with an explicit "not endorsed" does not do that. The line is in English only for now.
  • NOTICE gained a "Changes made for ShareCraft" section, with one dated line per change.

The product icons were kept: they show the generic SolidCraft cube, not a company mark. Their file names contain the application id io.tangencylabs.solidcraft; renaming them would break the packaging files that use that id.

How ShareCraft talks to it

SolidCraft does not use the shared bridge. The frame opens it at /editors/solidcraft/index.html?embed=editor and calls its page interface: it hands over the stored design with document.import, asks every 2 seconds (only while the tab is shown) whether there are unsaved changes, and on Save asks for the design with document.export, uploads it, and only after the server has stored it tells the editor with document.saved. So the editor never believes it is saved when it is not. A request that gets no answer within 15 seconds shows "The editor did not answer. Show this tab and try again." This part of ShareCraft has automated tests that use a stand-in for the editor, and its main path was checked against the real editor (below).

The cost of the unsaved-changes check. SolidCraft's page interface has no question that only asks "are there unsaved changes?", so every 2 seconds the frame asks for the whole design and keeps only that answer. On a small design this is cheap; on a large one it is real work for the browser every 2 seconds. It also means that changes made in the last 2 seconds before the tab is closed are not known yet, and the browser does not warn about leaving.

Formats

According to the fork's README, SolidCraft reads and writes STEP, IGES, 3MF, STL, OBJ and glTF where supported, and has its own .sc design files. ShareCraft stores a SolidCraft document as the design's JSON text, in a file named .solidcraft.json, because that is what the editor's page interface hands over. A stored file that is not UTF-8 text is reported as an error and not sent to the editor. New designs can be made from the home page, and .solidcraft.json files can be uploaded. Binary .sc files cannot be stored.

Build

Version 0.40.0-rc.3. The build took about 50 minutes: 17 minutes compiling and the rest in the optimiser, which used up to 5.6 GB of memory. The installed editor is 160.0 MB, almost all of it one 153.1 MB WebAssembly file: about 122.9 MB of compiled code and 30.0 MB of data. Correction, 11 November 2026: this page first said the file was large because the release build kept debugging information in it. That was wrong. A rebuild on 11 November 2026 with release debug information turned off gave the same 153.1 MB file, and the file holds no debug information at all. Size-oriented compiler settings were tried on 11 November 2026 (see the next heading), and the editor is sent compressed instead. On the local machine it loaded in under 20 seconds. It was built from the clean temporary copy described in section 11, so the owner's local override of SolidCraft's geometry kernel was not used.

Size experiment, 11 November 2026

Size-oriented compiler settings do shrink the WebAssembly file, but they slow the editor down. Optimising for size (opt-level s) gave a 105.9 MB file. Optimising for smallest size (opt-level z) with whole-program optimisation (fat LTO) and one code-generation unit gave 88.9 MB. The smallest build ran CAD operations about twice as slowly: a four-edge vertical fillet on a freshly loaded design took 75 seconds against 36 seconds, and cuts were about 1.5 to 2 times slower. So the normal release build was kept, and the editors are sent compressed instead (section 02). The other 30 MB of the file is data: interface translations, command documentation, a materials catalogue and licence texts.

What was checked in the browser, 10 November 2026

  • A new Bracket.solidcraft.json opened the editor in the frame (at ?embed=editor, with no name in the address), with no policy violations, and no service worker was registered.
  • Adding a 40 × 30 × 20 box through the editor's page interface changed the status to "Unsaved changes" (found by the 2-second check).
  • The frame's Save changed it to "Saved" and stored a new Git revision holding the design as JSON text (694 bytes). The editor then reported itself saved, so the confirmation step worked.
  • After a reload the design was imported again: the box was drawn, it was listed in the editor's browser tree, and the editor's document name was "Bracket".

What was checked in the browser again, 11 November 2026

07 / Found in the browser checks

These were found on 10 and 11 November 2026 and apply to more than one editor.

  • The editor answers the frame's Save button only while its tab is being shown. The editors do their work as they draw the screen, and a browser does not draw a hidden tab. So pressing Save in another way while the tab is hidden (for example from a script or an extension) does nothing until the tab is shown again; the upstream code says this in its own timeout message. Saving with the editor's own Ctrl+S is not affected, because the person is then looking at it. For SolidCraft the page is written to wait 15 seconds and then say the editor did not answer; that was not checked in a browser.
  • Built files contain the builder's local folder paths. The WebAssembly files hold paths such as C:\Users\<name>\.cargo\… inside log messages. Builds are made on the machine that runs ShareCraft and are not published, so this stays local today. Before any build is published, it must be rebuilt with path remapping (Rust's --remap-path-prefix), so that it does not carry a user name or folder layout.
  • The editors' own File menus offered New, Open and Close. Fixed 11 November 2026. Seen in GridCraft on 10 November: using them replaced the document inside the frame, and a later Save stored that other document as this one, as a new revision. The owner chose to turn them off in each fork, and the follow-up builds do (sections 03 to 05; SolidCraft already did). When hosted, New, Open and Close are refused, including from shortcuts, keytips and search, and dropped or picked files are ignored or refused (in GridCraft also Data ▸ Get Data and the start dialog's buttons). Save, Save As, Print and Export stay. What stays reachable: PdfCraft may still open some views (attachments, portfolios, revisions, signed versions, comment summaries, Combine results) as extra tabs, but Save always stores the document ShareCraft opened. The forks' changes are on each fork's sharecraft branch, pushed on 11 November 2026. Checked in a browser for all four editors; dropping files was not (section 08).
  • WordCraft: the first typing after the refused shortcuts did not land. Found on 11 November 2026: after Ctrl+N, Ctrl+W and Ctrl+O were refused, the first typing did not appear until the page was clicked once. Not investigated.
  • Narrow windows. At about 680 pixels wide the frame bar wraps and the Share button moves to a second row. It still works.
  • An empty lock file was installed with each editor. The build tool used by the editors (Trunk) leaves an empty .trunk-lock file in its output. Since 10 November 2026 the install step leaves out files whose names start with a dot, so the next build of each editor no longer has it. The four editors installed before then still do; it is harmless and is served only to signed-in people.
  • The editors are trusted code. Each editor is served from ShareCraft's own address, so that its bridge to the frame page works. A page from the same address can do anything the signed-in person can do on ShareCraft: read their documents, save, share. So the forks' code must be trusted as much as ShareCraft's own. The editors' security policy (BUILDING.html, section 17) stops a script that someone manages to inject from running, but it does not confine the editor itself. The real fix is to serve the editors from a separate address; that needs a change in each fork, and is left for later.

10 / Bringing a fork up to date with its upstream

The upstream projects keep changing. To take their newer work into a fork, move the fork's few changes onto a newer upstream commit (a rebase), rebuild, and check again. The fork's changes are listed in its NOTICE, so it is clear what has to survive. Run these in the fork's folder, beside ShareCraft (for example ../GridCraft):

  1. Fetch the upstream: git fetch upstream. (When the fork was cloned, the original project was added as the remote upstream.) Choose the new base, usually the newest commit on upstream/main.
  2. Keep the old commit reachable, so that a build made from it can still be traced: git tag sharecraft-<date> sharecraft.
  3. Move the changes: git switch sharecraft, then git rebase <new base>. Resolve any conflict so that every line under "Changes made for ShareCraft" in NOTICE is still true.
  4. Look again for the upstream brand in what the web build shows (About, title bar, Help, home screen, loading screen), since the upstream may have added some. Change only what a person sees, and add a dated line to NOTICE for each new change.
  5. Run the fork's own checks for the crates touched (its formatter and cargo check for the user-interface crate, as the fork's README or AGENTS.md describes).
  6. Push the branch and the tag to the fork, never to the upstream: git push --force-with-lease origin sharecraft and git push origin sharecraft-<date>.
  7. In ShareCraft, update the editor's table in editors.toml: base becomes the new upstream commit, commit the new head of sharecraft.
  8. Rebuild and install: cargo xtask editors build <id>, then cargo xtask editors verify.
  9. Repeat the browser check for that editor (sections 03 to 06 list what was checked), and record what was and was not checked.
  10. Update this page (commits, version, size, what works) and commit editors.toml and this page together in ShareCraft.

Step 2 and the use of tags are a suggestion of this page, not something the build tool needs.

11 / Risks

The forks depend on storytold's own copies of other projects

GridCraft, WordCraft and PdfCraft are built against storytold's modified copies of two libraries, egui (drawing the user interface) and winit (windows and input), and against storytold's craft-libs repository, which holds shared pieces including the bridge the frame talks to (craft-web-host). They are fetched from GitHub by exact commit when an editor is built. If storytold deletes, renames or rewrites those repositories, the forks can no longer be built from a clean machine, even though their own code is unchanged. A machine that has built them before keeps copies in Cargo's cache. Mirroring the repositories into the ThineCraft organization would remove the risk; that is not done and needs the owner's decision.

SolidCraft's Cargo.toml names none of these: it uses the published egui and keeps its own copies of winit, egui-wgpu and its geometry kernel inside its repository.

Other risks

  • The editors run with the signed-in person's rights. Because ShareCraft serves them from its own address, an editor's code could call ShareCraft's interface as the person using it. They are code ThineCraft builds from its own forks, and their security policy stops injected scripts from running (BUILDING.html, section 17). Serving them from a separate address would be safer still but needs a change in three forks (decision D20).
  • A developer's Cargo settings in a parent folder would change a build. Cargo applies a configuration file found in any folder above the one it builds in. One such file exists on the owner's machine, above the repositories folder, and points one of SolidCraft's libraries at a local copy. The build tool therefore builds each editor from a clean temporary copy of the fork outside the repositories folder, and refuses to build if it finds such a file above that copy (BUILDING.html, section 13).
  • Published builds must be rebuilt with path remapping (section 07).
  • Desktop builds would carry the upstream brand (section 09).
  • The person's name is passed to the editor in the frame's address (?author=), for GridCraft, WordCraft and PdfCraft, which use it to credit comments and changes. It is not logged by the server, but it is in the browser's history for that frame.

12 / Licences and notices

All four editors are licensed MIT or Apache 2.0, like ShareCraft. Apache 2.0 asks that changed files be marked; each fork does this in the "Changes made for ShareCraft" section of its NOTICE. Every licence and attribution file was kept: LICENSE-MIT, LICENSE-APACHE, NOTICE and ATTRIBUTION.md in each fork, and also ATTRIBUTION.toml, LICENSES.toml and licenses/ in PdfCraft and DISCLAIMER.md and the geometry kernel's own notice in SolidCraft. The only licence file removed is PdfCraft's licence for the brand files, which covered nothing else once they were deleted.

The build tool copies each fork's licence, notice and attribution files into the installed editor's licenses/ folder, and refuses to install a build without a licence and a notice file.
