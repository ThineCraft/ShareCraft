01 / Principle

Co-authoring is the single most important feature of ShareCraft, so it is the first thing that works and the thing everything else is shaped around. The first stage builds the collaboration plumbing end to end: two people editing the same document in two browsers, with the result saved as a Git revision. Sites, libraries, metadata, permissions, search, governance and the rest are then built onto that working core, never beside it.

The consequence that keeps the system simple: there is only one way to edit anything. A person editing alone is a shared session with one participant. Saving is a session checkpoint. No second, single-user save path exists to be reconciled with co-authoring later, which removes the rework risk at its source.

Status. Two things here are the owner's explicit direction of 9 November 2026: ShareCraft is built in Rust like the other Craft applications, and co-authoring is built first as the main feature with the rest formed alongside it. The stage boundaries, spine rules and pairings below are proposed detail and are not yet approved. Stage 1 is partly implemented: see the progress note in the Stage 1 card and BUILDING.html. Nothing else is implemented. No dates, costs or release commitments are implied.

02 / Built in Rust

  • Explicit direction: ShareCraft's server, collaboration service and storage layer are written in Rust.
  • Proposed: one Cargo workspace with separate crates for the collaboration core, the revision service (Git, JSON, PostgreSQL), permissions, the HTTP API and the web server, so each can be tested on its own.
  • Proposed: the part of the collaboration core that merges edits is compiled both for the server and to WebAssembly for the browser, so the same code decides the result on both sides. The browser editors link to that one client library.
  • Established by inspection: all four upstream editors are written in Rust and already have WebAssembly browser builds, so the collaboration library can be linked into each directly. See editor-readiness.html.
  • Open: the Rust libraries for Git access, PostgreSQL, the web framework and edit merging. Mature Rust options exist for each; they are selected in Stage 0 and Stage 1, not by this document.

03 / The collaboration spine

The spine is the plumbing built in Stage 1. These rules hold from the first stage onward, and every later module is built to them.

Ref.RuleWhat it gives the rest of the platform
S1Every editable thing (file, list item, page, metadata record) has an identifier that does not depend on its name or location.Rename and move never break a session, a link or a sync client.
S2Every edit happens inside a session. A session has one or more participants, each with read-only or edit rights.Single-user editing, co-authoring and exclusive check-out are the same mechanism with different limits on who may join.
S3Live session state lives outside Git. A checkpoint turns it into one Git revision with its JSON metadata, crediting everyone who contributed.Version history (SC-08) and Git-backed metadata (SC-21) come from the same save path. No commit per keystroke.
S4Every checkpoint states the revision it was based on. A stale checkpoint is refused with an explicit conflict.API writes, DriveCraft sync and offline reconciliation all meet edits through one conflict rule.
S5Joining and staying in a session depends on a permission check that is repeated when permissions change.Revoking access removes a person from a session in progress (A04), for every kind of content.
S6The spine carries edits without understanding them. Each editor defines what its edits mean and how two of them combine.Text, spreadsheet, PDF and CAD editors plug in without the spine changing. New Craft applications join the same way.
S7Session start, join, leave, removal and checkpoint are published as events.Audit, the change feed, notifications and search indexing subscribe to one stream.

Extending sessions to list items, pages and metadata (S1, S2) is a proposal. It means two people editing the same list row or page see each other's changes too. The scope requires co-authoring only for the named editors; if this is not wanted, those content types still save through S3 and S4 as sessions of one.

04 / Stages

Two tracks run together from Stage 2: the editor track adds one co-authoring editor at a time, and the platform track adds the SharePoint-baseline modules onto the spine. Scope references (SC) and acceptance tests (A) are from scope.html.

Stage 0 · No product code

Definition and editor inspection

  • Settle the decisions Stage 1 cannot start without (section 07), including the approach to merging concurrent edits, which now comes first instead of last.
  • Done 9 November 2026: the source of WordCraft, GridCraft, PdfCraft and SolidCraft was read and reported in editor-readiness.html. All four are Rust, run in a browser, can be embedded by a host page and route changes through one entry point; none has co-authoring code.
  • Draft the editor integration contract (SC-15) from what is found.
  • Exit: decisions recorded in the scope; a readiness report per editor; spine rules S1–S7 confirmed or amended.
Stage 1 · The spine

Co-authoring working end to end

  • Rust workspace and build. Document identity. Session service: join, presence, attribution, transport, save status, reconnect after interruption.
  • Revision service: checkpoint to Git revision, JSON metadata and PostgreSQL record, with stale-write conflicts (the core of SC-21).
  • Minimal identity and a per-document permission check, including removal from a live session when access is revoked.
  • A deliberately plain built-in text editor in the browser as the first client. It exists to prove the spine and becomes the basis for simple text fields later.
  • Real editors, one person at a time: create the four forks, remove the upstream brand assets, record provenance (SC-24), and serve each editor's existing browser build. Connect each editor's existing host bridge so a file opens from ShareCraft and saves back as a checkpoint, as a session of one.
  • Exit: two browser sessions edit the same plain-text document at once, see each other, reach the same result, survive a disconnect, lose access on revocation, and reopen the saved Git revision. This is A07 in miniature, plus the save and conflict parts of A13. Separately, a WordCraft, GridCraft, PdfCraft and SolidCraft file each opens in the browser from ShareCraft and saves back as a Git revision, which is the fork, build and launch part of A17.
  • Progress, 9 November 2026: the first plan meets these parts of the exit: two browser sessions edit one plain-text document at once, reach the same result, survive a disconnect, and a checkpoint is saved as a Git revision with JSON metadata and reopened. Not yet met: removal from a session when access is revoked, PostgreSQL records, and the four editors opening from ShareCraft. Stage 1 is not complete. See Building and running ShareCraft.
Stage 2

Libraries and access · GridCraft

  • Platform: SC-01 organizations, sites and navigation; SC-02 libraries and file operations; SC-11 identity, permissions, sharing, inheritance without size limits, inheritance explorer; SC-25 site branding and brand management.
  • Editor: live co-authoring in the GridCraft fork: lasting identities for sheets, rows and columns, changes sent through the spine, reconciliation built on its existing reference adjustment, per-person undo and presence. A GridCraft file clicked in a library opens in the browser with live co-authoring. The parts that are not spreadsheet-specific go into the shared collaboration library for the editors that follow.
  • Exit: A14, A15, A04, A18; A07 and the rest of A17 for GridCraft.
Stage 3

Metadata and history · WordCraft

  • Platform: SC-03 lists; SC-04 columns; SC-05 taxonomy; SC-06 content types; SC-07 views and forms; SC-08 versions, publishing, check-out and locking, defined in terms of sessions and checkpoints.
  • Editor: live co-authoring in the WordCraft fork, including two people typing in the same paragraph.
  • Exit: A01, A02, A03, the rest of A13; A07 and the rest of A17 for WordCraft.
Stage 4

API and change feed · PdfCraft

  • Platform: SC-14 administration and extensibility; SC-23 DriveCraft integration API. The change feed is built on the spine's event stream and reports when a file is in a live session.
  • Editor: live co-authoring in the PdfCraft fork.
  • Exit: A16, including a sync client behaving correctly against a file in a live session; A07 and A17 for PdfCraft.
Stage 5

Knowledge and governance · SolidCraft

  • Platform: SC-09 pages and news; SC-10 search; SC-12 retention, records and audit; SC-13 FlowCraft workflows; SC-16 hybrid continuity; SC-17 migration.
  • Editor: live co-authoring in the SolidCraft fork. DeckCraft per its established scope and release allocation.
  • Exit: A05, A06, A08, A09; A07 and A17 complete for all four editors.
Stage 6 · Can run alongside Stage 5

Intake, forms, evidence and services

  • SC-18 public portals; SC-19 forms and paper capture; SC-20 signatures and timestamp evidence; SC-22 services on the platform.
  • Exit: A10, A11.
Final gate · Not a feature stage

Production readiness

  • Migration rehearsal, security, accessibility and performance checks, recovery exercise and handover.
  • Exit: A12.

The pairing of each editor with a platform stage shows roughly when it lands, not a dependency. The editor track moves at the pace each codebase allows. Its order (GridCraft, WordCraft, PdfCraft, SolidCraft) follows the editor readiness report and was approved by the owner on 9 November 2026: GridCraft's changes are already structured data and its rule for reconciling row and column changes largely exists, so it is the lowest-risk first proof on a real editor; SolidCraft, where one person's change can invalidate another's and rebuilds block the screen, stays last. Opening real editors in Stage 1 was approved at the same time, because it needs only the host bridge each editor already has.

05 / The standing proof

From the end of Stage 1, an automated two-session test runs on every build: two participants edit one document at once, one disconnects and returns, one has access revoked, and the checkpoint is reopened from Git. It starts with the plain text editor and gains a case for each real editor as it joins.

Each platform module must pass with that test still green. A change to storage, permissions, locking or the API that breaks co-authoring is caught on the day it is made, which is the practical meaning of forming everything alongside the main feature.

08 / Changes

Version 0.1 built co-authoring as the last feature stage, with earlier stages reserving room for it and a test stand-in imitating it. The owner reversed that order on 9 November 2026: co-authoring is built first and the platform forms around it. The stand-in is replaced by the real collaboration core, and the reservations became the spine rules. Rust was recorded as the implementation language in the same instruction.

Version 0.3 applies two findings from the editor inspection, approved by the owner on 9 November 2026: GridCraft moves ahead of WordCraft on the editor track, and all four editors are forked and opened from ShareCraft, one person at a time, in Stage 1.

Scope of Works v0.7 records both instructions as D14 (Rust) and D15 (co-authoring first), and its delivery order now matches this plan.
